# Velnor Rust-only redesign — CI stops being a bottleneck at same confidence

Status: redesign from the owner's binding decisions in `rust-only-brief-v1.md` (2026-11-19). Sources: design v2 (`v2/velnor-runner-architecture.md`), decision log (`v2/decisions.md`, I/N/S ids), design-feedback comparison (`v2/design-feedback-comparison.md`, F-H/F-B ids), evidence pack (`evidence.md` §A–§F), cluster/Mac experiments (`v2/experiments/mbx-cache-cluster.md`, `mbx-cache-mac.md`, `blaze.md`), and read-only code in `~/Projects/tailrocks/velnor-new`, `~/.cache/ci-ambition/refs/{velnor-legacy,actions-runner,arc,mr-boxington-cache,blaze}`. Tags: **[M]** measured, **[E]** estimate with arithmetic, **[T]** target. Confidence contract is v2 §1.2 C1–C7, unchanged; false greens have zero tolerance, false reds are budgeted (v2 §1.3).

Binding decisions honoured throughout: (1) Rust-only native executor, official C# runner never in production; (2) latest official release is lab conformance oracle only; (3) latest APIs only — scale-set sessions, broker long-poll, JIT config, run-service acquire/renew/complete, Results twirp, cache v2, artifacts v4, OIDC in; legacy AES session, legacy pipelines/distributed-task, DTExpressions, cache v1, artifacts v3 out; (4) no Node/JS actions — closed native set, unknown actions refused pre-job; (5) `velnor-legacy` archived, code copied/reviewed/owned in `velnor-new` only; (6) experimental deps judged on evidence; (7) GitHub stays platform; (8) no fork PRs — drop fork handling, isolation for trusted-but-buggy authors, PR results never promote to `main` caches/receipts without verification; (9) macOS release builds paused, Linux-only on owner's cluster, design stays open to macOS later; (10) build once, verify once, reuse everywhere by content address, release promotes `main` artifacts verbatim; (11) correctness first, reuse only when key provably complete; (12) CI on demand via label flow, merge queue always verifies, merge requires green `Required` on exact PR head.

## 1. Summary

Velnor is a GitHub App + scale sets whose jobs are executed by a native Rust executor (`velnor-exec` + `velnor-dispatch`, §3) on pre-warmed Linux sandboxes — the official runner runs only in `velnor-lab` as differential oracle (§5). Verification is content-addressed: `velnor-ledger` mints one signed receipt per obligation keyed by everything its sandbox contains (v2 §4.1), so PR, merge-group, `main`-push, nightly and audit runs share work by lookup, and a release promotes the exact `main` artifacts (§2b). Compile hot path is plain cargo over a reflinked warm `main` snapshot at fixed path `/w/velnor-new` (0.25 s clone, 0.31 s no-op [M]); `mbx-cache` is cross-node filler only, gated by the 10%/20-runner-min threshold (§6). PR CI starts only on label `velnor:verify` (§8); pushes without it do zero heavy work, and `main` never rebuilds what the queue verified.

Committed (stretch in brackets), final-head push → merged, weekly P50/P90 over merged PRs: **PR verdict ≤90 s / ≤4 min (60 s / 2.5 min); push-to-merge ≤3 min / ≤8 min (1.75 min / 5 min)** in phase 3, at **≤35 (15) runner-min per merged PR**, false-green tolerance zero, false-failure ≤1% (§11). Phase-4 stretch with pre-push `velnor verify`: verdict 30 s/100 s, push-to-merge 100 s/4 min. Today's baseline: push-to-merge 85/457 min [M], PR run 26.7/92.3 min [M], 285–347 runner-min/merge [E] (v2 §1.1).

**Bottleneck summary.** Today waiting dominates working: PR run without hosted queue is ~11 min [M] but push-to-merge median is 85 min. The design removes waiting (cluster gates, warm pool, webhook `ensure`), removes duplicate work (receipts, §2b), then removes the code floor (`Journal::open`, crate split). Irreducible in phase 3: webhook 1–2 s + GitHub job creation ~15 s (parallel, hidden), enqueue→run 19 s + finish→merge 26 s ≈ **45 s of GitHub queue latency per merge** — the largest single term once verdict is <1 min (v2 §13 Q11).

(c) *Chosen: (b) plus profile-in-key everywhere.* Every obligation key includes profile + features + flags, so debug receipts can never satisfy release obligations and vice versa — no silent rebuild, no silent reuse. Release tag promotes builder digests; if no builder generation exists for the tagged tree (e.g. direct push), release blocks until builder produces it — it never rebuilds inline. Numbers favour (b): per merged PR, (a) costs ~(60–110 s extra × ~3.5 runs) ≈ 210–385 s of foreground build vs (b) ~150–200 s once on batch capacity. ### 3.2 Protocol client — latest APIs only

In: scale-set sessions + broker long-poll; JIT runner configuration (`generatejitconfig`); run-service `acquirejob`/`renewjob`/`completejob`; Results twirp (logs, timeline, step summaries); cache service v2 (twirp) and artifacts v4 behind native actions; OIDC token endpoint for attestations; node24-era semantics (contexts, env files, defaults, workflow commands). Out, with reason: legacy session + AES message encryption (replaced by JIT+broker; needs private key on disk for no benefit); legacy pipelines/distributed-task (plans/timelines/`distributedtask` — superseded by run-service + Results; velnor-legacy `protocol.rs` still carries it and it is *not* copied, N59); `DTExpressions` (one evaluator only, `Expressions2`); cache v1/artifacts v3 (deprecated by GitHub). A CI check greps endpoint strings: any legacy API string fails the build (work item 7 acceptance).

Ground truth is `actions/runner` source. Seams that shape the design: the broker message is only a reference — the job body comes from run-service `acquirejob` (evidence §F); a job cannot move runners after acquire (second acquire 409s, `RunServiceHttpClient.cs:106-107`), hence placement-before-acquire; renewal and force-fail use the job's own token (`Runner.Listener/JobDispatcher.cs:734-746,1208-1219,1244-1249`); only `Runner.Listener` touches the RSA key manager (S6), and Velnor keeps all credentials in the dispatcher, never in a sandbox.

### 3.3 Job-message model

Executor input is the run-service job message as the oracle defines it: plan id, job id, run-service URL, job token (all four required to `completejob` after a crash — `RunServiceHttpClient.cs:123-160`; this is why crash-only/no-journal I009 was rejected). Velnor models it as typed Rust structs in `velnor-exec` (request context, steps with `if`/`continue-on-error`/timeouts, matrix expansion already applied by GitHub, `needs` outputs, masked secret refs resolved at execution, never logged). The dispatcher journals *before* acting: persist request identity + acquisition intent → `acquirejob` → persist sealed response → hand message+token to the chosen node's executor (F-H24 fix; the draft journaled after acquire). Job tokens expire ~1 h, so long jobs rely on renewal, not token lifetime.

### 3.4 Expression engine

Exactly one evaluator: `Expressions2`, copied from velnor-legacy's engine (3,565 lines, transcribed from actions/runner v2.337.0, with its tests — I016/N60) and re-proven against the oracle's expression corpus (§5) before admission. It evaluates `if:` (including `success()`/`failure()`/`always()`/`cancelled()`), contexts (`github`, `runner`, `job`, `steps`, `matrix`, `needs`, `inputs`, `vars`, `secrets`), env interpolation, and workflow-command parsing. No second evaluator, no fallback: a parse/eval difference vs the oracle is a conformance failure, not a runtime branch. Legacy `DTExpressions` code is not copied.

### 3.5 Step, composite and post-step semantics

Steps run in order in the job sandbox; `run:` steps spawn via the agent's process supervisor with the scrubbed env (§3.6); `uses:` steps dispatch to native actions (§4) or local composites (`./.github/actions/*`, `actions/setup-velnor`) executed with composite semantics (inputs→env, nested steps, outputs). Post steps (`post:` / `post-if:`) run in reverse order after the main steps *including on cancellation/failure*, matching the oracle — order and results are compared exactly in §5 (a reordered/missing post step is one of the ten planted-difference tests). `continue-on-error`, job/step `timeout-minutes`, and matrix/`needs` output plumbing follow node24 semantics. A job naming any action outside the qualified set (or an unqualified SHA) is refused *before its first step* with an error naming it and listing the supported set; `velnor-gen` emits only qualified SHAs (generator test), so Renovate SHA bumps pass the harness first. Refusal is a job failure, never a silent skip — GitHub counts a skipped required check as passing (`hard-decisions.md:216-219`), so nothing on the required path may skip.

### 3.6 Contexts, env, secrets and masking

Contexts are built from the job message + webhook event exactly as the oracle builds them and compared as JSON (minus normalised fields) in §5. Env layering: workflow env → job env → step env, plus `GITHUB_ENV`/`GITHUB_PATH`/`GITHUB_OUTPUT`/`GITHUB_STEP_SUMMARY` files consumed between steps. Two env regimes must not be confused: *job* sandboxes get the full GitHub env the workflow expects; *obligation* (build/test) sandboxes under C5 get a scrubbed env — no `GITHUB_*`, no `.git`, fixed `HOME`/`PATH`/locale, fixed CPU count per class (part of definition digest), loopback-only network, no event file. The trusted helper (not candidate nextest config — `crates/velnor-runner/.config/nextest.toml` is candidate-controlled, F-H44) creates one namespace per test binary. Secrets are injected per-step by the executor, masked in all log/timeline output (mask set = secret values + OIDC/JIT tokens; masking verified by planted test "secret left unmasked"), and never written to receipts, stores, or the ledger. The `event.json` rewrite race (each action step rewrites it, `ActionRunner.cs:140`, `ExecutionContext.cs:1322-1336`, while a background step parses it — I023) is fixed by snapshotting `GITHUB_EVENT_PATH` before background steps (phase 0).

### 3.7 Cancellation, timeouts and lock renewal

Lease loop written fresh, renewing from `lockedUntil` in each response (about half the remaining time, nominal 60 s — the Listener's cadence, `JobDispatcher.cs:393-405` first-renewal rule kept): the upstream overload dereferences a null `request` when renewal fails (`JobDispatcher.cs:748-852`, N10/F-H25) and is not transcribed. "Job not found" on renew is treated as cancel. Cancellation sources: GitHub `JobCancel` (broker session only — standby dispatcher must hold/reopen sessions, F-H24), workflow `timeout-minutes`, step timeouts, and ledger claim-drop on supersede. Executor cancels the sandbox process tree, runs post steps with `cancelled()` context, then completes the job as cancelled; a superseded PR run's *ledger executions* survive iff another request claims the same keys (§2b). Timeouts are enforced by the agent (cgroup kill + exit proof), not by trusting the job's own report.

### 3.8 Logs and timeline via Results

Executor streams log lines, timeline records and step summaries through Results twirp as steps execute (no end-of-job bulk upload); obligation steps satisfied by receipt complete with a log line naming the receipt (key, producer, inventory) so the job log remains a complete audit trail. Completion uses `completejob` with outputs, step results and annotations (`CompleteJobRequest.cs:10-41` — logs are *not* in that request, so the Results stream must be sealed before completing; velnor-legacy #672's empty-step-results bug is a regression test: missing log blobs / hidden annotations fail conformance). Synthetic completion (N06/F-B03) is restricted to versioned generated plan/verdict jobs whose whole contract is proven, uploads a real log via Results plus one synthetic step result, and requires required checks bound to integration 15368 first — otherwise the executor runs the job normally. Reports/large outputs go to the site store by digest; job logs reference digests.

### 3.9 Crash safety

Journal discipline copied from velnor-new's runner (I010): persist intent → make call → record outcome; unknown is never absent. Executor journals plan id, job id, run-service URL, job token, pod UID before acting; after a crash it resumes or fails the job with its own token, never twice, and reconciles sandboxes by UID (a restarted agent kills/adopts by UID; an execution whose sandbox is gone is rescheduled, never double-reported). Ledger persists execution intent (key, node, epoch) before a sandbox starts; results land by compare-and-swap on that epoch, so a node that lost its epoch can report nothing into it (N37). `ensure` is idempotent: repeats return same receipts or join same executions. Fault injection in the lab before cutover: crash around every remote call, journal write and step boundary; dropped-after-success responses; lease lost mid-job; duplicate/reordered webhooks; ledger partition; lost node/control plane/site (v2 §3.9). Releases: cluster runs only released executor versions (never the change under test); 10% of jobs for a day before full rollout; previous release stays installed, switch-back drilled weekly; post-cutover rollback is previous Velnor release, never the official runner (N64). Executor cutover additionally waits for control-plane/site-loss qualification (3 k3s servers across failure domains or per-site independent admission with durable fencing — today one server, velnor-237).

### 3.10 Copied vs fresh; fastest job start

Copied into `velnor-new`, reviewed, adapted to latest APIs, owned there, each piece with tests and only after oracle pass (N60): expression engine (above); broker/run-service/Results clients + scale-set session; native checkout (`checkout.rs`, `git_mirror.rs`) and cache adapters; trust-scope model; legacy incidents as regression tests. From velnor-new's `crates/velnor-runner`: journal discipline, crash recovery, UID absence/ownership proofs, wire types (`velnor-runner-github`) and lifecycle types (`velnor-runner-core`) where they match latest APIs; `velnor-local` as harness. Fresh: dispatcher placement/lease logic, ledger/keys/receipts, executor step engine around copied clients, all native actions' local implementations, conformance harness. Not taken: legacy pipelines/distributed-task, cache v1, JS sidecars, Docker actions, the 37k-line `executor.rs`/`runner.rs` as wholes, BuildKit handling, Firecracker (phase 5). `velnor-legacy` gets no commits, no dependency, no published crates (owner decision 5).

Fewest-milliseconds job start (broker message → first step ≤1 s P50 / ≤2 s P90 [T], vs 2–3 s idle ARC, 12–14 s on-demand [M]): (1) scale-set sessions pre-opened, broker long-poll already waiting — no session setup per job; (2) JIT identities pre-minted by dispatcher, node chosen before acquire — no post-acquire move; (3) sandboxes pre-created per class per node (claim <0.2 s), warm snapshot reflink 0.25 s [M]; (4) toolchain/tools/action state mounted read-only — no installs or downloads; (5) acquire pipelined with sandbox claim: dispatcher acquires only after node confirms a sandbox slot, executor receives message+token+sandbox in one hand-off. Starting Node costs only 87–147 ms/action [M] — the win is locality and removed round trips (H1), stated honestly: Rust is for control of the whole path, not interpreter speed.

## 5. The conformance oracle

The official runner is never a production fallback (owner decisions 1–2). It exists in `velnor-lab` as the differential oracle: every claim "Velnor behaves the same" is proven against the *latest* official release, not asserted. `velnor-conformance` (5k lines) seeds from `velnor-new`'s `qualification.yml`, which already compares a hosted job with a scale-set job.

**Differential harness.** Lab repo dispatches each corpus case twice from the same commit+event — once per runner label (Velnor scale set, official-runner label) — pairs jobs by workflow/job/matrix, and collects via GitHub API: runs, jobs, steps, logs, annotations, step summaries, caches, artifacts, attestations, plus Results timeline. Cases run with publication pointed at lab repo/registries only.

**Corpus (three parts).** (1) *Full job set*: every job of all 16 workflow files under each triggering event, at pinned commits, including recorded failures, cancellations and re-runs; release workflows included against lab targets. (2) *Semantics corpus*: velnor-legacy + actions/runner expression tests; every context (`github`/`runner`/`job`/`steps`/`matrix`/`needs`/`inputs`/`vars`, secrets masking); `if:` with `success()`/`failure()`/`always()`/`cancelled()`; `continue-on-error`; outputs via `GITHUB_OUTPUT`, step/job outputs and `needs`; `GITHUB_ENV`/`GITHUB_PATH`/`GITHUB_STEP_SUMMARY`; workflow commands/annotations; post steps; cancellation at every step boundary; job/step timeouts; cache/artifact round-trips; OIDC tokens; the ten planted differences (wrong output, unmasked secret, reordered/missing post step, wrong `cancelled()`, lost annotation, among others — harness must catch each). (3) *Refusals*: actions outside the set, Node/Docker actions, legacy features (AES session, distributed-task, cache v1) — Velnor must refuse pre-job; oracle behaviour recorded but refusal is the expected Velnor outcome, allow-listed as intentional divergence.

**Normalisation and comparison.** Removed before compare: ids, timestamps/durations, runner names/labels/versions/machine names, workspace/temp/tool-cache paths, tokens, official runner's own lines (action downloads, banners, Node setup), ANSI codes, interleaving of concurrent output. Contexts compared as JSON minus those fields. Pass requires, after normalisation, *exact equality* of: step outcomes/conclusions, outputs, contexts/env, expression results, annotations, step summaries, cache/artifact effects (keys, hits, file lists, digests), post-step order/results, cancellation/timeout outcomes; same timeline structure and user-visible log lines. Any other difference fails the case unless an owner-signed allow-list entry with reason covers it. Gate is **100% of cases** — no percentage pass.

**Against each new official release; drift within hours.** Harness runs: blocking on every executor/native-action/protocol change; nightly; and within 24 h of each new official release (discovered via releases API). Velnor reports the runner version it last passed against; GitHub's 63-day version window (evidence §F) becomes the conformance deadline — failing to pass a new release inside it blocks executor releases, never production (production never waits on the oracle). Protocol drift therefore surfaces as a failing lab case within a day, plus a canary job every 10 min through each executor path in production (I017) catches GitHub-side changes that no release announces (webhook/queue/broker behaviour). Drift response: fix + release inside the window; jobs' own `ensure` covers webhook gaps meanwhile (§3.9 degraded mode: obligations run fresh, slower, never wrong).

**Cutover pass criteria (all required, N64).** (1) Corpus 100% vs latest official release on two consecutive nightly runs, every allow-list entry signed off. (2) Two weeks + ≥300 merges of non-blocking twin jobs (every `velnor-new` job also runs on Velnor, publication off, outside required checks); every verdict difference fixed+replayed or shown by paired reruns to be a flake on both sides. (3) Per job class, Velnor twin no slower than official at P90; job start ≤2 s P90. (4) Fault injection (§3.9), previous-release switch, control-plane and site loss qualified. Cutover change routes `velnor-new` to Velnor scale sets and deletes ARC's `velnor-new` scale sets in the same change; rollback after is previous Velnor release only.

### 6.2 Tiers, trust, budgets

L0 sandbox dir on node XFS; L1 node store (toolchains, tools, crate sources, Git mirror, action archives, warm snapshots — read-only or agent-made clones); L2 per-site store/ledger/`mbx-cache`; L3 GitHub cache only for hosted stragglers, 10 GB budget. Nothing synchronous crosses the 35 ms DE–FI WireGuard link. Only trusted `main` builds write snapshot generations and `mbx-cache`; generations immutable; agent harvests outputs when the build phase ends, before any test runs (a test writing into `target/` cannot poison later requests); merge groups never write trusted scope — receipts become trusted when exact SHA lands. Lineage restart (lock/toolchain change + daily) builds cold into a fresh `mbx-cache` namespace reading nothing older wrote. Budgets: last 3 `main` generations/root then LRU; 40% of node data volume across orgs, alert 70% (FI workers one 3.5 TB disk, DE 32–50 TB [M]); runner target 10.6 GiB [M].

### 6.3 Test-level scheduling across the cluster

Default stays in-sandbox: build test binaries once per configuration, run lanes in parallel (one target lane per check kind — cargo locks a target dir exclusively, `hard-decisions.md:56-62` — clippy/doc metadata pre-built, one jobserver as CPU budget across lanes). ### 6.5 Verdict reuse without trusting anything unproven — soundness per mechanism

Contract is C1–C7 (v2 §1.2). For *every* reuse/skip mechanism below: (1) why the key is complete, (2) failure mode if not, (3) detection, (4) automatic fallback. When in doubt, re-execute (brief §11). Keys: per-root (ph2) = Git tree hashes of root + reached roots (only `ci-helper` reaches out, into 5 generator crates) + shared files (toolchain pin, `mise.*`, `.github/`, `.velnor/`) + declared extra inputs + definition digest (command, config, features, profile, nextest profile, helper/toolchain/image digests, sandbox class, CPU count); per-package (ph3) = same over cargo package-graph closure. Hashes from commit in <5 ms, no build. Execution manifest joins every key (event class, allowed env+values, path prefix, file modes/symlink targets as mounted). Sandbox is a sparse checkout of exactly the key's paths (tree hashes include directory membership, so enumeration/negative lookups covered — `golden.rs:19-41` enumerates samples and asserts non-empty [M F-H11]); receipt-minting runs log every `ENOENT` lookup outside the declared set; a class enrols only at 100% enforced-pass matching an unrestricted run's inventory+outcomes.

## 7. Scheduling and the cluster

Fleet: 5 workers × 96 threads = **480 threads**, ~125 GiB each, two sites (DE: velnor-240/105, FI: velnor-241/5/190; velnor-237 control plane) [M §B.0]. k3s stays fleet layer (deploy, quotas, priorities, network policy, accounting); Velnor places *work* (obligations), kube-scheduler places pods (v2 §7). ## 8. The merge queue and GitHub integration

### 8.1 On-demand trigger: the label flow (owner-binding, brief §12)

Label name: **`velnor:verify`** (single label; colours/description owned by repo settings). State machine per PR head SHA:

1. Draft PR, any pushes → **nothing runs**. (`pull_request` trigger types exclude draft-affecting activity as heavy work; see gate below.)
2. Mark ready for review → **still nothing**. (`ready_for_review` is not a trigger type for `ci.yml`.)
3. Add `velnor:verify` → CI starts on current head. (`labeled` event.)
4. Label present + new push → new pipeline immediately; previous pipeline cancelled immediately, **no stall** (ledger per-key join, §2b; GitHub concurrency cancels the old *run*, new run's obligations schedule without waiting for cancelled run's jobs — one-job shape has no `always()` `Required` to wait on, F-H06 removed).
5. Remove `velnor:verify` → no further PR verification. (`unlabeled` handling cancels in-flight PR runs/claims; later pushes hit the not-requested gate.)

Nothing else starts PR CI: no auto-labelling from ready-for-review or auto-merge, no `edited` trigger (dropped; retargets re-planned by ledger without restarting identical work, F-H07), no push trigger for PR branches. The label *starts* verification; it is never the gate — the gate is the `Required` check on the exact head SHA.

**Workflow shape (`velnor-gen` output).** `ci.yml` `on: pull_request: types: [labeled, synchronize, unlabeled]`, `merge_group`, `push: branches: [main]`. There is deliberately no job-level `if:` skip on `Required`: GitHub counts a skipped required check as passing (`hard-decisions.md:216-219`), so skipping is a false-green machine. Instead the single `Required` job's first step is a *native gate executed by `velnor-exec`* (label/draft check from the job's PR payload — code Velnor runs, not a YAML skip):

- Label present (and PR not draft, or draft explicitly labelled — labelling a draft is an explicit owner act and verifies it) → run `ensure` obligations, stream, conclude success/failure on real results.
- Label absent or PR draft without label → execute only the gate step: write step summary + log "CI not requested for <SHA> — add label `velnor:verify`", complete the job with conclusion **failure** (a non-success the ruleset blocks on; summary distinguishes not-requested from code failure; cost ~3–5 s [E], zero heavy work, zero sandboxes beyond the gate pod). Velnor never reports success for an unverified commit: before any run exists the head simply has *no* `Required` check (pending/expected), after a not-requested run it has a failed one. Both block merge.
- `unlabeled` where the removed label is `velnor:verify` → gate fails the run the same way *and* `velnor-hooks` calls the GitHub API to cancel any in-flight run for that PR + drops ledger claims for its head (executions another request claims keep running). Removing an unrelated label while `velnor:verify` remains → gate re-checks current labels and proceeds (labels read fresh, not from event alone).

`merge_group` and `push` to `main` have no label gate: the queue always verifies what it merges, and `main` always runs its (mostly lookup) run. Concurrency: `group: velnor-CI-<PR number or ref>`, `cancel-in-progress` for `pull_request` only; merge-group runs are never cancelled by PR pushes.

**How label events reach Velnor (verified + fallback).** Two independent paths. (a) *Workflow path*: `labeled`/`synchronize` create workflow runs — but runs triggered by `GITHUB_TOKEN` actions are suppressed (GitHub Docs, "Triggering a workflow": events triggered by `GITHUB_TOKEN`, except `workflow_dispatch`/`repository_dispatch`, do not create runs). A human adding the label in the UI, or an agent acting with a GitHub App installation token / PAT, is not `GITHUB_TOKEN`, so the run is created; an agent acting through a workflow's `GITHUB_TOKEN` (e.g. a bot workflow labelling PRs) would be suppressed. The design therefore never relies on token-labelled automation: agents label via App token or UI-equivalent API credentials, documented in the agent runbook. (b) *Webhook path (primary for latency)*: `velnor-hooks` receives the App's `pull_request` `labeled`/`unlabeled`/`synchronize` webhooks — webhook delivery to GitHub Apps is a separate subscription mechanism with no `GITHUB_TOKEN` suppression — verifies the signature, and calls `ensure` (or drops claims on unlabel) immediately, in parallel with any workflow run. The `Required` job, whenever GitHub creates it, joins that work. *Fallback if both paths miss* (suppressed creation + lost webhook): hooks replays missed App deliveries every minute (delivery-list API, N23), plus a 1-minute poller listing open PRs carrying `velnor:verify` whose head lacks a completed `Required` check and calling `ensure` + `workflow_dispatch` (exempt from suppression) to materialise the job. A lost webhook therefore delays by ≤~1 min and can never lose correctness: the job's own `ensure` is the final fallback (v2 §3.4 step 5).

### 8.2 Merge requires green on the latest head; queue is additional

**Ruleset (replaces today's 24396608 shape — requires `Required verdict`+`Required` with no `integration_id`, so any app or `statuses: write` token can post them [M S3/N12]).** For `main`:

- Require a pull request before merging; require status checks to pass: **`Required`** (single name after `velnor-gen` cutover; until then both legacy names, one writer per phase) bound to the **GitHub Actions integration (15368)** — the executor's jobs report as Actions, which the release gate also requires (`gate.rs:15,127-159,277-288`; `product-release.yml:86` asserts exactly one `Required` job in the `push` run of `.github/workflows/ci.yml` — file name pinned). Push runs keep that one real job (§2b).
- Enable merge queue: required check **`Required` in `merge_group` context** (same job name, merge-group event), grouping HEADGREEN initially (C1 restated for group tips, intermediates listed for bisection/release tooling — F-H01; switch to ALLGREEN once queue-tip bypass trees keep ejections nearly free, Q3), `min_entries_to_merge` 1 (so the 5-min wait never applies [M]), `check_response_timeout_minutes` 90 → 20 (ph3), `max_entries_to_build` 2 → 4 only when the under-load replay shows more merges/hour (about 4 @ ≤3% false failures, 8 @ ≤2% with bypass trees; at today's 8.1% discordance depth 4 disturbs 29% of windows, depth 8 49% — F-H05; GitHub starts replacements at once on failure, and one slot-1 failure invalidates up to 7 candidates behind it).
- Latest-head rule is structural: required checks are evaluated on the PR head SHA — a push changes the head, the old green check no longer applies, the new head shows pending/failed until its labelled run passes. While the label is present that run starts automatically on `synchronize` (flow step 4); without the label the PR can never go green and can never enter the queue (queue entry requires the PR checks green — an unlabelled PR is ineligible by construction). Velnor additionally refuses to mint a verdict for any commit it did not verify (C4) and binds every receipt to tree+manifest, so a stale green cannot be replayed onto a new tree.
- Block force-pushes to `main`; no bypass actors except owner break-glass (audited). No release is cut from a HEADGREEN intermediate commit (C1 list).

**No duplicate verification across PR → queue → `main`.** Merge group lists every obligation (hard decision 3, literally full) and satisfies each by receipt lookup on its own keys; it reuses the PR verdict *only* where trees/keys are identical (exact-tree equality is the degenerate case — today 0–18% of groups [M S4] because the window is hours; at a 1–5 min verdict window replays give 78–89% [E], per-package keys add 3–10 points). Push to `main` whose SHA passed its merge group executes only release/publication duties (§2b). **Speculation:** ordered prefixes `T_i = T_{i−1} ⊕ PR_i` plus single-ejection bypass trees (7 trees for 4 PRs) computed by `git merge-tree` on the mirror and verified at batch priority from phase 3 (shadow read-only from phase 0; kill below 70% tree match — 122/193 groups were built on an unlanded group commit [M], so speculating on `main ⊕ PR` (old M5) predicts the wrong tree). Wrong guesses waste preemptible CPU only.

**Auto-merge and agents.** Agents enable auto-merge when opening the PR (today 0/40 [M S2]; green→enqueue median 7.5 min of pure waiting), stop catch-up merges of `main` into branches (merge group tests the real candidate anyway), and label `velnor:verify` when the PR is ready to verify (not on every intermediate push — brief §12's 45%-cancelled waste is removed by never starting). First-push-to-merge, time-to-first-actionable-failure and failed-attempts-per-merge are guardrails beside push-to-merge so a fast last push cannot hide slow feedback (N42). The cancelled-run stall is gone by construction (§8.1) and reported as run-created→first-job with gate p90 ≤5 s.

## 9. What would make CI not a bottleneck at all

Written as an absolute: CI is not a bottleneck when *no human or agent ever waits for verification* — the verdict already exists when the decision to merge is made, and merging costs only the platform's serialisation latency. The design reaches it by moving verification *before* the wait (label-time `ensure`, pre-push `velnor verify`, queue-tip speculation) and making the wait itself a lookup.

**Theoretical floor for this repository (labelled, median generator/helper PR, warm cluster).**

| Term | Floor | Why irreducible |
|---|---|---|
| Push accepted → webhook delivered | 1–2 s [M] | GitHub event creation; measured push→run 1–2 s |
| Fetch + `merge-tree` + released plan | ~2 s [E] | Git object transfer of the delta + hashing; keys in <5 ms, dominated by fetch |
| Delta compile (changed closure only) | ~10–15 s [E] | Serial rustc chain of the changed crates; parallelism cannot shorten a dependency chain (cold runner build: 696 CPU-s but ~170 s chain [M]) |
| Longest changed test (after §6.4) | ≤15 s stretch / ≤60 s committed | One test's serial execution; sharding cannot split one test |
| Receipt lookup + `Required` completion | ~5 s [E] | Results streaming + `completejob` round trips |
| **PR verdict floor** | **~35 s typical, ~15–20 s if tree pre-verified pre-push** | Sum above; pre-verified pushes hide all but lookup+completion |
| GitHub merge queue (enqueue→run 19 s + finish→merge 26 s [M]) | **45 s** | GitHub serialisation; Velnor cannot remove it while GitHub lands merges |
| **Push-to-merge floor via GitHub queue** | **~80 s typical; ~50–65 s pre-verified** | Verdict (overlapped) + 45 s |
| Velnor merge train instead (phase-4 stretch, Q11): fast-forward `main` by compare-and-swap to the exact verified commit | ~5 s after verdict | One git CAS + check posting; every tip verified by construction (stronger than HEADGREEN) |
| **Push-to-merge floor via Velnor train** | **~40 s typical; ~10–25 s pre-verified** | Webhook + CAS + API visibility |

Floors by PR class: runner-workspace PRs floor at the crate-split serial chain (~1–1.5 min until split + template land); lockfile/toolchain PRs (10.5% touch a lockfile [M]) floor at the cold-ish rebuild (~40–90 s even with `mbx-cache`); C5 obligations (network/clock/random/publishing) always execute, so their runtime is a hard floor for any PR touching them. Unlabelled pushes have floor ∞ by design — no verdict is ever produced, which is the point (brief §12): the bottleneck is removed by *not doing work nobody asked for*, and the merge gate makes that safe.

**Design that reaches the floor.** (1) Verification starts at the earliest moment the tree exists: agent `velnor verify` (same sealed sandbox) → push webhook (labelled PRs) → `Required` job joins. (2) Everything already verified is a lookup (content keys, §6.5). (3) The queue's future trees are pre-verified (tip speculation, §8.2), so the merge-group run is also a lookup ≥85% of the time. (4) Reserved merge path + honest sizing make latency independent of cluster load (§7). (5) The only remaining serial terms are GitHub's — removed last by the merge-train stretch. At that point CI time is *overlapped* with authoring/review time and the observed push-to-merge is platform latency, not CI. **Irreducible costs that remain:** webhook delivery, delta serial compile chain, longest single test, Results/`completejob` round trips, and (until the train) 45 s of GitHub queue latency. Any design claiming below ~10 s push-to-merge on this repo is either not verifying the landed tree or not using GitHub to land it — both excluded by the brief.
