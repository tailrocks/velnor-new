# Velnor Rust-only runner and zero-bottleneck CI/CD architecture

## 1. Summary

Velnor replaces ARC and GitHub's C# runner (`Runner.Listener` and `Runner.Worker`) with a 100% Rust execution stack (`velnor-dispatch`, `velnor-node`, `velnor-exec`, `velnor-native-actions`, `velnor-ledger`, `velnor-store`, `velnor-hooks`, `velnor-conformance`) speaking only the latest GitHub APIs (scale-set sessions, broker long-poll, JIT config, run-service acquire/renew/complete, Results Twirp, cache v2, artifacts v4, OIDC).
Every Node and JavaScript action is eliminated; Velnor runs a closed native Rust action set against node-local state (bare Git mirror, read-only tool and crate stores, XFS reflinked `target/` snapshots, and site `velnor-store` blobs) and refuses unknown actions before step 1.
GitHub's official runner v2.338.0+ runs exclusively in `velnor-lab` as a differential conformance oracle enforcing 100% normalized output parity before cutover and within 24 h of every upstream release.
CI runs on demand via the `velnor:verify` label flow: unlabelled and draft pushes run zero heavy work and stay blocked at the ruleset, while labelled PRs, merge-group runs, `main` pushes, and releases share one content-addressed obligation ledger (`ensure`) where every compile, test, package, and attestation executes once per unique input closure and promotes by digest.
To resolve the debug-versus-release profile tension without duplicate compilation, tests use pre-optimized registry dependencies (`opt-level = 2`, `debug = false`, `debug-assertions = true`, `overflow-checks = true`) stored in the warm XFS snapshot with `opt-level = 0` workspace crates, while releasable binary closures (`velnor-ci`, `velnor-gen`, runner binaries) build once in `--release` inside the merge-group / `main` obligation graph and are promoted directly by SHA-256 digest into GitHub Releases without rebuilding.
- **PR verdict (labelled push to green `Required`), P50 / P90:** committed **45 s / 150 s** (Phase 3), stretch **18 s / 55 s** (Phase 4, 0 s after sealed pre-push `velnor verify`). Today: **26.7 min / 92.3 min** [M, evidence §A T2].
- **Push-to-merge (labelled final push to merged on `main`), P50 / P90:** committed **110 s / 4.5 min** (Phase 3), stretch **65 s / 120 s** (Phase 4 with queue-tip speculation and instant receipt lookup). Today: **85 min / 457 min** [M, v2 §1.1].
- **Cost per merged PR and per release:** committed **24 runner-min** (stretch **11 runner-min**) vs **285-347 runner-min** today [E, v2 §1.1], and **1.5 runner-min** per release (promotion only) vs **42-68 runner-min** today.

## 2b. Duplicate-work audit

We audited all 16 workflows in `.github/workflows/*.yml`, `velnor-gen`'s generated `rust-ci.yml` (`generator/samples/velnor-new/expected/.github/workflows/rust-ci.yml`) and `release.yml` (`crates/velnor-render/src/{release,release_binaries,release_finalize,release_steps}.rs`), and `ci-helper` (`crates/velnor-ci/src/{gate,plan,release,inputs}.rs`).

### Resolving the profile tension (debug tests vs release binaries)

In `velnor-new`, CI tests compile with Cargo's `dev`/`test` profile (`opt-level = 0`, `debug = true`, `panic = "unwind"`, except `sha2` at `opt-level = 3` and `turso_core` at `opt-level = 1`, `Cargo.toml:69-73`, `Cargo.toml:74`), whereas shipped binaries (`velnor-ci`, `velnor-gen`, `velnor-host`, `velnor-resource-probe`, `velnor-runner-attestation-helper`) compile with `--release` (`opt-level = "s"` or `3`, `lto = "thin"`, `strip = true`, `panic = "abort"`, `Cargo.toml:13-17`, `Cargo.toml:35-39`). We evaluated three designs with numbers:

1. **Option A: Run all CI tests in `--release` (`opt-level = 3`/`"s"`, `lto = "thin"` for workspace crates).** Rejected. Compiling workspace crates with LLVM optimization passes and thin LTO increases per-push delta compile time by 2.4-3.1x (for `velnor-ci` + `velnor-gen`, warm delta compile rises from 6.2 s to 16.5 s [E]; for `velnor-runner-*`, from 18 s to 52 s [E]). Furthermore, `panic = "abort"` in `[profile.release]` is incompatible with Rust test harnesses (`rustc` rejects `panic = "abort"` for `#[test]` binaries), and standard `--release` disables `debug-assertions` and `overflow-checks`, violating the same-confidence rule.
2. **Option B: Pure `opt-level = 0` in CI, rebuild `--release` from scratch at release time.** Rejected. This is today's behavior: it leaves third-party dependency code (`turso`, `bollard`, `serde`, `git2`, `sha2`) slow during test execution and forces `release-rust-ci-tools.yml`, `product-release-*.yml`, and `velnor-gen`'s `release.yml` (`build-<pkg>-<suffix>`) to recompile 100% of dependencies and workspace crates during release.
3. **Option C (Adopted): Hybrid test profile + content-addressed release-artifact obligations built once and promoted by digest.**
   - **Pre-optimized dependencies in the test profile:** We set `[profile.dev.package."*"]` and `[profile.test.package."*"]` to `opt-level = 2`, `debug = false`, `debug-assertions = true`, `overflow-checks = true`, while keeping workspace crates at `opt-level = 0`, `debug = "line-tables-only"`, `debug-assertions = true`, `overflow-checks = true`. Because `Cargo.lock` changes in only 10.5% of PRs [M, `proposals/fable-5.2.md`], all registry dependencies are pre-compiled in the node's warm XFS snapshot (`0.25 s` clone, `0 s` compile cost on 89.5% of PRs [M, S12]). Dropping third-party debuginfo and using line tables shrinks `target/` by 24% (from 10.64 GiB to 8.09 GiB [M, issue #585]) and cuts test execution CPU on the slowest database/serialization tests by 50-66% [M, `proposals/fable-5.2.md`, decisions I064], with zero loss of assertion or overflow coverage.
   - **Build release artifacts once per unique package closure, promote everywhere:** Releasable binaries (`velnor-ci` and `velnor-gen` for `x86_64-unknown-linux-musl` and `aarch64-unknown-linux-musl` cross-compiled via `musl-gcc`/`zigbuild` on the x86_64 cluster; plus `velnor-dispatch`, `velnor-node`, `velnor-exec`, `velnor-resource-probe`, `velnor-runner-attestation-helper`) are modeled as first-class obligations `release-bin(<pkg>, <target>)` keyed by the package's exact release input closure `K_rel(pkg, target)` (package + transitive path-dependency tree hashes, `Cargo.lock` subset, `rust-toolchain.toml`, target triple, `[profile.release]` settings; commit SHA is recorded in the external `COMMIT` and Sigstore provenance attestation rather than injected via `env!("VELNOR_COMMIT")`, matching `crates/velnor-render/src/release_binaries.rs:108-114`).
   - Each node keeps a warm XFS snapshot of `target/release-<target>` built by the `main` builder. When a `merge_group` (or `release-plz` Release PR) changes `K_rel(pkg, target)`, `ensure` runs `cargo build --release --locked --target <triple> -p <pkg> --bin <bin>` once over a reflink clone of the warm release snapshot (taking **8.5-13.0 s** for `velnor-ci`/`velnor-gen` because all 144 registry crates hit the warm release snapshot [E]), runs the binary smoke checks (`--version`, `check-tag`), packs deterministic `<bin>-<suffix>.tar.gz` (`--sort=name --mtime=@0`, `gzip -n`), stores the tarball in `velnor-store` by `sha256:<digest>`, and mints a signed `ReleaseArtifactReceipt(K_rel, sha256:<digest>, target)` in `velnor-ledger`.
   - When the commit lands on `main` and `release-plz` tags a release (or `product-release.yml` / `release-rust-ci-tools.yml` runs), the release workflow **never runs `cargo build`**. It looks up `ReleaseArtifactReceipt(K_rel, target)` in `velnor-ledger`, verifies that the tag commit's `K_rel` matches the receipt, fetches the exact verified `<bin>-<suffix>.tar.gz` bytes from `velnor-store`, writes `SHA256SUMS`, signs the OIDC Sigstore provenance bundle natively in Rust, and uploads the assets to GitHub Releases.

### 3.2 Protocol client: latest GitHub APIs only

Every legacy endpoint (`MessageListener.cs` AES-encrypted sessions, `_apis/distributedtask/hubs/build/plans/.../timelines`, `DTExpressions`, cache v1 `_apis/artifactcache`, artifacts v3) is excluded and banned by a CI string-lint test. `velnor-dispatch` and `velnor-exec` implement only:

1. **Scale-set administration and message session (`velnor-dispatch`):**
   - Authenticates with the Velnor GitHub App installation token (`POST /app/installations/{id}/access_tokens` -> `POST /repos/{o}/{r}/actions/runners/registration-token` -> `POST /actions/runner-registration` with `Authorization: RemoteAuth <token>`, returning the Actions service URL and admin JWT, refreshed 60 s before expiry; `actions/scaleset/client.go:937-1010,1083`).
   - Manages scale sets (`velnor-merge`, `velnor-gate`, `velnor-build`, `velnor-docker`) at `_apis/runtime/runnerscalesets?api-version=6.0-preview` (`scaleset/client.go:23,394-395`) and opens one message session per scale set (`POST .../runnerscalesets/{id}/sessions`, `scaleset/session_client.go:45`).
   - Long-polls `GET {session_url}?lastMessageId={id}` with timeout 120 s and header `X-ScaleSetMaxCapacity: <total_scale_set_capacity>` (never free slots, which violates the protocol contract; `scaleset/session_client.go:143-168`, `decisions I015`). HTTP 202 indicates an empty poll; HTTP 401 triggers a single-flight session token refresh (`session_client.go:175-190`).
   - On `RunnerScaleSetJobMessages` containing `JobAvailable` (`scaleset/types.go:21-57`), `velnor-dispatch` classifies the offer (`runnerRequestId`, `eventName`, `requestLabels`, `jobDisplayName`), selects the target worker node, calls `POST .../runnerscalesets/{id}/acquirejobs` with `[runnerRequestId]` (`session_client.go:278-303`), and deletes (acks) the queue message (`DELETE`, `204 No Content`, `session_client.go:215-240`) only after the acquisition intent is durable in its journal.
2. **Pre-registered JIT runner pool & V2 Broker long-poll (`velnor-dispatch`):**
   - `velnor-dispatch` pre-mints ephemeral JIT runner configurations via `POST .../runnerscalesets/{id}/generatejitconfig` (`{name, workFolder: "/w"}`, `scaleset/client.go:765-796`). It parses the base64 JSON map `{".runner": ..., ".credentials": ..., ".credentials_rsaparams": ...}` (`Runner.Listener/Runner.cs:234-253`) directly in memory, keeping the RSA private key inside `velnor-dispatch` and **never writing `.credentials_rsaparams` to any sandbox disk**.
   - Using `OAuthCredential` (`grant_type=client_credentials`, `client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer` signed with PS256/RS256 from `.credentials_rsaparams` against `authorizationUrlV2`; `Runner.Listener/Configuration/OAuthCredential.cs:25-55`, `Sdk/WebApi/WebApi/OAuth/VssOAuthConstants.cs:23,39,44,70`), `velnor-dispatch` keeps pre-opened V2 Broker sessions (`POST {ServerUrlV2}/session` with `TaskAgentSession{BrokerSession=true}`, `Sdk/WebApi/WebApi/BrokerHttpClient.cs:143`) polling `GET {ServerUrlV2}/message?sessionId=...&status=Online&runnerVersion=2.338.0&os=Linux&architecture=X64&disableUpdate=true` (`BrokerHttpClient.cs:70-101`), handling `BrokerMigrationMessage` (`Runner.Listener/MessageListener.cs:264-273`).
3. **Run Service `acquirejob`, `renewjob`, `completejob` (`velnor-dispatch` -> `velnor-exec`):**
   - When the broker delivers `RunnerJobRequest` (`RunnerJobRequestRef{id, runner_request_id, should_acknowledge, run_service_url, billing_owner_id}`, `Runner.Listener/Runner.cs:699-750`), `velnor-dispatch` sends `POST {broker}/acknowledge` (`BrokerHttpClient.cs:225-259`) and calls `POST {run_service_url}/acquirejob` with `{jobMessageId: runner_request_id, runnerOS: "Linux", billingOwnerId}` (`Sdk/RSWebApi/RunServiceHttpClient.cs:70-90`), treating HTTP 404/409/422 as terminal non-retriable states (`RunServiceHttpClient.cs:100-112`).
   - `velnor-dispatch` performs the mandatory first lock renewal `POST {run_service_url}/renewjob` (`{planId, jobId, requestId}`, returning `RenewJobResponse{lockedUntil}`, `RunServiceHttpClient.cs:184-200`) before starting execution, matching `Runner.Listener/JobDispatcher.cs:380-410`.

### 3.4 Expression engine (`Expressions2`)

We copy and own `velnor-legacy`'s 3,565-line `expression/` module (`lexer.rs`, `parser.rs`, `eval.rs`, `value.rs`, `spans.rs`, `mod.rs`, `tests.rs`), which is a direct Rust transcription of `actions/runner`'s `src/Sdk/DTExpressions2/Expressions2/` (`Runner.Worker/PipelineTemplateEvaluatorWrapper.cs:58-75`, without the legacy `DTPipelines` dual-evaluator wrapper):
- **Type system and coercion:** Exact IEEE-754 number parsing (including `NaN`, `Infinity`, hex `0x`, octal `0o`), case-insensitive object property lookup (`DictionaryContextData`), automatic string/number/boolean/null coercion matching C# `EvaluationResult`.
- **Built-in and status functions:** `case`, `contains`, `startsWith`, `endsWith`, `format`, `join`, `toJson`, `fromJson` (`eval.rs:216-247`), plus job/step status functions `success()`, `failure()`, `always()`, `cancelled()` (arity 0) and native Rust `hashFiles(pattern1, ...)` (1..255 glob arguments rooted at `GITHUB_WORKSPACE`, matching `Runner.Worker/Expressions/HashFilesFunction.cs:19-60` in pure Rust without spawning Node.js as `HashFilesFunction.cs:73,206` does!).
- **Resource bounds:** Enforces `MAX_DEPTH` and `MAX_LENGTH` (`expression/mod.rs:36`) and `MAX_ENV_CHARACTERS = 100_000` (`crates/velnor-render/src/rules.rs:28`).

### 3.5 Step, composite and post-step semantics

`velnor-exec` executes steps with exact node24-era official runner semantics (`Runner.Worker/StepsRunner.cs`, `ActionRunner.cs`, `ActionManager.cs:820-845`):
1. **Condition and template evaluation:** At each step boundary, `velnor-exec` evaluates the step's `if:` (`Condition`, defaulting to `success()` when omitted), `continue-on-error`, `timeout-minutes`, `display_name_token`, `working-directory`, `shell`, `env`, and `with` inputs (`TemplateToken` expansion against the live `ExecutionContext`).
2. **Parallel step groups (`background: true`):** `velnor-new`'s engine uses `background: true` steps with `ParallelGroupId` joined by a `wait-all` step (`JobStep.cs:29-50`, `docs/hard-decisions.md` §1). `velnor-exec` spawns `background: true` steps concurrently inside the sandbox under the shared jobserver, snapshots `GITHUB_EVENT_PATH` (`event.json`) per concurrent step so another step rewriting `event.json` (`ActionRunner.cs:140`, `ExecutionContext.cs:1322-1336`) cannot cause the `producer_event_invalid` truncation race (`decisions I023`), and joins all members at `wait-all`, propagating any member failure.
3. **Composite actions (`using: composite`):** Expanded inline into a scoped child `ExecutionContext` (`ActionManager.cs:820-845`, `docs/adrs/1144-composite-actions.md`, `1438-conditional-composite.md`). Inputs map to `inputs.<id>`, each composite has its own `steps` context and `GITHUB_STATE`, `env`/`PATH` writes propagate to outer steps, and any post steps registered by native actions inside a composite are pushed onto that composite's LIFO post-step stack and run when the composite exits (or at job post-step phase for `cache/restore` -> `cache/save` pairs).
4. **Outcome vs Conclusion and Post steps:** Each step records `outcome` (`success`, `failure`, `cancelled`, `skipped`). If `outcome == failure` and `continue_on_error == true`, `conclusion` becomes `success` while `steps.<id>.outcome` stays `failure` and `steps.<id>.conclusion` is `success`. Native actions that have a post phase (such as `actions/checkout` credential cleanup or `actions/cache` post-save) push a post-step closure onto the job's LIFO post stack upon starting; post steps execute in reverse order after all main steps finish, with their own `if:` condition (`always()`, `success()`, etc.) evaluated against the job's current `JobStatus`.

### 3.6 Contexts, env, secrets and masking

- **Contexts:** `github` (populated from `ContextData["github"]`, including `event`, `sha`, `ref`, `head_ref`, `base_ref`, `event_name`, `workspace`, `action`, `token`), `runner` (`os: "Linux"`, `arch: "X64"`, `name`, `temp`, `tool_cache`, `workspace`, `environment: "self-hosted"`), `job` (`status`), `steps` (`<id>.outputs`, `<id>.outcome`, `<id>.conclusion`), `env`, `vars`, `secrets`, `needs`, `inputs`, `matrix`, `strategy` (`JobRunner.cs:145-165`, `GitHubContext.cs`, `StepsContext.cs`).
- **Scoped environment per step kind:** Matching `ScriptHandler.cs:313-327` and `NodeScriptActionHandler.cs:54-93`, `run:` script steps receive `GITHUB_*`, `RUNNER_*`, `CI=true`, and `ACTIONS_ID_TOKEN_REQUEST_URL/TOKEN` (when `id-token: write` is granted), plus `ACTIONS_ORCHESTRATION_ID`, and **never** receive `ACTIONS_RUNTIME_TOKEN`, `ACTIONS_CACHE_URL`, or `ACTIONS_RESULTS_URL` unless invoked through a native action adapter that uses those endpoints internally.
- **File commands (`FileCommandManager.cs`):** Before each step, `velnor-exec` creates fresh per-step files for `GITHUB_OUTPUT`, `GITHUB_ENV`, `GITHUB_PATH`, `GITHUB_STATE`, and `GITHUB_STEP_SUMMARY`. After the step exits, `velnor-exec` parses key-value pairs and heredoc delimiters (`KEY<<EOF ... EOF`), rejects blocked environment keys (`LD_PRELOAD`, `NODE_OPTIONS`, `BASH_ENV`, etc., `FileCommandManager.cs:181`), updates the job environment and `$PATH`, and uploads `GITHUB_STEP_SUMMARY` via `CreateResultsStepSummaryAsync` (`ResultsServer.cs:88-97`).
- **Workflow commands:** Stdout lines starting with `::` are parsed (`workflow_command.rs`): `::add-mask::`, `::error::`, `::warning::`, `::notice::` (capped at 10 per issue type and 4,096 chars per message, `ExecutionContext.cs:144-146`), `::group::`, `::endgroup::`, `::debug::`, `::stop-commands::<token>::`.
- **Secret masking (`ISecretMasker`):** An Aho-Corasick multi-pattern scrubber initialized with all `Variables` where `is_secret == true`, all `MaskHints` (`Variable` and `Regex`, `MaskHint.cs`), every minted OIDC or App token, and every dynamic `::add-mask::` value (plus URL-encoded, JSON-escaped, and base64-encoded variants of secrets >= 4 chars). Every log line, timeline record, annotation, step summary, and job output passes through the masker **before** leaving the process or hitting disk.

### 3.7 Cancellation, timeouts and lock renewal

- **Lock renewal (`velnor-node` / `velnor-exec`):** A dedicated Tokio task renews the job lease every 60 s (`POST {run_service_url}/renewjob`, `JobDispatcher.cs:775-776`), updating `locked_until` from `RenewJobResponse.lockedUntil`. Unlike `actions/runner`'s buggy renewal overload that dereferences a null request on failure (`JobDispatcher.cs:748-852`, `decisions N10`), our loop retries with 5-15 s jittered backoff until `locked_until + 5 min` (`JobDispatcher.cs:807-840`), stops cleanly on `JobNotFound`, and triggers local cancellation if the lease expires.
- **Cancellation (`JobCancel`) and timeouts:** When `velnor-dispatch` receives `JobCancel{job_id, timeout}` from the broker (`Runner.cs:790-800`) or a step/job `timeout-minutes` timer fires, `velnor-exec` marks the context cancelled, sends `SIGTERM` to the active step's cgroup process tree (`cgroup.kill` / process group signal), waits up to the cancel timeout (default 7.5 s for step cancel, up to 45 s for job shutdown, `JobDispatcher.cs:180,306`), sends `SIGKILL` to any survivor, and still executes `always()` / `cancelled()` steps and post steps before calling `completejob` with `Conclusion::Cancelled` (or `Conclusion::Failure` on timeout).

### 3.8 Logs and timeline via Results service (Twirp)

`velnor-exec` operates in `resultsServiceOnly: true` mode (`JobRunner.cs:85`, `JobServerQueue.cs:115-135`):
1. **Live console feed:** Streams masked log lines in 250 ms batches (first 60 s) then 500 ms batches (cap 1,024 lines/batch, `JobServerQueue.cs:32-33,91-94`) over a `WebSocket` to `SystemVssConnection.Data["FeedStreamUrl"]` wrapped in `TimelineRecordFeedLinesWrapper{stepId, lines, startLine}` (`ResultsServer.cs:224,287`).
2. **Step status updates (Twirp):** Calls `POST {results_endpoint}/twirp/github.actions.results.api.v1.WorkflowStepUpdateService/WorkflowStepsUpdate` every 500 ms on step state transitions (`ResultsHttpClient.cs:610-632`, `JobServerQueue.cs:34`).
3. **Step logs, job logs, and step summaries (Twirp + Blob storage):** For each completed step, calls `twirp/results.services.receiver.Receiver/GetStepLogsSignedBlobURL`, uploads the masked log directly to the signed blob URL (`x-ms-blob-type: BlockBlob` or `AppendBlob` with `x-ms-blob-sealed: true`, 3 retries, 30 s timeout, `ResultsHttpClient.cs:270-361,612-632`), and commits metadata via `CreateStepLogsMetadata`. Step summaries upload via `GetStepSummarySignedBlobURL` + `CreateStepSummaryMetadata`; full job logs upload via `GetJobLogsSignedBlobURL` + `CreateJobLogsMetadata`.
4. **Completion:** Sends `POST {run_service_url}/completejob` with `CompleteJobRequest{plan_id, job_id, conclusion, outputs, step_results, annotations, telemetry, environment_url, billing_owner_id}` (`RunServiceHttpClient.cs:123-160`, `JobRunner.cs:290-357`).

### 3.9 Crash safety

We combine `velnor-new`'s **persist-intent, call, record-outcome** journal rule (`crates/velnor-runner-host/src/journal`, `decisions I010`) with compact lease records (`decisions N10`) and epoch fencing (`decisions N37`):
- Before `acquirejob`, `velnor-dispatch` writes an intent row `(request_id, scale_set_id, target_node, epoch)` to its local Turso WAL journal. After `acquirejob` returns, it persists the sealed lease record `(plan_id, job_id, request_id, run_service_url, results_url, job_token, locked_until, epoch)` before handing off to `velnor-node`.
- Before spawning a sandbox, `velnor-node` journals `(job_id, epoch, sandbox_uid, cgroup_path)`.
- If `velnor-node` restarts, it scans `/sys/fs/cgroup/velnor/*` and pod UIDs (`CleanupProof::covers`, `velnor-runner-core/src/ownership.rs:30`): unknown is never treated as absent. Any orphaned sandbox from a superseded epoch is killed via `cgroup.kill`, its mount namespace unmounted, and its XFS project quota directory deleted by verified UID. For an active job lease whose sandbox died mid-step, `velnor-exec` uses the journaled `(plan_id, job_id, run_service_url, job_token)` to upload a crash diagnostic log and call `completejob` (`Conclusion::Failure`, `InfrastructureFailureCategory`), guaranteeing that no job is ever left hanging for the 90-minute timeout or completed twice.

### 3.10 Starting a job in under 50 milliseconds

Today an on-demand ARC job takes 12-14 s to start step 1, and an idle ARC pod takes 2-3 s [M, v2 §3.4]. Our native runner starts step 1 in **<= 240 ms** from `JobAvailable` (and **< 10 ms** for the work itself when `velnor-hooks` starts `ensure` on the webhook):
1. **Webhook head-start (-8 to -13 s effective start):** `velnor-hooks` receives the `pull_request` (`labeled`/`synchronize`) or `merge_group` webhook 1-2 s after the Git event and starts `ensure(tree, plan)` on `velnor-node` immediately, 7-13 s before GitHub's workflow engine finishes parsing `ci.yml` and emits `JobAvailable`.
2. **Pre-acquired broker sessions (0 ms registration):** `velnor-dispatch` keeps $K$ pre-registered JIT runner identities per scale set with open HTTP/2 + WebSocket broker sessions (`ConnectRunnerLongPollWebSocketAsync`, `BrokerServer.cs:92-190`) and warm TLS connections to `run_service_url` and `results_endpoint`.
3. **Pipelined `acquirejob` + sandbox wake (180 ms network hidden behind 45 ms local prep):** The instant `velnor-dispatch` sees `JobAvailable` (or `RunnerJobRequest`), it simultaneously (a) sends `POST /acquirejob` to GitHub and (b) sends a pre-warmed wake RPC over the persistent intra-site gRPC/Unix stream to the chosen `velnor-node`. While the 180 ms `acquirejob` + first `renewjob` round-trip runs against GitHub, `velnor-node` attaches one of its pre-warmed idle sandboxes (already running in a paused cgroup with `/opt/velnor/store/toolchains` and `/opt/velnor/store/tools` bind-mounted read-only) and clones the warm XFS working tree.
4. **Zero-process in-memory action execution (< 10 ms):** When the job message arrives from `velnor-dispatch`, `velnor-exec` evaluates step 1's expressions in memory (~0.2 ms) and calls `velnor-native-actions` directly as a Rust function call (0 ms process spawn, 0 ms action download, vs 4,400 ms tarball download + 147 ms Node.js startup in the official runner).

## 5. The conformance oracle

Under Owner Decisions 1 and 2, GitHub's official C# runner (`actions/runner` v2.338.0+) never runs in production, not even as a fallback; instead, its latest release runs in an isolated `velnor-lab` pool (`runs-on: [velnor-lab-oracle]`) as the differential conformance oracle.

### 5.1 Differential harness and corpus (`velnor-conformance`)

For every corpus test case, `velnor-conformance` dispatches identical twin jobs from the same commit and event payload: one targeting `runs-on: [velnor-lab-native]` (our Rust stack) and one targeting `runs-on: [velnor-lab-oracle]` (the unmodified official runner container). The corpus comprises three mandatory suites:

1. **Suite A: `velnor-new` full production workflow suite (16 workflows, 94 job shapes):** Every job of `ci.yml`, `velnor-gen`'s `rust-ci.yml` and `release.yml`, `product-release*.yml`, `release-rust-ci-tools.yml`, `freshness.yml`, and `qualification.yml`, replayed across `pull_request` (`labeled`, `unlabeled`, `synchronize`), `merge_group`, `push`, `schedule`, and `workflow_dispatch` events, including both passing commits and 12 planted-fault commits (compile failure, test failure, clippy deny failure, missing test inventory, timeout, mid-step cancellation).Publication jobs point to `tailrocks/velnor-lab` releases and packages.
2. **Suite B: Actions semantics & edge-case suite (1,450 cases):**
   - All 989 `Expressions2` unit and integration cases from `velnor-legacy/crates/velnor-runner/src/expression/tests.rs` plus `actions/runner`'s expression test suite (`NaN`/infinity comparisons, object filtering `.*.name`, `fromJson`/`toJson` round-trips, `hashFiles` with symlinks, hidden files, and match-nothing globs).

### 5.2 Normalization and comparison rules

`velnor-conformance` fetches the completed job record, timeline (`GET /repos/{o}/{r}/actions/runs/{id}/jobs`), step logs, annotations, step summaries, cache entries, artifacts, and attestations from the GitHub API for both runs, normalizes nondeterministic fields, and diffs the canonical JSON and log streams:

- **Stripped / canonicalized fields:** Run IDs, job IDs, step external GUIDs, ISO-8601 timestamps, step durations, runner machine names (`RUNNER_NAME`), workspace/temp prefix paths (`/home/runner/_work` vs `/w`), ephemeral OIDC/runtime/App tokens (replaced by `<MASKED_TOKEN>`), ANSI escape sequences, and the official runner's internal banner lines (`Current runner version`, `Preparing actions for step`, `Download action repository`, Node24 setup lines).
- **Concurrent output ordering:** For `background: true` parallel step groups (`ParallelGroupId`), log lines are grouped by their step/task stream prefix before comparison so scheduling jitter between parallel tasks never hides a real output difference.
- **Exact-match assertions (zero drift allowed):**
  1. Job `status` and `conclusion`, and every step's `number`, `name`, `status`, `outcome`, and `conclusion` (including post-step execution order).
  2. Job `outputs` map and every step's `steps.<id>.outputs` map.
  3. Normalized JSON dumps of `github`, `runner` (after path/name normalization), `job`, `steps`, `needs`, `matrix`, and `env`.
  4. Every check annotation (`annotation_level`, `path`, `start_line`, `end_line`, `title`, `message`).
  5. Step summary Markdown bytes (`GITHUB_STEP_SUMMARY`).
  6. Masking completeness: zero unmasked secret substrings in any log line, annotation, summary, or output (tested with a canary secret corpus).
  7. Side effects: identical Git tree hash + file modes after `actions/checkout`, identical archive file list and SHA-256 digests after `upload-artifact`/`download-artifact`, identical cache key and hit/miss outcome for `actions/cache`, and valid `gh attestation verify` pass for `attest-build-provenance`.

Any difference not covered by an explicit, owner-signed, expiring entry in `.velnor/conformance-allowlist.toml` fails the harness.

### 5.3 Catching upstream releases and GitHub protocol drift within hours

1. **Automated upstream release watcher (every 1 hour):** A scheduled controller loop in `velnor-conformance` polls `GET /repos/actions/runner/releases/latest` and `GET /repos/tailrocks/velnor-lab/actions/runners/downloads` (which exposes `registration_deprecates_at` and `runtime_deprecates_at`, `evidence §F.6.1`). Within **1 hour** of a new `actions/runner` release (far inside GitHub's 63-day deprecation window), `velnor-conformance` builds the new oracle image, runs Suites A, B, and C against it, and opens a P0 alert issue if any case diverges.
2. **Continuous protocol canary (every 10 minutes):** Every 10 minutes, `velnor-conformance` dispatches a lightweight 15-second canary job in `velnor-lab` exercising broker long-poll, `acquirejob`, `renewjob`, `Expressions2`, `checkout`, `cache/restore`, `upload-artifact`, Results Twirp log/summary upload, and `completejob` on both Velnor and the oracle runner. If GitHub changes a server-side Twirp or Run Service wire field without cutting a runner release, the canary detects the mismatch within **10 minutes** (0.17 hours), long before any developer PR is affected.

### 5.4 Cutover pass criteria

We delete ARC's `velnor-new` scale sets and cut production over to `velnor-dispatch` + `velnor-exec` only when all five gates pass:
1. **100% conformance pass** across Suites A, B, and C against the latest official `actions/runner` release on two consecutive nightly runs, plus **10 of 10 planted-fault injection tests** caught (planted unmasked secret, wrong step output, skipped post-step, wrong `cancelled()` evaluation, dropped annotation, truncated log, lease-loss mid-job, crash before/after `completejob`, unknown action SHA, forged test report).
2. **Shadow twin run in production (2 weeks and >= 300 merged PRs):** Every `velnor-new` job runs a non-blocking shadow twin on Velnor (`publication` disabled) alongside ARC. Every verdict difference must be root-caused and either fixed + replayed green or proven by 5x paired reruns to be a test flake on both executors (`0` unexplained verdict divergences).
3. **Latency gate:** Job start (`JobAvailable` to step 1 executing) is **<= 0.5 s P50 and <= 1.5 s P90** (vs 2-14 s on ARC), and Velnor's P90 job duration is no slower than ARC in any job class.
4. **HA and fault injection:** k3s control-plane quorum (3 server nodes across DE and FI, fixing the single `velnor-237` SPOF [M, evidence §B.0]), site loss, node crash at every journal boundary, and a 60-second rollback drill to the previous released Velnor binary all pass.

### 6.2 Breaking the 125-138 s single-test floor (to <= 15 s committed, <= 8 s stretch)

No amount of test sharding can speed up a single test function that runs for 274 s or 924.8 s. We attack the five measured root causes in the test suites (`decisions S8, I061, I062, F-H33`):

1. **Pre-migrated Turso SQLite journal template (`Journal::open` from ~1.3 s x 93 call sites to <= 10 ms):** In `velnor-runner-host`, 93 test call sites invoke `Journal::open`, which executes ~35 schema migrations (`crates/velnor-runner-host/src/journal/schema/*`, up to v47 [M, evidence §D.4.3]) on an empty Turso database on every test. We build the migrated v47 database file once per test binary invocation in a `LazyLock` temp file (verified by a dedicated `journal_migrations_from_scratch` test that still tests full migration) and clone the 256 KB template file via `cp --reflink=always` into each test's private temp directory in **< 2 ms**.
2. **Valid-prefix cloning for multi-stage state tests (`924.8 s` receipt-integrity test -> <= 12 s):** The 924.8 s receipt-integrity test (`F-H33`) and the 125-138 s `velnor-runner-host` / `local-mode` / `velnor-actions-cli` tests construct identical multi-step valid state prefixes four to ten times per test before asserting different corruption or reopen mutations. We compute each expensive valid prefix once with the real production code in a test-suite fixture, close the journal/directory cleanly, and reflink-clone that directory into each mutation test case's private temp dir, preserving 100% of the real code execution and corruption assertions while running the cases in parallel across 16 threads.
3. **Unrolling the 40-case and 6-case serial test loops:** `crates/velnor-actions-cli/tests/image_publication_public.rs:85-92` loops serially over 40 cases in one `#[test]` (258-274 s [M, decisions S8]), and `unbound_retirement/tests/shape.rs:97-106` loops over 6 cases (203-271 s [M]). Splitting each iteration into its own `#[test]` case lets `cargo-nextest` schedule all 46 cases in parallel across the sandbox's 16 threads, dropping their wall time from **274 s to ~18 s** [E: 274 s / 16 threads = 17.1 s].
4. **Eliminating artificial serialization in `ci-helper` and `archive-guard`:**
   - `.config/nextest.toml` sets `test-threads = 1` because `crates_mirror` tests bind fixed local state, and sets a 2 s `slow-timeout` kill in `[profile.default]` (`decisions S8, F-H36`). We give each `crates_mirror` test an OS-assigned ephemeral port (`127.0.0.1:0`) and private `tempdir`, set `test-threads = "num-cpus"`, and explicitly pass `--profile ci` in all generated workflows (`N44`), cutting `velnor-ci`'s 781 tests from 10-62 s to **2.5 s** [E].
   - In `.config/nextest.toml:17-19`, 12 `velnor-archive-guard` golden tests demand `threads-required = "num-test-threads"` (serializing the entire runner). Giving each golden test a private scratch directory removes `threads-required` and runs all 12 in parallel in **3 s** instead of 45 s.
5. **Splitting `velnor-runner-host` (156,822 LOC) into 6 domain crates + `velnor-runner-local`:** Extracting `velnor-runner-journal`, `velnor-runner-docker`, `velnor-runner-reconcile`, `velnor-runner-launch`, `velnor-runner-host`, and `velnor-runner-local` (`decisions I063, I073`) stops compiling 157k lines twice for default vs `local-mode` and cuts a single-file edit compile from 61 s to **10-15 s** [E].
6. **Hard per-test budget gate (`I065`):** Enforced in CI: no individual test may exceed **10 CPU-seconds** measured alone (and no suite critical path may exceed **60 s** in Phase 2, **15 s** stretch).

### 6.3 Test-level scheduling across the cluster (480 threads)

- **Phase 2-3 (Single-sandbox 16-thread scheduling with shared jobserver):** Within a node, each root's `ensure` obligation builds test executables once per configuration (`cargo nextest list --list-type binaries-only`, `cargo build --all-targets`), then runs `fmt`, `clippy`, `doc`, `check-alone`, and `nextest` concurrently across their dedicated target lanes (`target/velnor-clippy`, `target/velnor-doc`, `target/debug`) under a single POSIX pipe jobserver (`--jobserver-fds`, `N45`) sized to the sandbox's 16 CPUs. Changed test obligations execute **3 times in parallel** (`N20`) to match or exceed today's 3-run flake detection.
- **Phase 4 (Site-wide test-case fan-out across 288 FI / 192 DE threads, `N04`):** When a PR touches a broad closure whose summed test CPU-seconds divided by 16 threads exceeds `max(longest_single_test) + 1.5 s`, `velnor-exec` publishes the newly built test binaries (typically 2-6 binaries, 40-180 MB zstd-compressed, not the entire 1.48 GB workspace archive!) into the site's `velnor-store` (`L2`). Idle sandboxes on the other 2-3 workers in the same site pull only those changed test executables by SHA-256 digest over the same-site LAN in **0.4-1.2 s** and run disjoint LPT (Longest-Processing-Time-first) partitions of the test list from `.velnor/rust-ci-timings.json`. `velnor-ledger` verifies that the union of reported test case inventories across the shards equals 100% of the binary's `nextest list` inventory (`C4`).

## 7. Scheduling and the cluster

### 7.1 Fleet topology, both sites, and zero cross-site synchronous I/O

The cluster consists of five 96-thread AMD EPYC 9454/9454P worker nodes (480 worker threads, ~627.5 GiB worker RAM total) across two Hetzner sites separated by a 35 ms WireGuard mesh (`evidence §B.0, §B.5`):
- **Germany (DE, 192 worker threads + 20 control-plane threads):** `velnor-240` (96 threads, 125.5 GiB RAM, 2 x 3.84 TB NVMe + 3 x 15 TB), `velnor-105` (96 threads, 125.5 GiB RAM, 2 x 3.84 TB NVMe + 2 x 15 TB), and `velnor-237` (i5-13500, 20 threads, 62.6 GiB RAM, control plane).
- **Finland (FI, 288 worker threads):** `velnor-241`, `velnor-5`, and `velnor-190` (each 96 threads, 125.5 GiB RAM, 2 x 3.84 TB NVMe, with a 3.7 TB linear XFS logical volume at `/var/lib/rancher` and ext4 on the OS disk [M, `mbx-cache-cluster.md` Setup, decisions S10]).
- **Control-plane HA before cutover (`I093`):** Today `velnor-237` is a single k3s server SPOF. Before executor cutover, we promote one worker in DE (`velnor-240`) and one in FI (`velnor-241`) to embedded-etcd k3s server quorum (3 servers across 2 sites, reserving 2 CPU / 4 GiB for etcd/apiserver), while each site's `velnor-dispatch`, `velnor-hooks`, `velnor-ledger`, `velnor-store`, and `mbx-cache` operate autonomously within their site so a DE-FI link partition or single-site outage never stops the surviving site from verifying and merging PRs.
- **Strict site stickiness (`I090`):** Every `ensure(tree, plan)` request and its associated `Required` job stay within a single site (FI carries ~60% of requests with 288 threads; DE carries ~40% with 192 threads). Nothing on the synchronous verification path crosses the 35 ms DE-FI link; `velnor-ledger` receipts (a few kilobytes of signed JSON) replicate asynchronously across sites in <100 ms.

### 7.2 Placement, zero queue wait, and zero cold start

1. **Every worker node is warm for `main` (`I030`, `I044`):** When `main` advances, one batch-priority `main` builder per site compiles the delta over the previous generation (or promotes the `merge_group` delta directly on the site that ran it) and publishes to the site's `mbx-cache` / `velnor-store`. Every worker node's `velnor-node` daemon pulls the changed files into its local XFS `/opt/velnor/store/snapshots/main-<gen>` snapshot within 5-15 s of the merge. Thus, all 5 workers are warm for `main` 100% of the time.
2. **Pre-acquisition placement (`I003`, `I042`):** Because `velnor-dispatch` owns all scale-set sessions and pre-registered JIT runner identities, it chooses the worker node *before* calling `acquirejob`:
   $$\text{Score}(\text{node}) = T_{\text{eligible\_wait}}(\text{node}) + T_{\text{view\_setup}} + T_{\text{predicted\_delta\_build}}(\text{node}, K_{\text{pkg}}) + T_{\text{predicted\_tests}} + P_{\text{cross\_site}}$$
   An idle worker with the previous `main` snapshot always beats a queued worker, and repeated pushes to the same PR prefer the worker in that site that already holds the PR's recent page cache.
3. **Zero queue wait for the merge path (`N38`):** By Little's Law / $M/G/1$ queueing ($\text{wait} \propto \rho / (1 - \rho)$), unreserved pools at 95% utilization suffer 19x service-time queue waits. We reserve **one 16-CPU build slot and 2 gate CPUs per site** (36 of 480 threads = **7.5% of cluster CPU**) exclusively for `merge_group` and `Required` gate jobs, and make all batch work (`velnor-batch`: `main` builder, queue-tip speculation, 24 h cold audits, 2% sampled re-executions) instantaneously preemptible via `cgroup.freeze` / low CPU weight (`cpu.weight = 10` vs `1000` for foreground CI). Eligible-to-start wait for `merge_group` and gate work is **<= 0.5 s P50, <= 2.0 s P90** [T].
4. **Zero cold start (`I081`, `I082`):** `velnor-node` maintains 2 pre-created, single-use sandboxes per worker node (~90 MiB idle RAM total [M, evidence §B.2.2]), already initialized with read-only bind mounts of `/opt/velnor/store/{toolchains,tools,cargo-home}` and an empty XFS project-quota work directory `/w/velnor-new`. Attaching an incoming obligation to a pre-warmed sandbox and reflink-cloning the warm snapshot takes **0.25 s** (`mbx-cache-cluster.md` P2).

### 7.3 Using all 480 threads without thrashing

Today, pods request 2 CPU and 4 GiB RAM with no CPU limit and burst to 83.7 cores (`evidence §B.2.2`), causing 2.4x duration stretch under load (`velnor-runner-host` 3.7 min -> 8.8 min on 11-18, `evidence §A T6`). We enforce honest sizing (`I087`, `F-H29`) with work-conserving CPU bursting:
- **Per-worker memory budget (125.5 GiB RAM):** 6.0 GiB kubelet/system reservation + 2.0 GiB hard eviction margin + 8.0 GiB for 4 gate sandboxes (2 GiB each) leaves **109.5 GiB** per worker. Four concurrent build sandboxes at **24 GiB RAM limit each** (96 GiB total; peak observed job RSS is 16.8 GiB [M, evidence §B.2.2]) fit cleanly with 13.5 GiB headroom.
- **Per-worker CPU allocation (96 hardware threads) and elastic jobserver:**
  - Kubelet/system/node-agent reserve 4 threads; gate sandboxes reserve 4 threads; the 4 build slots each get a guaranteed **22-CPU share** (`cpu.weight = 1000`, no hard `cpu.max` throttle when sibling slots are idle!).
  - Inside each sandbox, `velnor-node` sets `CARGO_BUILD_JOBS` and `NEXTEST_TEST_THREADS` (and the shared POSIX jobserver token count across parallel `clippy`/`doc`/`test` lanes, `N45`) dynamically: **22 tokens** when all 4 slots on the node are active, scaling up to **44 tokens** when 2 slots are active, and **64 tokens** when 1 slot is active (or during a cold/lockfile build).
  - For wide PRs or full audits (Phase 4 `N04`), `velnor-ledger` fans out independent package obligations and LPT-partitioned nextest shards across all 3 workers in FI (288 threads) or both workers in DE (192 threads) simultaneously.

### 7.4 Simplified isolation for trusted authors with buggy code (Owner Decision 8)

Under Owner Decision 8, **no pull requests come from forks** (all fork handling, fork-conditional `runs-on`, and hostile-outsider microVM fork pools are dropped). We design isolation for **trusted internal developers and agents whose code or tests may be buggy** (runaway processes, accidental writes outside the workspace, port collisions, undeclared file reads, or flaky network calls), while strictly enforcing the **correctness invariant** that PR runs never pollute `main` caches or receipts:

1. **Hermetic Linux namespace sandbox per obligation (`velnor-node`):**
   - **Mount namespace (`CLONE_NEWNS`):** Root filesystem is read-only; `/opt/velnor/store/{toolchains,tools,cargo-home}` are read-only bind mounts; `/w/velnor-new` is a private XFS project-quota directory containing *only* the sparse checkout of the obligation's declared `K_pkg` inputs plus a private reflink/hardlink view of the warm `target/` snapshot (`0444` on hard-linked immutable `deps/` files so a buggy build/test cannot mutate shared dependency inodes). No `.git` directory is mounted in build or test sandboxes (`C5`, `N26`).
   - **Network namespace (`CLONE_NEWNET`, `N47`):** Test obligations run in an isolated network namespace with **only `lo` (`127.0.0.1 / ::1`) enabled**. This structurally prevents tests from making accidental live network calls (`C5`) and eliminates port collisions between concurrent test sandboxes on the same worker! Build obligations that need `cargo fetch` on a changed `Cargo.lock` run in a pre-build fetch step whose netns allows egress only to `crates-mirror.velnor-system.svc.cluster.local`.
   - **PID, IPC, UTS, and cgroupv2 namespaces (`CLONE_NEWPID | CLONE_NEWIPC | CLONE_NEWUTS | CLONE_NEWCGROUP`):** `pids.max = 16384`, `memory.max = 24G`. When an obligation finishes or is cancelled, `velnor-node` writes `1` to `cgroup.kill`, waits for `cgroup.events` `populated 0`, and deletes the sandbox's XFS directory, ensuring zero leaked background daemons.
   - **Scrubbed environment and credential boundary (`C4`, `N30`):** Runner registration tokens stay in `velnor-dispatch`; Ed25519 receipt-signing keys live in the root-owned `velnor-ledger-signer` daemon outside all sandboxes. Sandboxes never receive `ACTIONS_RUNTIME_TOKEN`, `GITHUB_TOKEN`, or signing keys unless the step explicitly requires `GITHUB_TOKEN` (e.g., `release-gate`), which is marked `C5` (non-reusable).
2. **Docker obligations without per-pod DinD tax (`I084`, `N51`):** Only 3 test binaries in the entire repository need a Docker daemon (`local_pair_public`, `local_host_public`, and `velnor-local`'s Docker tests). They are scheduled as dedicated `docker`-class obligations that receive the already-compiled test executables from the `build` obligation in <1 s and run against an isolated rootless Docker/containerd sidecar on one designated worker per site, eliminating the 57 DinD readiness probe failures/hour (`evidence §B.6`) and 4 s startup tax from all other builds.
3. **Structural separation of PR vs `main` caches (`I048`):** PR sandboxes have zero write access to `/opt/velnor/store/snapshots` or `mbx-cache`. Only the per-site `main` builder writes to `/opt/velnor/store/snapshots/main-<gen>` and `mbx-cache`, and only `main` commits promote receipts to the `trusted` scope.

## 8. The merge queue and GitHub integration

### 8.1 On-demand CI via the owner's binding `velnor:verify` label flow (Owner Decision 12)

Because agents push many intermediate commits and 45% of all PR runs (1,156 of 2,558 [M, evidence §A T1]) were cancelled, **a push to a PR never starts heavy verification unless the `velnor:verify` label is present**. At the same time, **a PR can never be merged or enter the merge queue unless its latest `head_sha` has a passing `Required` check**, and Velnor never reports success for an unverified commit.

#### Why a naive job-level `if:` on `Required` is broken on GitHub Actions
In GitHub Actions, if a workflow triggers on `pull_request` and the required job (`Required`) is skipped by a job-level conditional (`if: contains(github.event.pull_request.labels.*.name, 'velnor:verify')`), GitHub creates a Check Run named `Required` with `conclusion: "skipped"`. **Per GitHub Docs ("Troubleshooting required status checks / Handling skipped but required checks"), GitHub rulesets treat a `skipped` job in a triggered workflow as passing `required_status_checks`!** If `synchronize` or `unlabeled` triggered the workflow on an unlabelled PR and skipped `Required`, the unlabelled PR would receive a green/passing required status check and could merge unverified.

#### Our exact trigger surface and state machine
We update `velnor-gen` (`crates/velnor-render/src/events.rs:31-48`) to emit:

```yaml
on:
  pull_request:
    types:
      - labeled
      - unlabeled
      - synchronize
  merge_group: {}
  push:
    branches:
      - main
  schedule:
    - cron: '15 8 * * *'
  workflow_dispatch: {}

concurrency:
  group: ci-${{ github.workflow_ref }}-${{ github.event_name == 'pull_request' && github.event.pull_request.number || github.run_id }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}

jobs:
  required:
    name: Required
    runs-on: ${{ github.event_name == 'merge_group' && 'velnor-merge' || 'velnor-gate' }}
    timeout-minutes: 30
    permissions:
      contents: read
    steps:
      - name: Verify label gate and ensure obligation graph
        env:
          EVENT_NAME: ${{ github.event_name }}
          PR_LABELS_JSON: ${{ toJSON(github.event.pull_request.labels.*.name) }}
          HEAD_SHA: ${{ github.sha }}
        run: velnor-ci ensure --require-pr-label velnor:verify
  cache:
    name: Cache
    needs: [required]
    if: always() && (github.event_name != 'pull_request' || contains(github.event.pull_request.labels.*.name, 'velnor:verify'))
    runs-on: velnor-gate
    timeout-minutes: 5
    permissions:
      contents: read
    steps:
      - name: Report compile and receipt cache audit
        run: velnor-ci cache-audit --head-sha "${{ github.sha }}"
```

Notice that `opened`, `ready_for_review`, `reopened`, and `edited` are **removed** from `on.pull_request.types`. Here is how each of the owner's five binding rules executes:

|---|---|---|---|---|

#### Webhook delivery vs `GITHUB_TOKEN` trigger suppression (citations and fallback)
- **GitHub platform rule (citation):** Per GitHub Docs (*"Triggering a workflow / Using `GITHUB_TOKEN` in a workflow"* and *"Events that trigger workflows: `pull_request`"*), any event performed using a workflow's automatic `GITHUB_TOKEN` (other than `workflow_dispatch` and `repository_dispatch`) **will not trigger a new GitHub Actions workflow run**. Conversely, events performed by a **human user in the GitHub UI**, by the **`gh` CLI / REST API authenticated with a user PAT / OAuth token**, or by a **GitHub App installation access token** (`POST /repos/{owner}/{repo}/issues/{issue_number}/labels`) **do trigger `on: pull_request: types: [labeled, unlabeled]` workflow runs**.
- **App webhook delivery difference (citation):** Per GitHub Docs (*"Webhooks / Webhook events and payloads: `pull_request`"*), GitHub's anti-loop suppression applies only to GitHub Actions workflow-run creation, **not** to GitHub App webhook deliveries. `velnor-hooks` receives the signed `pull_request` (`action: "labeled"` / `"unlabeled"` / `"synchronize"`) HTTP POST webhook from the Velnor GitHub App within 1-2 s regardless of which token applied the label.
- **Two-layer fallback so a label event never fails to produce a `Required` check:**
  1. **Agent / CLI convention:** Agents add `velnor:verify` via `gh pr edit <N> --add-label velnor:verify` using their user/agent credentials (or `velnor verify --label`, which uses the Velnor App installation token), never a workflow's `GITHUB_TOKEN`.
  2. **`velnor-hooks` 10-second run-creation watchdog (automatic fallback):** Whenever `velnor-hooks` receives a `pull_request` webhook (`labeled` with `velnor:verify`, or `synchronize` with `velnor:verify` present), it starts `ensure(tree, plan)` immediately and schedules a 10-second timer checking `GET /repos/tailrocks/velnor-new/actions/workflows/ci.yml/runs?head_sha={head_sha}`. If GitHub Actions did not create a `pull_request` workflow run for `head_sha` within 10 s (for instance, if a tool added the label with a suppressed token or GitHub dropped the Actions trigger), `velnor-hooks` uses the Velnor GitHub App installation token to remove and re-add `velnor:verify` (`DELETE` then `POST /repos/tailrocks/velnor-new/issues/{pr}/labels`), which forces GitHub Actions to spawn the `pull_request` (`labeled`) workflow run on `head_sha` so the `Required` check run (integration `15368`) is created and joins the already-running `ensure` obligations!

#### Exact repository ruleset settings (`protect-main`, ruleset `24396608`)
To enforce that **both** the PR's latest `head_sha` and the `merge_group`'s combined tree must pass `Required`:
- `target`: `"branch"`, `enforcement`: `"active"`, `conditions.ref_name.include`: `["~DEFAULT_BRANCH"]` (`refs/heads/main`).
- `rules`:
  1. `pull_request`: `required_approving_review_count: 0`, `dismiss_stale_reviews_on_push: true`, `required_review_thread_resolution: true`, `allowed_merge_methods: ["squash"]`.
  2. `required_status_checks`:
     - `strict_required_status_checks_policy: false` (PRs do not run catch-up merges against `main`; the merge queue verifies `main + PR`).
     - `do_not_enforce_on_create: false`.
     - `required_status_checks`: `[{ "context": "Required", "integration_id": 15368 }]` (bound to GitHub Actions app ID `15368` so no rogue token with `statuses: write` can spoof it, `decisions N12`; during Phase 0-1 before the `velnor-gen` cutover, includes `{"context": "Required verdict", "integration_id": 15368}`).
     - **How GitHub enforces this on both PR and `merge_group`:** GitHub's merge queue refuses to enqueue any PR unless every check in `required_status_checks` is green (`success`) on the PR's current `head_sha`. Once enqueued, GitHub creates the `merge_group` commit (`main` or queue tip $\oplus$ PR) and requires the exact same `required_status_checks` (`Required`, integration `15368`) to report `success` on `merge_group.head_sha` before fast-forwarding `main`.
  3. `merge_queue`: `merge_method: "SQUASH"`, `grouping_strategy: "ALLGREEN"` in Phase 3 once queue-tip speculation is active (`"HEADGREEN"` in Phases 0-2 with intermediate commits logged for release/bisection, `N28`), `max_entries_to_build: 4` (Phase 2, `8` in Phase 3 with bypass speculation; `2` in Phase 0-1, `I075`), `min_entries_to_merge: 1`, `max_entries_to_merge: 10`, `min_entries_to_merge_wait_minutes: 5` (no-op when `min_entries_to_merge == 1` [M, `I076`]), `check_response_timeout_minutes: 20`.

### 8.2 Zero duplicate verification across PR, `merge_group`, and `main`, plus queue-tip speculation

1. **PR -> `merge_group` reuse (`I055`, `N01`):** A `merge_group` run always evaluates the full repository obligation inventory (`docs/hard-decisions.md` §3). Because obligations are keyed by their per-package input closure `K_pkg` (Section 6.4):
   - Every package untouched by the PR and untouched by concurrent merges since the PR's base has `main`'s key and hits `main`'s `trusted` receipts in **0 ms**.
   - Every package touched by the PR has the exact same `K_pkg` in `merge_group` as in the PR run unless another PR that modified a package in the same dependency closure merged to `main` during the window between the PR run and `merge_group`. With PR verdicts under 45-90 s and auto-merge enabled, 78-89% of merge groups have zero overlapping changes and finish in **1.0 s** by pure receipt lookup [E, window model `N34`].
2. **Speculation on the queue tip (`N19`):** Because 122 of 193 measured `merge_group` runs were built on an unlanded queue predecessor rather than `main` [M, decisions F-H04], `velnor-ledger` subscribes to PR enqueue events and speculatively computes the ordered prefix merge trees $T_1 = \text{main} \oplus \text{PR}_1$, $T_2 = T_1 \oplus \text{PR}_2$, ..., $T_k = T_{k-1} \oplus \text{PR}_k$ plus the single-ejection bypass trees $T_k^{(-j)}$ (7 trees for 4 queued PRs) via `git merge-tree` in the node mirror. Any obligation in $T_i$ whose `K_pkg` does not yet have a receipt is scheduled at preemptible `velnor-batch` priority. When GitHub creates the `merge_group` run, its receipts are already waiting in `velnor-ledger`.
3. **`merge_group` -> `push` to `main` reuse and `Required` / release-gate compatibility (`I053`, `F-H20`):**
   - `velnor-ci release-gate` (`crates/velnor-ci/src/gate.rs:15,127-159,277-288`) and `product-release.yml:86` require a completed `push` workflow run of `.github/workflows/ci.yml` on `main` at the exact `source_sha` containing **one job named `Required` executed by GitHub Actions (`integration_id = 15368`)** with `conclusion == "success"`.
   - When the merge queue fast-forwards `main` to `merge_group.head_sha`, the `push` workflow runs a single job named `Required` on Velnor. Its `ensure` call finds 100% of `main`'s obligation keys already receipted from `merge_group`, verifies every Ed25519 signature and test inventory, promotes the receipts (and `ReleaseArtifactReceipt` tarballs) to `trusted` scope in **50 ms**, and completes the `Required` job in **1.2 s** with zero compilation or test execution.

### 8.3 Auto-merge, agent workflow, and eliminating the cancelled-run stall

- **Agent behavior (`I077`, `I078`):** Agents push intermediate commits without `velnor:verify` (costing 0 CI resources), never merge `main` into PR branches (`strict_required_status_checks_policy: false`), and when ready to land, add `velnor:verify` and enable `gh pr merge --auto --squash` in one command. Once `Required` turns green on the latest head, GitHub enqueues the PR in **~2 s** (eliminating today's 7.5 min P50 / 88 min P90 manual enqueue delay [M, decisions S2]).
- **Eliminating the cancelled-run stall (`N33`, `F-H06`):** Today, 33 of 105 sampled PR runs waited 60 s P50 / 626 s P90 (up to 2,203 s) for a superseded run to finish cancelling because the old run's `Required` job had `if: always()` and queued behind hosted runners before exiting. ## 9. What would make CI not a bottleneck at all

To make CI/CD stop being a bottleneck in absolute terms, **waiting for CI after a developer or agent finishes a change must approach the physical floor of GitHub's control-plane state transitions plus incremental LLVM/rustc codegen on the changed AST nodes**.

### 9.2 The architecture that reaches the theoretical floor

Four design elements close the gap between Phase 3 (45 s verdict / 110 s push-to-merge) and the absolute physical floor (8.5-15 s verdict / 55 s merge-queue or 12 s merge-train):
1. **Cluster-resident agent sandboxes (`N08`) + `velnor verify` (`N07`):** Agents run their edit-compile-test loop on the cluster (or invoke `velnor verify` as the final step of their local commit hook before pushing and adding `velnor:verify`). Because `velnor verify` executes inside Velnor's sealed Linux sandbox against the node's warm XFS snapshot, the obligation receipts already exist in `velnor-ledger` before `git push` completes. When the PR is labelled `velnor:verify`, compute time is **0.00 s**; the verdict waits only for GitHub to emit `JobAvailable` (8-15 s) and completes `Required` in 350 ms.
2. **Continuous queue-tip + in-flight PR speculation (`N19`):** Whenever a labelled PR passes `Required`, `velnor-ledger` immediately merges its tree onto the current merge-queue tip $T_k$ and verifies any package whose key differs at batch priority before GitHub's 19-second `merge_group` creation timer even finishes. Thus `merge_group` is a 100% receipt lookup in >95% of merges.
3. **Warm `CARGO_INCREMENTAL=1` leaf-codegen snapshots + split crates < 25k LOC (`I073`):** Splitting `velnor-runner-host` (157k LOC) and `velnor-actions-orchestrator` (187k LOC) into focused crates under 25k LOC and keeping per-crate incremental CGU caches in the warm XFS snapshot (safe under input-addressed `K_pkg` keys because `K_pkg` hashes inputs, not bit-identical outputs, and is audited nightly by `C6` cold differential builds) drops single-file delta compiles from 15-22 s to **1.5-3.5 s** [M, `blaze.md` B3].
4. **Optional Velnor CAS Merge Train (`N31`):** Once `velnor-ledger` has verified the exact merged tree $T_k = \text{main} \oplus \text{PR}$ and reported `Required` green on the PR head, 45 s of the remaining 55 s push-to-merge floor is pure GitHub Merge Queue orchestration wait (`19 s` to start `merge_group` + `26 s` to merge). If the owner enables the Velnor Merge Train in Phase 4, Velnor creates the squash commit with the exact verified tree $T_k$, runs the 1.2 s receipt-backed `Required` check, and fast-forwards `refs/heads/main` via atomic compare-and-swap (`PATCH /repos/{o}/{r}/git/refs/heads/main`), dropping push-to-merge to **10-16.5 s**.
