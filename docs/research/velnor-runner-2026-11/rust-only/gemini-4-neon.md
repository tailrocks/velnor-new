# Velnor Rust-Only Runner & Verification Architecture

## 1. Summary

Velnor replaces GitHub's official C# runner, ARC, Node/JS actions, and all GitHub-hosted jobs with a **100% native Rust verification and execution plane** on the 5-worker (480-thread) Hetzner cluster, keeping GitHub only as source control, ruleset/merge-queue authority, and latest-API protocol surface (`scaleset`, V2 broker, RunService, Results Twirp+WS, Cache v2, Artifacts v4, OIDC). Official `actions/runner` runs solely as a lab conformance oracle. Every PR runs **on demand** via the owner's `velnor:verify` label flow (zero compute on drafts, unlabelled pushes, or ready-for-review; `Required` stays Expected/blocking until verified), eliminating the 45% cancelled-run waste and the 2,203 s concurrency stall. A native Rust node agent (`velnor-node`) starts isolated Linux namespace + cgroup v2 + overlayfs/XFS-reflink sandboxes in **<15 ms** (0 idle RAM), serves warm `main` snapshots + `velnor-actions` natively from node-local NVMe mirrors/stores, and uses `mbx-cache` strictly as a threshold-gated cross-node fill layer (`blaze` is rejected on measured failures and false-green lints). Input-addressed verification receipts (`velnor-ledger`) make **build once, verify once, reuse everywhere** structural across pushes, concurrent/stacked PRs, agent pre-push runs, merge groups, `main`, and zero-rebuild release promotion, backed by 3× parallel execution of changed obligations, 100% cold 24 h audits of landed commits, and automatic epoch revocation (zero tolerance for false greens).

### Resolving the debug-vs-release profile tension (with numbers)

`ci-helper/Cargo.toml:13-17` and `generator/Cargo.toml:35-39` ship `--release` with `opt-level = "s"`, `lto = "thin"`, `strip = true`, `panic = "abort"`, while root/runner CI tests run `dev`/`test` (`opt-level = 0`, `panic = "unwind"`, `debug_assertions = true`, `overflow_checks = true`, `turso_core` at `opt-level = 1`, `sha2` at `opt-level = 3`). Three options exist:
1. *Test only `--release` on PRs:* **Rejected.** `panic = "abort"` breaks unwind tests (`#[should_panic]`), stripping `debug_assertions` and `overflow_checks` violates same-confidence (turning assertion failures into false greens), and thin-LTO adds **+25–45 s** on `generator`/`ci-helper` and **+70–110 s** on `velnor-actions`/`velnor-runner` to every PR compile [E].
2. *Build `--release` only when a release tag is cut:* **Rejected.** Rebuilds from cold on every release (15–45 min), duplicates `source-preview`/`job-image-candidate`/`product-release`, and violates Binding Decision 10 ("a release promotes the exact artifacts `main` built and verified; it never rebuilds them").
3. **Chosen design — Split verification profile (`ci-test`) + asynchronous content-addressed `main` release build & zero-rebuild promotion:**
   - **Critical path (PR / MG):** `ci-test` profile keeps workspace `opt-level = 0`, `debug_assertions = true`, `overflow_checks = true`, `panic = "unwind"`, `debug = "line-tables-only"`, and builds third-party dependencies at `opt-level = 3, debug = "none"` (validated in Phase 1 against `debug-assertions` on deps; cuts `Journal::open` test CPU by **~66%** [M, `I064`] and shrinks `target/` by **24%** [M, `I108`], compiled **once per `Cargo.lock`** in the warm snapshot).
   - **Off critical path (`push: main` post-merge):** The site's trusted `main` builder computes `K_rel(pkg, target, profile_digest, closure_tree_hash, rustc_digest)` for each releasable binary (`velnor-ci`, `velnor-gen`, `velnor-actions`, `velnor-resource-probe`, Velnor runner daemons) and OCI image. Only when `K_rel` misses `velnor-store` (typically 1 package, ~15–45 s on 32 cores) does it compile `--release` (native `x86_64-unknown-linux-musl` + cross `aarch64-unknown-linux-musl` via zig/musl-cross), run the **release-binary verification suite** (smoke + golden + `check-tag` against the exact stripped binary), pack deterministic `<bin>-<target>.tar.gz` + `SHA256SUMS`, and store them immutably under `K_rel` with a signed receipt.
   - **Release cut (`release-plz` / `product-release`):** **0 s compile.** Verifies `release-gate`, fetches the exact `K_rel` tarballs + `SHA256SUMS` from `velnor-store`, checks SHA-256 against the signed `main` receipt, attests via native OIDC/Sigstore, and publishes. (If `release-plz` bumped `Cargo.toml` in a release PR, `K_rel` was built once when that release PR merged to `main`, and the immediately following tag promotes it in **<15 s** with zero compilation!)

### 3.3 Job-message model, expressions, steps, contexts, masking, cancellation, crash safety

- **Job-message model** (`actions-runner/src/Sdk/DTPipelines/Pipelines/AgentJobRequestMessage.cs:16-300`): Deserializes `Plan`, `Timeline`, `JobId`, `JobDisplayName`, `JobName`, `EnvironmentVariables` (ordered `TemplateToken` overlay, last wins), case-insensitive `Variables`, `MaskHints`, `Resources.Endpoints`, `ContextData`, `Workspace`, `Steps` (`JobStep` / `ActionStep` including `Background` and `ParallelGroupId`), `FileTable`, `JobOutputs`, `Defaults`, `ActionsEnvironment`. **Pre-step admission gate:** Before creating step 1's timeline record, `velnor-exec` recursively walks `Steps` (and any local composite actions after checkout) and **refuses the job immediately** if any `ActionStep.Reference` is outside the qualified closed action set + pinned SHAs.
- **Expression engine** (`velnor-expr`, ref `DTExpressions2/Expressions2/ExpressionConstants.cs:8-61`): Single engine (`Expressions2`, `MaxDepth = 50`, `MaxLength = 21000`, `NumberFormat = "G15"`), short-circuit `&&`/`||` returning operand values, `*` wildcard projection, `case`, `contains`, `endsWith`, `format`, `join`, `startsWith`, `toJson`, `fromJson`, plus `always()`, `cancelled()`, `failure()`, `success()`, `hashFiles(...)` (`StepsRunner.cs:93-97`).
- **Step, composite, and post-step semantics** (`JobExtension.cs:63-739`, `StepsRunner.cs:39-288`, `ActionRunner.cs:66-285`, `CompositeActionHandler.cs:32-300`):
  - `"Set up job"` → Pre steps FIFO (sharing `IntraActionState[step.Id]` with Main) → Main steps FIFO (supporting native `background: true` members joined by `wait-all`, plus auto-wait of any unwaited background steps before Post, `StepsRunner.cs:64`) → Post steps popped **LIFO** (`Stack<IStep>`, `ExecutionContext.cs:1059`) → `"Complete job"` (`JobOutputs` evaluation + secret scrub).
  - Composites isolate `steps` under `childScopeName`, set `inputs`, `GITHUB_ACTION_PATH`, `GITHUB_ACTION_STATUS`, track embedded post steps on `Root.EmbeddedStepsWithPostRegistered` / `EmbeddedIntraActionState` (running Post only for embedded steps that actually executed), and evaluate composite `outputs`.
- **Contexts, env, file/workflow commands, secrets & masking** (`ExecutionContext.cs:1003-1051`, `FileCommandManager.cs:19-496`, `ActionCommandManager.cs:21-200`, `SecretMasker.cs:11-300`):
  - Full contexts: `github`, `vars`, `strategy`, `matrix`, `needs`, `inputs`, `jobs`, `secrets`, `runner` (`RUNNER_*`), `job`, `env` (case-sensitive on Linux, overlaid workflow → job → step → `GITHUB_ENV`), `steps` (`outputs`, `outcome`, `conclusion`).
  - Per-step file commands under `<sandbox_tmp>/_runner_file_commands/`: `GITHUB_PATH` (dedup prepend), `GITHUB_ENV` (blocking `NODE_OPTIONS`), `GITHUB_OUTPUT`, `GITHUB_STATE` (`STATE_<key>`), `GITHUB_STEP_SUMMARY` (1 MiB cap, scrubbed line-by-line before Results upload), `GITHUB_ARTIFACTS`. Exact `NAME=VAL` and `NAME<<DELIM` heredoc parser.
  - Stdout commands `::error/warning/notice/debug/group/endgroup/add-mask/stop-commands::` (auto-masking stop-command tokens >6 chars).
  - `SecretMasker`: `AhoCorasick` (`LeftmostLongest`) + regex `MaskHints` + all 11 upstream `ValueEncoders` (`HostContext.cs:103-113`: Base64 + shift1/2, CLI/expr/JSON/URI/XML escapes, quote-trim, PS escapes) + line-splitting + `base64("x-access-token:" + github.token)`. Applied to every stdout/stderr line, WS frame, log blob, step summary, annotation, and `JobOutputs` (dropping any output mutated by masking, `JobExtension.cs:821-825`).
- **Cancellation, timeouts, and lock renewal**:
  - Signal escalation (`ProcessInvoker.cs:32-33,443-499`): `SIGINT` (7,500 ms) → `SIGTERM` (2,500 ms) → cgroup `cgroup.kill` (`SIGKILL` whole tree, zero orphan leaks!). On job cancel, re-evaluate active step's `if:` (`always()`/`cancelled()` finish within `max(timeout, 60 s) - 15 s`, `JobDispatcher.cs:1277-1285`); step timeout marks step `Failed` (`StepsRunner.cs:324-330`).
  - **Lock renewal:** Keep upstream's mandatory **first `renewjob` barrier before starting execution** (`JobDispatcher.cs:395-406`), then run a fresh renewal timer scheduled at `min(60 s, (lockedUntil - now) / 2)` (never transcribing upstream's buggy null-dereferencing `JobDispatcher.cs:748-852` loop). Stop immediately on `404`.
- **Crash safety (intent → call → record + epoch fencing):**
  - `velnor-dispatch` writes durable SQLite WAL intent (`dispatch_leases(request_id PRIMARY KEY, runner_id, node_id, epoch, state, plan_id, job_id, run_service_url, job_token_enc, locked_until)`) **before** `acquirejob`, then seals `{ plan_id, job_id, run_service_url, job_token, locked_until }` before handing off to `velnor-node` over mTLS gRPC.
  - `velnor-node` persists `node_sandboxes(sandbox_uid PRIMARY KEY, job_id, obligation_key, cgroup_path, upperdir, epoch, state)` before creating the sandbox. On crash/restart: `velnor-node` proves sandbox absence via cgroup + PIDFD/UID, writes `1` to `cgroup.kill` for any orphan cgroup, removes `upperdir`, and reports `Lost` to `velnor-dispatch`; `velnor-dispatch` calls `completejob(Failed, infrastructureFailureCategory)` **at most once** using its sealed job token (and standby dispatcher reopens scale-set sessions cleanly from journal). `velnor-ledger` persists `ledger_executions(obligation_key, epoch, node_id, state)` and accepts receipts strictly by compare-and-swap on `(obligation_key, epoch)` so a partitioned node can never write stale receipts.

### 3.5 Sub-second job start pipeline (< 15 ms sandbox, ≤ 250 ms acquire-to-step-1)

Instead of ARC's 8-step pod creation (6–14 s [M]) or idle pod recycling (2–3 s [M]):
1. **Pre-warmed broker sessions & JIT pool:** `velnor-dispatch` maintains warm `ScaleSetSession` long-polls and a pool of pre-generated JIT identities (zero pods, ~4 KiB RAM each) already authenticated to `BrokerClient` (`POST session` open, `GET message` parked).
2. **Webhook-driven pre-execution:** For labeled PRs and `merge_group`, `velnor-hooks` starts `ensure(tree, plan)` **~13 s before GitHub even emits `JobAvailable`** (1.5 s webhook vs ~15 s job creation).
3. **Pipelined acquisition + sandbox preparation:** On `JobAvailable`, `velnor-dispatch` scores nodes in <1 ms (site, warm snapshot, free threads, running `ensure` affinity), assigns a pre-authenticated JIT identity, calls `acquirejobs` + `acquirejob` + mandatory first `renewjob` (~150–250 ms total RTT), while **in parallel** sending a `PrepareSandbox(tree, class)` hint to the chosen `velnor-node` (which creates the Linux mount/PID/UTS/IPC/net namespaces + cgroup v2 + overlayfs/reflink view in **~15 ms**).
4. **Result:** Broker message → first step executing takes **≤ 250 ms P50 / ≤ 500 ms P90** [E] (4–8× faster than v2's 1–2 s target and 50× faster than ARC on-demand), and when joining webhook-started `ensure`, step 1 streams live progress immediately.

## 4. Native actions

`velnor-actions` implements **every action** across `velnor-new`'s 16 workflows AND `velnor-gen`'s `ALLOWED_ACTIONS` (`generator/crates/velnor-render/src/rules.rs:8-23`) natively in Rust, pinned to an explicit `(repo, sha)` registry. **No Node runtime, no npm, no tarball download from GitHub, no JS interpreter exists on any worker.** Any unlisted action or unapproved SHA fails the job in `velnor-exec` preflight before step 1 with an actionable error listing the allowed set.

| Action (pinned SHA / scope) | Uses | Native Rust design & local acceleration (vs network) | Today [M] | Native [E/T] |

### Native action implementation invariants

- **Checkout freshness without `.git` (`N55`):** For pure build/test obligations, `velnor-node` materialises the target Git tree from its bare mirror directly into the sandbox's `/w/velnor-new` (leaving `.git` outside the sandbox so `build.rs` cannot observe branch/commit metadata, `C5`). Every file whose blob SHA equals the warm `main` snapshot's manifest inherits the exact recorded snapshot mtime; every modified or added file receives `max(snapshot_output_mtimes) + 1 s`; removed paths become overlayfs whiteouts. For workflow steps that explicitly inspect git history (`release-plz` `fetch-depth: 0`), `actions/checkout` attaches a read-only `.git/objects/info/alternates` link to the node mirror (zero object copy).
- **Pure-Rust Sigstore attestation (`actions/attest-build-provenance` / `actions/attest`):** Mint OIDC JWT via `GET $ACTIONS_ID_TOKEN_REQUEST_URL&audience=sigstore` (after the 1 s `JobRecordUpdated` barrier) → generate ephemeral P-256 keypair in memory (zeroized on drop) → exchange OIDC JWT + CSR at Fulcio `/api/v2/signingCert` → construct canonical SLSA v1.0 in-toto DSSE envelope over SHA-256 subject digests → submit hashed-rekord entry to Rekor v2 for inclusion proof → upload Sigstore bundle to `POST /repos/{owner}/{repo}/attestations`. Zero Node, zero `cosign` binary, verified by `gh attestation verify` in `velnor-conformance`.
- **Generator closed-set invariant:** `velnor-gen` (`generator/crates/velnor-render/src/rules.rs:8-23`) and `velnor-actions` share one compiled table of qualified `(action, full_40_hex_sha)` pairs; a Renovate/manual action SHA bump cannot merge until `velnor-conformance` passes against the updated upstream action in `velnor-lab`.

## 5. The conformance oracle

GitHub's latest official `actions/runner` release runs **exclusively in `velnor-lab`** as a continuous differential oracle (`velnor-conformance`); it is never deployed or kept as a fallback on production runners.

## 8. The merge queue and GitHub integration

### 8.1 On-demand PR trigger flow (`velnor:verify`) and avoiding GitHub's `skipped = PASS` bug

**The GitHub Ruleset trap (verified against GitHub Docs):** GitHub Rulesets treat required status check conclusions of **`success`**, **`skipped`**, and **`neutral`** as **PASSING**. Putting `if: contains(github.event.pull_request.labels.*.name, 'velnor:verify')` on a top-level `Required` job in `ci.yml` would mark `Required` as `skipped` on every unlabelled push — **allowing unverified PRs to merge!** Conversely, when a **reusable workflow caller job** is skipped via `if:`, the callee workflow is never expanded and its inner `Required` check is **never created**, remaining **`Expected — Waiting for status to be reported`** (which **blocks** merge and merge-queue entry) while consuming **0 runner jobs**.

**Exact workflow skeleton (`.github/workflows/ci.yml` → `.github/workflows/ci-verify.yml`):**
```yaml
# .github/workflows/ci.yml — NO opened/ready_for_review/edited/unlabeled; NO PR concurrency stall
name: CI
on:
  pull_request: { types: [labeled, synchronize] }
  merge_group:  { types: [checks_requested] }
  push:         { branches: [main] }
permissions: { contents: read }
jobs:
  ci:
    if: >-
      github.event_name != 'pull_request' ||
      (contains(github.event.pull_request.labels.*.name, 'velnor:verify') &&
       (github.event.action == 'synchronize' || github.event.label.name == 'velnor:verify'))
    uses: ./.github/workflows/ci-verify.yml
```
```yaml
# .github/workflows/ci-verify.yml — single job; NO if: always() blocker; cancelled = blocking
on: { workflow_call: {} }
jobs:
  required:
    name: Required
    runs-on: velnor-native
    steps:
      - name: Verify via Velnor ledger
        run: velnor-ci witness --event "$GITHUB_EVENT_NAME" --sha "$GITHUB_SHA"
```
GitHub registers the inner check context as **`ci / Required`**. Because `ci` is skipped whenever `velnor:verify` is absent, `ci / Required` is never instantiated on unlabelled PRs and stays **`Expected`** (blocking merge and merge-queue entry) with zero runner jobs.

### 8.2 `GITHUB_TOKEN` label-trigger suppression vs GitHub App webhook delivery (verified)

- **GitHub Docs behavior:** Per GitHub Docs (*Triggering a workflow from a workflow*), mutations performed with a workflow's automatic `GITHUB_TOKEN` (including adding a label via `gh pr edit`) **suppress downstream `pull_request: types: [labeled]` Actions workflow runs** to prevent recursion; furthermore, per GitHub Docs (*About protected branches / Required status checks*), `workflow_dispatch` runs **do NOT satisfy** PR required status checks. **However, GitHub App webhooks (`pull_request` event, `action: "labeled"`) ARE delivered** to external webhook receivers (`velnor-hooks`) for mutations by users, PATs, GitHub Apps, and `GITHUB_TOKEN`.
- **Two-layer fallback (zero silent hangs):**
  1. Humans (GitHub UI / `gh`) and agents authenticate with user/PAT/GitHub App tokens (never a workflow's `GITHUB_TOKEN`) when adding `velnor:verify`, so both `ci.yml` and `velnor-hooks` fire natively.
  2. If any workflow ever adds `velnor:verify` with `GITHUB_TOKEN`, `velnor-hooks` still receives the `pull_request.labeled` App webhook, immediately runs `ensure(tree, plan)` on the cluster, and starts a **10 s watchdog**. If no `ci.yml` Actions run appears for `(pr, head_sha)` within 10 s, `velnor-hooks` authenticates with the **Velnor GitHub App installation token** and performs a one-shot `DELETE` + `POST` of `velnor:verify` (fenced by a durable `(pr, head_sha)` replay marker in `velnor-ledger` so it can never loop), firing an eligible `pull_request.labeled` Actions trigger! A 60 s reconciliation loop over open `velnor:verify`-labelled PRs also heals dropped webhooks.

### 9.2 The architecture that reaches the floor

Four concrete shifts close the gap from today's 85 min to the **~15 s cold / ~4 s preflighted** physical floor:
1. **Move verification left of `git push` (cluster-backed preflight & agent workspaces):** Agents already spend 11 s median (≥30 s for 38% of pushes) between committing and pushing (`cmp:88`). 2. **One high-clock compile/test node + 6-way `velnor-runner-host` split:** Because `rustc` front-end + linking and single-test critical paths are single-thread-clock-bound (not thread-count-bound), adding one desktop-class 5.5+ GHz node (for the serial compile/longest-test tip) alongside the 480 EPYC threads (for parallel fan-out, 3× repeats, speculation, and cold audits) cuts the remaining serial compute floor by ~1.4×.
3. **App-native `Required` Check Run cutover (Phase 4):** Updating `velnor-ci/src/gate.rs` and `product-release.yml` together to accept the Velnor GitHub App's `integration_id` removes GitHub Actions' 15 s job-creation floor on PRs and merge groups while keeping zero-rebuild `release-gate` integrity.
4. **Velnor Compare-and-Swap Merge Train (Phase 4, optional under Binding Decision 7):** On GitHub's own Merge Queue, **45 s is an absolute platform floor** (`19 s + 26 s`). If the owner later approves replacing GitHub's Merge Queue with Velnor's CAS fast-forward merge train (shadowed first to ≥95% tree match, fast-forwarding `main` atomically via GitHub's Git Refs API ONLY to a commit whose every obligation holds by receipt), push-to-merge drops from **~50 s to ~4 s** (preflighted) / **~15 s** (cold).

### 9.3 Irreducible costs (what can NEVER be zero at same confidence)

1. **Speed-of-light GitHub API RTTs:** ~1–2 s webhook arrival, ~0.4 s check-run write, ~0.8 s ref update (and **45 s** if using GitHub's Merge Queue).
2. **Real compilation of changed Rust code:** ~3–5 s incremental `rustc` + `rust-lld` link per changed crate (never replaced by an unsound compiler like `blaze`).
3. **Real execution of changed tests (3× parallel):** ~3–5 s for the longest unmocked integration test (parallelism hides the 3× multiplier completely on 480 threads).
4. **Async soundness tax (0 s on critical path, ~6–12 runner-min/merge off-path):** Every landed commit still runs a 100% cold full verification within 24 h on batch capacity, and every 20th merge runs a cold differential build — guaranteeing zero silent false greens forever.
