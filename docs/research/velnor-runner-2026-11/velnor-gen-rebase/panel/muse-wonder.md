## 1. Verdict in ten lines

1. **The final design still stands on velnor-gen — but only as a destination, not as a description of today.** The generator (`velnor-gen` → `velnor-model` types → `velnor-rust` planner → `velnor-render` YAML → `velnor-ci` at run time) is a strictly better foundation than the 39-job engine `ci.yml` the plan was written against: selection, verdict keys, and the `Required` gate already live in typed Rust, not YAML.
2. **velnor-gen already gives the plan its hardest primitives for free:** typed selection (`velnor_rust::select`), a typed verdict (`VerdictSpec` + `decide`), content-addressed cache keys rendered from one place, helper pinning that makes the plan itself come from a released version, and a PR delta layer. The ledger does not need a new universe; it needs `velnor-model` extended.
3. **Correctness is currently broken in production, and that outranks every speed item.** Main is red, `Required` fails on ~98% of PR runs, and 157/173 recent merges landed with a failing `Required` on the head (admin bypass inferred; ruleset still allows it). No ledger, no executor, no cache design matters until `Required` is trustworthy.
4. **The single most important change to the plan: invert Phase 0.** Old Phase 0 optimised the gate (ALLGREEN, bind contexts, move jobs). New Phase 0 must first restore a green, non-bypassable `Required` on velnor-gen, then revive the merge queue, then add the generator-owned label mode that makes an unlabelled PR *unmergeable*. Only then do executor/storage work start.
5. **The label flow as built is the opposite of the owner’s decision on the mergeability question.** `pr_ci = "label"` (`.velnor/rust-ci.toml:10`) gives an unlabelled ready PR a green `Required` after the quick set, and a draft a green `Required` with a notice. Owner decision 12 requires the opposite: unlabelled = never green. This is a generator bug to fix in `velnor-rust`, not a product decision to re-litigate.
6. **Reuse today is zero at the verdict level and real below it.** PR → queue → push → release each re-runs; the only prior-run lookup (`velnor-ci merge-group-passed`) is off. But cargo fingerprints + restored mtimes, MBX CAS, delta source identity, and helper digests already provide the digest vocabulary a ledger must reuse instead of inventing new hashes.
7. **The Rust-only executor still conflicts with the rule book** (`docs/goals.md:16`: “Jobs are always executed by GitHub's official runner”). velnor-gen does not resolve this; the owner must approve the exact wording change in §7 before any X-stream work starts. Everything else in the plan can proceed without it.
8. **Speed on the new baseline is genuinely fast and genuinely unproven.** Post-cutover: PR heavy runs P50 2.9 / P90 6.2 min, push runs P50 7.5 / P90 11.3 min, queue P50 2–13 s, `rust-root` the long pole (P50 67 s PR / 371 s push). But the sample is 4.3 h, main was red, and success-path durations are under-sampled (2 PR + 4 push successes, all docs-only). Targets must be re-derived after a green baseline, not inherited from the pre-cutover 85/457 min push-to-merge.
9. **About half the delivery plan survives unchanged; the other half is rewritten or gone.** E’s count (174 items: VALID 86, CHANGED 50, CONFLICT 20, DONE 10, OBSOLETE 8) is directionally right at tip; after `#1747`/`#1335`/`#1274`/`#1748` the DONE/OBSOLETE buckets grow and the per-root, engine-job, and `executor/`-root premises are dead. Streams V (ledger), AN (agent-native), H (conformance), C (caches/mirrors), ST (storage) survive; streams X (native executor) and F01 (delete runner) stay gated on the owner.
10. **Be ambitious where the generator makes it cheap:** let velnor-gen emit the verification contract itself — verdict keys at plan time, the same plan driving local agent runs and cluster runs, and a generator-owned benchmark. That is the foundation’s real advantage over the old engine, and the old design did not imagine it.

### 2.1 Verification ledger and verdict keys

**Today [C].** There is no verification ledger. What exists is its vocabulary, already typed:

- Selection is `RustSelection::{None, Some(BTreeMap<PackageName, SelectionReason>), All(AllTrigger)}` (`crates/velnor-model/src/selection.rs:45-49`), with `SelectionReason::{Changed, DependsOn, DependsOnUnread, Input, Lock}` (`:65-71`) and `AllTrigger::{Event, ToolchainFile, CargoConfig, WorkspaceManifest, UnknownPath, Global, GeneratedWorkflow, BaseUnavailable, MostPackages}` (`:74-84`). More than half the workspace selected collapses to `All(MostPackages)` (`:53-60`). Unknown paths fail closed (`AllTrigger::UnknownPath`, A§2.3).
- The verdict is `VerdictSpec { plan: JobId, jobs: Vec<VerdictJob { id, when: Vec<JobCondition>, tests: Vec<RootSlug> }> }` (`crates/velnor-model/src/verdict.rs:64-75`), decided by `velnor_rust::decide` (`crates/velnor-rust/src/verdict.rs:278`) over `needs` JSON and the plan outputs `rust_deny`/`rust_root_tests` plus `tests_run/listed/ignored/by_package`. “Green means verified” is goals.md:41, enforced by the gate today.
- Cache keys are one typed enum `CacheKey::{Tools, Sources, Target, Delta}` (`crates/velnor-model/src/cache.rs:95` area) rendered only by `velnor-render::render_key` (`crates/velnor-render/src/cache.rs:20-61`); every commit-varying part is a GitHub expression, so the workflow bytes do not change on a dependency bump (A§3.1). `compat` (16 hex of SHA-256 over schema/rustc/target/profile/image/RUSTFLAGS/workspace/driver) and `lock_root` (SHA-256 of `Cargo.lock` with workspace path-package versions blanked, `crates/velnor-rust/src/lock_key.rs`) are the existing content hashes.
- The delta layer already binds a verdict-adjacent digest: `velnor-ci delta prepare` computes `base8` = first 8 hex of SHA-256 of the matched target key, and `delta stage/apply` binds a full tracked-source snapshot digest (`docs/rust-ci-cache-keys.md:57`; R:172-190, 396-444). `velnor-ci inputs save/restore` records per-file blob id + mtime (ns) + mode in `target/.velnor/inputs.tsv` and restores mtimes so cargo fingerprints hit (A§5.2).
- The one verdict-level reuse that exists is `velnor-ci merge-group-passed` (`crates/velnor-ci/src/merge_group.rs:46-86`) gated by `[ci] skip_push_after_merge_group` (helper ≥0.1.82, `crates/velnor-gen/src/helper_gate.rs`): on `push`, look for a completed successful `merge_group` run of the same workflow with `head_sha == GITHUB_SHA`; write `skip=true` only on proof, `skip=false` on every error (“Never fails: whatever it cannot establish means run everything”, `crates/velnor-ci/src/merge_group.rs:46-47`). It is **off** in this repo (no `merge-group-passed` step in `.github/workflows/rust-ci.yml`). Per-step skip is `Step.skip_after_merge_group: Option<PlanFrom>` (`crates/velnor-model/src/plan.rs:110`), applied by `merge_group_skip::apply` to the `is_check` set and rendered from plan output `skip_push` (`MERGE_GROUP_SKIP_OUTPUT` at `crates/velnor-model/src/plan.rs:19`).

**Where the ledger lives.** Generator-time first, run-time second — deliberately not a new service first:

- **Generator-time (keys):** extend `velnor-model`, do not create `velnor-ledger` as a separate root. Add a `VerdictKey` struct next to `CacheKey` (`crates/velnor-model/src/cache.rs`) and `VerdictSpec` (`crates/velnor-model/src/verdict.rs`): fields = tree digest, per-package closure digest (from `RustSelection`), toolchain/`compat`, `lock_root`, executor identity, helper digest, and the `AllTrigger`/`SelectionReason` provenance so `--explain` can name a reuse (`crates/velnor-model/src/selection.rs:118-142` `Display` impls). Reuse `CacheKey::layout()` (`crates/velnor-model/src/cache_layout.rs:63`) as the canonical serialisation; keep the single-renderer rule (`render_key` only).
- **Generator-time (planner):** `velnor-rust::plan()` (`crates/velnor-rust/src/plan.rs:40-112`) and `velnor-rust::select_event()` (`crates/velnor-rust/src/select_event.rs:12-44`, already takes the diff as a closure and returns `(selections, ChangeSet)`) compute the key at plan time. A lookup hit turns `Some/All` into `None`-for-reused only with digest equality (goals.md:40: skip only when provably unaffected). Add `SelectionReason::Reused(VerdictKey)` / `AllTrigger::Reused` variants so `velnor-ci plan --explain` (`crates/velnor-ci/src/io/plan.rs:37-90`) prints the provenance.
- **Run-time (lookup + gate):** new `velnor-ci ledger` subcommand family (`lookup`, `record`, `explain`) in `crates/velnor-ci/src/cli.rs:35-175`; new `HelperCommand` variant (`crates/velnor-model/src/steps.rs:158-167`) + `helper_gate.rs` minimum if declared workflows may call it (`crates/velnor-workflows/src/helper_call.rs` `HELPER_COMMANDS`). The gate (`velnor-rust/src/verdict.rs:278` `decide`) must accept “reused” only with evidence; today the sole reused case is `push && skip_push == 'true'`. `tests_expected` (`crates/velnor-rust/src/required_job.rs:149`) and the `tests_run/listed/ignored/by_package` outputs must still match.
- **Runner-side (writes):** only trusted events write trusted records, mirroring `mbx_store::trusted_event` (`crates/velnor-ci/src/mbx_store.rs:28-37`: push/schedule on default branch). PR writes stay isolated (goals.md:43, rule 8). Candidate vs trusted scopes are the design’s two tiers, implemented as two key namespaces, not two systems.

**Free.** Plan-from-released-version (goals rule 12) already holds: `.velnor/rust-ci.lock` pins helper 0.1.95 at commit `3a77d53ce64b…` with per-platform SHA-256, installed via `actions/setup-velnor@<release commit>` (R:71-76) and re-verified on every invocation through the `VELNOR_EXEC` launcher (R:77-82). The ledger inherits that trust anchor instead of building a new one. Content addressing below the verdict (fingerprints, MBX CAS, delta identity, helper digests) is already correct; the ledger’s job is to *name* it at the verdict level, not to re-hash the world.

**Naming collisions to resolve in an ADR (E§3.9):** `velnor-ci inputs audit` (existing) vs design “audit A1/A2”; velnor-local authority “ledger” (dispatch-event ledger, `local/README.md:135`) vs verification ledger; `velnor-ci report` vs `velnor trace`; `velnor-ci gate`/`release-gate` vs `velnor check`/`verify`. Pick one noun per concept before code lands.

**Hard-decision gate.** HD3 (`docs/hard-decisions.md:223-229`) bans baseline-gated skipping / a second skip mechanism without owner approval. It formally binds the old engine only (`docs/hard-decisions.md:14-19`; goals.md:14), and the engine is deleted, but Gate 5 history (“Removed … every obligation now executes unless a non-baseline decision applies”, `docs/implemented/gate-5-trusted-baseline.md:3-7`) means an owner decision is still the safe course. See Q-N8 in §7.

### 2.2 The `Velnor / Verified` App status

**Today [C].** The gate is a normal Actions check named `Required` (`required_check = "Required"` at `.velnor/rust-ci.toml:5`; job `Required` at `.github/workflows/rust-ci.yml:631-672`, R:631-672), produced by `velnor-ci gate --spec-env GATE_SPEC` with `GATE_SPEC='--plan rust --job rust=always --job policy=policy --tests rust=root'` and `NEEDS_JSON=toJSON(needs)` (R:664-669). The live ruleset `protect-main` (id 24396608, read via `gh api` in C§4 and re-read in E§0) requires only `Required`, with **no `integration_id` binding** and `bypass_actors = [RepositoryRole 5 admin]` (`regen/c-data/ruleset-main.json`: `required_status_checks: [{context: "Required"}]`, `bypass_actors: [{actor_id: 5, actor_type: "RepositoryRole", bypass_mode: "pull_request"}]`). Any App — or a workflow token with `statuses: write` — can therefore post `Required`. `velnor-ci release-gate` currently *refuses* non-Actions App checks (`crates/velnor-ci/src/gate.rs:295-298` area), which is the opposite of the design’s App gate.

**Where it lives.** Not in generated YAML. The status writer is a new runner-side service; velnor-gen’s role is limited to naming and transition:

- **New crate `velnor-control`** (runner-side, under `crates/`, not `executor/`): webhook receiver, label state machine, reconciler (10 s re-read of GitHub state, ruling Q3), fenced status writer for `Velnor / Verified`, merge-group handling. Permissions per UX §1.1: `statuses: write`, `checks: write`, `pull_requests: read`, `contents: read`, `metadata: read`. Agent identity that cannot edit the ruleset is a separate App/installation, not a user token.
- **Generator-time:** once the App gate is live, `.velnor/rust-ci.toml` gains no new key for the status itself; instead the transition keeps `Required` as the Actions gate until shadow parity (L06) is proven, then the ruleset swaps the required context from `Required` to `Velnor / Verified` and `Required` is deleted from `rust-ci.yml` in the same change (migrate and delete). During transition, `velnor-ci gate` stays the producer of `Required`; after cutover, `Required` must not be emitted at all — a leftover Actions `Required` that can satisfy the ruleset would be a second gate.
- **Run-time:** `velnor-ci release-gate` must learn `--app-check` (accept `Velnor / Verified` written by the App’s integration id) — today it has only `--pr-only-check` (`crates/velnor-ci/src/cli_release.rs:12-23`) and already requires push-run job evidence (`crates/velnor-ci/src/gate.rs:141-172`). That delta is small and well-scoped.

**Free.** The fenced-writer discipline already exists in the runner journal: persist intent → perform external call → record success or uncertainty, no DB transaction across HTTP/Docker (`docs/proposed/macos-scaleset-runner.md:165-168`). The App writer should reuse that discipline, not invent a new one. The `Velnor / Details` check-run (UX §4) maps onto `velnor-ci report` / `ci-metrics.json` (A§3.3) — extend, do not rebuild.

### 2.3 Label flow

**Today [C] — the as-built flow, verified against the workflow.** Config `pr_ci = "label"` (`.velnor/rust-ci.toml:10`; `PrCi::Label` parsed at `crates/velnor-rust/src/config_pr_ci.rs:14`, mutually exclusive with `skip_draft_pull_requests` at `crates/velnor-rust/src/error.rs:198`). Triggers include `labeled` but **not `unlabeled`** (`.github/workflows/rust-ci.yml:5-12`: `opened, synchronize, reopened, ready_for_review, edited, labeled`). Job gating:

- `rust` job `if` (R:35): non-draft and (`action != labeled` or label ∈ {`ci:run`, `ci:auto`}) and (`action != edited` or base changed). Drafts: `rust`/`policy`/`cache` skipped; `required` runs under `always()` and on a draft only prints `::notice title=Draft::draft: CI not requested` (R:642-644), so **`Required` is green on a draft**.
- Ready PR without a label: `PrRun::Quick` (`crates/velnor-rust/src/plan.rs:330-333`: `PrCi::Label => PrRun::Quick`) runs plan, Format, Lint, policy — the “quick set” (`docs/rust-ci.md:80-90`). Tests are `PrRun::Requested` (`crates/velnor-rust/src/plan.rs:337-340`). The gate step is conditional on the label, so an unlabelled ready PR’s `Required` is the quick-set result and is **green and mergeable** (R:636-668; E§1).
- `ci:run` = one-shot (label removed by job `ci-run-label`, R:673-686, the only job with `pull-requests: write`); `ci:auto` = every push. Concurrency cancels older PR runs except unrelated labels (`Concurrency::CancelOlderPullRequestRunsExceptUnrelatedLabels`, `crates/velnor-model/src/plan.rs:62-65`; rendered at R:22-24). Labels in the repo are `ci:run` / `ci:auto`; `velnor:verify` does not exist (`gh label list`, E§1).
- Fork PRs: quick set only on `ubuntu-latest` (R:57 fork fence), full suite only in the merge queue (A§2.5).

**Owner’s requested flow (decisions 15–17 in the brief; owner decision 12).** Draft → nothing; ready → nothing; label attached → every push runs and cancels the previous run; label removed → stops; a PR can never merge without a green verdict on its latest commit.

**Where the fix lives — generator-time, almost entirely:**

- **Config:** new `pr_ci` value (e.g. `pr_ci = "verify"`) or a breaking change to `"label"` semantics — pick one, delete the other (no side-by-side). Keys in `crates/velnor-rust/src/config_keys.rs:4-38`, parse in `crates/velnor-rust/src/config_pr_ci.rs`, field in `RustCiConfig` (`crates/velnor-model/src/repo.rs`), docs in `generator/CONFIG.md` `pr_ci` table + `docs/rust-ci.md:80-90`, helper minimum in `crates/velnor-gen/src/helper_gate.rs:8-51` if a new `velnor-ci` behaviour is needed.
- **Model:** `PrRun` (`crates/velnor-model/src/plan.rs:119-128`: `Always, Ready, Quick, Related, Requested, Unrequested`) gains the semantics for “not requested = blocked”. Today `Unrequested` exists but the `Required` job does not fail on it. The `Required` job construction in `crates/velnor-rust/src/required_job.rs` (notably `tests_expected` at `:149` and the `on_label` branch at `:112-142`) must emit a `Required` job that **fails** with “CI not requested” for a non-draft PR without the label, runs on `labeled` **and `unlabeled`**, and cancels in-flight runs on `unlabeled`. A skipped required job passes in GitHub, so “blocked” must be an explicit failure, not a skip (E§1 technical constraint).
- **Triggers:** add `PullRequestType::Unlabeled` (`crates/velnor-model/src/plan.rs:41-49`; `ALL` at `:52-58` currently has 5 entries, `Labeled` added conditionally at `crates/velnor-rust/src/plan_budget.rs:59`). Rendered triggers are built in `crates/velnor-rust/src/plan_budget.rs:49-70` (`triggers`, `draft_guard`).
- **Run-time:** almost nothing. `GITHUB_TOKEN` label changes do not trigger workflows, so agents must label with an App or user token — the design already says this (UX §9); no `velnor-ci` change hides it.
- **Docs/tests:** `docs/rust-ci.md`, `generator/CONFIG.md`, golden samples under `generator/samples/` (A§1.4).

**Free.** Cancellation, the `-ignored-<run id>` concurrency suffix for unrelated labels (R:23), the `edited`-only-on-base-change filter (R:35), and draft skipping of the heavy jobs already implement owner steps 1, 3 (partially), and 4 (for `ci:auto`). What is missing is precisely steps 2, 5, and 6: ready-runs-nothing (or an owner-approved quick set), stop-on-unlabel, and never-green-when-unlabelled.

No PR result is consumed by the queue run, the push run, or release. The queue run recomputes lint/tests for the same diff; the push run after a fast-forward merge recomputes again. `skip_push_after_merge_group` is off, so the push repeats even when the queue proved the identical SHA (A§5.3). **Where reuse lives (same home as §2.1, staged by risk):**

1. **First, prove the plumbing with what exists.** Turn the queue back on, then enable `[ci] skip_push_after_merge_group = true` (`generator/CONFIG.md:26-40`; needs helper ≥0.1.82). This is the only reuse that is already implemented, already fail-safe, and already measured-able. It becomes the ledger’s `merge_group → push` edge.
2. **PR → queue (exact-tree).** Generator-time: the queue plan (`velnor-ci plan` with `merge_group.base_sha..head_sha`, A§2.6) computes the same `VerdictKey` as the PR plan; a hit on tree+closure+toolchain+executor short-circuits to the PR’s record. Run-time: `velnor-ci ledger lookup` called from `plan` after `select_event`. The design’s “60–75% of groups match the PR tree” (UX §4) is an estimate [E] with no queue traffic today to measure it — revive the queue first, then measure (see §4).
3. **Queue → main.** Already covered by (1) once the queue is used; generalise `Step.skip_after_merge_group` to a second `PlanFrom` (`crates/velnor-model/src/plan.rs:110`) only if a ledger hit needs a different output than `skip_push`.
4. **Agent run → PR.** Candidate records (§2.6) written by `velnor verify` in a sealed sandbox, read by the label-time `plan` as a lookup. Trust: candidate until a trusted event or the queue re-witnesses it (goals.md:43).
5. **Main → release.** §2.5 (promotion by digest) — release consumes main’s verified binaries instead of rebuilding.

**Free.** The digest vocabulary is already coherent: `compat`, `lock_root`, `base8`, delta source identity, MBX CAS (`actions/cas`, `actions/executable-identities`, `actions/task-manifests`, `actions/action-results`), and helper archive/binary SHA-256 in `.velnor/rust-ci.lock`. The ledger should compose these, not introduce a parallel hash scheme.

### 2.5 Release promotion by digest

**Today [C].** Tools release rebuilds from source and reuses nothing from main (A§4.1, verified):

- Bump PR (release-plz, `release-plz.toml:22-47`, group `tools`: `velnor-ci` lead, `velnor-gen` joins, tag `tools-v<ver>`) → tag created by the release App (rulesets `protect-tags`/`release-tags`; drift checked by `tag-ruleset-drift` job at `.github/workflows/release-rust-ci-tools.yml:16-85`) → `release-rust-ci-tools.yml` rebuilds both binaries (musl, `ubuntu-24.04` + `ubuntu-24.04-arm`, no cache, no MBX) → prerelease with `SHA256SUMS`/`BINARY-SHA256SUMS`/`COMMIT` → human/agent runs `velnor-gen pin-helper` + regenerate (`#1742` is the live example).
- The `gate` job (`.github/workflows/release-rust-ci-tools.yml:86-105`) only checks ancestry (`behind|identical` vs default branch via compare API). It declares `checks: read` but never calls it, so it does **not** verify `Required` passed — contrary to `docs/goals.md:77` (“released only from a tag on a commit of the default branch whose required check passed”). #1608 (open) fixes exactly this for the push run; see §6.
- Runner release: `release-plz.toml:49+` declares group `runner` (lead `velnor-runner-cli` + 7 crates, tag `runner-v<ver>`), but **no workflow builds or publishes it** (A§9.1). The generator can emit `release.yml` for consumer repos (`crates/velnor-render/src/release*.rs`, config `.velnor/release.toml`), but this repo has no `.velnor/release.toml`, so no `release.yml` exists here.

**Where promotion lives:**

- **Generator-time:** `velnor-release` (`crates/velnor-release/src/lib.rs:31-52`, `ruleset.rs`, `family.rs`, `release_plz.rs`) already models release setup; `velnor-render/src/release.rs:31` (`HOSTED_RUNNER` pin) and `release_attest.rs:70` (`gh attestation verify --deny-self-hosted-runners`) encode the current “hosted + attested” policy. Promotion changes the *source* of release bytes (main’s verified build) without changing that policy surface — unless the owner chooses self-hosted releases (Q-N5), which would require dropping `--deny-self-hosted-runners` and re-pinning runners.
- **Run-time:** `velnor-ci release-gate` (`crates/velnor-ci/src/gate.rs`, `cli_release.rs`) is the single release authority. It already requires push-run evidence (`gate.rs:141-172`); promotion adds “the binaries’ digests equal the digests recorded by the push/queue run for this commit” as a gate input, reusing the `SHA256SUMS` format the release workflow already emits. `velnor-ci release {record,publish,preflight,family-tag,align,check-config}` (`crates/velnor-ci/src/cli.rs:35-175`) are the existing subcommands to extend; `release align` (#1720) already handles combined release groups.
- **No new crate.** The missing piece is a workflow for `runner-v` (N07 in §5) and the decision whether release bytes are *promoted* (built once on main/queue, published by digest) or *rebuilt* (today). Owner decision 10 (“build once, verify once, promote”) points to promotion; the profile tension (CI tests use dev profile, release uses `release-tools` = opt-level s, thin LTO, strip, panic abort at `Cargo.toml:126-131`) must be resolved explicitly with numbers (test the release build vs build release artefacts once at merge time) — never silently rebuild.

**Free.** Digest plumbing (`SHA256SUMS`, `COMMIT`, `velnor-gen check-tag` at `crates/velnor-gen/src/lib.rs:121-131`, `velnor-gen pin-helper` at `crates/velnor-gen/src/io/pin.rs:15-50`) and the “publish job checks out nothing, runs no repo code, checks digests” shape (goals rule 13, already true of `release-rust-ci-tools.yml:228-253`) are done. Promotion reuses them; it does not need a new signing scheme.

### 2.6 Agent-native `velnor verify` / `velnor cargo` / `velnorD`

The `velnor-new` scenario (#1718) exists but has no recorded run (B§2.4) — recording one is N22, a precondition for using any of this as evidence.

### 2.7 Velnor Native executor vs GitHub Official

**Today [C].** Nothing in Rust executes Actions jobs. Every job is executed by GitHub’s unmodified official C# runner (`Runner.Listener`/`Runner.Worker`, pinned 2.338.0 in `.velnor/runner.lock`; the architecture doc cites v2.338.2 — reconcile, B§6 row 2c, E§4 §5.3). Production CI runs on ARC (Go `gha-runner-scale-set` 0.15.1, Hetzner k3s, evidence snapshot 2026-11-18), not on velnor-host. The Rust code implements the *scale-set listener side* only: sessions, long-poll, acquire, JIT, ack, refresh (`crates/velnor-runner-github`, 8.2k lines, pure wire types; HTTP in `crates/velnor-runner-host`), plus a macOS-first host controller (`velnor-host`, ~181k lines incl. tests, journal v58 on Turso 0.8.3) that launches one official-runner container + one private dind container per job. Broker long-poll, run-service acquire/renew/complete, Results, OIDC, and cache v2 (production) are **not** implemented in Rust (B§1.3). `docs/goals.md:16` and `docs/proposed/macos-scaleset-runner.md:37-39` currently *forbid* a native executor.

**Where each executor lives (after the owner gate in §7):**

- **Interface (runner-side library):** `velnor-executor` with `Executor::identity/run`, `Work::{Job, Obligation}`, `Role::{Production, Reference}` (architecture §5.3). Identity (kind, version, image digest) is part of every verdict key (§2.1), so switching executors re-verifies once and can never produce a false green (decision 20).
- **Velnor Native (`velnor-exec` + `velnor-native-actions`):** expressions, steps, composites, post steps, masking, cancellation, run service, Results; closed action set, no Node. The closed set must be reconciled first: the generator allows 16 actions (`crates/velnor-render/src/rules.rs:17-34` `ALLOWED_ACTIONS`, SHA-pinned in `crates/velnor-render/src/pinned_actions.rs`), including `docker/login`, `setup-buildx`, `build-push`, `github-script` (JS) — the design’s native set lacks them (E§4 §5.6). Either add native implementations or remove them from the generator list (N20); shipping a native executor that refuses workflows velnor-gen emits would be incoherent.
- **GitHub Official (`velnor-official`):** drives the latest official runner in the same sandboxes/pools/ledger/caches. Two modes: *acquired job* (release, image, scheduled — completes against GitHub’s run service) and *obligation* (Velnor synthesises the job message; the command runs under a new `velnor-ci obligation exec` that reports exits and the test inventory over a channel the sandbox cannot write). Reference role (decision 19): conformance gate, sampled shadow runs, “run both and diff” — never a verdict, cache, or release.
- **Generator-time routing:** `.velnor/` names the executor per job type or globally, read from the base commit (never the PR under test). Today the only routing knob is `runner = "ubuntu-26.04-scale-set"` (`.velnor/rust-ci.toml:4`) plus per-job overrides (`test_groups.runner`, `crates_mirror.runner`, `[[workflow]] runner`, A§7.2). An executor key follows that pattern: new key in `config_keys.rs`, parse in a `config_<x>.rs`, field in `RustCiConfig`, helper minimum in `helper_gate.rs`, `StepKind`/rendering only if the workflow bytes must change. Placement must be in `crates/velnor-*` under the single workspace — the design’s separate `executor/` Cargo root with its own lockfile contradicts #1290/#1594 and its rationale (delete engine crates without touching new code) is moot after #1747 (E§4 §5.2).

**Free.** The official-runner wrapper is substantially built: pair spec audit (`crates/velnor-runner-host/src/docker_spec.rs`, `HOST_NEEDLES` at :47), seccomp profile, runner/dind images with pinned digests (`.velnor/runner.lock`), job-start hook channel (`crates/velnor-resource-probe/src/job_hook.rs:10-20`), `velnor-host compare` fail-closed lane comparison, and the scale-set wire client with uncertainty classification (`acquire.rs` `Certainty`). What is genuinely new is broker/run-service/Results and the expression/step engine — size it as new, do not budget it as a “port” of velnor-host.

### 2.8 Platform trait

**Today [C].** There is no trait. `git grep "trait Runtime"` is empty; ~50 non-test files import `bollard` 0.21.1 (`Cargo.toml:50`); the only backend is Docker on one local engine (`unix://` socket only, `crates/velnor-runner-host/src/docker_client.rs:98` `connect_unix`). A competing proposal (`docs/proposed/kubernetes-runtime.md`, #1324, design only, 495 lines) proposes a `Runtime` trait with `RuntimeKind::{Docker, Kubernetes}`, `WorkloadRef/StorageRef/NetworkRef`, `Observation::{Present, AbsentProven, Unknown}`, `AbsenceProof`/`OwnershipProof`, Pod-per-job, and node-local PVC cache slots — and it *keeps* the Turso journal, while architecture §5.10 *deletes* the journal at the final milestone. Two incompatible directions are in-tree (B§6.1); N12 (§5) reconciles them before code.

**Where it lives.** Runner-side library `velnor-platform` (capabilities: reflink, shared page cache, privileged dind, snapshot, network policy, CPU pinning, arch/OS — decisions 13/21) + `velnor-k8s` + `velnor-docker` backends. The core describes environments generically (CPU, memory, mounts, network policy, lifetime) and never names pod/container concepts; it branches only on capabilities, and a missing capability falls back to a slower but correct path (copy instead of reflink; refuse Docker-class jobs instead of sharing a daemon; whole-tree keys without a read audit). Lifecycle, crash recovery, ownership proofs, and teardown are part of the backend contract; conformance runs per backend (P06).

**Free.** The observation model is the reusable core: `velnor-runner-core` lifecycle/capacity/ownership types (small, pure), `CleanupProof::covers` requiring full 64-hex id + named volume (`crates/velnor-runner-core/src/ownership.rs:31-34`, fixed in #1275), the journal’s tri-state discipline, and the pair audit rules. The Docker backend is a *refactor* of existing `velnor-runner-host` code (P03 rewritten, E§6.2), not a fresh write; the Kubernetes backend is genuinely new (no `kube` dependency today, no `deploy/` dir, ARC manifests live in an external checkout — N11 decides the repo home).

### 2.9 Storage

**Today [C].** No storage abstraction. Per-job Docker volumes/tmpfs with btrfs awareness from the resource probe; cluster storage is k3s `local-path` with no PVs/PVCs, every runner volume `emptyDir` on XFS/LVM (B§3.2, snapshot 2026-11-18). `git grep -i "rustfs|nvme|reflink"` outside research finds nothing in code. The only “S3” concept is MBX’s own cache modes, consumed by mise/MBX, not by Velnor.

**Where it lives.** Runner-side `velnor-storage` (blob-store trait: local filesystem, RustFS single-node, RustFS multi-node erasure-coded per site, any S3-compatible store) with tiers composed in config (`local`, `local → site`, `local → site → cross-site`) and each data class routed separately (`actions/cache`, artifacts v4, release artefacts, mbx-cache store, warm-snapshot shipping). Backends declare capabilities (reflink, server-side copy, multipart, conditional writes, replication); the cache layer picks the fastest correct path. Defaults: Docker/local macOS = local only; Kubernetes = node NVMe + RustFS cluster per site. Invariant: a misconfiguration can only make things slower, never wrong; content is verified on every read.

**Free.** Almost nothing at the blob layer — this is new code. What exists is the *policy* layer above it: the 8 GB budget (`cache_budget_bytes = 8000000000`, `docs/rust-ci-cache-keys.md:135`), `velnor-ci cache decide/trim/verify/budget` (R:353-367, 626-630), and the delta layer’s cumulative-overlay + mtime discipline. Storage work should keep those policies and replace only the backing store (ST03 is gated on goals.md:59, see §3).

### 2.10 `actions/cache` server

**Today [C].** Production cache is GitHub’s (four families: tools/sources/target/delta, §2.1). The native implementation exists only as a local emulator: `velnor-cache-rules` (728 lines: read own ref/base/default, write own ref, immutable keys, eviction, fork read-only; `crates/velnor-cache-rules/RULES.md`) + `velnor-local cache-server` (Twirp v2 + blob, archives as files + `index.json` under flock), with conformance replayed from lab probes (`local/conformance/*.json`: `cache-other-pr`, `cache-own-pr`, `cache-pr-reads`, `cache-restore-keys`, `cache-save-existing`, `event-payload`, `needs-result`, `token`; 5 of 8 reproduced locally, B§2.3). The official runner on ARC pods still talks to GitHub’s cache; there is no way to point production at the emulator (open question in decision 22: can `Runner.Worker` be pointed at a Velnor v2-compatible endpoint?).

**Where it lives.** Run-time service `velnor-cache` grown from `velnor-cache-rules` (the executable spec of GitHub cache semantics — keep `RULES.md` as the contract), backed by `velnor-storage` tiers (L0 node NVMe unpacked + reflink clones, L1 RustFS per site, L2 cross-site replication in background). GitHub’s cache service leaves the hot path; branch scoping (read own/base/default, write own, immutable keys, PR writes never reach `main`) is enforced by Velnor’s layer on every tier, not by the backend. Prefetch (dispatcher evaluates `hashFiles('Cargo.lock')` ahead of the job and warms L0) and content-addressed chunk dedup are new. For the Official executor, ST05 (cache endpoint the official runner can be pointed at) is the critical unknown — verify in runner source before promising it.

**Free.** The semantics, the conformance data, and the test fixtures from real `@actions/cache` 6.1.0 are the hard part, and they exist. The production gap is an authoritative index across nodes and a storage backing — both are ST-stream work, not research.

### 2.12 Warm snapshots

**Today [C].** Absent in code. ARC `minRunners` idle pods (4/4/2) are the only warm capacity (evidence snapshot); velnor-host launches the pair on demand per job (“pairs are single-use”). The Kubernetes proposal’s `NodeCache` PVC slots (`docs/proposed/kubernetes-runtime.md:268-310`) are design-only. No reflink clone, no warm snapshot, no pool, no NVMe tier (B§3.5).

**Where they live.** Runner-side node agent (`velnor-node` DaemonSet / host daemon): warm pools sized by demand, verified generations (a generation is a sealed tree + build output whose digests A1 has confirmed), reflink clones into the job’s pre-mounted volume (a running pod takes no new mount — the clone lands in the warm pod’s volume, architecture §3 stage 3). Publication is run-time: `velnor-ci` records the landed group’s build output as the next generation, trusted when A1 gives equal digests (design row 19). Storage tiers (§2.9) ship snapshots between nodes; the `inputs restore` mtime rule (A§5.2.4) is the correctness hinge — a snapshot with wrong mtimes is a slow cache, not a wrong one, and must be treated as a miss.

**Free.** The delta layer *is* a snapshot mechanism at PR scope (cumulative overlay, mtime preservation, fingerprint invalidation when the source snapshot differs, `docs/rust-ci-cache-keys.md:57`). Warm snapshots generalise it from “per-PR delta over a GitHub-cache base” to “per-node generation over a local base”. Reuse the stage/apply code paths and their guards (500 MB cap, no-save-on-no-compile, cold-run-saves-nothing) as the generation guards.

### 2.13 `mbx`

**Today [C].** MBX (“mr-boxington”, cargo wrapper `mbx` via `[wrappers.cargo] command = "mbx"` in `mise.toml:44-46`, `mr_boxington = true` at `mise.toml:20-25`) is the compiler-level content-addressed store (`actions/cas` etc.). This repo sets `mbx_shared_store = true` and **not** `cache.mbx_remote` (`.velnor/rust-ci.toml:7`). Behaviour (`generator/CONFIG.md:91-101`; `crates/velnor-ci/src/mbx_store.rs:12-37`): `velnor-ci mbx-store` (R:83-84, every job) shares the node-wide `VELNOR_MBX_SHARED_DIR` only on trusted events (push/schedule on default branch); `velnor-ci mbx-seed` (R:85-87, PR and merge_group only) copies missing files from read-only `VELNOR_MBX_SEED_DIR` into a private `$RUNNER_TEMP/velnor/mbx`. `tools-local` does the same for mise/rustup. No sccache anywhere. MBX keys rustdoc on the whole workspace tree, which is the stated reason `docs = "post_merge"` and `check_alone = "post_merge"` exist (`generator/CONFIG.md:96-119`).

**Where it lives in the design.** Generator-time: unchanged config surface (`mbx_shared_store`, `mbx-store`/`mbx-seed` steps) — MBX is executor-independent and already node-aware. Run-time: `velnor-ci mbx-store`/`mbx-seed` stay; the node agent’s job is to *provide* `VELNOR_MBX_SHARED_DIR`/`VELNOR_MBX_SEED_DIR` on the right volumes (node NVMe, trusted-write / read-only-seed split). The design question is not “replace MBX” but “measure it”: C08 (mbx-cache head-to-head) must be rewritten with the shared-store baseline (#1411 shipped), and `velnor cargo` (§2.6) must decide whether it replaces or wraps the `mbx` wrapper slot. Do not stack two wrappers and call it a design.

**Free.** The trusted/seed split, the symlink/ownership checks in `mbx-seed`, and the per-job private store already implement the PR-isolation rule (goals.md:43) for the compiler cache. The runner work is provisioning, not protocol.

### 4.2 The next five levers (in order of saved minutes per merge)

Saved minutes are [E] against the post-cutover heavy-lane numbers until N09 gives a green baseline; each lever names its measurement so the estimate can be replaced.

**L1 — Stop re-verifying the same tree three times (PR + queue + push).** Today content is verified twice (PR + push; queue unused, C§5) and would be three times with the queue revived and no reuse. Enabling `skip_push_after_merge_group` (§2.4 step 1) removes the push re-run for queue-merged PRs; exact-tree ledger hits (§2.1) then remove most queue re-runs. *Saving:* up to one heavy push run per merge (≈7.5 min P50 wall, more in runner-minutes) minus the audit. *Measure:* `velnor-ci bench compare` before/after on the same cohort; count `skip_push=true` pushes and ledger hits in `velnor-ci plan --explain` output; runner-minutes per merged PR from `ci-metrics.json` (completed vs cancelled vs superseded split, architecture §1.1).

**L2 — Make the second push to a PR cheap (delta layer, measured).** PR deltas shipped in helper 0.1.95 (#1107, pinned at #1742) with **no timing measured** (A§3.2). The mechanism (restore target → `delta prepare` `base8` → restore delta → `delta apply` → build → `delta stage`, 500 MB cap) should make push 2 compile only what changed since push 1 (goals target). *Saving:* the difference between a base-restore build and a delta-restore build on the same PR — unknown until measured; the honest range is “0 if deltas miss, most of the compile if they hit”. *Measure:* N19 — instrument `velnor-ci report` with delta hit/miss, staged bytes, and compile counts (`ci-metrics.json` already carries `first_cargo_seconds` and per-cache hit kind); run the `velnor-new` scenario (N22) plus 20 real PR second-pushes.

**L3 — Shrink the `rust` job’s serial tail: parallel `policy`, post-merge-only work stays post-merge.** `policy` waits for all of `rust` (R:466-469); deny/machete need only the plan outputs (`rust_deny`/`rust_machete`), not the test results. The 31 alone-checks and `cargo doc` already run post-merge only (`docs`/`check_alone = "post_merge"`, `.velnor/rust-ci.toml:8-9`) — keep that. *Saving:* `policy` wall (≈78 s in run 44536064168, C§3.1) overlapped instead of serial, on every labelled PR and push. *Measure:* run wall (created → last job end) for `Required` before/after; `policy` start time relative to `rust` start.

**L4 — Cut the compile that selection does not save (warm generation + MBX hit rate).** Because lint/build are `--workspace` (G12), selection saves test execution but not the workspace compile. The compile is paid from the target cache + MBX CAS; its cost is therefore a cache question, not a selection question. Sub-levers: (a) target restore hit rate and `compat` stability (a `compat` change orphans the whole line — `docs/rust-ci-cache-keys.md` Compat section); (b) MBX shared-store hit rate on PRs (seeded, not shared — measure before promising); (c) the 7-day base expiry forcing cold `plan --full` runs (R:194-204). *Saving:* bounded by the compile share of `rust-root` (371 s P50 on push); a warm hit is the difference between that and the goals target “0 crates compiled” for an unchanged tree. *Measure:* `velnor-ci report` compiled-vs-should-have-compiled counts; `Cache` job waste reports; MBX file/byte/second logs from `mbx-seed`.

**L5 — Shape: earn a second job only when it pays (timings file + groups).** `shape = auto` cannot leave `one-job` without `.velnor/rust-ci-timings.json` (`crates/velnor-rust/src/shape.rs:18-59`; `SECOND_JOB_COST_SECONDS = 5`, sharding off). Writing the timings file (`velnor-ci timings --repo`) lets `lint-test` or `groups` split the long pole *if* the split saves more than the second job’s start-up (goals rule 5). `[[test_groups]]` and the merged `[[workspace_groups]]` (#1274, `crates/velnor-rust/src/groups.rs`) are the tools; `velnor-gen suggest-groups` proposes groups from timings. *Saving:* critical-path reduction on the heaviest roots only — for this single-root workspace, likely small; for multi-root consumers, the main structural lever. *Measure:* `velnor-ci timings` medians (≥3 runs) before; run wall after; never split on a guess (goals.md:44: every speed claim has a measurement).

**Explicitly not levers (yet):** a native executor (off the verdict path once the ledger lands — architecture §1.1: “the executor is off the verdict path; an executor claim needs its own race”); RustFS/storage tiers (no verdict waits on them until ST06 passes); high-clock nodes (D20, benchmark-only until BM15 measures ≥1.15×).

## 8. Be ambitious

What a generator-first foundation makes possible that the old design — written against a 39-job engine workflow with logic in YAML and a ledger bolted on afterwards — did not imagine. Ordered by hardness, not by ease.

### 8.1 The generator emits the verification contract itself

Today velnor-gen emits *workflows*; the verification contract (what must pass, in what order, with what test inventory) is implicit in the YAML and reconstructed at run time by `velnor-ci gate` from `needs` JSON. A generator-first design inverts this: `velnor-gen` emits, alongside `rust-ci.yml`, a signed **obligation inventory** — the typed list of checks (from `WorkflowPlan` steps), each with its `VerdictKey` fields, its expected test IDs (from the plan’s `tests_expected` logic, `crates/velnor-rust/src/required_job.rs:149`), and its reuse class. The inventory is generated from the base commit by a released generator (goals rule 12 already guarantees the *plan* comes from a released version; extend the guarantee to the *contract*). Consequences the old design could not get: the App (`velnor-control`) verifies against a document it can diff, not a workflow it must interpret; a PR that drops an obligation fails by inventory comparison (C3) without running anything; `velnor-gen check` (Item 4) grows from “workflow is fresh” to “workflow *and contract* are fresh”. The hard problem is canonicalisation — the inventory must be byte-stable across generator versions that mean the same thing, or every generator release re-verifies the world. `CacheKey::layout()` is the seed; budget the canonical-form work honestly.

### 8.2 Verdict keys computed at plan time, not reconstructed at gate time

The gate today reconstructs intent from job outputs after the fact. With keys at plan time (§2.1), the run becomes a *lookup with executions for misses*: `velnor-ci plan` prints, before any cargo runs, the full key set, which are hits, which need one witness, which need two, and which are C5-fresh (clock/network/event readers that always run). That one change gives three things the old design wanted but could only approximate: (a) `velnor resolve` (UX §5) becomes a real dry-run — “what would the label do?” answered from the plan alone; (b) scheduling becomes optimal in a way a job graph cannot be — witnesses are placed on different nodes *because the keys say they are independent*, not because YAML `needs` happened to allow it; (c) flake accounting gets a denominator (keys attempted vs keys reused) instead of a vibe. The hard problem is key completeness (C2): a key that omits an input is a false-green machine. The design’s answer — whole-tree keys until an enrolled contract narrows one, read audits that can only *narrow* with evidence, epochs revoked on first disagreement — is right, but the read audit (V07, eBPF/LSM on the node agent) is the least-proven component in the entire plan and should be treated as research, not engineering, until it reproduces the trimmed-sandbox failure (architecture C2: a trace-keyed lookup passed a tree where 12/40 fresh runs fail) and explains it.

### 8.3 One plan, three drivers: local agent, PR gate, cluster

Because the plan is typed data (`WorkflowPlan`), the same value can drive: the cluster gate (App + dispatcher), a PR’s Actions run (today’s path, kept until cohorts move), and an agent’s local run (`velnor verify` on the Docker backend via `velnor-local`’s pair mode). The old design treated local mode as a *simulation* of GitHub (runner.server, cache emulator) whose results were advisory by construction. A generator-first design treats local as *the same obligations on a different platform capability set*: whole-tree keys on Docker (no read audit), per-package keys where the audit exists, trust tier from the signer, records that the label can consume as candidates. `velnor-local`’s conformance corpus then stops being a Mac curiosity and becomes the per-backend acceptance test (P06) that every new platform must pass. The hard problem is identity: a local record must never be promotable to trusted by accident — signer class in the key, candidate namespace, and A1 as the only promotion path. Get that wrong and `velnor verify` is a false-green printer.

### 8.4 A generator-owned benchmark

The delivery plan’s BM stream rents comparators and replays traces — necessary, but it measures *runners*. A generator-first benchmark measures the *generator*: for a corpus of real repositories (starting with velnor-lab and velnor-new itself), generate the workflow, run it, and score the generator’s decisions — shape chosen vs shape optimal in hindsight, selection precision (crates compiled vs crates that changed), cache-key stability across version bumps, delta hit rate, timings-file accuracy. `velnor-gen` already has the harness shape: golden samples (`generator/samples/<name>/` → `expected_with_notes` diff, A§1.4), `record-sample` from a real checkout, and `velnor-ci bench/timings` for the run side. A nightly “generator benchmark” that fails when a generator change makes any corpus repo slower — with the raw data committed, per goals rule 14 — is the regression gate the speed work currently lacks (`docs/rust-ci.md:114`: no merged check compares wall time with a limit). The hard problem is corpus honesty: a benchmark the generator’s authors curate will drift toward repos the generator is already good at. Include one repo the generator handles badly, forever, as the canary.

### 8.5 The queue as a speculation engine (not just a gate)

With keys at plan time, the merge queue stops being a serial re-verification and becomes a predictor: when a PR is labelled, the system already knows the queue-tip tree it will likely merge into; verifying *that* tree speculatively (charged as speculation in runner-minutes, cancellable without record pollution) turns the enqueue into a lookup for the common case. The design gestures at this (V10 queue-tip speculation; UX §4 “resolved merged with the queue tip”); the generator makes it precise, because the speculative key is *computable before the group exists*. The hard problems are real: speculation multiplies flake exposure (every speculative failure must be distinguished from a group failure, or agents learn to ignore reds), and queue-tip prediction under churn (62 enqueues in one hour pre-cutover, C§1) can waste more than it saves. Measure the prediction hit rate on the revived queue (Item 5) before building the engine; if HEADGREEN-era churn persists under ALLGREEN, speculation is a tax, not a lever.

### 8.6 Deleting GitHub from the verdict path — and knowing what that costs

The end state (PR and group verdicts with no Actions run; one App status) removes GitHub’s queue wait, run creation, and job scheduling from the critical path. It also removes GitHub’s *independent* observation of the verdict: an Actions `Required` is witnessed by GitHub’s scheduler, log store, and retention in a way an App status is not. A generator-first design can buy that independence back *in the generator*: the obligation inventory (§8.1) is committed (or its digest is), the receipts name the generation compiled over, and A1’s cold audit is scheduled by a different code path than the gate that wrote `success`. The ambitious version goes further — the generator emits the *audit plan* too (which obligations A1 re-runs cold, on what sampling schedule), so “who watches the watcher” is a generated, reviewable artefact rather than a service’s internal policy. The hard problem is operational, not technical: when the App is down, nothing merges (by design), and D15’s break-glass path is the only door. That door must be drilled — run the break-glass verifier monthly on purpose, or it will not work the one time it is needed.

### 8.7 What not to be ambitious about

Do not be ambitious about: a second storage system before ST06 proves RustFS beats `local` on the real workload; a merge train (D18) before 50–200 queue merges quantify GitHub’s 45 s share; per-test-case receipts (AN09 stretch) before per-package keys graduate; or a native executor for job types whose verdict is already a lookup. Ambition spent where the generator already made the problem cheap (keys, contracts, benchmarks) compounds. Ambition spent re-platforming things that are not on the critical path is how the old plan got to 174 items with the gate still red.
