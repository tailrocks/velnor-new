## 0. Executive summary (the facts that matter most)

1. Three generator-owned workflows and one generator-owned cleanup workflow are live: `rust-ci.yml` (from `.velnor/rust-ci.toml`), `rust-cache-trim.yml` (derived from the same plan), `qualification-gen.yml` (from `.velnor/workflows.toml`). Each carries `# Generated by velnor-gen.` plus a `# velnor-gen-sha256:` digest of the body (R:1-2; `C/velnor-render/src/header.rs:23-45`). The other three workflows are not generated by velnor-gen: `ci.yml` (hand-maintained, 4 lint jobs), `release-rust-ci-tools.yml` (hand-written), `qualification.yml` (old engine, "Velnor Actions 0.1.82").
2. On a pull request this repo runs ONE big job, `rust`, not a graph. `shape = auto` with no `.velnor/rust-ci-timings.json` resolves to `one-job` (R:32; `C/velnor-rust/src/shape.rs:28-33`). Lanes are steps, not jobs (31 `Check <crate> alone` steps, R:214-306). The job graph is `rust` -> `policy` -> `Required`, plus `Cache`, `ci-run-label`, and (default branch only) `Cache maintenance`.
3. `pr_ci = "label"` (`.velnor/rust-ci.toml:10`): a ready PR gets only the "quick set" (plan, Format, Lint, policy). Tests run only when a maintainer adds `ci:run` (one run, label auto-removed) or `ci:auto` (every push). Drafts run nothing; `Required` passes with a notice. Fork PRs never get the full suite from a label; it runs in the merge queue.
4. Required check name is `Required` (`rust-ci.toml:6`; R:631-672). It is a hand-rolled gate (`velnor-ci gate`) over `needs` JSON, not a plain `needs`. `ci.yml` jobs (Alint, Cargo Deny, Cargo Machete, Jactionlint) are separate checks. Whether they are in the GitHub ruleset is NOT knowable from the repo.
5. Selection is the Rust library `velnor_rust::select` (`C/velnor-rust/src/select.rs`) shared between generator and the runtime helper `velnor-ci plan` (`C/velnor-ci/src/io/plan.rs:37-90`). It reads recorded metadata from `.velnor/rust-metadata.json`, never runs cargo at plan time, and fails closed to "select everything".
6. Caches: four families (`tools`, `sources`, `target`, `delta`). Only push/schedule/dispatch on `main` writes tools/sources/target. PRs from this repo write only a per-PR delta layer (#1107, shipped in helper 0.1.95, pinned at #1742). No sccache. MBX (`mbx`, the cargo wrapper in `mise.toml:44-46`) is the compiler-level store; `mbx_shared_store = true` and a node-local `tools-local` store, plus a crates mirror, all self-hosted-only.
7. Release of the tools is a separate, rebuild-from-source flow: release-plz bump PR -> `tools-v<ver>` tag -> `release-rust-ci-tools.yml` rebuilds both binaries (musl, 2 targets, hosted runners, no cache) and creates a pre-release -> a human/agent runs `velnor-gen pin-helper` and regenerates. Nothing from main's CI is reused by release, and the release gate only checks "commit is an ancestor of the default branch", not that `Required` passed (goals.md:77 says it should).
8. Result reuse across PR / merge queue / push-to-main / release: none at the verdict level. Content-addressed reuse exists only below the verdict (cargo fingerprints + restored mtimes, MBX CAS, delta source identity, helper digests). The one "prior run lookup" that exists (`velnor-ci merge-group-passed`, config `[ci] skip_push_after_merge_group`) is OFF in this repo.
9. Old engine: 12 `velnor-actions-*` crates are still workspace members and are still built and tested by the new CI (R:405-436 lists them). Its Rust-CI lanes, product-release, source-preview, state-seal, etc. were deleted in #1523, #1550, #1420; deletion continues under #608/#1433/#1459. What still touches CI: `qualification.yml` and `.velnor/config.toml`/`generator.lock`.
10. docs/goals.md sets hard targets (section 8 below). Notable gaps against them as built: release gate (rule 13), two duplicated policy lanes (ci.yml and rust-ci `policy`), `Cache` check advisory, no wall-time check wired (`docs/rust-ci.md:114`), no `[budget]` table in this repo's config.

### 1.2 Pipeline (input -> files)

1. `velnor-gen generate|check` (`C/velnor-gen/src/io/mod.rs:174-196`): `toplevel(root)`, list `.github/workflows/*.y*ml`, `read_view()` builds a `RepoView` of exactly the files the generator may read (`velnor-rust::wanted_files`, `C/velnor-rust/src/detect.rs:30-70`: `.velnor/rust-ci.toml`, `.velnor/release.toml`, `.velnor/workflows.toml`, `.velnor/rust-ci.lock`, `.velnor/rust-inputs.lock`, `.velnor/rust-ci-timings.json`, `mise.lock`, `rust-toolchain*`, mise configs, `.cargo/config*`, nextest config, every `Cargo.lock`, Rust sources, nested toolchains, release-plz configs) plus recorded `cargo metadata` reduced into `.velnor/rust-metadata.json`.
2. `expected_with_notes(view)` (`C/velnor-gen/src/lib.rs:77-105`): `detect(view)` -> `check_helper` -> `check_tools` -> source-root limit -> `plan_and_render` -> `reusable_workflows` -> delta cleanup workflow (only if the plan contains a `CacheSave(Delta)` step, `lib.rs:88-96`) -> `release::release_workflow` (only with `.velnor/release.toml`) -> notes.
3. `plan_and_render` (`plan_render.rs:15-40`): plan with deltas; if rendering exceeds 500 000 bytes (`velnor-render/src/lib.rs:114`) and the plan has delta steps, re-plan `plan_without_deltas` and emit a note. So the delta layer is the designated "relief valve" for GitHub's workflow size cap.
4. Output set: `.github/workflows/rust-ci.yml`, `.velnor/rust-metadata.json` (added in `generated_with_notes`, `lib.rs:43-52`), optional `rust-cache-trim.yml`, declared workflows from `workflows.toml`, optional `release.yml`.
5. `drift()` (`drifts.rs:52-80`) classifies each path as `Changed | Missing | Stale | Foreign | Unmarked`; `generate` refuses to proceed on a `Foreign` file (`io/mod.rs:189-191`) and otherwise `apply`s (writes + removes stale generator-owned files); `check` exits 1 and prints the drifts (`io/mod.rs:122-128`). Unmarked files are tolerated when `.velnor/config.toml` exists (`engine_configured`, `drifts.rs:75`, `io/workflows.rs:12`), which is the rule that lets `ci.yml` and `qualification.yml` coexist.

### 1.4 What it emits and how generated files are verified

- Header: line 1 `# Generated by velnor-gen. Change .velnor/rust-ci.toml and run \`velnor-gen generate\`.` Line 2 `# velnor-gen-sha256: <hex>` = SHA-256 of everything after line 2 (`header.rs:23-34` `seal`; `digest_verifies` `:36-45`). `rust-cache-trim.yml` has line 1 only (legacy undigested header accepted, `header.rs:47-62`).
- `owner_of()` (`header.rs:64-90`) returns `VelnorGen | Forged | Engine | Nobody`. "Forged" = marker present, digest wrong. The digest is unkeyed: it stops accidental copies and hand edits of generated bodies, not a deliberate forger (comment at `header.rs:20-22`). Engine markers are `# Generated by Velnor Actions ` / `velnor-actions ` (`header.rs:6-9`).
- Freshness checks that exist: (a) `velnor-gen check` (exit 1 on drift, `io/mod.rs:122-128`); the repo's PRs #1739/#1742 say it is run by out-of-repo scripts (`regen-main.sh`, `prepush.sh`; not in the checkout; "Opened by regen-main.sh" in #1739). I found NO step of any in-repo workflow that runs `velnor-gen check`: `StepKind::GeneratorCheck` is defined (`velnor-model/src/steps.rs:108`) and rendered (`velnor-render/src/steps.rs:285`, `helper_steps.rs:74-80`) but no planner constructs it (grep over `velnor-rust`: no hit). (b) `velnor-ci check-metadata` runs in every Rust lane after tools install (R:142-144) and fails unless `.velnor/rust-metadata.json` equals what `velnor-gen generate` would write for that root. (c) Plan-time: a changed `rust-ci.yml` selects everything (`AllTrigger::GeneratedWorkflow`, `classify.rs:68-69`).
- Golden tests: `crates/velnor-gen/tests/it/golden.rs` runs every `generator/samples/<name>/` (38 samples: `view/`, `manifests.txt`, `symlinks.txt`, `cargo-metadata/<root>.json`, `expected/`) through `expected_with_notes` and diffs; `UPDATE_GOLDENS=1` rewrites; `record-sample` records from a real checkout (`generator/TESTING.md:19-37`). `mise run lint-generator-samples` lints each `expected/` workflow with jactionlint (`mise.toml` task; CI job name "generator-samples" per TESTING.md:35). The sample `generator/samples/velnor-new` is a stale snapshot of this repo, NOT equal to the live `rust-ci.yml` (differs at least in `labeled` type and cron).
- Test isolation: `.config/nextest.toml:24-38` wraps `velnor-gen`, `-model`, `-release`, `-render`, `-rust` test binaries in `env PATH=/nonexistent`; 2 s per-test limit (`generator/TESTING.md:15-17`).
- Workflow rules enforced at render time (`velnor-render/src/rules.rs`): only 16 allowed actions, all SHA-pinned (`ALLOWED_ACTIONS`, `rules.rs:17-34`, pins `pinned_actions.rs`), each `run:` is one simple command (no `| & && || ; $( \` <( >(` and no `if/for/while/case/coproc`, `rules.rs:44-45`; <= 2000 chars), cache key <= 512 chars (`rules.rs:42`, `key_length.rs`), workflow <= 500 000 bytes. This is goals.md rule 9 made executable. Long shell lives in env-var-carried launchers (R:69-82, evaluated with `eval "$VAR"`; YAML anchors dedupe them `&velnor_0..3`, `yaml.rs:93-112`).

### 2.1 Triggers (R:4-19), draft and label handling

Every label event starts a run, but a run for a label other than `ci:run`/`ci:auto` has every job skipped (`github.event.action != 'labeled' || label in (ci:run, ci:auto)` in each job `if`, e.g. R:35, R:257) and gets its own concurrency group suffix `-ignored-<run id>` so it cannot cancel the real run (R:23). Docs: `docs/rust-ci.md:80-90`.

- Fork PRs: `runs-on` is an expression that picks `ubuntu-26.04-scale-set` when the event is not a PR or the head repo is this repo, else `ubuntu-latest` (R:57, same on every job). A fork PR gets the quick set only; `ci-run-label` is skipped for forks. `CONFIG.md:5-16` states the real boundary is repo settings (fork approval, runner group access), not this expression.

### 2.3 The plan (selection) - how `velnor-ci plan` decides

Where: first logic step of the job, after helper install and `mbx-store`/`mbx-seed`, before tools install (R:88-90): `velnor-ci plan --explain` (`velnor-ci/src/io/plan.rs:37-90`). Checkout is `fetch-depth: 2` (R:62-66, `PLAN_DEPTH = 2`, `velnor-rust/src/plan.rs:36`).

Algorithm (`io/plan.rs:37-161`):
1. `read_recorded_checkout` + `detect()` rebuild `RepoFacts` from the committed `.velnor/rust-metadata.json` and config (no cargo, no mise at this point). A wrong `default_branch` vs the event payload is a hard error (`event.rs:53-65`, goals rule 10).
2. Event kind from `GITHUB_EVENT_NAME` (`io/plan.rs:130-140`); `--full` or `schedule` => everything (`:49`).
3. `selects_by_diff` (`velnor-rust/src/select_event.rs:12-18`): PR: always by diff; push/merge_group: by diff only if `on_main = affected` (default; this repo); schedule/dispatch: never.
4. Diff base (`io/git.rs:12-79`): PR => requires `HEAD^2` to exist (the PR merge commit) and diffs `HEAD^1..HEAD` (`pull_request_base`; error "check out with fetch-depth: 2" otherwise); push/merge_group => event payload range (`before..after`, or `merge_group.base_sha..head_sha`, `event.rs:40-51`), requires base to be an ancestor of HEAD in the checkout. Any failure to establish a base prints the error and selects everything (`io/plan.rs:170-179`).
   - Inference (not verified by a run): with `fetch-depth: 2`, a multi-commit push or a multi-PR merge group whose base is deeper than HEAD^1 fails the ancestor check and therefore degrades to "select everything". Single-PR squash/rebase queue entries and one-commit pushes have base == HEAD^1.
5. `select()` (`select.rs:17-138`). For each changed path `place()`:
   - user `[[inputs]]` globs map to named packages; `non_inputs` map to nothing (`classify.rs:35-50`);
   - `Cargo.lock` of a root: `lock_affected(base, head)` compares old and new lock text and seeds only packages that reach a changed lock entry (`SelectionReason::Lock`), else `AllTrigger::WorkspaceManifest` (`select.rs:152-194`); a root `Cargo.toml` change selects everything unless only dependency versions changed together with the lock (`select.rs:119-122,196-205`);
   - files inside a package dir select it if under `src/ tests/ benches/ examples/`, equal to `build.rs`, or the package is "whole" (any file under a non-root-manifest member directory; `select.rs:91-106`); plus declared target sources;
   - then reverse-dependency closure: every dependent of a selected package, and every "unread" unowned package (path dep outside workspace), is seeded (`select.rs:73-86`);
   - whole-tree triggers (`AllTrigger`, `selection.rs:73-84`; `classify.rs:60-82`): `rust-toolchain(.toml)`, any Cargo config, root workspace manifest, the generated `rust-ci.yml`, `mise.toml/.mise.toml/mise.lock`, any `Cargo.lock` that cannot be diffed, `.velnor/rust-ci.toml`, `.velnor/rust-ci.lock`, `rust-ci-timings.json`, `rust-inputs.lock`, `rust-metadata.json`; plus `UnknownPath(path)` for any file the plan cannot place (fail closed), `BaseUnavailable`, `Event`, and `MostPackages` (more than half of members selected => everything, `selection.rs:51-62`);
   - ignored (select nothing) when `default_ignores = true` and not sheltered inside a package/root dir: `docs/`, `LICENSES/`, `.github/ISSUE_TEMPLATE/`, `.github/PULL_REQUEST_TEMPLATE*`, root `NOTICE`, `CODEOWNERS`, `LICENSE*`, root `*.md` (`classify.rs:22-27,84-97`). Note this repo maps `LICENSE`/`NOTICE` back to `velnor-actions-workflow-renderer` via `[[inputs]]` (rust-ci.toml:16-22) and `scripts/ci-fixtures.sh` to two packages.
   - `.github/workflows/ci.yml`, `qualification*.yml`, `release-rust-ci-tools.yml` are NOT whole-tree triggers: a change there is an unplaceable path => `UnknownPath` => selects everything (inference from `classify.rs:57`, `select.rs:132-136`; only exact `rust-ci.yml` has its own named trigger).
6. Outputs per root (`velnor-ci/src/plan.rs:19-63`): `rust_<slug>_mode` (`none|some|all`), `_packages`, `_test_filter` (`package(a) | package(b)` nextest expr or `all()`), `_package_args` (`-p a -p b` or `--workspace`), `_doctests`, `_doctests_known`, `_docs`, plus global `rust_deny`/`rust_machete` (`policy_runs`), `rust_<slug>_tests` (`tests_expected`), and per-group `rust_<slug>_group_<name>`. Root slug for `.` is `root`. `--explain` prints each selected package with its reason (`changed:`, `depends-on:`, `depends-on-unread:`, `input:`, `lock:`) or the `all:` trigger, plus "check does less" warnings for config weakenings introduced by the PR (`io/plan.rs:60-89`).
7. Doc/doctest/docs need: `optional_steps` reads sources (<= `SOURCE_LIMIT`) to decide whether doctests/docs steps exist (`io/plan.rs:92-128`).
8. Replan: after cache restore, `velnor-ci restored` may report `expired=true` (default-branch base older than 7 days, R:194-200); then `velnor-ci plan --full` runs and downstream steps read `steps.replan.outputs.* || steps.plan.outputs.*` (R:201-204, e.g. R:206). On the default branch an expired base forces a full cold run.

HD 11 caveat (`docs/hard-decisions.md:486-512`): lint, test build, nextest archive, doctests and `cargo doc` run `--workspace` (`cargo clippy --workspace` R:210, `cargo-nextest nextest run --workspace` R:324), while only test execution is narrowed by `-E "$TEST_FILTER"`; alone-checks and docs use `-p`. This was adopted because `-p` changes feature unification and defeats the cache. It bends goals.md promise 1 for doctests and lint scope (doc says so, `:508-510`). So selection narrows what RUNS (tests), not what COMPILES.

### 2.6 Merge queue and push-to-main specifics

- `merge_group: {}` is a trigger of both `rust-ci.yml` and `ci.yml`. Plan uses the group's `base_sha..head_sha`; `on_main = affected` default so a queue run is also a diff-selected run, and the whole-tree triggers and "unknown path" rule apply identically.
- Full suite on queue and on push, because `pr_ci = label` only throttles `pull_request` events (`CONFIG.md` "pr_ci" table).
- `docs = post_merge` and `check_alone = post_merge` drop `cargo doc` and the 31 `Check <crate> alone` steps from PR and merge-group runs; they run only after merge (push) and nightly (`CONFIG.md:96-101`). Reason given: MBX keys rustdoc on the whole workspace source tree, and alone-checks use a different feature set so rarely hit cache.
- `skip_push_after_merge_group` is NOT enabled (see 5). So the push to `main` that follows a queue merge repeats the plan and the tests.
- Merge queue cache access: `merge_group` runs restore base caches (scope reads the default branch) but never read PR delta scopes (`docs/rust-ci-cache-keys.md:61`) and never write.
- Private-token rules for merge queue exist (`velnor-ci private-token-allowed`, `rust-ci.md:102`) but this repo has no `private_sources`.

### 3.1 Keys and families (`docs/rust-ci-cache-keys.md`, `velnor-model/src/cache.rs`, `velnor-render/src/cache.rs:20-61`)

Single typed source of key text: `CacheKey::{Tools, Sources, Target, Delta}` rendered by `render_key`; every part that changes between commits is a GitHub expression, so dependency bumps change no workflow byte.

| Family | Exact key (as rendered in R) | Restore fallbacks | Path | Saved by |
|---|---|---|---|---|
| tools | `velnor-tools-${{runner.os}}-${{runner.arch}}-mise2026.11.10-${{hashFiles('mise.lock')}}` (R:108) | none | `~/.local/share/mise`, `~/.rustup` | default branch, on miss only (R:129-137); first the node-local `tools-local` store (R:94-99, R:124-128) |
| sources | `velnor-src-<host>-all.roots-<hash of all Cargo.lock>` (R:160) | `velnor-src-<host>-all.roots-` (R:161) | `~/.cargo/registry/{index,cache}`, `~/.cargo/git/db` | default branch, only when `cache decide` says `sources=true` and all deps are proven public; after `velnor-ci sources fetch --roots .` (R:374-394) |
| target | `velnor-tgt-rust.root.<host>-<compat>-<lock_root>-${{github.sha}}-${{github.run_id}}` (R:168, R:367) | `...-<compat>-<lock_root>-` then `...-<compat>-` (R:169-171) | `target` | default branch push/schedule/dispatch when `cache decide` says `save=true` (>= 1 crate compiled/checked/documented; build dir < 8 GB budget) (R:353-367) |
| delta (PR layer, #1107) | `velnor-dlt-pr<PR>-rust.root.<host>-<compat>-<base8>-${{github.run_id}}` (R:184) | `...-<base8>-` (R:185) | `target.velnor-delta` | same-repo PR, after the last compiling step, only if `delta stage` says `save=true` (R:438-444) |

- `compat` = first 16 hex of SHA-256 over `schema`, `rustc -vV`, target, CI profile env, repo `[profile]` tables, image, RUSTFLAGS, workspace path, build driver (`docs/rust-ci-cache-keys.md:65-71`; `velnor-rust/src/compat.rs`). `COMPAT_SCHEMA` is bumped by hand.
- `lock_root` (helper >= 0.1.86): SHA-256 of `Cargo.lock` with workspace-own path-package versions blanked, so a release version bump does not move the key (`docs/rust-ci-cache-keys.md:16-22`; `velnor-rust/src/lock_key.rs`).
- Target keys carry commit + run id so the exact key never hits; restore always takes the newest entry with the same lock hash, else same `compat` (GitHub prefix semantics; emulated in `velnor-cache-rules/src/lookup.rs:33-39`: exact, else newest by `created`).
- `base8` = first 8 hex of SHA-256 of the target restore's actual `cache-matched-key` (`velnor-ci delta prepare`, R:172-177): a delta is valid only against the exact base it was staged from.
- `VELNOR_BASE_MAX_AGE_DAYS = 7` on the default branch (R:198): an older restored base is dropped, the run builds cold and selects everything (`restored` + `plan --full`, R:194-204).

### 3.2 Isolated PR build deltas (#1107, shipped in helper 0.1.95, pinned by #1742)

Commit `7f16e1fe15` "feat(cache): reuse isolated PR build deltas (#1107)": "A second push to the same PR must reuse what its first push compiled. PR-written build artifacts must never reach main or another PR."
- Flow on `pull_request` from this repo (R:172-190, 396-444): restore Target (read from default-branch scope) -> `delta prepare` (compute `base8`, source identity, check tracked paths) -> restore the PR's own delta (`restore-keys` limited to same PR and same base) -> `delta apply` (overlay cumulative delta, preserve mtimes, invalidate cargo fingerprints if the saved source snapshot differs; `docs/rust-ci-cache-keys.md:57`) -> `inputs restore` -> build -> `inputs save` + `delta stage` (only changed artifacts plus the effective input manifest; deletion records) -> `actions/cache/save` of `target.velnor-delta`.
- Guards (`docs/rust-ci-cache-keys.md:55-63`; `CONFIG.md:41-43`): helper >= 0.1.95 and default target dir only; no delta steps when `private_sources` exist; forks restore only; a run that compiles nothing saves nothing; staged payload > 500 000 000 bytes saves nothing; cold run with no matched base saves nothing; main and merge-group never restore or save deltas; lane jobs have no `actions: write`.
- Cleanup: `rust-cache-trim.yml` (`workflow_run` of "Rust CI" completed; `permissions: {}`; job `rust-trim` with `actions: write`; no checkout; runs only for same-repo `pull_request` runs of `.github/workflows/rust-ci.yml`; `velnor-ci cache trim-deltas --run-id`; per-PR concurrency group, no cancel; `rust-cache-trim.yml:1-33`). It keeps the newest delta per lane/root/host. Note: this is a `workflow_run` workflow, so it runs from the default branch's copy (`jactionlint ignore=dangerous-triggers`, line 4).
- Target "as saved on main": "Build the tests" prebuild step (R:307-309) exists solely so the saved target holds nextest test binaries (`docs/rust-ci-cache-keys.md:32`). PRs only restore.
- Measured effect: none recorded. #1742 says "No timing measured". No in-repo benchmark of the delta.

### 3.3 Save budgets and trim

- `cache_budget_bytes = 8000000000` (default and maximum, `docs/rust-ci-cache-keys.md:135`; R:358, R:630). `velnor-ci cache decide`: save only if the build dir alone fits the budget (`velnor-rust/src/cache_budget.rs`). `Cache maintenance` (default branch only) runs `cache trim` per family (keeps the two newest entries per key group), `cache verify` (exact entry on the saving ref; catches upload errors the pinned action only warns about), `cache check`, then `cache budget` (deletes closed-PR deltas always; while over budget: deltas idle >= 3 days, Target/Sources beyond newest two, Tools idle >= 7 days except newest per host, remaining deltas by access time). Deleted-first rule: a Target entry whose compat family is not that of the newest entry for the same job/root/host/ref (`docs/rust-ci-cache-keys.md:141`). Sources entries restored in the last 24 h are never trimmed.
- Goals check: "Cache storage at most 8 GB of GitHub's 10 GB, pull request layers included" (goals.md:59) maps to `cache budget`, which only runs on the default branch (R:566-630); PR deltas between default-branch runs are bounded only by the 500 MB per-delta cap and the cleanup workflow.
- `Cache` job: `report --check` over `ci-metrics-*` artifacts fails when a crate compiled although the restored cache held it, or a save failed (goals rule 3). Advisory here.

### 3.4 crates mirror, MBX, sccache

## 5. Reuse / dedup as built

### 5.1 What is recomputed across contexts (this repo)

| Work | PR (ready, no label) | PR + ci:run | merge_group | push main | nightly | release |
|---|---|---|---|---|---|---|
| plan (diff) | yes | yes | yes (new range) | yes (new range) | yes (--full) | n/a |
| fmt + clippy `--workspace` | yes | yes | yes | yes | yes | n/a |
| nextest (selected pkgs) | no | yes | yes | yes | yes | n/a |
| doctests | no | yes (if any) | yes | yes | yes | n/a |
| cargo doc, 31 alone-checks | no | no | no | yes | yes | n/a |
| deny + machete | yes | yes | yes | yes | yes | n/a |
| ci.yml alint, deny, machete, jactionlint | yes | yes | yes | yes | no | n/a |
| compile of the shipped binaries | no | no | no | no | no | full cold rebuild per target |

- `ci.yml` and `rust-ci.yml` both run cargo-deny and cargo-machete (`ci.yml:68-134` and R:540-546 via `policy`), on the same events: duplicated work. They have different semantics (`ci.yml` machete passes explicit crate paths; `policy` runs `cargo machete` at root).
- `policy` is serialised behind `rust` (`needs: rust`, R:466-469), so deny/machete wait for the whole build+test instead of running in parallel (inference on cost: on a PR it adds the wall time of `policy` setup after `rust`).
- No result of a PR run is consumed by the merge-queue run, or the push run, or release. A merge-queue run on `main`'s next commit recomputes lint/tests for the same diff, and the push run after a fast-forward merge recomputes again.

### 5.2 Digest/content-addressed mechanisms that DO exist

1. Helper binaries: archive SHA-256 in the lock and action inputs; binary SHA-256 re-checked at each invocation (R:71-82).
2. Generated-file body SHA-256 (R:2).
3. `compat` hash, `lock_root` hash, `sources_locks` hash (`hashFiles` of every `Cargo.lock`), `base8` of the matched base key: all in cache keys.
4. `velnor-ci inputs save/restore`: `target/.velnor/inputs.tsv` records, for every tracked file, blob id of the bytes on disk, mtime (ns) and mode; `restore` resets mtimes of files whose bytes did not change so cargo's mtime-based fingerprints hit; `restored` assigns distinct times to files sharing one (`docs/rust-ci.md:63`, `docs/rust-ci-cache-keys.md:38,57`). This is the mechanism that makes a restored `target` usable on a fresh checkout.
5. Delta source identity: digest of the full tracked source snapshot bound to the saved records (`delta stage` / `apply`, `docs/rust-ci-cache-keys.md:57`).
6. MBX's own content-addressed action results (CAS) in the node store (see 3.4).
7. `velnor-ci inputs audit` + `.velnor/rust-inputs.lock` (path<TAB>package for files read at compile time, `rust-inputs.lock`): a content-input map to improve selection, verified on schedule/dispatch/expired base.
8. Release assets: `SHA256SUMS`/`BINARY-SHA256SUMS`/`COMMIT` (4.1).

### 5.3 The only "prior-run lookup" in the new stack

`velnor-ci merge-group-passed` (`C/velnor-ci/src/merge_group.rs:46-86`), config `[ci] skip_push_after_merge_group = true`, helper >= 0.1.82 (`helper_gate.rs:33-39`): on a `push`, ask the Actions API for a completed successful `merge_group` run of the same workflow file with `head_sha == GITHUB_SHA`; write `skip=true` only on proof; every error path writes `skip=false` ("Never fails: whatever it cannot establish means run everything", `merge_group.rs:46-47`). When true: Format, Lint, Documentation, alone-checks, test setup, tests, doctests skip (`velnor-rust/src/merge_group_skip.rs:8-55`, `is_check` set; the asker step is inserted right after `Plan`, and job gets `actions: read`); cache-warming builds and every cache save keep running; the gate accepts "no test counts" only for `event == push && skip_push == 'true'`. NOT enabled in this repo, so none of it applies to rust-ci.yml today (grep: R has no `merge-group-passed`).

## 8. What docs/goals.md sets (targets, rules, promises)

(Changing it needs the owner's explicit approval, `goals.md:3`.)

Promises (`:34-36`): 1. nothing to do means nothing runs (a run that selects no crate runs no Rust job); 2. work is never done twice (within a run nothing compiled twice for the same purpose; across runs nothing a warm cache holds is downloaded or compiled again); 3. fast never means checked less.
Never compromise (`:40-45`): 1 correct before fast (skip only when provably unaffected; unknown file => run everything); 2 green means verified (required check passes only when everything selected ran and passed; a test step that ran no tests is not a pass); 3 broken cache is slow, never wrong, never silent (red `Cache` check); 4 secrets never reach the build (short-lived scoped token revoked before project code runs, cargo offline, checkout stores no credentials, read-only `GITHUB_TOKEN`, PR writes only its own cache scope, fork PRs read only, nothing from private deps cached when forks can read); 5 every speed claim has a measurement (before/after numbers from real runs); 6 inside GitHub's free limits (10 GB cache, standard hosted runners).
Targets (`:51-61`; medians of >= 3 runs): no-crate-selected run: Velnor's own jobs <= 1 minute; select-everything-but-nothing-changed warm: 0 crates compiled, 0 downloaded; some crates selected warm: only those compiled and tested; second push to same PR warm: compiles only what changed since the first push; job start to first cargo command <= 30 s (cache restore included); job count does not grow with crate count; cache <= 8 GB of 10 GB incl. PR layers; ordinary PR vs previous version: wait for the required check and runner-minutes must not get worse (except a correctness check with measured, owner-accepted cost); generator's own tests < 1 minute.
Design rules (`:63-78`): 1 analyse then decide; 2 what a run selects (changed file read by a crate's build/tests/lint/docs selects it and its dependents; source/manifests/build scripts always; other files in the crate dir select it unless shown unread; toolchain file, cargo config, the workflow itself select everything; changed lock selects packages reaching a changed entry; docs/licence outside crates select nothing; any file it cannot place selects everything until mapped; scheduled run selects everything; push/merge queue per project choice); 3 the cache proves itself (`Cache` check red on cache waste/failed save; visible on every PR, does not block); 4 compile at most twice per configuration (metadata once for lint+docs, full once for tests; test binaries built once per configuration and handed to every test group); 5 the shape fits the project (one job per workspace by default; extra job only if it shortens the wait by more than its start-up; measured build/test times; reason written into the workflow); 6 test groups carry their needs; 7 no pointless steps and no silent ones (left-out steps listed with reasons); 8 a PR builds on its own last run (PR saves what it built; only that PR reads it); 9 no logic in YAML (every `run:` one command; actions only from a fixed SHA-pinned list; logic in one Rust helper shipped prebuilt); 10 configuration matches reality (e.g. default branch name; mismatch fails the run); 11 local first (verify on the developer's machine with the official runner started by the Velnor runner, local stand-in for GitHub, cache enforcing GitHub's rules); 12 proven on real projects (lab project `tailrocks/velnor-lab` first; this repo runs on its own generator; plan and required check always from a released version); 13 projects stay current (a new Velnor version reaches a project only after passing on the lab project; Velnor's own programs released only from a tag on a default-branch commit whose required check passed; the publishing job checks out nothing, runs no repo code, publishes files built by a job without write permission after checking digests); 14 decided by experiment (question, measurements and picking rule written before the first run; Project-level choices (`:82-91`): what a push/merge queue selects (default what the change selects), scheduled full run (default nightly), test groups (default one, split when long), workspaces sharing a job, sparse checkout (default off), receiving new Velnor versions (default merged automatically).
Review rule (`:95`): check the change against every promise/target/rule it can affect; "a target that gets worse needs the owner's acceptance"; then check one big crate, many workspaces, Docker tests, private deps, a large checkout.
