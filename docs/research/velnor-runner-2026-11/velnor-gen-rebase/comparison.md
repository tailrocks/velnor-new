## 1. Verdict table

| Model | One-line verdict | Single most important change (as the model states it) |
|---|---|---|
| OP | Design stands. velnor-gen makes the correctness half cheap. Runtime half (Native, ARC, RustFS) stays blocked by goals.md and is off the critical path | A strict phase-0 order. First make `Required` mean "this exact commit was verified": fix the preflight bug, then add a label mode in which `Required` is never green or skipped without a verdict. Then bind the ruleset, remove bypass, and turn on the queue and auto-merge |
| FA | Goals and core idea ("one verdict per tree, proven once, reused") stand. The build order does not | Move the centre of the plan from the runner to the generator. Ledger, keys, label flow and reuse are built first in `velnor-model`/`velnor-rust`/`velnor-ci` on the official runner. Native comes later and shrinks to a plan-manifest executor |
| AS | Design stands. The released generator defines *what must pass*, the runner proves it passed | First prove one green change through PR, a real ALLGREEN group and an audited landed SHA, under enforced protection, with a merge freeze until then |
| SO | Keep the goal (build and verify once, promote verified bytes) | Make the verification contract an *output of velnor-gen* (`VerificationContract`/`ObligationSpec`/`KeyRecipe`), shared by Actions and runners. First restore a real merge gate |
| MW | Design stands "as a destination, not a description of today" | Invert phase 0: green, non-bypassable `Required`, then a revived queue, then a label mode that makes an unlabelled PR unmergeable. Executor and storage work come only after that |
| MF | Centre stronger, sequence wrong | Move the verification contract into the generator. velnor-gen emits the obligation inventory and the verdict-key vector at plan time, digested like `rust-ci.yml`. The ledger caches generator obligations and is "never a second planner" |
| GN | Thesis stronger. Topology, phase 0 and layout are obsolete | Promote velnor-gen from YAML emitter to the single verification compiler: `RepoFacts → WorkflowPlan → ObligationInventory` drives YAML, the ledger and local `velnor verify` |
| GC | Core runner design holds. Old migration scaffolding is gone | "Architectural unification": velnor-gen is the sole compiler of the contract and emits `rust-ci.yml`, `.velnor/obligations.json` and the CLI check definitions in one `velnor_rust::plan` pass |
| GA | Architecture stands and is "dramatically simpler" | velnor-gen plus velnor-ci becomes the control plane and obligation compiler. Phase 0 becomes "stop bypassing a red gate and fix `pr_ci = label`" |

**Consensus readings.**

- (9/9) Correctness comes before speed, and phase 0 is now repair work, not the old ruleset-first sequence.
- (9/9) A generator-emitted verification contract is the main long-term idea. Six models (FA, SO,
  MF, GN, GC, GA) call it *the* most important change. The other three (OP, AS, MW) name a phase-0
  correctness order as most important and put the contract in section 8.
- (9/9) The `executor/` Cargo root and per-root keys are dead.

## 7. Where the panel as a whole is wrong or timid

1. **It planned against a frozen tip while the team kept shipping.** Within 33 minutes of
   `0eb2d76a5c`, the preflight fix, the alint/deny fix, the `skip_push` fix, the generated release
   workflow, 0.1.96, #1200 and #1026 all landed. #1770 (skipped `Required`) and #1777 are open now.
   Eight of nine answers schedule work that is done or in flight. The merged plan must be issued as
   issues that link these PRs, not as a document that re-plans them.

2. **Nobody named the systemic cause of red main.** The cause is helper/generator version skew.
   Red main has shown three faces:
   - At the tip: the preflight built by helper 0.1.95 is rejected by nextest 0.9.152.
   - At live head: the generator emits `inputs restore-all`, which pinned 0.1.96 lacks.
   - Also at live head: metadata goes stale after a manifest edit.

   `helper_gate.rs` checks feature minima, not that every rendered command parses under the pinned
   helper. OP's preflight contract test points the right way. The ambitious version makes the
   *pinned helper's CLI schema* an input to `velnor-gen check`, so a regen that the pin cannot run
   fails before merge. W1 above adds this.

3. **The panel is timid on trust in the gate itself.** Only OP, FA, AS and SO say plainly that a PR
   runs its own workflow and policy and can weaken its own gate. Under owner decision 8 (agents
   are trusted but fallible), that is the realistic false-green path once bypass is gone. A
   base-branch contract comparison (W10) is cheap with velnor-gen and should not wait for the App.

4. **Some answers are confident about numbers they never measured.** Not one test-running green
   verdict exists on the new shape. Even so:
   - GA gives "Day 1: 1.8/4.2 min".
   - GN tightens the goal to 60 s/3 min.
   - GC and GN price a 5-minute queue floor that GitHub's semantics say does not exist at
     `min_entries_to_merge: 1`.

   The only defensible targets are 4/9 and 9/20, labelled as trial budgets (AS, SO).

5. **Half the panel would have turned on an unsafe skip.** MW, MF, GC and GA recommend enabling
   `skip_push_after_merge_group`. At the tip that would have dropped docs and all 18 alone-checks
   for good. Reuse proposals need a golden-test rule ("skip only what the earlier run ran"), not
   a config flip.

6. **Three models put runner crates in the first ten while main is red.** GC, GN and GA schedule
   `velnor-platform`, `velnor-official` and storage crates. This violates the panel's own
   "correctness first" verdict and adds about 40–60 agent-hours of review load at the worst time.

7. **The panel is timid about the queue.** Whole-tree reuse from PR to queue rarely fires on a busy
   main (FA says so). Only FA goes further: its §8.7 has the label run test the PR rebased on the
   current queue tip. AS adds look-ahead. Nobody puts this in a first-ten item, although it would
   make the queue group a lookup and is the cheapest path to the 3/8 push-to-merge goal.

8. **Duplicate effort across panel members is not reconciled.** Sizes for the same ten items
   range from ≈44 h (OP) and ≈52 h (GC) to 142–242 h (AS). The spread reflects review overhead
   and lab rigour, not scope. The merged list (≈81 h) uses OP/FA sizing with AS/SO's lab gates
   only where GitHub semantics are in doubt (W2, W6).

9. **The brief's own facts were partly stale and most models did not correct them.** The brief

   corrected most of these. MW, MF and GN repeated some of them.
