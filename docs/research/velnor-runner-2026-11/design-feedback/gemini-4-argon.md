# Velnor runner architecture: design feedback (Gemini 4 Argon)

## Verdict

No. It keeps confidence on what runs, but it misses minimum push-to-merge time by deferring the dispatcher and ledger to weeks 6 to 20, keying Phase 3 receipts on whole-repository trees that miss 82% to 100% of merge groups, and leaving runner and engine PR verdicts at 4 to 6 minutes.
Ambition: 6/10. The design adopts late-binding `Runner.Worker` acquisition and content-addressed receipts, yet it stretches delivery over 20 weeks, spends 6 weeks tuning ARC, and leaves `Plan`, `Required`, and `velnor-runner-host` compilation on the critical path.
Soundness: 6.5/10. The 7-clause confidence contract (C1 to C7) is sound in principle, but eight concrete code and kernel contradictions in the draft would break releases on `main`, serialize parallel Cargo lanes, wipe reflinked `target/` snapshots during checkout, or crash lock renewal.

## Correctness and confidence holes

1. **[CRITICAL] Phase 1 push-skip (`I053`, Work Item 7) and Phase 4 Velnor-App `Required` check (`I013`, `N12`) break both release gates on `main`.**
   - *Evidence:* `ci-helper/crates/velnor-ci/src/gate.rs:66, 83-116, 127-159` (`velnor-ci release-gate`, executed by `.github/workflows/release-rust-ci-tools.yml:100`) filters workflow runs strictly by `run.event == "push" && run.head_sha == sha` (`gate.rs:137-138`) and requires every non-exempt required check (`Required` and `Required verdict`) to pass as a job inside a `push` run on `main`. If a check is marked `--pr-only-check`, `gate.rs:84-95` fails if it ever runs on `push`, and `gate.rs:236-240` fails if all required checks are exempt. Furthermore, `gate.rs:15, 277-288` hardcodes `const ACTIONS_APP_ID: i64 = 15368;` and rejects any required check bound to a non-Actions GitHub App (`"only a check from GitHub Actions (15368) can be tied to a push run"`). Likewise, `.github/workflows/product-release.yml:86` (`latest_ci_run` and `assert_required_job`) queries `.github/workflows/ci.yml` filtering strictly for `.event == "push" and .head_branch == "main"` and asserts a job named `"Required"` succeeded in that `push` run.
   - *Fix:* Before reducing the `push` run in Phase 1, either update `ci-helper/crates/velnor-ci/src/gate.rs:127-159` and `product-release.yml:86` to accept `run.event == "merge_group"` on the exact `head_sha`, or keep `plan` and `Required` running on `push` while `plan` short-circuits all build roots from the `merge_group` receipt in under 5 seconds. In Phase 4, drop `I013` (posting `Required` from a separate Velnor App id) and instead use `N06` (`velnor-dispatch` completing the `Required` job via Run Service `completejob` with no pod), which preserves `integration_id = 15368`.

2. **[HIGH] Retiring `mbx` (`I111`, §5.3) while converting `velnor-gen` steps to `background: true` parallel lanes (§6.1) either serializes on Cargo's `.cargo-lock` or triggers 32 GiB pod OOMs.**
   - *Evidence:* `docs/implemented/native-rust-crate-jobs.md:38-60, 74-105` documents that Cargo holds an exclusive flock on `<target-dir>/<profile>/.cargo-lock` for every build or check, and that `cargo clippy` and `cargo doc` require check-mode metadata that `cargo test --no-run` does not produce. In `generator/samples/velnor-new/expected/.github/workflows/rust-ci.yml:203-261`, `velnor-gen` runs `Format`, `Lint`, `Documentation`, 14 `Check <pkg> alone` steps, and `Test` sequentially against one `target/` directory. If `velnor-gen` marks them `background: true` without `mbx`: (a) sharing one `target/` serializes every parallel Cargo step on `target/debug/.cargo-lock` for zero speedup, while concurrent `cargo nextest` or `cargo test --doc` freshness checks race with rewrites; (b) giving each lane its own `CARGO_TARGET_DIR` without `mbx`'s cross-lane scheduler lets up to 10 concurrent background steps (`JobExtension.cs:525`) each spawn 16 `rustc` processes (`CARGO_BUILD_JOBS=16`, §7), running 64 to 160 `rustc` processes in one 32 GiB pod (single builds already peak at 16.8 GiB, evidence §B.2.2) and recompiling every modified crate independently per lane.
   - *Fix:* First, the warmer must populate `target/` with `cargo nextest run --no-run`, `cargo clippy --workspace --all-targets`, and `cargo doc --workspace --no-deps` before freezing the generation so all fingerprint types exist. Second, after checkout, `velnor-node` creates separate host-side XFS reflink clones (`target`, `target-clippy`, `target-doc`) in ~0.5 s each. Third, `velnor-ci` collapses the 14 `Check <pkg> alone` commands into one step and starts a pod-wide GNU Make jobserver FIFO (`CARGO_MAKEFLAGS="--jobserver-auth=fifo:/tmp/velnor-jobserver"` with 16 tokens) inherited by all parallel `background: true` steps, bounding total concurrent `rustc` processes across all lanes to 16 without `mbx`.

3. **[HIGH] Pre-job reflink cloning in Step 7 (§3.3) is wiped by `actions/checkout`, fails with `EXDEV` across container bind mounts, and misses 100% of fingerprints if warmer paths drift (§5.2, §5.3).**
   - *Evidence:* (a) In §3.3 steps 7 to 9, `velnor-node` reflinks the job directory before handing the message to `Runner.Worker`. When `Runner.Worker` runs step 1 (`actions/checkout@v7`, `rust-ci.yml:114`), `actions/checkout` deletes any non-git workspace directory before initializing, or runs `git clean -ffdx` (`clean: true` default), destroying any pre-populated `target/`. (b) §3.6 states build pods have *"no host paths except what the agent mounts read-only"*; in Linux `fs/remap_range.c` (`vfs_clone_file_range`), `ioctl(FICLONE)` returns `EXDEV` if source and destination file descriptors traverse different mount structs (`file_in.f_path.mnt != file_out.f_path.mnt`), even on the same XFS superblock. (c) `ci-helper/crates/velnor-ci/src/io/setup.rs:50` hashes `workspace: root.display().to_string()` into `compat`, and Cargo's `target/debug/.fingerprint/*` dep-info files embed absolute paths; if the `warmer` pod (§3.6) builds at a different path than `/home/runner/_work/velnor-new/velnor-new`, or does not run `velnor-ci inputs save` (`ci-helper/crates/velnor-ci/src/io/inputs.rs:19-64`), Cargo recompiles 100% of workspace crates cold.
   - *Fix:* Mount `/var/lib/rancher/velnor/sandboxes/<pod-uid>/work` as the pod's `/home/runner/_work`. Trigger the `target/` reflink **after `actions/checkout`** by having `velnor-ci` send a `CloneTarget` request over the agent Unix socket; `velnor-node` executes `FICLONE` on the host mount `/var/lib/rancher` (same `vfsmount`), and the `warmer` pod must build at `/home/runner/_work/<repo>/<repo>` and run `velnor-ci inputs save`.

4. **[HIGH] `velnor-gen` cutover (§6.1, Work Item 8) lacks fixture setup and pinned `mise 2026.11.1` required by `velnor-actions-cli` and `velnor-archive-guard`, and misdiagnoses the 89 s fixture step (§6.6).**
   - *Evidence:* `docs/implemented/ci-maintenance/repo-verification.md:88-142` and `crates/velnor-actions-cli/tests/image_publication_public/support/runtime.rs:133-148` show that `velnor-actions-cli` and `velnor-archive-guard` fail immediately unless `VELNOR_IMAGE_PUBLICATION_FIXTURE`, `VELNOR_QUALIFICATION_DIAGNOSTICS_FIXTURE`, and `VELNOR_QUALIFICATION_CLOCK_DRIVER` point to pre-built `--example` binaries (`test = false` in `crates/velnor-actions-cli/Cargo.toml:17-28`, so `cargo nextest` does not build them), and `check_runtime_identity_public` fails unless `mise@2026.11.1` (not `2026.11.9` as in `rust-ci.yml:146`) is first on `PATH`. None of these exist in `.velnor/rust-ci.toml:1-10` or `generator/samples/velnor-new/expected/.github/workflows/rust-ci.yml`. Moreover, §6.6 line 484 claims *"Engine PRs stay at 5 to 6 min until the image-publication fixture (89 s) and its suite are fixed"*, and `proposals/opus-5.5.md` §5.2 calls the fixture a network-reading step. In reality, `image-publication-fixture` (`crates/velnor-actions-cli/Cargo.toml:18-21`) is a purely local fake CLI binary; its 89 s step in `evidence.md` T10 was just `cargo build -p velnor-actions-cli --example image-publication-fixture` cold-compiling 218 crates before `Build test executables` ran.
   - *Fix:* Configure `[[test_setup]]` in `.velnor/rust-ci.toml` (`generator/crates/velnor-model/src/repo.rs:337`) to build the three `--example` binaries and export their canonical paths, align the `mise` pin, and include `--examples` in the warmer snapshot so fixture setup takes under 1 s and engine PR verdicts drop from 5 to 6 minutes down to ~60 seconds.

5. **[MEDIUM] Phase 3 exact-tree receipts (§4.1, §4.3) hash the whole repository tree, missing 82% to 100% of `merge_group` runs when `main` advances in an unrelated root, while Phase 4 binary-digest closure keys (§4.1, `N02`) defeat zero-pod short-circuit (`N06`).**
   - *Evidence:* Measurement `S4` (`decisions.md:23`) shows `0 of 40` merge groups on Nov 18 and `11 of 60` (18%) on Nov 16 to 17 had the same whole-repo base tree as their PR run. Keying Phase 3 receipts on the root Git tree hash means a merge to `main` in `generator/` or `docs/` invalidates the PR receipt for a PR that only touched `ci-helper/` or `crates/velnor-runner/`. Conversely, Phase 4's closure key (§4.1: *"the digest of the test binary + the digests of its declared runtime inputs"*) cannot be computed until a build pod starts, clones a 9 GB target, and runs Cargo to produce the test binary, making `N06` (completing the job in `velnor-dispatch` with no pod) impossible on moved bases and leaving `clippy`, `doc`, `fmt`, and `check-alone` uncovered.
   - *Fix:* Key Phase 3 receipts by each obligation's **Package Input-Closure Tree Digest**: the Merkle digest of the Git blob hashes of the package, its transitive workspace dependencies from `.velnor/rust-metadata.json`, its root `Cargo.lock`/`Cargo.toml`, its audited compile-time reads in `.velnor/rust-inputs.lock` (`ci-helper/crates/velnor-ci/src/cli.rs:214`), its declared runtime `[[inputs]]` in `.velnor/rust-ci.toml`, and the obligation definition digest. `velnor-dispatch` computes this key directly from the node's bare Git mirror in under 5 ms with zero pods, covering compile, lint, doc, and test obligations across 75% to 88% of merge groups.

6. **[MEDIUM] Transcribing `Runner.Listener/JobDispatcher.cs:748-852` for node-held lease renewal (§3.3 step 5, §3.7) copies an upstream `NullReferenceException` bug that aborts renewal on the first transient error.**
   - *Evidence:* In `actions/runner/src/Runner.Listener/JobDispatcher.cs:750-824`, the Run Service renewal loop `RenewJobRequestAsync(IRunServer runServer, ...)` leaves `TaskAgentJobRequest request = null;` unassigned when `runServer.RenewJobAsync` returns `renewResponse` (line 760), then dereferences `request.LockedUntil.Value` inside `catch (Exception ex)` at lines 810 and 823. Any transient network error after the first renewal crashes the renewal task with `NullReferenceException`. Also, `IRunServer` connects to `SystemVssConnection.Url` (`JobDispatcher.cs:1248`), not `RunnerJobRequestRef.run_service_url`.
   - *Fix:* In `velnor-node`, update `locked_until` from each `RenewJobResponse.LockedUntil` (seeded from `AgentJobRequestMessage.LockedUntil`), connect to `SystemVssConnection.Url` with `SystemVssConnection.Authorization.Parameters["AccessToken"]`, and persist `{plan_id, job_id, request_id, billing_owner_id, system_vss_url, job_access_token, pod_uid, locked_until}` in the sealed lease record.

7. **[MEDIUM] `Hot Worker` (§3.3 step 8, §3.5, `N05`) starts `Runner.Worker` before `.runner` exists and omits `.credentials`, dropping HTTP user-agent identifiers, suppressing runner identity logs, and spawning 5,040 .NET processes per hour.**
   - *Evidence:* `Runner.Worker/Program.cs:14` constructs `new HostContext("Worker")`, which calls `LoadDefaultUserAgents()` (`Runner.Common/HostContext.cs:222, 290-350`) **before** `Worker.RunAsync` waits on the pipe (`Worker.cs:54-63`). If `.runner` and `.credentials` do not exist when `Runner.Worker` starts, `HostContext.UserAgents` omits `ClientId`, `RunnerId`, and `GroupId` on all Run/Results/Launch service calls. When `JobExtension.InitializeJob` later runs (`Runner.Worker/JobExtension.cs:86-100`), omitting `.credentials` causes `credData == null`, skipping `Runner name:`, `Runner group name:`, and `Machine name:` output lines. Yet `.credentials` holds only the public `clientId` and OAuth URLs (`OAuthCredential.cs:27-40`); the private RSA key is in `.credentials_rsaparams` (`HostContext.cs:474-478`). Finally, replacing idle Workers every 25 s across 35 warm pods spawns 5,040 .NET processes/hour to save 45.4 ms of CLR startup (`proposals/gemini-4-carbon.md` §2 H1, log `134779761482`).
   - *Fix:* Write `.runner` and public-only `.credentials` (with `clientId` and no `.credentials_rsaparams`) at pod creation time. Either spawn `Runner.Worker` on job arrival (45 ms) or freeze the pre-started Worker's cgroup (`cgroup.freeze = 1`) after `channel.StartClient` and unfreeze (`cgroup.freeze = 0`) when delivering the job message, eliminating the 25 s respawn loop.

8. **[MEDIUM] Invoking mount-namespace enforcement through `nextest`'s `run-wrapper` (§4.3) relies on candidate-controlled `.config/nextest.toml` and pays 781 to 3,657 kernel mount-namespace teardowns per run.**
   - *Evidence:* `nextest` loads `run-wrapper` from `.config/nextest.toml` inside the candidate checkout (`local/.config/nextest.toml:8-11`, `generator/.config/nextest.toml:8-17`, where `generator` already sets `filter = "all()"` to `run-wrapper = "no-programs"`). Relying on candidate config to invoke the sandbox violates C3/C4. Furthermore, `nextest` executes `run-wrapper` once per `#[test]` case (781 in `velnor-ci`, 3,657 across `velnor-new`); creating and tearing down 781 to 3,657 Linux mount namespaces triggers kernel `umount` + `synchronize_rcu()` per test (~5 to 15 ms each = 4 to 55 s of pure kernel overhead).
   - *Fix:* Have trusted `velnor-ci` / `velnor-node` create **one hermetic mount namespace per test binary** (1 binary in `velnor-ci`, 1 in `generator`, 19 in `velnor-runner`) before invoking `cargo-nextest` (or the test binary), and compose any repo-defined wrapper inside that namespace.

## Where the design is too timid

1. **Running `Plan` and `Required` as pod-executed jobs in Phases 0 to 3 (§6.1, §6.6, `I013`, `N06`) instead of Dispatcher-Native In-Memory Execution.**
   - *What is timid:* Phase 3 (§6.6) still budgets `10 s` for `Plan` and `10 s` for `Required` inside pods, plus `30 s` for a receipt-satisfied `merge_group` run that executes zero obligations (§6.6 line 492). Decision `I013` keeps `Plan` as a pod job *"because only `completejob` can publish the outputs `needs` reads."*
   - *Bolder alternative:* `velnor-dispatch` acquires `rust-plan` and `required` via `acquirejob` and executes both in-memory in `<0.5 s` with **no pod and no `Runner.Worker`**, publishing `needs` outputs directly in `CompleteJobRequest.Outputs`.
   - *Mechanism:* Upon receiving `RunnerJobRequest` for `rust-plan` or `required`, `velnor-dispatch` calls `POST /acquirejob` and `POST /renewjob`, reads the commit diff directly from the node-local bare Git mirror via `libgit2` (`<20 ms`), runs `velnor_ci::plan` or `velnor_ci::required` against `.velnor/rust-metadata.json` and `velnor-ledger` receipts (`<10 ms`), uploads a 1 KB summary log to Results Twirp, and calls `POST /completejob` with `Outputs` populated (`RunServiceHttpClient.cs:123-146`).
   - *Expected numbers and arithmetic:* `Plan` drops from `10 s` (`54 s` today) to `0.4 s` (`2 × 120 ms` RTT + `30 ms` local compute); `Required` drops from `10 s` (`49 s` today) to `0.4 s`. That cuts `19.2 s` off every PR critical path and drops receipt-satisfied `merge_group` and `push` runs from `30 s` to **`3.5 to 5 s`** (`0.4 s` Plan + `2.5 s` GitHub DAG transition + `0.4 s` Required).
   - *Risk:* A panic or hang in `velnor-ci` could stall the dispatcher. Run `velnor-ci` in a sandboxed helper process with a 2 s timeout and fall back to a warm gate pod on failure.
   - *How confidence stays the same:* The exact pinned `velnor-ci` binary computes the plan and gate check from the exact Git commit SHA (`C3`, `docs/goals.md` rule 12), and GitHub Actions (`integration_id = 15368`) records the official job completion and outputs.
   - *Cheapest experiment (1 day):* In `velnor-lab`, write a 150-line Rust test using `velnor-runner-github` that acquires a job declaring `outputs:`, skips `Runner.Worker`, posts `CompleteJobRequest` with `Outputs`, and verifies a downstream job reads `needs.plan.outputs.*`.

2. **Discarding `merge_group` build outputs and running 5 post-merge batch warmers (§3.4, §5.3, `I030`, `I044`) instead of Seal-on-Build + Zstd Delta Broadcast + Atomic Promote-on-Land.**
   - *What is timid:* §5.3 forbids `merge_group` runs from preparing the next `main` snapshot (*"A merge group never writes it, because a merge group may never land"*), so after every merge all 5 workers independently wake up a batch warmer and recompile `main` 5 separate times (taking 35 to 170 s), leaving incoming PRs and back-to-back merge groups on a stale generation during the rebuild.
   - *Bolder alternative:* Harvest the `merge_group` (or speculative `M5`) post-build `target/` snapshot as `candidate/<tree-sha>` before tests run, multicast only its changed files (`zstd -1` delta against `trusted/<parent-tree>`) to the other 4 nodes while tests execute, and atomically rename `candidate/<tree-sha>` to `trusted/<tree-sha>` on all 5 nodes in `<1 ms` when `main` advances to `<tree-sha>`.
   - *Mechanism:* Because the build pod's `target/` is an XFS reflink clone of `trusted/<parent-tree>`, `velnor-node` identifies files modified during the build phase (before any test runs, §5.3), runs `velnor-ci inputs save`, freezes `candidate/<tree-sha>`, and streams the changed files (typically `50 to 300 MB` compressed out of `6 to 9 GB`) to the other 4 workers. Each peer applies the delta over a reflink clone of `trusted/<parent-tree>`. When the `push` webhook for `main` arrives with `<tree-sha>`, all 5 nodes verify the tree hash and promote `candidate/<tree-sha>` to `trusted/<tree-sha>` via atomic rename.
   - *Expected numbers and arithmetic:* Post-merge cache warming lag drops from `35 to 170 s` to **`<0.001 s`** (`100%` of PRs and consecutive merge groups start from the exact `main` tip). Cluster warming CPU drops by **`80%`** (1 build instead of 5 per merge, saving `4 × 1.5 = 6.0` cluster CPU-minutes per merge).
   - *Risk:* A merge group fails its tests or is evicted from the queue. Then `candidate/<tree-sha>` is never promoted to `trusted` and is unlinked on queue exit.
   - *How confidence stays the same:* `candidate/<tree-sha>` is harvested *before* tests run (§5.3) in the same unprivileged, network-isolated build sandbox as the warmer, and is promoted to `trusted` only after GitHub confirms `<tree-sha>` is on protected `main`.
   - *Cheapest experiment (2 days):* Time a 1-crate and 5-crate incremental build on `velnor-240`, stream the modified files in `target/` with `tar --zstd` to `velnor-241` over WireGuard, apply them to a reflinked base `target/`, and confirm `cargo check --workspace` compiles 0 crates.

3. **Deleting `target/debug/incremental` on local NVMe (`ci-helper/crates/velnor-ci/src/io/cache.rs:49`, §5.3) and accepting a 4-minute runner PR verdict (§6.6) instead of Keeping Reflinked Incremental Query Caches + Splitting `velnor-runner-host` (`I073`) + Consolidating Its 26 Test Binaries.**
   - *What is timid:* §5.3 adopts `velnor-ci cache decide` (`ci-helper/crates/velnor-ci/src/io/cache.rs:49, 90-131`), which deletes every `incremental/` directory from `target/` (a workaround for GitHub's 10 GB remote tarball limit), and §6.6 budgets `35 to 99 s` to rebuild the 156,822-line `velnor-runner-host` monolith after a 1-file edit (`4 min` PR verdict for the 33.5% of PRs touching the runner workspace).
   - *Bolder alternative:* Retain `target/debug/incremental` inside node-local XFS reflink snapshots (`CARGO_INCREMENTAL=1`) for PR and merge-group builds, split `velnor-runner-host` (`156,822` LOC) in Phase 2 into 5 domain crates (`velnor-runner-journal` 64k LOC, `velnor-runner-launch` 48k LOC, `velnor-runner-docker` 25k LOC, `velnor-runner-local` 12k LOC, `velnor-runner-host` 8k LOC), and consolidate its 26 separate integration test binaries (`crates/velnor-runner/crates/velnor-runner-host/tests/*.rs`) into 1 unified binary (`tests/it.rs`, matching `velnor-ci` and `velnor-gen`).
   - *Mechanism:* XFS reflinks clone unchanged `incremental/` CGU object files and `dep-graph.bin` in 0 data bytes and `<0.2 s`. Splitting `velnor-runner-host` isolates the 64k-line Turso journal crate so edits to `launch/` or `local/` skip re-typechecking `journal/`. Consolidating 26 integration test binaries into 1 eliminates 25 redundant `rust-lld` links of a 150 MB binary.
   - *Expected numbers and arithmetic:* As measured in `proposals/fable-5.2.md` §2 H4 (line 161), keeping warm `incremental/` drops a 1-function edit in `velnor-runner-host` from `82 to 99 s` down to **`10.9 s`** (`-71 to -88 s`). Consolidating 26 test binaries to 1 cuts link time from `26 × 1.8 s = 46.8 CPU-s` to `1.8 CPU-s`. Combined with crate splitting, runner-workspace PR rebuilds drop from `35 to 99 s` to **`6 to 11 s`**, cutting runner PR verdicts from `4 min` to **`45 to 60 s`**.
   - *Risk:* Rare `rustc` incremental query cache bugs. If `rustc` fails with an ICE, `velnor-ci` deletes `incremental/` and retries once with `CARGO_INCREMENTAL=0`; nightly full runs and release builds use `CARGO_INCREMENTAL=0`.
   - *How confidence stays the same:* The pinned `1.99.1` compiler executes the exact same typechecks, borrow checks, lints, and 430 `#[test]` functions (each still isolated in its own `nextest` process).
   - *Cheapest experiment (1 day):* On a worker node, benchmark a 1-file edit in `velnor-runner-host` over an XFS-reflinked `target/` with `incremental/` preserved (`CARGO_INCREMENTAL=1`) vs stripped (`CARGO_INCREMENTAL=0`), and with 1 unified test binary vs 26 binaries.

4. **Waiting for GitHub's 5 to 15 s job-offer pipeline before starting work (§6.6, `M1`, `N09`) instead of Webhook-Driven Pre-Execution on Every Push and Merge Group.**
   - *What is timid:* §6.6 accepts `5 to 10 s` of dead time waiting for GitHub to turn a push into a scale-set `JobAvailable` offer, plus `10 s` for `Plan`, before a build pod even starts cloning (`20 s` elapsed before compilation begins). `M1` treats push-webhook start (`N09`) only as a fallback if `push-to-offer P50 exceeds 20 s`.
   - *Bolder alternative:* Make **Webhook-Driven Pre-Execution (`N09`)** the default in Phase 3: `velnor-dispatch` subscribes to the repository's `push`, `pull_request` (`opened`, `synchronize`, `reopened`), and `merge_group` (`checks_requested`) webhooks (`~200 ms` delivery latency) and starts fetching, planning, building, and testing in a warm sandbox **5 to 15 seconds before GitHub's workflow engine even emits `JobAvailable`**.
   - *Mechanism:* On `pull_request` or `merge_group` webhook arrival, `velnor-dispatch` fetches the head SHA from GitHub into the node Git mirror, computes the merge tree (`git merge-tree --write-tree` against `base.sha` for PRs, or `head_sha` directly for `merge_group`), runs `velnor_ci::plan` in-memory, and launches the build/test obligations on the best node. When GitHub's `RunnerJobRequest` for `rust-plan` and `rust-<root>` arrive 5 to 15 s later, `rust-plan` completes immediately in `0.4 s`, and `rust-<root>` attaches to the in-flight execution (streaming buffered logs to Results Twirp) or short-circuits via `N06` receipt if already complete.
   - *Expected numbers and arithmetic:* Overlaps `100%` of GitHub's `5 to 15 s` push-to-offer latency and `Plan` job latency with real compilation and testing, shaving **`10 to 20 s`** off the critical path of every PR and merge-group run (bringing a 42 s median PR run down to **`22 to 30 s`** from `git push`).
   - *Risk:* If `main` advances in the 1 to 2 seconds between a `pull_request` webhook and GitHub creating `refs/pull/<n>/merge`, the merge tree computed against `payload.pull_request.base.sha` may differ from `refs/pull/<n>/merge`.
   - *How confidence stays the same:* Every receipt is keyed by the exact tree and Package Input-Closure Tree Digest (`C2`). When `acquirejob` returns the authoritative `AgentJobRequestMessage`, `velnor-dispatch` verifies the checked-out merge tree hash matches the pre-executed tree hash; any mismatch discards the pre-execution and runs against `refs/pull/<n>/merge`.
   - *Cheapest experiment (2 days):* Record webhook arrival timestamps vs scale-set `JobAvailable` timestamps and compare `git merge-tree --write-tree base.sha head.sha` against `refs/pull/<n>/merge` across 50 PR pushes.

5. **Stretching delivery over 20+ weeks and 6 sequential phases (§10) instead of a 4-Week Parallel Blitz.**
   - *What is timid:* §10 takes 6 weeks just to configure ARC and node snapshots (`Phases 0 to 2`), delays `velnor-dispatch` and `velnor-ledger` to weeks 6 to 12 (`Phase 3`), and pushes closure receipts, speculative merge queue, and receipt short-circuit to weeks 12 to 20+ (`Phases 4 to 5`).
   - *Bolder alternative:* Compress Phases 0 to 4 into **4 weeks** by running workflow/test fixes, XFS storage/warmer setup, and `velnor-dispatch` + `velnor-ledger` implementation in parallel across dedicated agent workstreams.
   - *Mechanism:* `velnor-runner-github` (`6,878` LOC) and `velnor-legacy/crates/velnor-runner/src/scaleset/` (`1,488` LOC) + `protocol.rs` already implement the Scale Set `6.0-preview` and Run Service wire types. Building `velnor-dispatch` (acquiring jobs, running in-memory `Plan`/`Required`, and handing `AgentJobRequestMessage` to `velnor-sandbox` + `Runner.Worker`) is ~3,000 lines of Rust, which one agent workstream can build and qualify on `velnor-lab` in Week 2 while another workstream lands the Phase 0/1 workflow, test-floor, and XFS snapshot changes in Weeks 1 to 2.
   - *Expected numbers and arithmetic:* Reaches `≤ 45 s` median PR verdict and `≤ 2.0 min` median push-to-merge in **Week 4 instead of Week 20**, saving 16 weeks (`~1,600` PR merges × `15 min` saved = **`400 hours`** of merge latency).
   - *Risk:* Concurrent changes to workflows and runner infrastructure could obscure the cause of a regression. Mitigate by qualifying `velnor-dispatch` on `velnor-lab` in Week 2 and cutting `velnor-new` over by label in Week 3 while keeping ARC live on its fallback label (§3.7).
   - *How confidence stays the same:* Every numeric phase gate (50 merges on `velnor-new`, zero obligation inventory diff in shadow mode, paired-rerun flake sampler) remains mandatory before flipping traffic.
   - *Cheapest experiment (3 days):* Time a focused agent building the minimal `velnor-dispatch` + `velnor-sandbox` + `Runner.Worker` bridge on `velnor-lab` using `velnor-runner-github`.

## The hardest problems

1. **Reusing verdicts across PR, merge queue, and `main` when `main` keeps moving (`0% to 18%` whole-tree match today), without trusting anything unproven.**
   - *Why it blocks a 1-minute verdict:* Measurement `S4` shows `0 of 40` merge groups on Nov 18 and `11 of 60` (`18%`) on quieter days matched the whole-repo tree their PR run tested, because other PRs merge while a PR waits. Whole-tree keys (`tree/<hash>`) miss 82% to 100% of the time; `fanotify` open traces miss `ENOENT` negative lookups and unexecuted branches; and Phase 4's compiled test-binary digest key (§4.1) still requires launching a build pod and running Cargo before a receipt lookup can happen (defeating `N06` zero-pod short-circuit and omitting `clippy`, `doc`, `fmt`, and `check-alone`).
   - *Concrete attack:*
     - **Package Input-Closure Merkle Keys:** Key every obligation (`fmt`, `clippy`, `doc`, `check-alone`, `test`) in `velnor-ledger` by the Merkle digest of its Git input closure: `H(package_tree, transitive_workspace_dep_trees, root_Cargo_lock, audited_compile_reads, declared_runtime_inputs, tool_pins, obligation_definition)`. `velnor-dispatch` computes this key directly from the node's bare Git mirror in `<5 ms` without starting a pod.
     - **Enforced Input-Closure Projection Mounts:** When `velnor-node` runs an obligation for package $P$ during the PR run, it constructs the sandbox's `/home/runner/_work/velnor-new/velnor-new` as a read-only bind/overlay projection containing **only** the repository files in $P$'s declared input closure (from `.velnor/rust-metadata.json`, `.velnor/rust-inputs.lock`, and `.velnor/rust-ci.toml` `[[inputs]]`). Any undeclared file is absent from the mount namespace (`ENOENT` to `open`, `stat`, `access`, and `getdents64`), turning the input closure from an assumption into a kernel-enforced proof (`C2`, `C3`).
     - **Speculative Queue-Wide Merge-Tree Pre-Verification (`M5`):** Whenever `main` advances or the merge queue updates (`max_entries_to_build = 8`), `velnor-dispatch` computes the cumulative merge trees $T_1 = \text{main} \oplus \text{PR}_1, \dots, T_k = T_{k-1} \oplus \text{PR}_k$ via `git merge-tree --write-tree` (`<15 ms` each). Disjoint packages (`75% to 88%` of obligations) hit the PR's existing Input-Closure receipt in `<1 ms`; any obligation whose input closure changed in $T_i$ is pre-executed immediately at batch priority. When GitHub creates the `merge_group` run, 100% of obligations already hold in `velnor-ledger` and `velnor-dispatch` completes the run via `N06` in **`3.5 to 5 seconds` with zero pods**.

2. **Breaking the 200 to 534 s test and compile floor so runner and engine PRs finish in under 60 seconds.**
   - *Why it blocks a 1-minute verdict:* `velnor-runner-host` compiles 156,822 LOC into 26 test binaries (`81 to 126 s`) and runs tests for `192 to 534 s` (pinned by `shape.rs:97-106`, burning `1.03 × 10¹²` instructions in `turso_parser` replaying 47 historical SQL migrations); `velnor-actions-cli` spends `89 s` building `image-publication-fixture` and `258 to 274 s` in one 40-case loop (`image_publication_public.rs:85-92`); `maintenance-helpers` takes `508 s` (`--config build.jobs=2` + 12 serial golden tests).
   - *Concrete attack:*
     - **Unroll the 3 serial test loops:** Split the 40-case loop in `crates/velnor-actions-cli/tests/image_publication_public.rs:85-92` into 40 `#[test]` functions (`~6.5 s` each), the 6-case loop in `crates/velnor-runner/crates/velnor-runner-host/src/launch/bootstrap/unbound_retirement/tests/shape.rs:97-106` into 6 `#[test]` functions, and the 4 `family_publication` tests (`115 to 136 s`) into per-case `#[test]` functions so `nextest` runs all cases in parallel across 16 threads (`274 s -> 15 s`).
     - **Eliminate Turso SQL parsing in tests:** Land PRs `#1333` (validate schema once per open) and `#1349` (cache historical-schema SQLite files), pre-bake the 52 historical journal database states as read-only template files cloned into `/tmp` in `<50 µs`, and set `[profile.ci.package.turso*]` (or `[profile.ci.package."*"]` for third-party deps) to `opt-level = 3` with `debug-assertions = true` and `overflow-checks = true` (`-66%` test CPU measured in `proposals/fable-5.2.md` §8a rank 4, with zero loss of assertion checks).
     - **Remove self-inflicted serialization:** Delete the 8 `--config build.jobs=2` and `--jobs 2` flags in `mise.toml:90-193`, replace `threads-required = "num-test-threads"` on the 12 `velnor-archive-guard` golden tests (`.config/nextest.toml:17-19`) with isolated per-test `TempDir` paths, and change `test-threads = 1` in `ci-helper/.config/nextest.toml:5` to `num-cpus` (`55 s -> 7 s`).
     - **Crush the `velnor-runner-host` compile floor (`81 s -> 9 s`):** Keep `target/debug/incremental` in local XFS reflink snapshots (`10.9 s` measured 1-file rebuild vs `82 to 99 s` without incremental), split `velnor-runner-host` into 5 domain crates, merge its 26 integration test binaries into 1 `tests/it.rs` binary (eliminating 25 redundant 150 MB links), and pre-build `--examples` in the warmer so `image-publication-fixture` takes `<1 s` instead of `89 s`.

3. **Zero cold start (`≤ 2 s` from assignment to first Cargo command) and cache-affine placement when GitHub hides job-to-runner bindings.**
   - *Why it blocks a 1-minute verdict:* `generatejitconfig` takes only `{name, workFolder}` (`evidence.md` §F.1.3) and GitHub assigns an acquired job to whichever idle runner polls the broker. Meanwhile, cold pods (`6 s`), `Set up job` (`4.9 s`), checkout (`6 s`), tool setup (`10 to 18 s`), and remote cache restores (`44 to 107 s`) burn `70 to 150 s` before Cargo starts.
   - *Concrete attack:*
     - **Centralized Broker Pool in `velnor-dispatch`:** `velnor-dispatch` registers $M$ idle JIT runner identities and holds all $M$ broker sessions in memory. When GitHub assigns a job to identity $I_k$, `velnor-dispatch` calls `POST /acquirejob` and `POST /renewjob` (`~250 ms`), inspects the authoritative `AgentJobRequestMessage`, and places the job on the node and warm pod with the lowest predicted finish time (`clone + delta_build + test`).
     - **Cgroup-Frozen Hot Worker (`velnor-sandbox`):** When an idle pod starts, `velnor-sandbox` writes `.runner` and public-only `.credentials`, spawns `Runner.Worker spawnclient`, lets it initialize the .NET runtime (`45 ms`) and connect to the pipe, and freezes its cgroup (`cgroup.freeze = 1`). On job hand-off, `velnor-sandbox` unfreezes the cgroup (`<1 ms`) and writes the UTF-16LE message (`<5 ms`).
     - **Zero-Network Setup + Host-Side XFS `FICLONE`:** Pre-seed `ACTIONS_RUNNER_ACTION_ARCHIVE_CACHE` (`0 s` action download), bind-mount `/opt/velnor/seed` (`rust 1.99.1` + `mise` tools, `<0.2 s`), borrow Git objects from the node's bare mirror via `/etc/gitconfig` `alternates` (`<0.5 s` checkout), and have `velnor-node` execute a host-side XFS `FICLONE` of `target/` (`~0.5 s` for 6 to 9 GB). Total time from job assignment to first Cargo command: **`1.5 to 2.0 seconds`**.

4. **Eliminating the 8.1% false-failure rate and 2.4× load stretch on a 5-node, 480-thread cluster shared by 3 organizations.**
   - *Why it blocks a 1-minute verdict:* `10 of 124` push runs failed on an already-green `merge_group` SHA (`8.1%`, `S1`), so two full runs per merge fail `15.5%` of merges falsely (`1 - 0.919²`), ejecting PRs and rebuilding the queue behind them. Under peak load, 40+ pods requesting `2 CPU` burst to `83.7 cores` (`evidence.md` §B.2.2), stretching `velnor-runner-host` from `3.7 min` to `8.8 min` (`§A T6`) and tripping `2 s` nextest timeouts (`ci-helper/.config/nextest.toml:11`).
   - *Concrete attack:*
     - **Hard Slot Admission + 16-CPU CCD-Aligned Pods + Pod Jobserver:** Size build pods to `16 CPU` (`request == limit == 16` or 16-CPU cgroup weight with max 5 build pods per 96-thread worker = 80 threads, reserving 16 threads for gate pods, `velnor-node`, and kubelet/system). Advertise `X-ScaleSetMaxCapacity` equal to free slots so bursts wait at GitHub in priority order (`merge_group > gate > pr > batch`). Inside each pod, pass `--test-threads = 16` to nextest (preventing 96-thread spawn storms) and share a 16-token GNU Make jobserver FIFO across all parallel background Cargo steps.
     - **Remove the 3 deterministic flake sources:** Snapshot `GITHUB_EVENT_PATH` before background steps (`I023`, eliminating `producer_event_invalid` when `ActionRunner.cs:141` truncates `event.json`), raise the `2 s` nextest `slow-timeout` in `ci-helper` and `generator` to `10 s`, and isolate the 12 golden tests' temp directories.
     - **10× Stress Gate on New/Modified Tests:** Whenever a PR adds or edits a `#[test]` function, `velnor-ci` runs that modified test `10` times (`cargo nextest run --stress-count 10 -E <test>`, `<2 s`) so new flakes are caught before merge. On `main`, the 5% paired-rerun sampler tracks per-test flakes and auto-opens an owner quarantine issue on 2 false failures in 7 days.

5. **Starting CI before `git push` (`≤ 10 to 15 s` post-push verdict) when agents work on macOS arm64 and CI runs on Linux x86_64.**
   - *Why it blocks a 1-minute verdict:* Local test runs on a developer or agent Mac (`arm64-apple-darwin`) cannot back a Linux (`x86_64-unknown-linux-gnu`) receipt and run outside Velnor's trust boundary (`M8`). Waiting until after `git push` forces the developer to pay GitHub's push, webhook, plan, build, and test latency sequentially.
   - *Concrete attack:*
     - **Automatic `velnor-ci preflight` in `scripts/verify-local.sh` and `pre-push` (`N07` pulled into Phase 3):** When an agent runs `scripts/verify-local.sh` (or `git push`), `velnor-ci preflight` exports a thin Git pack of the unpushed working-tree commits (`<50 KB` typical) to `velnor-dispatch` over HTTPS in `<150 ms`.
     - **Cluster-Executed Preflight Mints Trusted Receipts:** `velnor-dispatch` writes the objects into the node Git mirror, computes `main ⊕ commit`, and runs the selected obligations inside a normal isolated `build` pod on the Linux x86_64 cluster (offloading compilation and tests from the agent's Mac to the 480-thread EPYC cluster!). Because `velnor-node` starts and observes the test processes in the required sandbox class on Linux x86_64 (`C4`), it writes signed `pr/` and `closure_tree/` receipts into `velnor-ledger`.
     - **Zero-Pod Post-Push Short-Circuit:** When the agent's `git push` lands on GitHub seconds later, `velnor-dispatch` matches 100% of the PR's Package Input-Closure Merkle Keys in `velnor-ledger` and completes `rust-plan`, `rust-<root>`, and `required` via `N06` `completejob` in **`4 to 8 seconds` with zero pods started after the push**.

## Decisions you would overturn

1. **`I013` (Adopted-later, Phase 4: *"the Velnor GitHub App posts `Required` once every obligation holds... Plan stays a job, because only `completejob` can publish the outputs `needs` reads"*).**
   - *Why overturn:* First, `ci-helper/crates/velnor-ci/src/gate.rs:15, 277-288` (`velnor-ci release-gate`) rejects any ruleset required check whose `integration_id` is not `15368` (GitHub Actions), and `.github/workflows/product-release.yml:86` requires a completed job named `"Required"` inside the `ci.yml` workflow run. Having an external Velnor App post `Required` via the Checks API breaks both release gates. Second, `Plan` does not need a pod to call `completejob`: under `N06`, `velnor-dispatch` acquires both `rust-plan` and `required` and completes them in-memory via `POST /completejob` (`RunServiceHttpClient.cs:123-146`) in `<0.5 s` with `Outputs` populated and `integration_id = 15368` preserved.

2. **`I030` / `I044` (Adopted, Phase 2) and `I031` (Rejected: *"Only the warmer writes the trusted scope. A merge group never writes it, because a merge group may never land"*).**
   - *Why overturn:* Discarding the `merge_group` build output and starting 5 post-merge batch warmers wastes `4 × 1.5 = 6.0` CPU-minutes per merge and leaves a `35 to 170 s` window after every merge where all 5 nodes serve a stale `main` generation. Instead, harvest the `merge_group` (or speculative `M5`) post-build snapshot before tests run as `candidate/<tree-sha>`, delta-stream its changed files (`50 to 300 MB` zstd) to the other 4 nodes during test execution, and atomically rename `candidate/<tree-sha>` to `trusted/<tree-sha>` (`<1 ms`) once GitHub confirms `<tree-sha>` landed on protected `main`.

3. **`N01` (Phase 3 whole-repo `tree/<hash>` receipts) and `N02` / `I038` / `I039` / `I041` (Phase 4 test-binary digest closure receipts).**
   - *Why overturn:* Keying Phase 3 receipts on the whole-repository Git tree hash misses `82% to 100%` of `merge_group` runs because `main` advances in unrelated packages (`S4`: `0 of 40` on Nov 18, `11 of 60` on Nov 16 to 17). Keying Phase 4 closure receipts on the compiled test binary digest (§4.1) requires starting a build pod, cloning 9 GB, and running Cargo before the receipt key is even known (defeating `N06` zero-pod short-circuit and omitting `clippy`, `doc`, `fmt`, and `check-alone`). Replace both in Phase 3 with **Package Input-Closure Merkle Keys** computed directly from the node's Git mirror in `<5 ms` and enforced by read-only input-projection mount namespaces.

4. **`I063` (Rejected: *"Deduplicate the runner-host default and local-mode test sweeps... `local-mode` gates production code and the release build refuses the feature"*).**
   - *Why overturn the architecture that forces two sweeps:* Running `velnor-runner-host` twice (`5.5 + 6.5 = 12.0` runner-min, `evidence.md` T3) happens only because `src/local/*` lives inside the 156,822-line `velnor-runner-host` crate behind `#[cfg(feature = "local-mode")]` (`crates/velnor-runner/crates/velnor-runner-host/Cargo.toml:13`). Extract `src/local/*` and its `local_host_public` / `local_pair_public` tests into a separate workspace crate `velnor-runner-local` that depends on `velnor-runner-host`. Then `velnor-runner-host` has only one feature configuration (compiled and tested once!), the release binary never links `velnor-runner-local`, and 100% of both configurations' tests run without compiling 157k lines and running 390 shared tests twice.

5. **`I064` (Owner decision: *"Build runner-workspace dependencies at opt-level 3 in the test profile"*).**
   - *Why overturn to Adopted in Phase 1:* `crates/velnor-runner/Cargo.toml:75` already sets `opt-level = 1` for `turso_core`. Setting `[profile.ci.package."*"]` (third-party dependencies only) to `opt-level = 3` with `debug-assertions = true` and `overflow-checks = true` keeps every debug assertion and integer overflow check intact while cutting `velnor-runner-host` test CPU by **66%** (`142.5 -> 47.9 CPU-s`, `proposals/fable-5.2.md` §8a rank 4).

6. **`I073` (Experiment-gated, Phase 2: *"Split velnor-runner-host (157k lines) into 6-10 crates"*).**
   - *Why overturn to Committed in Phase 2:* `velnor-runner-host` is `156,822` LOC (`85%` of its workspace, `evidence.md` §D.2). Without splitting `journal/` (`64k` LOC), `launch/` (`48k` LOC), `docker/` (`25k` LOC), and `local/` (`12k` LOC) and keeping `target/debug/incremental` across local XFS reflink snapshots, every 1-line edit in the runner workspace pays a `35 to 99 s` compile floor (§6.6).

7. **`N05` (Experiment-gated, Phase 3: *"velnor-sandbox keeps one Worker process waiting in every idle pod and replaces it every 25 s"*).**
   - *Why overturn the 25 s respawn loop:* Respawning `Runner.Worker` every 25 s across 35 idle pods causes 5,040 .NET process starts per hour to save 45.4 ms (`proposals/gemini-4-carbon.md` §2 H1), and starting it before `.runner` and public `.credentials` exist breaks `HostContext.LoadDefaultUserAgents()` (`HostContext.cs:301-348`). Write `.runner` and public `.credentials` at pod init, start `Runner.Worker`, and freeze its cgroup (`cgroup.freeze = 1`) after pipe connection (`0` respawns/hour, `<1 ms` wake-up).

8. **`N15` (Experiment-gated, Phase 4: *"PR-light, queue-full: PR pushes run only fast obligations; the merge queue runs everything the change selects"*).**
   - *Why overturn to Rejected:* Deferring selected obligations from the PR run to the merge queue lowers PR verdict confidence to a partial check and turns any failure in the deferred obligations into a merge-queue ejection that invalidates and rebuilds every queued PR behind it (§1.3). Once the test floor is broken (`≤ 15 s`) and incremental XFS snapshots are active (`≤ 11 s` build), the full selected PR run takes `25 to 55 s`, making `PR-light` counterproductive.

## Anything missing

1. **The 386 separate integration test binaries (`tests/*.rs`) bloating `target/` to 6 to 9 GB and burning hundreds of linker CPU-seconds.**
   - Look at `evidence.md` §C.5 (line 756): while `velnor-ci` (781 tests) and `velnor-gen` (627 tests) each compile **1** integration test binary (`tests/it`), `velnor-actions-workflow-renderer` compiles **177** separate `tests/*.rs` binaries, `velnor-actions-orchestrator` compiles **109**, `velnor-actions-cli` compiles **44**, `velnor-runner-host` compiles **26**, `velnor-actions-contract` compiles **20**, and `velnor-archive-guard` compiles **10** (`386` standalone ELF executables in total!).
   - In Cargo, every `tests/*.rs` file is linked as a separate 20 to 180 MB executable duplicating `libstd`, `tokio`, `turso`, and workspace crates. That is why `target/` is 6 to 9 GB and why a 1-crate edit spends tens of seconds in `rust-lld` relinking dozens of binaries. Because `cargo-nextest` already isolates every `#[test]` function in its own subprocess, consolidating each package's `tests/*.rs` into a single `tests/it/main.rs` binary (matching `velnor-ci` and `velnor-gen`) keeps 100% of test isolation while shrinking `target/` by **70% to 85%** (from `6 to 9 GB` to `~1.5 GB`) and cutting incremental link time from `20 to 45 s` to **`1 to 2 s`**.

2. **A pod-wide GNU Make Jobserver (`CARGO_MAKEFLAGS`) for parallel `background: true` Cargo steps.**
   - When `mbx` is retired (`I111`), running `cargo clippy`, `cargo doc`, `cargo check -p <pkg>`, and `cargo nextest` in parallel as `background: true` steps (§6.1) over reflinked target directories lacks a shared compiler process limiter. Cargo natively implements the GNU Make jobserver client protocol (`MAKEFLAGS="--jobserver-auth=fifo:/tmp/velnor-jobserver"`). Having `velnor-ci` open one 16-token FIFO per pod lets all concurrent background Cargo steps share an exact 16-CPU `rustc` budget without `mbx`.

3. **Extracting `velnor-runner-local` to eliminate the double `velnor-runner-host` + `local-mode` compile and test sweep without losing coverage.**
   - Decision `I063` keeps two full compilations and test sweeps of the 156,822-line `velnor-runner-host` crate because `local-mode` is a Cargo feature on `velnor-runner-host`. Moving `crates/velnor-runner/crates/velnor-runner-host/src/local/*` (and its two integration test targets `local_host_public` and `local_pair_public`) into a dedicated workspace member `velnor-runner-local` removes the feature flag from `velnor-runner-host`, cutting `5.5 to 8.9` runner-minutes per run at zero coverage loss.

4. **Retiring `cache-prune.yml` and the State seal workflow (`workflow_run` / `push` storm on `main`).**
   - `cache-prune.yml` triggers on `workflow_run` after every `CI` and `State seal` completion on `main` (`40` runs on Nov 18, `evidence.md` T11 line 399, §C.1 line 627). The draft retires `state seal` in Phase 2 (`I029`), but forgets `cache-prune.yml`, which will keep firing on every merge and burning hosted slots and GitHub API quota unless deleted or restricted to hosted-only caches.

5. **GitHub REST API rate-limit protection via a `velnor-dispatch` metadata cache.**
   - On Nov 18 the repo created 1,000 workflow runs (`evidence.md` T11). `velnor-ci` commands (`release-gate`, `cache trim/budget`, `timings`, `collect`) and speculative/audit loops query GitHub's REST API directly. During multi-agent bursts, per-job REST pagination (`gate.rs:181-209, 290-296`) risks hitting GitHub's 1,000 req/hr `GITHUB_TOKEN` or secondary rate limits. `velnor-dispatch` should expose cached webhook/check/ruleset state to `velnor-ci` over the node agent socket so jobs make zero direct GitHub REST calls.

6. **Enforcing Clause C5 (no undeclared network or event-payload reads) structurally with `CLONE_NEWNET` (`lo`-only) test namespaces.**
   - Clause C5 (§1.2) requires obligations that read the network or `event.json` to run fresh every time, but the draft provides no mechanism to detect whether a test read the network or `GITHUB_EVENT_PATH`. Running all non-Docker test binaries inside a network namespace with only a loopback interface (`CLONE_NEWNET` with `lo` up, no external veth) and with `GITHUB_EVENT_PATH` unmounted makes network and event-payload independence a kernel-enforced guarantee rather than an honor system.
