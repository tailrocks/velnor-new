# Design feedback: Velnor runner architecture

## Verdict

No, not as written. The draft cuts today's 85 min push-to-merge median down to roughly 8 to 12 min, then stalls on broken scale-set admission mechanics, unschedulable node memory math, unaddressed release gates, and `main` base-movement rebuilds (`decisions.md` S4).
**Ambition: 5/10.** It keeps ARC and a 3-to-4-job serial GitHub DAG for 12 weeks, defers every mechanism that removes the second verification and breaks the 60 s wall to weeks 12 to 20+, and spends 50.5k lines of Rust wrapping `Runner.Worker` and copying file trees instead of deleting job hops and mounting O(1) layers.
**Soundness: 6/10.** The confidence contract (`C1` to `C7`) is clear, yet the draft ships verified protocol bugs (`X-ScaleSetMaxCapacity`, pre-registered idle JIT runners vs `acquirejobs`, logless `completejob` calls, 60 s lease renewal), 136 GiB pod requests on 125.5 GiB nodes, an unsound `CARGO_BIN_EXE_*` closure key, and a `push` skip that breaks release and image publication.

## Correctness and confidence holes

1. **`[CRITICAL]` Scale-set admission deadlock and priority bypass (`velnor-runner-architecture.md:172-184`, `I015`, `M9`).**
   - Sending `X-ScaleSetMaxCapacity = free_slots` (`line 173`) breaks scale-set polling. GitHub defines that header as total capacity (`busy + free`), capping `TotalAssignedJobs` (`scaleset/README.md:42,49`, `arc/cmd/ghalistener/main.go:101`). `velnor-legacy` tried `N - occupied` (`velnor-legacy/crates/velnor-runner/src/scaleset/allocator.rs:135-138`) and `velnor-new` explicitly banned it (`velnor-new/docs/proposed/macos-scaleset-runner.md:133`, `crates/velnor-runner/crates/velnor-runner-host/src/launch/pressure.rs:25-35`). When 20 of 35 slots are busy, sending `15` tells GitHub the scale set is over capacity and stalls all 15 free slots; when 0 slots are free, sending `0` enters drain mode and suppresses `JobAvailable` offers completely.
   - Simultaneously holding idle online JIT broker sessions equal to capacity (`lines 176-177`) defeats priority admission (`line 172`). Whenever idle runners exist in a scale set, GitHub assigns queued jobs directly via `JobAssigned` in FIFO order, bypassing `JobAvailable` and `acquirejobs` (`scaleset/README.md:19-20,34`, `arc/docs/automatically-scaling-runners.md:278`, `velnor-new/.../launch/steps/scoped/acquire.rs:171-177`). Classifying `gate`, `build`, and `docker` *after* `acquirejob` on one shared scale set (`lines 181-184`) also deadlocks whenever both docker nodes are full while build slots stand idle.
   - **Fix.** Keep separate scale sets per priority and capability (`velnor-merge`, `velnor-gate`, `velnor-build`, `velnor-docker`). Send `X-ScaleSetMaxCapacity = total_slots` clamped to `max(busy, 1)`. Hold zero pre-registered online JIT runners whenever a backlog exists so `acquirejobs` orders `JobAvailable` offers before `generatejitconfig` mints an identity.

2. **`[CRITICAL]` Closure key misses 171 `CARGO_BIN_EXE_*` and example-binary invocations (`velnor-runner-architecture.md:301-304,330-337`, `M4`).**
   - Closure receipts key test obligations on `digest(test_binary) + digest(declared_runtime_inputs) + definition_digest` (`lines 301-303`). Across `velnor-new`, 102 test files invoke `env!("CARGO_BIN_EXE_<bin>")` 171 times across 8 binaries (`velnor-ci` 117, `velnor-actions` 33, `velnor-resource-probe-release` 8, `velnor-local` 5, `velnor-gen` 4, `velnor-archive-guard` 2, `velnor-golden-collector` 1, `velnor-local-test-job-hook` 1), plus 3 env-injected fixture binaries (`VELNOR_IMAGE_PUBLICATION_FIXTURE` at `crates/velnor-actions-cli/tests/image_publication_public/support/runtime.rs:134`, and `VELNOR_QUALIFICATION_{DIAGNOSTICS_FIXTURE,CLOCK_DRIVER}` at `crates/velnor-archive-guard/tests/golden_collector_public/support.rs:27,138`).
   - `crates/velnor-actions-cli` has no `lib.rs` (`src/main.rs:9`). Editing any of its 2,963 lines rebuilds `target/debug/velnor-actions` while `digest(test_binary)` for `image_publication_public` stays byte-identical. Mounting `target/debug` without hashing sibling executables yields silent false greens on broken CLI code; omitting them fails 102 test files under mount-namespace enforcement. Also, `line 373` mis-cites `proposals/opus-5.5.md`'s 88% figure as closure reuse when that replay measured package-level change selection (`comparison.md:294`).
   - **Fix.** Parse `cargo test --no-run --message-format=json` to hash every workspace `[[bin]]` and `--example` executable reachable by a test target into the output-addressed closure key, and mount only those hashed binaries read-only into the test namespace.

3. **`[CRITICAL]` `merge_group` reading `PR scope` allows cache poisoning of `main` (`decisions.md:313-315`, `velnor-runner-architecture.md:198,314,334-336,386-388`).**
   - `decisions.md:314` claims a `PR scope` is *"written by the agent, never by the job, and read only by that PR and its merge group."* Post-build harvest (`line 386`) snapshots the job's writable `target/` *after* PR `build.rs` scripts and proc-macros ran with full write access to `target/.fingerprint/` and `target/debug/deps/`. Commit 1 on a PR can corrupt or backdate artifacts of an untouched crate in `target/`, commit 2 can revert `build.rs`, and `merge_group` will inherit the poisoned `PR scope` on the gate to `main`, breaking `C1`.
   - Mounting the privileged `velnor-node` socket into untrusted build pods (`lines 198, 334-336`) also exposes `L2` stores and host namespace creation to PR-controlled `.config/nextest.toml` `run-wrapper` commands (`generator/.config/nextest.toml:8-16`) and background processes left by `build.rs`.
   - **Fix.** Clone `merge_group` workspaces exclusively from immutable `trusted` (`main`) generations, never from `pr/<number>`. Gate the agent socket with per-step capability tokens revoked during Cargo compilation, and enter the pod's existing UID, cgroup, and network namespace when spawning test sandboxes.

4. **`[CRITICAL]` Unschedulable worker memory math and unbounded 96-thread CPU bursts (`velnor-runner-architecture.md:511-528,553`).**
   - All 5 EPYC workers have `125.48 GiB` RAM (`131,578,888 Ki`, `evidence.md` §B.0:442-446). Subtracting `6 GiB` kube and system reservation plus `2 GiB` eviction threshold (`line 518`) leaves `117.48 GiB` Allocatable [M].
   - Requesting `4` running build pods at `32 GiB` (`128 GiB`) plus `4` idle gate pods at `2 GiB` (`8 GiB`) totals `136 GiB` (`200 GiB` if the `2` idle build pods are separate from the `4` running). `line 513` (*"An idle pod costs about 45 MiB"*) confuses RSS with `requests.memory`, which `kube-scheduler` reserves in full for pre-created pods. Even 3 build pods (`96 GiB`) plus 4 gates (`8 GiB`) leave `13.48 GiB` for `velnor-node`, `crates-mirror`, the `warmer` pod (which peaks near `16.8 GiB`), `ChainArgos`, and `jackin`.
   - Setting `no CPU limit` (`line 514`) makes `Static CPU manager` (`line 553`) a Kubernetes no-op (`Burstable` QoS) and causes `std::thread::available_parallelism()` inside `cargo` and `nextest` (`test-threads = "num-cpus"`) to read `96` (`evidence.md` §B.2.2:519), spawning `288` threads across 3 pods and recreating the `3.7` to `8.8 min` load stretch (§A T6). Tainting 1 docker node per site (`line 528`) also removes half of DE's 2 workers (`velnor-240` and `velnor-105`, §B.0:442-443).
   - **Fix.** Replace static pod reservations with elastic `velnor-node` cgroup slots (Section 3), or size build pods at `16 CPU / 18 GiB` request and `24 GiB` limit, inject `CARGO_BUILD_JOBS=16` and `NEXTEST_TEST_THREADS=16` explicitly, and run `docker` jobs in KVM microVMs on any worker instead of tainting half of DE.

5. **`[HIGH]` Phase 1 `push` skip and Phase 4 App-posted `Required` break release and image publication (`velnor-runner-architecture.md:321,453,488,695-697`).**
   - Four release contracts demand a completed `push`-event GitHub Actions run with a `Required` job (`integration_id == 15368`): `.github/workflows/product-release.yml:86` (and `-images.yml:222`, `-binary.yml:198`, `-generator.yml:122`, `schema2_release_eligibility.rs:19-52`); `.github/workflows/source-preview-publication.yml` (`schema2_generator_source_preview_source.py:187-195`, requiring `"Required verdict"` on `push`); `velnor-gen`'s `release.yml` (`generator/crates/velnor-render/src/release.rs:91-106`) plus `velnor-ci release-gate` (`ci-helper/crates/velnor-ci/src/gate.rs:134-143,236-240,277-288`), which ignores `merge_group` runs and rejects non-GitHub-Actions `integration_id`s; and consumer `publish.yml` (`docs/hard-decisions.md:446-450`, `image_publish_scripts.rs:51-65`), which downloads `velnor-image-{id}-{arch}` from the `push` `ci.yml` run. Inside `rust-ci.yml`, `velnor-ci gate` (`verdict.rs:278-358`) also fails on `push` if scheduled packages report `tests_run == 0`.
   - **Fix.** Before Work Item 7, update `velnor-ci gate`, `velnor-ci release-gate`, `schema2_release_eligibility.rs`, and `publish.yml` to accept signed `merge_group` ledger receipts and the Velnor App `integration_id`, and promote `merge_group` build artifacts by digest.

6. **`[HIGH]` Fork PRs are hard-failed instead of routed to hosted runners (`velnor-runner-architecture.md:182-183,253,523,669,698`).**
   - `velnor-gen` emits a static `runs-on` string (`generator/crates/velnor-render/src/workflow.rs:67`) with no fork expression. Setting `runs-on` to `velnor-gate` and `velnor-build` sends fork PRs to Velnor, where `N11` (`line 183`) fails them with an annotation instead of running them on GitHub-hosted runners.
   - **Fix.** Emit `runs-on: ${{ github.event.pull_request.head.repo.fork && 'ubuntu-26.04' || 'velnor-build' }}` in `velnor-gen` until the KVM microVM fork class is live.

7. **`[HIGH]` Parallel lanes on one `target/` serialize on `.cargo-lock`, clobber fingerprints, and miss `PR scope` (`velnor-runner-architecture.md:386-388,412-417`).**
   - `velnor-gen` currently runs steps sequentially on one `target/` (`generator/crates/velnor-rust/src/root_jobs.rs:205-356`). Turning `clippy --workspace`, `doc --workspace`, and `cargo check -p <pkg>` ("check alone") into parallel lanes on one `target/` (`line 415`) hits three defects: Cargo's `.cargo-lock` serializes concurrent writers (`docs/hard-decisions.md:56-71`); mixing `--workspace` with `-p <pkg>` alters feature unification (`docs/hard-decisions.md:494-498`), rebuilding shared deps and failing `velnor-ci report --check` (`ci-helper/crates/velnor-ci/src/report.rs:65-242`); and snapshotting `target/` right after building test binaries (`line 386`) omits `clippy`, `doc`, and `check alone` `.rmeta` files from `PR scope`. Merging all 30 crates into one root workspace (`line 412`) under Hard Decision 11 (`--workspace`) also forces a 1-file edit in `velnor-ci` to check and link `velnor-runner-host` (`157k` LOC).
   - **Fix.** Mount separate O(1) `overlayfs` views per lane (`build`, `clippy`, `doc`, `alone`) over a `main` generation whose warmer pre-builds both test binaries and `clippy`/`doc` metadata, and isolate `-p` check-alone outputs into a separate overlay upperdir.

8. **`[HIGH]` Job-level `fanotify` audit is blind inside whole-workspace jobs (`velnor-runner-architecture.md:341-343,428-430`, `I069`).**
   - Inside a `velnor-gen` root job, `cargo fmt --all --check` and `cargo clippy --workspace` legitimately open every `.rs` and `Cargo.toml` file in the workspace (`reviews/gemini-4-argon.md:70-72`), defeating per-package input verification. `fanotify` also never observes skipped crates and misses `ENOENT` negative `stat`/`access` probes and `getdents64`.
   - **Fix.** Trace file reads per `build.rs` and per test-binary process tree (via mount-namespace isolation or eBPF `sched_process_fork` + VFS hooks), and audit all crates during nightly full runs.

9. **`[HIGH]` Podless `completejob` calls (`N06`, `N11`, `velnor-runner-architecture.md:183,204,235`) cause `BlobNotFound` logs and blank failure UIs.**
   - `CompleteJobRequest` (`actions-runner/src/Sdk/RSWebApi/Contracts/CompleteJobRequest.cs:10-41`) carries `outputs`, `stepResults`, and `annotations`, never log bodies. `velnor-legacy` proved in production (`crates/velnor-runner/src/runner.rs:18342-18345,18915-18917`, issue `#672`, run `33344851591`) that empty `stepResults` hide annotations behind a zero-step UI and skipping Results Twirp blob uploads (`ResultsHttpClient.cs:584-636`) makes GitHub return `BlobNotFound` for job logs.
   - **Fix.** Every podless completion in `velnor-proto` must emit one synthetic `StepResult`, upload and seal step and job logs via Results Twirp, and populate `CompleteJobRequest.outputs`.

10. **`[HIGH]` 60 s lease renewal (`velnor-runner-architecture.md:191`), ~1 h token expiry, and orphaned `JobCancel` on failover (`lines 179,271-272`, `N10`).**
    - Run Service issues `~30 s` `lockedUntil` windows in production (`velnor-legacy/crates/velnor-runner/src/runner.rs:12053-12056`); a 60 s renewal cadence (`line 191`) expires live leases. `SystemVssConnection` `AccessToken` also expires after `~1 h` (`velnor-legacy/runner.rs:12121-12125`), failing unmodified `Runner.Worker` `completejob` (`JobRunner.cs:335-341`) with `401` when the RSA key stays in `velnor-dispatch`. Finally, `RenewJobResponse` (`RenewJobResponse.cs:7-15`) carries no cancel bit; `JobCancel` arrives only on the broker session (`Runner.cs:790-800`), yet `line 179` journals acquisitions before node placement and omits JIT RSA keys needed for a standby dispatcher to reopen broker sessions.
    - **Fix.** Renew at `min(25 s, (lockedUntil - now) / 2)`, journal encrypted JIT credentials plus assigned `node_id` so failover reopens broker sessions, and proxy `401` token refreshes through `velnor-dispatch`.

11. **`[MEDIUM]` Phase 1 read-only `RUSTUP_HOME` crashes `ci.yml:438`, and `kubelet --root-dir` breaks 5% eviction (`velnor-runner-architecture.md:519,544,546,687-694`).**
    - Work Item 5 mounts read-only toolchains in Phase 1 before `velnor-gen` cutover (Work Item 8), triggering `rust_installed_manifest_unwritable` in `.github/workflows/ci.yml:425,438`.
    - Moving kubelet `--root-dir` onto `/var/lib/rancher/kubelet` merges `nodefs` onto DE's `49.9 TB` and `34.6 TB` XFS volumes (`evidence.md` §B.1.4:483-486), where `nodefs.available: 5%` (`§B.1.3:472`) locks out `2.5 TB` and `1.73 TB`, stops monitoring `/` (`ext4`) against `/var/log/pods` growth, lacks XFS `prjquota` (`velnor-runners/PLAN.md:80`), and leaves FI's `3.5 TiB` OS NVMe 97% idle while crowding FI's single `3.5 TiB` data NVMe. Also, `N05`'s 25 s `Runner.Worker` respawn across 35 idle pods creates `~5,040` `_diag/Worker_*.log` files/hour (`HostTraceListener.cs:168`), omits `.runner` `User-Agent` IDs (`HostContext.cs:342-348`), defaults `IsHostedServer = true` if `ServerUrlV2` is omitted (`ConfigurationStore.cs:115`), and risks zero-padded UTF-16LE truncation on 30 s cancel (`StreamString.cs:50-77`).
    - **Fix.** Satisfy `pin_check()` in `ci.yml` first, set fixed-GiB eviction thresholds (`nodefs.available: 100Gi`), enable `prjquota` during node drain, place `/tmp` and logs on FI's OS NVMe, and drop `N05` for `velnor-exec` (Section 3).

12. **`[MEDIUM]` Misread `ci-helper` config and 3 unaddressed 200+ s bottlenecks in Work Item 4 (`velnor-runner-architecture.md:90-91,479,488,682-686,709`).**
    - `ci-helper/.config/nextest.toml:3-31` has no `2 s` kill in `[profile.ci]` (only `[profile.default]`), and sets `threads-required = "num-test-threads"` on `crates_mirror` tests (`lines 16-23`), blocking Phase 4's `55 s` to `12 s` 8-thread target (`line 488`).
    - Work Item 4 (`lines 682-686`) misses the 12 serialized `golden_collector_public` tests (`212` to `246 s`, `.config/nextest.toml:17-19`), the 12-case `blob_faults` loop plus 36 duplicate archive projections in `image_publication_public.rs:140-183,256-301`, and the redundant 89 s cold `Prepare image publication fixture` build (`ci.yml:965-967`). Work Item 10 (`line 709`, *"executes no obligation"*) also contradicts `C5` (`line 61`) while `cargo-deny` (`ci.yml:127`, `deny.toml:14-15`) fetches live RustSec advisories over the network.
    - **Fix.** Isolate temp dirs/ports on `crates_mirror` and `golden_collector_public` to drop `threads-required`, split `blob_faults` and memoize `project_runner_archive` via `OnceLock`, fold `image-publication-fixture` into `--all-targets`, and pin the RustSec advisory tree in `.velnor/` (Section 7).

## Where the design is too timid

1. **Keeping a 3-to-4-job serial GitHub DAG (`Plan -> Root -> Required`) through week 12 (`velnor-runner-architecture.md:411-420,475-481`, `I013`, `N06`).**
   - **Bolder alternative.** Collapse `rust-ci.yml` to a **single GitHub job (`Verify`)** as soon as the 5 workspaces merge into 1 root workspace in Phase 2, and have the Velnor GitHub App post `Required` directly in Phase 3.
   - **Mechanism.** `Plan` exists today only to emit `not_affected_jobs` for 31 separate YAML jobs (`evidence.md` §C.1:639). With one root workspace (`line 412`), the released `velnor-ci` binary computes the exact obligation plan inside `Verify` in `200 ms` from the node's bare Git mirror, checks `velnor-ledger`, executes unverified obligations, and exits; when receipts already hold, `velnor-dispatch` completes `Verify` without a sandbox via `completejob` + Results Twirp (`N06`).
   - **Numbers and arithmetic.** Deletes 2 serial GitHub job scheduling hops (`Plan` `10 s` + `Required` `10 s` = `20 s` at P50 in `lines 477,480` [E], and `35` to `60 s` at P90 under GitHub dispatch jitter), cutting a warm median PR verdict from `96 s` (`line 481`) to `35` to `45 s` [E].
   - **Risk.** Release workflows checking specifically for a job named `Required`.
   - **Same confidence.** Name the single job `Required` (or post `Required` from the bound Velnor App after updating `velnor-ci release-gate`); the released `velnor-ci` binary enforces identical `C1` to `C3` plan and test-count checks inside it.
   - **Cheapest experiment (2 days).** Emit a 1-job `Required` workflow on `velnor-lab` and time 30 pushes end-to-end against the 3-job `Plan -> Root -> Required` graph.

2. **Walking 40k to 100k files with XFS `cp --reflink` (`velnor-runner-architecture.md:352,380,386`) instead of O(1) `overlayfs` stacks.**
   - **Bolder alternative.** Replace recursive `FICLONE` directory copies and full-tree post-build snapshots with **multi-lower `overlayfs` mounts** (`lowerdir=pr_delta:main_gen`, `upperdir=lane_upper`) on XFS.
   - **Mechanism.** Frozen `main_gen` directories are immutable (`line 383`), so `ESTALE` cannot occur. `velnor-node` mounts an `overlayfs` build view in `< 5 ms`. When compilation finishes, `velnor-node` unmounts and freezes `build_upper` as read-only `pr_delta` in `< 5 ms` (it holds only the `20` to `200` files Cargo modified), mounts 4 separate `overlayfs` views (`tests`, `clippy`, `doc`, `alone`) over `pr_delta:main_gen` in `< 5 ms`, and streams zstd-compressed `pr_delta` (`50` to `150 MB`) to `L2` `velnor-store` so **every node in the site** has the warm PR layer.
   - **Numbers and arithmetic.** Setup, harvest, and `rm -rf` teardown of 40k to 100k inodes across 4 parallel lanes drop from `6` to `15 s` to `< 20 ms` [E]. Because XFS reflinks allocate distinct inodes (`i_mapping`), 4 concurrent build pods duplicate Linux page cache (`4 * 9 GiB = 36 GiB`); `overlayfs` shares one `lowerdir` inode cache (`9 GiB`), freeing `27 GiB` of RAM per worker [E]. Streaming a `100 MB` `upperdir` delta to `L2` takes `< 0.5 s` vs `10+ s` for a `9 GB` target tree.
   - **Risk.** Cargo opening an unchanged `.rlib` with `O_RDWR` would trigger copy-up (`.cargo-lock` is 0 bytes, so its copy-up is free).
   - **Same confidence.** Frozen lower layers are kernel-enforced read-only (`C4`), and `velnor-ci inputs restore` preserves Cargo's exact mtime/fingerprint rules (`C1`).
   - **Cheapest experiment (1 day).** During Work Item 6 on one drained worker, benchmark 4 concurrent `overlayfs` builds vs `cp -a --reflink=always` on the `9 GB` `velnor-new` target, measuring mount time, `du -sh upper`, page-cache RSS, and teardown latency.

3. **Deferring ARC replacement, `Slots, not pods` (`I082`), and a tiny `velnor-gen` step runner (`I005`) behind 12 to 20 weeks of K8s pod wrappers and 25 s `.NET` respawns (`N05`).**
   - **Bolder alternative.** Build `velnor-dispatch` + `velnor-node` directly over **elastic Linux cgroup v2 / `pivot_root` namespace slots (`I082`)** in Phase 2/3, paired with a **2.5k-LOC Rust step runner (`velnor-exec`)** restricted strictly to `velnor-gen`'s 1-command-per-step profile (`docs/goals.md:73`), keeping cold `Runner.Worker` in the same slot as instant fallback for non-`velnor-gen` workflows.
   - **Mechanism.** Every `velnor-gen` step is a single `velnor-ci` command (`docs/goals.md` rule 9) once git, tools, and caches live on the node. `velnor-exec` evaluates step `if:` conditions (checked against `velnor-legacy`'s 3.5k-LOC expression corpus), spawns `velnor-ci` directly in the slot's user/mount/pid/net/cgroup namespace in `< 30 ms`, streams logs to Results Twirp, and calls `completejob`.
   - **Numbers and arithmetic.** Assignment-to-first-cargo drops from `15 s` (Phase 2) and `5 s` (Phase 3) to `< 0.4 s` (`150 ms` `acquirejob`+`renewjob` + `5 ms` `overlayfs` + `25 ms` spawn), removing `8` to `14 s` of `.NET` boot, `runnerresolve/actions` WAN calls (`LaunchHttpClient.cs:35`), and `node24` wrappers (`20%` to `33%` of a `42 s` warm PR run, clearing `I005`'s 10% bar by `2` to `3x` [E]). Dropping static `32 GiB` idle-pod K8s reservations increases worker concurrency from `3` capped pods to `5` or `6` elastic slots (`+67%` capacity) and deletes `5,040`/hr idle `Runner.Worker` spawns.
   - **Risk.** Semantic divergence if run on arbitrary YAML.
   - **Same confidence.** Only workflows stamped with `velnor-gen`'s profile header enter `velnor-exec`, after 100 paired shadow runs with zero diff (`I007`); every other workflow invokes unmodified `Runner.Worker` before step 1 (`I008`).
   - **Cheapest experiment (3 days).** Prototype `velnor-exec` against `velnor-local` scenarios and 50 `velnor-lab` runs, timing `acquirejob` to first `rustc` against `Runner.Worker`.

4. **Leaving Speculative Merge Queue (`N03`/`M5`) and Webhook Pre-Start (`N09`) in Phase 4 while accepting a 6 to 8 min Phase 3 merge time (`velnor-runner-architecture.md:494-499,660-661`).**
   - **Bolder alternative.** Ship **webhook pre-start (`N09`), continuous merge-queue speculation (`N03`), and receipt short-circuit (`N06`) in Phase 3** right on top of exact-tree receipts (`N01`).
   - **Mechanism.** Exact-tree receipts miss `82%` to `100%` of merge groups passively (`S4`) only because `main` moves while PRs wait. For `k = 4` queued auto-merge PRs `[P1..P4]`, there are only `4` cumulative merge trees (`T_i = merge-tree(T_{i-1}, P_i)`) plus `3` single-fault bypass trees (`merge-tree(T_{i-2}, P_i)`), `7` trees total. Computing those trees on the bare mirror in `< 50 ms` whenever `main` advances or a PR enqueues, and verifying them on preemptible `velnor-batch` slots, populates **exact `tree/<T_i>` receipts** before GitHub even emits `merge_group`. Likewise, starting PR verification on the `push` webhook hides GitHub's `8` to `497 s` job-creation delay (`proposals/gpt-6.2-astra.md:54`).
   - **Numbers and arithmetic.** Merge-group exact-tree hit rate jumps from `0` to `18%` [M, `S4`] to `>= 85%` [E] (at `<= 2%` queue failure rate, `0.98^4 = 92%` prefix survival). Merge-group run time falls from `~150 s` to `1` to `2 s` (`N06`), cutting Phase 3 push-to-merge P50 from `6` to `8 min` to `~55 s` (PR) + `19 s` (enqueue [M]) + `2 s` (MG short-circuit [E]) + `26 s` (merge [M]) = **`~1.7 min`** [E].
   - **Risk.** Speculative batch CPU wasted on simultaneous queue failures (harmless: `velnor-batch` is immediately preempted).
   - **Same confidence.** Pure **exact-tree receipts (`C1`, `C2`)** on the identical Git tree bytes GitHub's merge group tests, needing zero hermetic-closure assumptions.
   - **Cheapest experiment (2 days, Phase 0).** Run a read-only shadow daemon logging `git merge-tree --write-tree` predictions on `main` advances and comparing tree SHAs against real `merge_group` commits over 50 merges.

5. **Rebuilding `main` 5 redundant times on every merge (`velnor-runner-architecture.md:214,383`).**
   - **Bolder alternative.** Build each `main` advance **once per site** (1 worker in DE, 1 in FI) at 32-thread parallelism and replicate the compressed `overlayfs` `upperdir` delta (`50` to `300 MB`) to peer workers via `L2` `velnor-store`.
   - **Mechanism.** `velnor-store` (`line 355`) already holds snapshot seeds. Streaming an immutable BLAKE3-verified delta layer unpacks onto peer workers in `< 2 s`.
   - **Numbers and arithmetic.** Cuts warmer CPU burn by `60%` (`5` builds down to `2` [E]), halves time-to-warmth on `main` bursts, and eliminates generation skew when busy workers preempt local warmers.
   - **Risk.** Path-dependent compiler outputs if build paths vary (fixed by canonical `/work/velnor` mount path in every slot).

## The hardest problems

1. **Breaking the 35 to 99 s `velnor-runner-host` compile wall and 200 to 540 s test floor so heavy PRs also finish under 60 s.**
   - **Why it looks impossible.** Even with 100% warm dependency caches and split loops, a 1-line edit inside the 157k-LOC `velnor-runner-host` crate recompiles all 157k lines (`35` to `99 s` [M, `proposals/fable-5.2.md`]) and relinks 26 integration test executables (`evidence.md` §D.2:761). Merging all 5 workspaces into 1 root workspace (`velnor-runner-architecture.md:412`) drags shared-crate PRs into that same compile and link wall.
   - **Concrete attack.**
     1. *Slice `velnor-runner-host` into 6 DAG crates along its existing module boundaries (`evidence.md` §D.3:837):* `journal` (~35 schema modules), `docker-engine`, `scaleset-proto-client`, `reconcile`, `local-pair`, and a thin `host-daemon` crate (~15k LOC). Editing `journal` or `local-pair` then compiles ~20k LOC (`4` to `7 s`) instead of 157k LOC.
     2. *Consolidate multi-binary integration suites into one `it` binary per feature configuration:* `velnor-ci` runs 781 tests from 1 `it` binary and `velnor-gen` runs 627 from 1 `it` binary, whereas `workflow-renderer` links `177` separate binaries, `orchestrator` `109`, `actions-cli` `44`, and `runner-host` `26` (`evidence.md` §C.5:758-763). Collapsing `tests/*.rs` into 1 `tests/it/main.rs` per crate eliminates `95%` of repeated `rust-lld` linking (`15` to `40 s` saved [E]).
     3. *Stream individual test binaries (not a 1.48 GB archive) across all same-site threads (`M6` decoupled from `M4`):* One zstd-compressed `it` binary (`25` to `40 MB`) transfers across `L2` in `< 0.4 s` even on `1 Gbit/s`, letting `velnor-node` execute cases longest-first across 192 to 288 site threads in `< 12 s` [E] inside a single GitHub job.

2. **Reusing verdicts across PR, merge queue, and `main` when `main` advances (`0%` to `18%` passive tree match, `S4`) without trusting unproven heuristics.**
   - **Why it looks impossible.** On busy days, `0` of `40` merge groups match the tree the PR run tested (`decisions.md` S4). Job-level `fanotify` misses untaken branches and `ENOENT` probes; naive binary digests miss `CARGO_BIN_EXE_*` and relink churn.
   - **Concrete attack.**
     1. *Turn `S4` from `0%` into `>= 85%` proactively via fault-tolerant queue speculation:* Maintain an in-memory DAG of open `auto-merge` PRs `[P1..Pk]`. Whenever `main` advances or the queue changes, compute `T_i = git merge-tree --write-tree T_{i-1} P_i` (happy path) and `T'_i = git merge-tree --write-tree T_{i-2} P_i` (single-ejection bypass, `2k - 1 = 7` trees for `k = 4`) in `< 50 ms` on the local mirror, and pre-verify them on `velnor-batch` slots. When GitHub creates the `merge_group` commit, an **exact `tree/<T>` receipt (`C1`, `C2`)** already exists, so `velnor-dispatch` completes the job in `< 1 s`.
     2. *Compiler-oracle + binary-graph `pivot_root` receipts when speculation misses:* On an unspeculated tree `T_new`, run the warm `overlayfs` delta build (`8` to `20 s` from immutable `main_gen`, never `PR scope`). `rustc` and `cargo` act as the exact semantic oracle over macros, `cfg`s, types, and `include_bytes!`. Compute each test obligation's closure key over `BLAKE3(test_bin || reachable_CARGO_BIN_EXE_and_example_bins || declared_fixture_blobs || env_map || nextest_args || image_digest)`, and run the test inside a `pivot_root` empty mount namespace containing *only* those hashed immutable files (`/proc` masked, loopback only, `ENOENT` on every undeclared path). Identical closure keys are then a mathematical proof of identical syscall-visible inputs.

3. **Starting CI before `git push` and defeating GitHub's 8 to 497 s workflow-creation black box.**
   - **Why it looks impossible.** GitHub takes `5` to `20 s` normally and `497 s` (`25.5 min` P90 on 11-18, `proposals/gpt-6.2-astra.md:54`) before creating job records, plus `19 s` enqueue-to-`merge_group` and `26 s` post-green-to-merge (`45 s` fixed state-machine floor [M]).
   - **Concrete attack.**
     1. *Hook `velnor-ci preflight` into the agent's local test/push command:* Before or during `git push`, stream a thin packfile (`git bundle create - origin/main..HEAD`, typically `< 200 KB`, `< 150 ms`) over HTTPS to `velnor-dispatch`. The cluster immediately computes `head` and `merge-tree(main, head)`, builds in an `overlayfs` slot, runs tests on real `linux/amd64` hardware, and writes `tree/` receipts.
     2. *Trigger execution on GitHub `push` / `pull_request` / `merge_group` webhooks (`< 300 ms`), never waiting for Actions `JobAvailable`:* By the time GitHub Actions finishes parsing YAML `8` to `497 s` later and emits `RunnerJobRequest`, `velnor-ledger` already holds the `tree/` receipt and `velnor-dispatch` completes the job via `completejob` in `< 1 s`.
     3. *Sub-100 ms sandbox start:* Use `velnor-node` cgroup/`overlayfs` slots (`< 30 ms`) for `build`/`gate`, and pre-booted Cloud-Hypervisor or Firecracker KVM microVM snapshots (`dockerd` already warmed in guest RAM, restored via CoW memory mapping in `< 80 ms`) for `docker` and `fork` jobs.

4. **Controlling job priority and placement when GitHub's Scale Set protocol hides job details and assigns idle runners FIFO.**
   - **Why it looks impossible.** `JobAvailable` omits fork status and steps; `generatejitconfig` takes only `{name, workFolder}`; and registered idle runners get assigned jobs directly by GitHub (`scaleset/README.md:34`).
   - **Concrete attack.**
     1. *Split scale sets by priority and capability* (`velnor-merge`, `velnor-gate`, `velnor-build`, `velnor-docker`) and send `X-ScaleSetMaxCapacity = total_slots` on each.
     2. *Decouple virtual JIT identities from physical nodes, with adaptive idle-session switching:* Keep `velnor-merge` and `velnor-gate` warm with virtual JIT broker sessions in `velnor-dispatch` RAM (`0` node RAM cost, instant `JobAssigned` delivery, placed onto any worker *after* `acquirejob` reads the full message). On `velnor-build`, hold virtual idle sessions only while `free_slots >= 4`; as soon as load crosses that watermark, drop idle sessions to `0` so all queued jobs arrive as `JobAvailable` offers that `velnor-dispatch` sorts (`merge_group` > light PR > heavy PR) before calling `acquirejobs` + `generatejitconfig` (`~150 ms`).
     3. *Make placement stateless within a site:* Because every worker has `main_gen` in `L1` and pulls `< 150 MB` PR `overlayfs` deltas from same-site `L2` in `< 0.5 s`, any idle worker in the site runs any PR warm.

5. **Driving false failures from 8.1% (`S1`) below 0.3% on a 3-org cluster bursting to 95% CPU (`evidence.md` §B.2.1).**
   - **Why it looks impossible.** At `8.1%` false failure per run, an 8-deep merge queue suffers a `1 - 0.919^8 = 50.8%` chance that at least one entry falsely fails and invalidates the queue behind it, while `ChainArgos` (max 60) and `jackin` (max 40, 24-lane bursts) share the same 5 workers (`§B.3.2`).
   - **Concrete attack.**
     1. *Hard cgroup v2 CPU/memory slices + Zen 4 CCD pinning:* Partition each 96-thread EPYC 9454 worker (8 CCDs of 6 cores / 12 threads) via systemd slices (`velnor.slice` guaranteed 72 threads, `tenant-arc.slice` guaranteed 21 threads burstable only to idle cycles via `cpu.weight`, `system.slice` 3 threads). Pin each `velnor-node` slot to 1 or 2 whole 12-thread L3 CCDs (`cpuset.cpus`) with matching `CARGO_BUILD_JOBS` and `NEXTEST_TEST_THREADS`, eliminating cross-job L3 thrashing and 84-core neighbor starvation completely.
     2. *Delete real-clock race conditions in tests:* Replace wall-clock sleeps and elapsed-time assertions (`runner_image_qualification_public.rs:388-393`) with `tokio::time::pause()` deterministic clocks and generous `30 s` nextest timeouts.
     3. *Zero-retry failure triage:* Keep `retries = 0` on `Required` so flakes never pass silently (`AGENTS.md`). Whenever a test fails, fail the check **and** immediately re-run that single test binary `3x` on an isolated CCD in the background (`< 5 s`), attaching cgroup PSI counters (`cpu.pressure`, `memory.pressure`) to prove whether the failure was a deterministic regression (`3/3` red) or a flake (`>= 1/3` green).

## Anything missing

1. **Integration-test binary bloat (`356` separate executables across 4 crates).** Every proposal counted crates; none counted `tests/*.rs` binaries (`evidence.md` §C.5:758-763). `velnor-ci` packs 781 tests into `1` binary and `velnor-gen` packs 627 into `1`, whereas `workflow-renderer` compiles and links `177` separate binaries, `orchestrator` `109`, `actions-cli` `44`, and `runner-host` `26`. Each file re-invokes `rust-lld` over `50` to `150 MB` of `.rlib`s, inflating `target/` by tens of gigabytes and burning `30` to `60 s` of link CPU on shared-crate changes. Merging `tests/*.rs` into one `tests/it/main.rs` per crate and feature set removes `95%` of test linking and `L2` binary transfer overhead.
2. **Hermeticizing `cargo-deny` instead of surrendering it to `C5` live network checks.** `ci.yml:127` and `deny.toml:14-15` fetch a live RustSec advisory database on every run. Leaving `cargo-deny` in `C5` ("always runs fresh", `velnor-runner-architecture.md:61`) means `merge_group` can never 100% receipt-short-circuit (`N06`), and a single upstream CVE published mid-day ejects all 8 innocent PRs in the merge queue simultaneously. Pinning the RustSec Git tree SHA in `.velnor/` (advanced by an hourly automated PR, like `freshness.yml`) turns `cargo-deny` into a `100%` offline, deterministic, receipt-cacheable obligation while routing new advisories cleanly through their own PR.
3. **Merge-queue bisection thundering herds under `HEADGREEN` at depth 8.** With `grouping_strategy: HEADGREEN`, `max_entries_to_build: 8`, and `max_entries_to_merge: 10` (`evidence.md` §C.1:660), one failure at queue slot `1` invalidates all `7` cumulative candidates behind it, causing GitHub to enqueue up to `7` replacement `merge_group` runs at once. Fault-skipping tree speculation (`merge-tree(T_{i-2}, P_i)`) and automatic admission throttling on correlated failures are needed before raising queue depth from `4` to `8`.
4. **Single-node DE control-plane SPOF (`velnor-237`) and cross-site Kubernetes `Lease` split-brain (`velnor-runner-architecture.md:527,783`).** Deferring control-plane HA to Phase 4 (`week 20`) leaves all cluster scheduling and `velnor-dispatch`'s leader `Lease` on one consumer `i5-13500` desktop (`velnor-237`) with an unmirrored NVMe (`velnor-runners/PLAN.md:66`, `evidence.md` §B.0:441). Worse, using a DE-hosted Kubernetes `Lease` for `velnor-dispatch` failover to FI fails whenever `velnor-237` or the DE link drops. Promote 2 workers to 3-node embedded etcd (or run independent per-site scale-set dispatchers in DE and FI) *before* Phase 3 replaces ARC.
5. **GitHub API primary and secondary rate-limit budgets.** Running canaries every 10 min per executor path (`144` to `288` runs/day, `line 705`), 5% paired-rerun workflows, 2% to 10% receipt audits, webhook fetches, and App check-run updates shares one GitHub App token budget and hits GitHub's secondary creation limits on check runs and workflow dispatches. Receipt audits and flake reruns must execute internally inside `velnor-node` slots (posting a check run only on disagreement) instead of creating synthetic GitHub workflow runs.
6. **Harvesting partial compiler progress across the `45%` cancelled PR runs (`1,156` of `2,558` PR runs, `evidence.md` §A T1:45).** Agents push rapid follow-up commits that cancel nearly half of all PR runs mid-build. Killing an in-flight build discards every `.rlib` compiled so far in its `overlayfs` `upperdir`. Letting `velnor-node` snapshot completed `.rlib`/`.rmeta` units (whose Cargo `.fingerprint` files were atomically closed before `SIGTERM`) into the PR's `L1` cache lets the superseding push resume where the cancelled build stopped instead of restarting from `main`.
7. **Compiler nondeterminism flags required for `M4` bit-identical test binaries (`velnor-runner-architecture.md:607-608`).** Cargo incremental compilation (`target/debug/incremental`) embeds session directory hashes and non-deterministic CGU splits across nodes, breaking `M4`'s assumption that identical inputs yield bit-identical binary digests across workers. `main` warmers and closure-eligible builds must enforce `CARGO_INCREMENTAL=0`, `SOURCE_DATE_EPOCH=0`, `--remap-path-prefix`, and fixed `codegen-units` so binary digests match deterministically across all 5 workers.
