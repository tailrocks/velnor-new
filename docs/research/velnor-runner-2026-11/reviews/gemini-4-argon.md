# Cross-Critique of Velnor Runner Proposals (A, C, D)

## Proposal A

### 1. Weakest assumptions

1. **Four-way `nextest --partition hash:k/4` divides `velnor-runner-host` (192 s) and `velnor-actions-cli` (238 s) test steps linearly to ~48–60 s (`§5.3`, `§5.5`).**
   - *What is wrong:* `cargo nextest run --partition` shards at the `#[test]` function boundary. In `velnor-runner-host`, one test function—`launch::bootstrap::unbound_retirement::tests::shape::an_initializer_that_was_not_proven_absent_is_not_claimed` (`crates/velnor-runner/crates/velnor-runner-host/src/launch/bootstrap/unbound_retirement/tests/shape.rs:97-108`)—loops serially over $3 \times 2 = 6$ cases and runs for 203–271 s in CI (>540 s on macOS, `evidence.md` §D.5). In `velnor-actions-cli`, one test function—`public_authority_rejections_preserve_registry_inputs_and_foreign_resources` (`crates/velnor-actions-cli/tests/image_publication_public.rs:85-92`)—loops serially over 40 cases (`authority_rejection_cases()`, lines 94–138) and runs for 258–274 s. Because an indivisible `#[test]` dominates each suite, 4-way sharding leaves the longest shard at ~200–270 s (3.5–4.5 min), falsifying `§5.5`'s 1.0 min median / 1.7 min p90 shard arithmetic and its 4–5 min PR verdict target.
   - *Evidence to settle it:* Per-test duration distributions from nextest logs before and after splitting those looped tests into one `#[test]` per case and landing the Turso journal schema-open fixes (PRs #1333, #1349).

2. **`Check / maintenance-helpers` (508 s median) is a "pure cold-compile job" that warm `mbx` caches will drop to 60–120 s (`§1.3`, `§2 H4`, `§4.5`).**
   - *What is wrong:* Reading `mise.toml:90-200` and job log `134191252252` exposes two non-cache bottlenecks that Proposal A missed: (a) eight `cargo` commands in `mise.toml:90,108,128,137,148,157,170,193` hardcode `--config build.jobs=2` (and `--jobs 2` on nextest at `mise.toml:193`), which overrides any `CARGO_BUILD_JOBS` environment variable set in the pod template (`§6.2`, `§8a` rank 4); and (b) 211–246 s of the 486 s step is `velnor-archive-guard` nextest running 54 tests where 12 golden tests set `threads-required = "num-test-threads"` (`.config/nextest.toml:17-19`), forcing serial execution. Even a 100% compile cache hit rate leaves >210 s of serial tests.
   - *Evidence to settle it:* Phase timings of `test-maintenance-helpers` (`mise.toml:97-200`) on a warm node before and after removing `--config build.jobs=2` / `--jobs 2` and isolating the 12 golden tests' temp roots.

3. **Layer A can bind an acquired job to a cache-warm pod while keeping unmodified `Runner.Listener` inside pooled pods, and pods can be reused across jobs (`§3.2`, `§4.3`, `§6.1`).**
   - *What is wrong:* Three code/protocol contradictions:
     - In the scale-set API (`actions/scaleset` `client.go:765-796`, `types.go:93`; `evidence.md` §F.1.3), `generatejitconfig` takes only `{name, workFolder}`—never a `runnerRequestId` or `jobId`. When multiple jobs are acquired in a fan-out and multiple `Runner.Listener` pods poll the broker, GitHub assigns each job to whichever idle runner in the scale set polls next. A scheduler outside `Runner.Listener` cannot bind job $J$ (needing root cache $R$) to pod $P$ on node $N$ within a single scale set.
     - `Runner.Listener` cannot sit "idle" in a pre-created pod waiting for a JIT Secret (`§6.1` line 384): `src/Runner.Listener/Runner.cs:234-266` reads `--jitconfig` once at startup and immediately opens its broker session.
     - Reusing a pod across jobs (`§6.1` line 384: *"returns to the pool for a fresh worker process... Isolation comes from one job per worker process and a fresh `_work` dir per job, not from pod death"*) leaves mutated container filesystems, background processes in the pod PID namespace, `/tmp`, `/home/runner`, and `docker:dind` state across jobs, violating `docs/goals.md:43` and `docs/proposed/macos-scaleset-runner.md` §5.
   - *Evidence to settle it:* A multi-job fan-out test against the scale-set API verifying whether job-to-node assignment is controllable without either per-affinity scale sets or centralizing `acquirejob` ahead of `Runner.Worker`.

4. **Cutting over to `velnor-gen` (`§5.3`, `§8 Phase 3`) preserves `mbx` object caching (`§4.1`), `background: true` parallel check steps (`§5.3`), and the `§3.4` fast-lane profile.**
   - *What is wrong:* In `generator/samples/velnor-new/expected/.github/workflows/rust-ci.yml` and `generator/crates/velnor-render/src/rules.rs:12-21, 43-55`, `velnor-gen` does **not** use `mbx` (it caches `path: target` tarballs via `actions/cache/restore` and `save` plus `velnor-ci inputs restore`, `rust-ci.yml:173-184, 273-280`, which Proposal A `§4.1` line 263 explicitly says not to do), does **not** emit `background: true` steps (`RenderedStep` in `rules.rs:43-55` has no `background` field; Format, Lint, Doc, per-package check, and Test run sequentially at `rust-ci.yml:199-258`), omits the `local-mode` feature run for `velnor-runner-host` (`.velnor/rust-ci.toml:1-10`, `rust-ci.yml:685-707`), and emits only the `Required` check (`rust-ci.yml:1631-1632`) while ruleset `protect-main` (id 24396608, `evidence.md` §C.1) requires both `Required verdict` and `Required`.
   - *Evidence to settle it:* Diffing `generator/samples/velnor-new/expected/.github/workflows/rust-ci.yml` against `.github/workflows/ci.yml` and qualifying `velnor-gen` with `mbx`, parallel check lanes, and `local-mode` on `velnor-lab` first.

### 2. Factual errors

- **Cargo sources cache miss cause (`§1.4` line 81, `§4.2` line 279):** Claims `sources-compat` *"includes platform/ImageOS identity, so hosted-produced entries never match scale-set consumers."* False: in `.github/workflows/ci.yml:445`, `sources-compat` hashes `family=sources`, `schema=2`, three `$RUNNER_TEMP/velnor/cargo/...` paths, `uname -s`, `uname -m`, and `$RUNNER_TEMP/velnor/cargo`—never `ImageOS` (which is only in `state` compat, `ci.yml:445,707`). Moreover, scale-set Rust jobs do not recompute `sources_key`; they pass `${{needs.plan.outputs.sources_key}}` directly (`ci.yml:671`), logging the exact key that hosted `Plan` hit (`evidence.md` T9a line 333). It misses because `actions/cache/restore` hashes its resolved `path:` input (`${{ runner.temp }}/...`, which is `/home/runner/_work/_temp` on scale-set pods vs `/home/runner/work/_temp` on hosted `Plan`, `evidence.md` §B.3.3 line 557) into the cache entry's internal `version` parameter.
- **Fast-lane `uses:` allowlist vs `velnor-gen` output (`§3.4` lines 235–239):** Claims a `velnor-gen` job *"uses no `uses:` step except `actions/checkout`, `actions/cache` restore and save, `actions/upload-artifact` and `actions/download-artifact`"* (copied from superseded `docs/deferred/self-hosted-runner.md`, `evidence.md` §D.6). In `generator/crates/velnor-render/src/rules.rs:12-21` and `generator/samples/velnor-new/expected/.github/workflows/rust-ci.yml:70,120,141`, every `velnor-gen` job also uses `tailrocks/velnor-new/actions/setup-velnor` and `jdx/mise-action`. Proposal A's admission rule would reject 100% of `velnor-gen` jobs.
- **Default Linux x86_64 linker (`§8a` rank 3, line 486):** Claims rolling back `mold` makes pods *"link with `cc` again"* and estimates up to 16 s saved on an 81 s build. Rust 1.99.1 on `x86_64-unknown-linux-gnu` already defaults to bundled `rust-lld` (since Rust 1.90).
- **`nodefs` filesystem type (`§8a` lines 485, 504):** Cites `234M inodes on nodefs today [E §B.1.4]` while arguing XFS is already the filesystem in use. On all workers, `nodefs` (`/`, 3.78 TB, 234M inodes) is `ext4` on the OS NVMe (`velnor-runners/PLAN.md:45`, `evidence.md` §B.1.4 line 493); only `/var/lib/rancher` (`imagefs`, 3.37B inodes on `velnor-105`) is XFS (`PLAN.md:77-80`).

### 3. Missed bottlenecks or risks

- **Merge-queue and agent-workflow delays outside single-run PR CI:** Proposal A never measures end-to-end push-to-merge time. It misses `max_entries_to_build = 2` in ruleset `24396608` (`evidence.md` §C.1 line 660), which capped throughput on Nov 18 to <2 merges/hour, misses that 0% of PRs use auto-merge, and misses agents pushing manual `main` catch-up merges into PR branches.
- **Non-CI workflows saturating the 20-job GitHub Free hosted pool (`§1.2`, `§5.1`):** Moving the 8 `ci.yml` gate jobs to the cluster leaves `source-qualification.yml` (267 runs × 5 hosted jobs on 11-18, `evidence.md` T11 line 399, §C.1 line 628) and `job-image-candidate.yml` (306 runs on 11-18) saturating the org's 20 hosted slots and starving `state-seal.yml` and release workflows.
- **Static 8-CPU pinning (`cpuManagerPolicy: static`, `request == limit == 8`, `§6.2`, `§8a` rank 1):** Pinning every build shard to 8 exclusive logical CPUs prevents heavy single-job compiles (`velnor-runner-host`) from bursting onto idle cores when a 96-thread node is only lightly loaded, slowing quiet-period builds.

### 4. Ideas worth taking

- **Pre-seeding `ACTIONS_RUNNER_ACTION_ARCHIVE_CACHE` and wiring `ACTIONS_RUNNER_HOOK_JOB_STARTED` (`§3.2` line 217):** Uses built-in official Worker hooks (`src/Runner.Worker/ActionManager.cs:1236-1290`, `JobExtension.cs:304-313`) to skip per-job action resolution/tarball downloads (~4.4 s/job) and verify trust-scope mounts before user steps run.
- **Per-slot `MBX_CACHE_DIR` layout (`<store>/slots/<slot>`, `§4.2` line 272, `§7.2` line 439):** Preserves `velnor-legacy/crates/velnor-runner/src/mbx_store.rs:6-13` so concurrent jobs on a node never serialize on the `mbx` registrar `flock` or Cargo target lock.
- **Non-blocking `Cache` check (`docs/goals.md:67`, `§4.4` line 298) with `warm|site|cold` tier logging (`§4.3` line 287):** Makes cache regressions immediately visible instead of silently skipping restores 3,636/3,636 times.

### 5. Verdict

Proposal A will not achieve its 4–5 min PR verdict target or minimum push-to-merge time: it assumes 4-way nextest sharding and warm compiler caches will shrink `velnor-runner-host`, `velnor-actions-cli`, and `maintenance-helpers` to ~1 min without inspecting the code and logs showing that single looped `#[test]` functions (203–274 s), hardcoded `--config build.jobs=2` flags (`mise.toml:90-193`), and 12 `threads-required = "num-test-threads"` golden tests (`.config/nextest.toml:17-19`) enforce a >3.5–4 min floor that sharding and caching cannot remove. Its single biggest flaw is an unworkable placement and pod-pooling architecture: keeping unmodified `Runner.Listener` inside pre-created pods (`§3.2`, `§6.1`) cannot bind specific acquired jobs to cache-warm nodes under the scale-set protocol (`generatejitconfig` is job-agnostic), and returning pods to a warm pool after running a job breaks sandbox isolation.

## Proposal C

### 1. Weakest assumptions

1. **Per-job cgroup `fanotify` read tracing allows skipping 88% of `merge_group` package-jobs while migrating to `velnor-gen`'s one-job-per-Cargo-root shape (`§5.2`, `§5.3`, `§5.4`).**
   - *What is wrong:* Those two mechanisms defeat each other. In `§5.2`, `velnor-node` records every file opened by any process in the job's cgroup and hashes that read set as the job's verdict key. In `§5.4`, Proposal C adopts `velnor-gen`'s one job per Cargo root (5 root jobs today, moving to 1 root workspace per `brief-v1.md:67`), where each root job runs workspace-wide `cargo fmt --all --check` and `cargo clippy --workspace --all-targets` (`generator/samples/velnor-new/expected/.github/workflows/rust-ci.yml:201,204,656,660`). A root job's cgroup therefore opens *every source file in that workspace* (plus `.git/HEAD`, `.git/index`, and packfiles whenever any build script, tool, or test runs `git`). Any commit merged to `main` in that workspace changes the root job's `fanotify` read-set hash, collapsing the 88% merge-group skip rate that `reuse.py` (`§5.3` line 290) estimated over 30 separate per-package jobs. In addition, `fanotify` open events miss directory scans (`getdents64`) and negative lookups (`ENOENT`), so a newly added file in a scanned directory is absent from the previous run's open trace.
   - *Evidence to settle it:* Running the `fanotify` tracer on real workspace-root jobs across 20 merge-group advances and measuring the actual root-job reuse rate and false-hit rate when new files are added to scanned directories.

2. **A single shared `MBX_CACHE_DIR` per node and trust scope can be bind-mounted read-only (for trusted `main`) and shared across concurrent jobs on a node (`§3.4` line 215, `§4` lines 230, 247, `§7` lines 380, 385).**
   - *What is wrong:* Proposal C cites `velnor-legacy/crates/velnor-runner/src/mbx_store.rs:1-12` in `§3.4`, but `mbx_store.rs:6-13` documents why a shared store directory failed in legacy: *"Inside it the layout is per slot, because mbx serialises on a registrar flock and Cargo on a target-dir lock, so two concurrent slots must never share either tree."* Furthermore, `mbx` creates and mutates registrar leases, action metadata, and temp files inside `MBX_CACHE_DIR` (`ci.yml:682` requires a writable `$MBX_CACHE_DIR/actions` directory); bind-mounting a trusted `MBX_CACHE_DIR` read-only into sandboxes (`§4` line 247) will fail on write or `flock` unless `mbx` reads the trusted store via `MBX_REMOTE_URL` or a per-slot writable overlay/copy.
   - *Evidence to settle it:* Running two concurrent `velnor-runner-host` builds in separate sandboxes on one node against a read-only or shared `MBX_CACHE_DIR` mount and measuring lock stall time and write errors vs per-slot stores.

3. **A central `velnor-dispatch` Deployment can feed `Runner.Worker spawnclient` inside worker-node sandboxes without `Runner.Listener` (`§3.2` lines 162, 178–196).**
   - *What is wrong:* `Runner.Worker` is not a self-contained stateless executor that only reads a JSON job message from a pipe. On startup, `JobRunner.RunAsync` calls `HostContext.GetService<IConfigurationStore>().GetSettings()` (`src/Runner.Worker/JobRunner.cs:47`), which reads `.runner` from disk and asserts `ArgUtil.NotNull(configuredSettings)` (`src/Runner.Common/ConfigurationStore.cs:280-297`) to obtain `AgentName` (`JobRunner.cs:167`), `WorkFolder` (`JobRunner.cs:146`), and `ServerUrlV2` (`ConfigurationStore.cs:102-112`). Normally `Runner.Listener` unpacks `--jitconfig` (`src/Runner.Listener/Runner.cs:234-253`) to write `.runner` and spawns `Runner.Worker spawnclient <pipeOut> <pipeIn>` as a child process inheriting numeric anonymous OS pipe file descriptors (`src/Runner.Common/ProcessChannel.cs:51-68`) that must stay open until job completion (`src/Runner.Worker/Worker.cs:106-121`). A remote `velnor-dispatch` pod cannot pass inherited pipe FDs across Kubernetes nodes; `velnor-node` (or an in-sandbox shim) must synthesize `.runner`, spawn `Runner.Worker`, hold the local pipe FDs open, and relay `MessageType.CancelRequest` frames (`Worker.cs:122-135`).
   - *Evidence to settle it:* A spike launching unmodified `Runner.Worker 2.338.0` via `velnor-node` without `Runner.Listener`, verifying `.runner` configuration loading, step execution, and mid-job cancellation.

4. **Moving to `velnor-gen` (`#1290`, `§5.1`, `§5.4`, `§8 Phase 3`) provides "one job per Cargo root, with lanes: build once, then clippy, docs and tests in parallel" and `mbx` integration.**
   - *What is wrong:* In `generator/samples/velnor-new/expected/.github/workflows/rust-ci.yml:173-280` and `generator/crates/velnor-render/src/rules.rs:12-21, 43-55`, `velnor-gen` runs Format, Lint, Doc, per-package check, and Test **sequentially** (no `background: true` steps), caches `target/` via `actions/cache` without `mbx`, omits the `local-mode` feature run for `velnor-runner-host`, omits `check-maintenance-helpers` and `check-generator-samples`, and emits only `Required` (omitting `Required verdict` required by ruleset `24396608`).
   - *Evidence to settle it:* Extending `velnor-gen` to emit `mbx` setup, parallel check steps, `local-mode`, and both required check names (or updating ruleset `24396608`) before Phase 3 cutover.

### 2. Factual errors

- **PR #1324 cache volume concurrency (`§3.4` line 215):** Claims PR #1324 specifies *"one `ReadWriteOncePod` cache volume per (node, family): it serializes jobs."* False: PR #1324 (`~/.cache/ci-ambition/evidence/k8s-1324.md:298-300`, `evidence.md` §D.9 line 937) explicitly shards each node into $K$ cache slots (`cache_slots_per_node`): *"For N concurrent jobs per node, shard into K cache slots per node (slot index is a label; slot selection is a pure function, like `local/slot.rs`)."*
- **LVM RAID0 striping across data NVMes on workers (`§8a` rank 5, line 418):** Proposes an XFS cache volume *"LVM-striped over the data NVMes (raid0 is fine because it holds cache only)."* Per `velnor-runners/state/inventory.md:32-55` and `evidence.md` §B.1.4 line 491, three of the five workers (`velnor-241`, `velnor-5`, `velnor-190`—the entire Finland site) have **only one data NVMe** (`1 × 3.5 TB` OS + `1 × 3.5 TB` data), so RAID0 striping across data disks is impossible on 3 of 5 workers; the two Germany workers (`velnor-240`, `velnor-105`) mix `3.5 TB` and `14 TB` drives.
- **`JobDispatcher.cs` line citation for 60 s renewal (`§3.2` line 194):** Cites `JobDispatcher.cs:734` for renewing the job lock every 60 s. Line 734 is the method header of `RenewJobRequestAsync`; the 60 s renewal loop (`await HostContext.Delay(TimeSpan.FromSeconds(60), token)`) is at `src/Runner.Listener/JobDispatcher.cs:775-776` (`evidence.md` §F.2.4 line 1241).

### 3. Missed bottlenecks or risks

- **Unsharded per-root jobs lose cross-node test and lint parallelism (`§5.4`, `§5.6`):** Proposal C collapses 31 per-crate jobs into 5 per-root jobs (and soon 1 consolidated root workspace per `brief-v1.md:67`) while claiming in `§5.6` that *"After the fixes above, no velnor-new suite qualifies"* for nextest sharding. Even after splitting the two looped tests, a full root-workspace run (`velnor-actions-orchestrator` 631 tests + `velnor-actions-workflow-renderer` 317 tests + `velnor-actions-cli` 226 tests + `velnor-archive-guard` 55 tests, `evidence.md` §C.5 line 756) inside a single 16–32 CPU sandbox leaves 448 of the cluster's 480 threads idle on a single-root or consolidated-workspace PR.
- **Unexplained Cargo sources 48/48 cache miss (`§1.4` line 109):** Notes that the sources cache missed in 48/48 logs, but never diagnoses why scale-set jobs missed the exact key that hosted `Plan` hit (`actions/cache` hashing `/home/runner/_work/_temp` vs `/home/runner/work/_temp` into `version`), which remains relevant for hosted fallback and Stage A.
- **Trusted builder lag under `max_entries_to_build = 6` (`§3.2` line 174, `§5.3` line 293):** Making the post-merge `velnor-node` builder the *only* writer to the trusted `mbx` store (`§3.2` line 174) means back-to-back merge queue batches start before the previous `main` advance finishes building unless jobs read content-addressed objects across recent `main` ancestors without waiting for a commit-level seal.

### 4. Ideas worth taking

- **End-to-end push-to-merge measurement and zero-code merge-queue fixes (`§1.1` lines 29–44, `§5.3` lines 295–297):** Measuring the 85.1 min push-to-merge median (399.5 min on 11-18) uncovered three immediate high-leverage fixes no other proposal quantified: raising ruleset `max_entries_to_build` from 2 to 6, requiring agents to enable auto-merge on PR creation (saving 7.5 min median / 87.9 min p90 green-to-enqueue delay), and stopping agents from pushing catch-up merges of `main` into PR branches (which trigger redundant full PR runs).
- **Exact code fixes for the three critical-path jobs (`§1.3` lines 68–91, `§5.5` lines 313–318):** Removing `--config build.jobs=2` / `--jobs 2` in `mise.toml:90,108,128,137,148,157,170,193`; isolating the 12 `threads-required = "num-test-threads"` golden tests in `.config/nextest.toml:16-19`; splitting the 40-case loop in `crates/velnor-actions-cli/tests/image_publication_public.rs:86` and the 6-case loop in `crates/velnor-runner/crates/velnor-runner-host/src/launch/bootstrap/unbound_retirement/tests/shape.rs:98` into individual `#[test]` functions; and landing the Turso journal schema-validation/caching fixes (#1333/#1349).
- **Post-assignment placement by terminating `acquirejob` in `velnor-dispatch` before selecting the node (`§3.2` lines 185–196):** Because `generatejitconfig` is job-agnostic, having the central dispatcher hold the JIT broker sessions and call `acquirejob` first is the cleanest way to inspect a job's trust class, repo, and cache family before binding it to a warm node.
- **Moving `kubelet --root-dir` / `emptyDir` scratch off the single OS NVMe onto the data volume (`§8a` rank 5, line 418)** and **setting CI debuginfo to `line-tables-only` / `none` (`§8a` rank 6, line 419, measured −14% wall / −27% CPU-s).**

### 5. Verdict

Proposal C has the best diagnostic depth of the three: it is the only proposal that measured the full 85.1 min push-to-merge loop, identified the `max_entries_to_build = 2` and 0%-auto-merge bottlenecks, and pinpointed every code-level bottleneck in `mise.toml:90-193`, `.config/nextest.toml:16-19`, `shape.rs:98`, and `image_publication_public.rs:86`. Its single biggest flaw is combining per-job cgroup `fanotify` verdict keys (`§5.2`) with workspace-wide `velnor-gen` root jobs (`§5.4`) and a shared read-only `MBX_CACHE_DIR` (`§4`): a workspace-root job opens every file in the workspace (plus `.git`), invalidating the job-level `fanotify` key on almost every `main` advance and wiping out its estimated 88% merge-group reuse, while a shared read-only `MBX_CACHE_DIR` breaks `mbx`'s writable per-slot registrar lock contract (`mbx_store.rs:6-13`).

## Proposal D

### 1. Weakest assumptions

1. **Routing the 8 hosted jobs to the cluster (Phase 1) will hit `PR p50 ≤ 12 min, p90 ≤ 20 min` across peak and quiet periods before any cache, parallelism, or test fix lands (`§1` lines 7, 46–49, `§8` lines 393, 397).**
   - *What is wrong:* Proposal D's 11.37 min p50 / 18.68 min p90 replay is a ceteris paribus counterfactual that replaces hosted queue waits with 12 s while holding recorded cluster job durations constant. On Nov 18, Proposal D's own replay produced **13.93 min p50 / 36.87 min p90** (`§1` line 48) and noted that GitHub pre-job admission alone had a **25.45 min p90** (`§1` line 49)—already failing its Phase 1 gate (`p50 ≤ 12 min, p90 ≤ 20 min` across peak and quiet periods, `§8` lines 393, 397). Worse, on Nov 18 the 21.6 min median hosted `Plan` queue (`evidence.md` T5 line 195) throttled how many 31-job fan-outs entered the cluster at once; even throttled, cluster CPU contention stretched `velnor-runner-host` median duration from 3.7 min to 8.8 min and fan-out span to 10.7–13.5 min (`evidence.md` T5/T6 lines 194–204). Removing the `Plan` queue barrier while every job still compiles 481 crates cold will increase simultaneous cluster concurrency and stretch Phase 1 fan-out times further.
   - *Evidence to settle it:* Measuring cluster pod concurrency, CPU pressure, and PR p50/p90 across 50 peak-and-quiet PR runs immediately after `velnor-actions` v0.1.81 moves the 8 gate jobs to the cluster.

2. **Keeping ARC (`§3` line 109, `§8` Phases 1–4) is compatible with achieving 75% warm-node cache placement (`§4` lines 161–165, 185).**
   - *What is wrong:* Proposal D keeps ARC's listener and controller (`arc/cmd/ghalistener/scaler/scaler.go:135,339`) and never schedules replacing it in Phases 1–4 (`§8` lines 397–400), yet `§4` line 185 assumes **75% of jobs land on a warm node** by minimizing queue + materialization + compile/test time and hashing on `repo/workspace/target/toolchain` (`§4` lines 162–163). Under ARC, `ghalistener` only patches an integer replica count on `EphemeralRunnerSet` (`scaler.go:270-339`); pods are scheduled onto nodes before job assignment, and GitHub assigns any acquired job on `[velnor, ubuntu-26.04-scale-set]` to whichever idle `Runner.Listener` polls next (`evidence.md` §F.1.3, §F.7.2). Without either separate scale-set labels per workspace or a custom dispatcher that calls `acquirejob` before selecting a node, ARC placement across 5 workers is cache-blind (~20% random node hit).
   - *Evidence to settle it:* Measuring the per-workspace node-affinity hit rate across the 5 workers under unmodified ARC during concurrent PR runs.

3. **Only ~two-thirds of compiler invocations are eligible for `mbx` lookup, capping combined node+site warm hits at ~60% of all invocations (`§4` line 186, `§7` lines 282–284).**
   - *What is wrong:* Proposal D summed 154 `mbx` summary lines (`18,818 hits, 272 misses, 26,808 not looked up, 306 bypassed`) from today's cold-pod runs, observed that `19,090 / 46,204 = 41.3%` (or ~2/3 on selected passes) were looked up, and multiplied its warm node+site hit rate (`90.4%`) by 2/3 in `§4` line 186 to claim *"At two-thirds eligibility this is only about 60% of all invocations."* That treats a cold-pod symptom as permanent compiler ineligibility: in today's jobs, Pass 1 (`Build test executables`) starts with an empty `$RUNNER_TEMP/velnor/mbx` and no remote (`ci.yml:678`), so 100% of Pass 1 units (`0 hits, 0 misses, 404 not looked up, 7 bypassed`, `velnor-p3-ci-baseline.md:104,120`) have no prior prediction manifest and log as `not looked up`. Once Pass 1 populates the store, Pass 2 (`Clippy`) looks up 359 of 395 units (`90.9%`) and hits on 355 (`98.9%`). On a node pre-warmed from `main`, Pass 1 already has prediction manifests.
   - *Evidence to settle it:* Running Pass 1 (`cargo nextest list --list-type binaries-only`) against a pre-warmed `MBX_CACHE_DIR` from `main` and measuring `(hits + misses) / total_compilations`.

### 4. Ideas worth taking

- **Exact diagnosis of the 48/48 Cargo sources cache miss (`§1` line 66):** Proposal D is the *only* proposal to compare the primary cache keys logged in the 48 Rust jobs against `Plan`, verify they matched byte-for-byte (`${{needs.plan.outputs.sources_key}}`), and identify `actions/cache`'s internal `version` hash (computed from resolved `path:` `/home/runner/_work/_temp` vs `/home/runner/work/_temp` and compression) rather than blaming the key formula.
- **Cost-based placement and rebuild-vs-restore decision (`§4` lines 152, 159, 164):** Formulating placement to minimize `queue_delay + materialization + compile_test + reporting`—so an idle same-site node with a 12 s restore beats a warm node busy for 35 s (`§4` line 164), and units cheaper to compile than restore are rebuilt cold.

### 5. Verdict

Proposal D is the most methodologically rigorous and security-disciplined of the three—its dependency-graph replay (`audit/replay.ts`), its identification of the `actions/cache` path-version mismatch (`§1` line 66), and its critique of single-branch `fanotify` read tracing (`§5` line 207) are all sharper than A and C. ## Cross-cutting

### Where the three proposals agree

- **Queueing on the 8 GitHub-hosted gate/lint jobs is the #1 immediate regression:** On Nov 18, 79–90% of PR wall time was queue wait on hosted `ubuntu-26.04` (`Plan`, `Ledger CLI`, 4 lints, `Required verdict`, `Required`), while cluster scale-set jobs queued 0.2 min median (`evidence.md` T4/T5). Moving those 8 jobs onto locked-down cluster pods (`velnor-actions` v0.1.81 / PR #1332) is Phase 0/1 for all three and drops the no-contention PR floor to ~10–11.4 min.
- **Three-tier cache hierarchy (node-local NVMe → same-site cache server → GitHub cache fallback):** All three recognize that cross-job cache reuse on the scale set is 0% today (`emptyDir` volumes, 48/48 sources miss, 58/58 toolchain miss, 68/68 empty `MBX_REMOTE_URL`, 3,636/3,636 skipped state restores) and that GitHub's remote cache (13.6–22.4 MB/s, 120 ms RTT, 65–110 s for a 1.46 GB bundle) cannot meet the 30 s first-cargo target (`docs/goals.md:57`). All three keep Tier 1 traffic same-site (DE vs FI) to avoid the 35 ms WireGuard link.
- **Stop re-running full CI on `push` to `main`:** All three skip the redundant 39-job `push` run when the pushed SHA equals a validated `merge_group` SHA (120/159 merges = 75%, saving ~46–62 runner-min per merge, `evidence.md` T7).
- **Keep official `Runner.Worker`, keep `mbx`, keep `blaze` out of the merge gate:** All three retain `Runner.Worker` as the production executor (gating any native executor for the restricted `velnor-gen` profile behind an A/B test requiring ≥10% / ≥30 s gain and owner approval of `docs/goals.md:16`), use `mbx` as the sole compiler cache (rejecting `sccache`), and reject `blaze` for CI gating because it ignores `rust-toolchain.toml` (1.99.1) in favor of `blaze-2026-10-27`, lacks `clippy`/`fmt`/`doc`/`nextest`, and violates `docs/goals.md:36`.
- **Pod CPU shaping and kubelet reservations:** All three add `kubeReserved`/`systemReserved`, bound pod CPU concurrency to stop single pods from bursting to 83.7 cores (`evidence.md` §B.2.2) and stretching busy-day job durations 1.2–2.4× (`evidence.md` T6), and match `CARGO_BUILD_JOBS` / nextest threads to the pod's CPU budget.

### Where they conflict, and which side the evidence supports

1. **Why the fan-out takes ~8.5–10.7 min and whether nextest sharding alone fixes it (A vs C & D):**
   Proposal A assumes `maintenance-helpers` (508 s) is pure cold compilation and that 4-way `nextest --partition` divides `velnor-runner-host` (192 s) and `velnor-actions-cli` (238 s) tests down to 48–60 s (`A §5.3, §5.5`). Proposals C and D inspected the code and logs and proved A wrong: `velnor-runner-host` is set by one 6-case loop test (`shape.rs:98`, 203–271 s in Turso SQL parsing, PRs #1333/#1349), `velnor-actions-cli` by one 40-case loop test (`image_publication_public.rs:86`, 258–274 s), and `maintenance-helpers` by eight `--config build.jobs=2` flags (`mise.toml:90-193`) plus 12 serial golden tests (`threads-required = "num-test-threads"`, `.config/nextest.toml:17-19`, 211–246 s). **The code and logs decisively support C** (D caught the two looped tests but missed `mise.toml`'s `-j2` and `.config/nextest.toml`'s serial golden tests).
2. **Why Cargo sources missed 48/48 on scale-set jobs while hitting 10/10 on hosted `Plan` (A vs D):**
   Proposal A blames `sources-compat` for hashing `ImageOS` (`A §1.4, §4.2`). Proposal D checked the logs and showed the 48 Rust jobs requested the exact `sources_key` that `Plan` hit (`ci.yml:671`) and missed because `actions/cache/restore` hashes its `path:` input (`/home/runner/_work/_temp/...` on scale-set pods vs `/home/runner/work/_temp/...` on hosted `Plan`) into its internal cache `version` (`D §1` line 66). **The workflow code (`ci.yml:445, 667-673`) supports D.**
3. **How to place jobs onto cache-warm nodes under the scale-set protocol (A & D vs C):**
   Proposal D keeps ARC through Phase 4 (`D §3, §8`) while assuming 75% warm-node placement (`D §4`); Proposal A keeps `Runner.Listener` inside pooled pods (`A §3.2, §6.1`). Both fail against `actions/scaleset` (`client.go:765-796`, `evidence.md` §F.1.3): `generatejitconfig` takes only `{name, workFolder}`, and GitHub assigns any acquired job to whichever idle runner in the scale set polls next. **The protocol code supports C's `velnor-dispatch` architecture (`C §3.2`)**—holding the JIT broker sessions centrally, calling `acquirejob` to inspect the full job message first, and then picking a warm node and launching `Runner.Worker` (via a local node shim that writes `.runner` and holds the anonymous pipes open, `JobRunner.cs:47`, `ProcessChannel.cs:51-68`).
4. **Node-local `mbx` store layout: per-slot directories (A) vs one shared read-only bind-mounted directory (C):**
   Proposal C mounts one node-wide `MBX_CACHE_DIR` read-only into sandboxes (`C §4` lines 230, 247). Proposal A uses one `MBX_CACHE_DIR` slot directory per runner slot (`A §4.2, §7.2`). **The code (`velnor-legacy/crates/velnor-runner/src/mbx_store.rs:6-13` and `ci.yml:682`) supports A**: `mbx` requires a writable `$MBX_CACHE_DIR/actions` directory and serializes on a registrar `flock`, so concurrent pods must use per-slot directories (or a node-local HTTP remote via `MBX_REMOTE_URL` / reflinked per-slot views).
5. **Merge-group verification reuse: whole-tree equality (A) vs per-job cgroup `fanotify` (C) vs static/dep-info closure with signed unit receipts (D):**
   Proposal A's full-tree comparison matches only 7/45 (16%) of merge-group runs (`evidence.md` T7). Proposal C's per-job `fanotify` trace (`C §5.2`) fails once jobs move to workspace-wide `velnor-gen` root jobs (`C §5.4`, where one root job's cgroup opens every crate in the workspace plus `.git`), and misses unexecuted branches and newly added files in scanned directories (`D §5` line 207). **The evidence supports D's signed per-unit receipts keyed on Cargo metadata + `velnor-ci inputs` dep-info closure + declared hermetic non-Rust inputs, combined with C's merge-queue operational fixes (`max_entries_to_build: 2 → 6`, auto-merge, no manual `main` catch-up merges).**

### Hypotheses (H1–H5) judged differently after reading the proposals

- **H5 (Change-aware workflows) and its interaction with job granularity:** Reading C's 85.1 min push-to-merge breakdown alongside C's `fanotify` flaw and D's input-closure rules sharpens my judgement on H5: collapsing 31 per-crate jobs into coarse workspace-root jobs (`velnor-gen` today, and soon 1 monolithic root workspace per `brief-v1.md:67`) is a net win **only if** selection, test filtering (`-E "$TEST_FILTER"`), and `merge_group` verdict receipts remain at **package/check-unit granularity**. If verdict reuse is keyed at the whole-job level, a single root-workspace job invalidates on almost every `main` advance and forfeits the 88% merge-group work reduction.
- **H2 (From-scratch runner) and H4 (Local caches) vs repository code ceilings:** C and D prove that no runner or cache architecture can push PR verdicts under 3.5–4.5 min until four code bugs inside `velnor-new` itself are fixed: `--config build.jobs=2` (`mise.toml:90-193`), 12 serial golden tests (`.config/nextest.toml:17-19`), the 40-case and 6-case serial test loops (`image_publication_public.rs:86`, `shape.rs:98`), and quadratic Turso journal opens (#1333/#1349). Conversely, H2 holds more strongly at the **dispatcher layer** (`velnor-dispatch` replacing ARC + `Runner.Listener`) than at the step-executor layer: because `generatejitconfig` is job-agnostic, owning `acquirejob` before node selection is the prerequisite for H4's cache-affine placement within a shared scale set.
