# Velnor: reimagining the runner for AI coding agents

## The picture

When AI agents write the code, separating local inner-loop commands from remote CI is pure waste.
Twelve builder agents and four reviewer agents run `cargo check`, `cargo clippy`, and `cargo nextest` dozens of times per task across local Apple Silicon worktrees, only for CI to repeat the same work on the pull request, the merge group, and `main` [M, 120 of 159 merges].
In an agent-native Velnor, the runner is not a post-push batch cluster.
It is the execution engine for the agent's inner loop itself.
Every agent command routes through a local `velnord` daemon and a `cargo` shim (`velnor-shim`).
Instead of burning local Mac cores on unshareable builds, `velnord` ships the byte delta of the agent's worktree to a warm cluster node, runs the command as a canonical Velnor obligation inside a sealed Linux sandbox over a reflinked `main` generation, streams compiler and test output back to the terminal, and mints an Ed25519-signed Witness 1 receipt in `velnor-ledger`.
When the independent verifier subagent (`tailrocks-verifier`) checks the change before pull-request creation, it runs Witness 2 on a second cluster node with a distinct test-order seed against the virtual merge of the worktree and the live merge-queue tip.
By the time the agent runs `git push` and adds `velnor:verify`, both witness slots in `velnor-ledger` are already full.
The pull-request verdict and the merge-group check become 1 to 3 second ledger lookups [E], leaving only GitHub's 45 second merge queue [M] and post-merge cold Audit A1.

### N01: Cargo and CLI shim routing agent inner-loop commands through a local Velnor daemon

Agents invoke `cargo check`, `cargo test`, `cargo nextest run`, and `cargo clippy` directly from shell tool calls.
Asking prompts to remember a new CLI command leaks runs back to raw `cargo`, so `velnor local up` prepends `velnor-shim` symlinks for `cargo`, `cargo-nextest`, and `cargo-clippy` into the agent's `PATH` alongside a background `velnord` daemon.
When an agent runs a command, `velnor-shim` parses the package, target, profile, and feature flags, normalizes them against the base commit's released `velnor-ci` obligation inventory (`§8.1`), hashes the working tree (`C2`), and queries `velnord` over a local Unix socket.
If `velnor-ledger` already holds a passing receipt for that exact key, `velnord` prints the cached summary and exits 0 in under 50 ms [E].
If the key misses, `velnord` dispatches the obligation through Velnor's sealed sandbox path, streams compiler and test output back to the agent, and records the resulting receipt.
Commands with ad-hoc filter strings or flags outside the released inventory still execute through `velnord` for fast feedback, but are tagged `Tier 0` and never enter `velnor-ledger` (`C3`, `C4`).

### N02: Remote-by-default inner-loop execution on warm cluster sandboxes against delta-synced worktrees

Local Apple Silicon Macs lack the cluster's 10.6 GiB warm Linux `target/` snapshots (`§7.5`), XFS reflink volumes, and eBPF file-access audit (`§6.4`), and 4 to 8 concurrent agent worktrees quickly saturate a laptop's RAM and CPUs (`61 s` for a one-file edit [M, `I073`]).
Under `velnord`'s remote-by-default mode, an agent's local command runs on the Hetzner cluster (`de` or `fi`) without requiring a `git commit` or `git push`.
`velnord` diffs the worktree index and untracked files against the commit already present in the node's bare Git mirror (`§7.4`), packs only the modified blobs (`Δ`, typically 5 to 50 KiB) into an in-memory bundle, and sends an `ensure(tree, obligations)` stream to `velnor-dispatch`.
The assigned `velnor-node` reflink-clones its sealed `main` checkout and warm generation `G` in `0.25 s` [M, `S12`], writes `Δ` with `M_G` mtimes (`§7.3`), verifies the full staged tree hash (`0.1 to 0.3 s` [E]), executes the command inside a warm `build` sandbox (`§5.8`) with the eBPF read audit active, and signs a `Tier 2` Witness 1 receipt via `velnor-signer` (`§6.5`).
The agent gets a 96-thread EPYC build in `0.56 s` (no-op [M]) to `15 to 25 s` (code edit [E]), and its interactive run counts directly as Witness 1 for CI.

### N03: Four-tier receipt provenance lattice and two-witness gate accounting

To prevent an unverified local environment from ever polluting CI, `velnor-ledger` enforces a strict four-tier provenance lattice across all verification record slots (`§6.2`).
`Tier 0` (`untrusted-feedback`) covers unsealed host execution and ad-hoc commands, and is never persisted.
`Tier 1` (`local-sandbox`) covers obligations executed inside a sealed Linux container or microVM on the developer's Mac and signed by the local root `velnor-signer` daemon.
It accelerates local cross-worktree reuse and the non-minting fast-red lane (`§6.2`), but fills zero merge-gate slots under standard `C2` rules.
`Tier 2` (`cluster-candidate`) covers obligations executed and observed by a cluster `velnor-node` over a verified generation `G` and signed by that node's out-of-sandbox Ed25519 signer, filling Witness Slot 1 and Witness Slot 2 in `velnor-ledger`.
`Tier 3` (`trusted-main`) covers records promoted from `Tier 2` only after their commit lands on `main` and cold Audit A1 reproduces equal binary digests and test outcomes (`§6.2`, `§6.5`).
`Velnor / Verified` requires every obligation in the released inventory to hold two passing `Tier 2` or `Tier 3` receipts in distinct slots (`node_1 != node_2`, `seed_1 != seed_2`, `gen_1 != gen_2` or cold) at the active epoch.

### N04: The `arm64` vs `amd64` problem

Developer and agent hosts are `aarch64` Apple Silicon Macs, while the production cluster workers (`velnor-105` to `velnor-241`) are `x86_64` EPYC 9454P Linux servers (`§9`).
Under `§6.1` (`C2`) and `velnor-user-experience.md` §1.2, the execution fingerprint (`arch`, `OS`, `kernel`, `CPU features`) is part of every obligation key, and running `x86_64` under QEMU or Rosetta on a Mac is both slow (2 to 5x) and unsound (emulation alters memory ordering, float rounding, and page size).
Option A, which fits Decisions 1 to 24 today, solves this by making `velnord` remote-by-default (`N02`).
The Mac acts as a thin editing and orchestration client, and every receipt-minting command runs natively on the `x86_64` cluster.
Option B is an **owner question**: split the obligation key into an architecture-invariant `LogicalObligationKey` (tree hash, lockfile, toolchain version, features, expected test IDs) and a per-slot `ArchFingerprint`, and permit a local `aarch64-unknown-linux-gnu` microVM (via Apple's Containerization framework, Decision 21, attested by a root Secure Enclave signer, `N09`) to fill Witness Slot 1, while strictly requiring Witness Slot 2 and Audit A1 to execute on cluster `x86_64-unknown-linux-gnu`.
Because the gate requires both slots to pass (`Slot 1 AND Slot 2`), an `arm64` pass can never mask an `amd64` failure, while fast local M3 and M4 Max cores absorb 50% of cluster witness load (`6 to 38` runner-min per PR [E]) and catch cross-architecture bugs before merge.

### N05: Continuous verification of committed-but-unpushed work (Owner question on Decision 12)

Decision 12 mandates that unlabelled PRs and intermediate pushes start no verification, because `45%` of historical PR runs (`1,156 of 2,558` [M, `§1.1`]) were cancelled before completion, and `D19` defaults to rejecting pre-label speculation.
However, in an agent workflow, there is a 30 to 180 second window between the agent's final `git commit` (while it runs `/deslop`, `/no-comments`, and formats the PR body) and the moment it opens or labels the PR.
If Velnor waits for the `velnor:verify` webhook to start Witness 2 (or any obligation missed during editing), the full `15 to 25 s` compile and `10 to 60 s` test chain stays on the label-to-verdict clock (`§3`).
We propose an **owner question** narrowing `D19`: allow a `.git/hooks/post-commit` hook in `velnord` (or an explicit `velnor preflight` hook triggered when the agent enters its PR-opening step) to submit the committed tree merged with the queue tip (`N11`) at strictly preemptible `batch` (`cpu.idle`) priority (`§9`, `N77`).
It writes zero GitHub statuses or check runs while unlabelled, preserving Decision 12's exact gate state machine (`§8.2`), and freezes or terminates immediately if foreground work needs the CPU or RAM.
For the `55%` of commits that get labelled (or `> 85%` when triggered at the agent's pre-PR step), `25 to 85 s` of verification finishes during PR authoring, cutting label-to-verdict to `1 to 3 s` [E] at a cost of `5 to 10` idle runner-minutes per superseded commit.

### N06: Agents querying the ledger to avoid duplicate work between agents

Under `AGENTS.md` and `user_global` rules, every implementation unit spawns independent subagents: a builder engineer writes and tests the change, `tailrocks-verifier` runs the repo's verification gates from the root, and `tailrocks-code-reviewer` (plus `arena` or `swarm` workers) inspects and tests the branch.
Without shared state, three agents run the same `cargo clippy` and `cargo nextest` suites on the exact same tree hash within minutes of each other.
By routing every agent through `velnord` (`N01`) and exposing `velnor ledger query --tree <tree_sha>`, concurrent agents share `InFlight` and completed obligation records in `velnor-ledger` (`§6.2`).
If Agent B requests key `K` while Agent A is compiling or testing `K`, `velnord` attaches Agent B to the live log stream of Agent A's execution (`N29`) instead of spawning a duplicate sandbox.
Better yet, when `tailrocks-verifier` runs after the builder agent, `velnor-shim` detects that Witness Slot 1 for key `K` is already filled by the builder's run and automatically schedules `tailrocks-verifier`'s invocation as **Witness Slot 2** (on a distinct cluster node with a distinct test-order seed and twin or cold generation, `§6.2`).
That turns the mandatory subagent verification gate into the second CI witness, eliminating an entire duplicate pass (`15 to 45` runner-minutes and `2 to 10 min` wall time saved per task [E]).

### N07: Flake detection during development

In synthesis measurement `S1`, `8.1%` of full push runs failed on a SHA whose merge-group run had just passed (`10 of 124` runs [M]), and requiring two witnesses doubles per-PR flake exposure to `15.5%` (`1 - 0.919^2` [M, `§1.3`]) with zero automatic retries.
When an AI agent hits a flaky test failure during local development, it assumes its own edit broke the test and can spend 20 to 60 minutes refactoring valid code or adding bad guards.
With `velnord` connected to `velnor-ledger`, every test failure triggers an immediate `< 20 ms` provenance check: if the exact obligation key `K` already holds a passing receipt in another witness slot or prior run, `velnord` flags `FLAKE_DISCORDANT_ON_KEY` (`pass` and `fail` observed on identical `C2` inputs).
If `K` is new because the agent edited a file, `velnord` checks whether the failing test ID has a recent discordance history in `velnor-ledger` and automatically dispatches a 2 to 5 second single-test run against `main`'s warm generation (`N02`) to prove whether the failure reproduces without the agent's diff.
The obligation key still fails closed and blocks merge (zero retries for green, `§1.2`), and the discordant pair is logged toward `§1.3`'s two-failures-in-7-days owner issue rule, while the agent receives an authoritative JSON verdict (`DETERMINISTIC_REGRESSION` vs `PRE_EXISTING_FLAKE`) so it never chases ghosts.

### N08: Scheduler priority for interactive agent commands

The cluster's five EPYC workers run at `92 to 95%` CPU during peak multi-org bursts (`tailrocks`, `ChainArgos`, `jackin` [M, `§B.2.1`]), where queueing delay reaches `~19x` service time (`§9`, `N38`).
If an agent's inner-loop `cargo check` or single-package test queues behind 39-job PR runs or cold Audit A1 rebuilds, the agent stalls for 2 to 4 minutes per tool call.
We split `velnor-dispatch`'s priority queue (`§9`) into five bands: `merge > gate > interactive-witness-1 > pr = other-org > batch`.
Any command initiated from an interactive `velnord` client stream with an expected duration `<= 30 s` enters at `interactive-witness-1`, subject to a token bucket of 1 concurrent slot per agent session and at most 50% of non-reserved site capacity.
On arrival, `velnor-node` immediately freezes (`cgroup.freeze`, `< 10 ms`) any `batch` (`cpu.idle`) containers on the node and gives the interactive sandbox access to the node's shared compile jobserver (`16 to 64` threads, `N96`).
If the interactive command runs past 30 seconds or its client disconnects, `velnor-node` demotes its cgroup weight to `pr` in place without restarting it.
The reserved `merge` and `gate` lane (`16` build CPUs + `2` gate CPUs per site, `§9`) remains strictly higher priority, so interactive agent bursts never delay a merge group while achieving `<= 0.5 s` P50 and `<= 2.0 s` P90 start latency [T].

### N09: Signing and attestation of local and remote results

If an agent could forge a receipt by writing a JSON file or calling an API from user space, a buggy test script or hallucinating agent could produce a false green.
Velnor enforces `C4` (`only what Velnor observed is evidence`) and `N35` through hardware- and privilege-separated signing (`§6.5`, `N89`).
On cluster workers (`Tier 2`), the Ed25519 private key per node and sandbox class lives inside `velnor-signer`, a root-owned daemon running outside every sandbox and separate from `velnor-node`.
When an agent runs `velnor exec --remote`, the sandbox has no network access to the ledger, no `.git`, and no signing key.
`velnor-ci obligation exec` reports each test event over a read-only file-descriptor pipe that only `velnor-node` holds (`§5.3`), and `velnor-signer` signs the receipt only after verifying the pre-run tree hash (`§7.4`), clean cgroup exit, zero out-of-contract eBPF syscall reads (`§6.4`), exact test-ID match against the base commit's inventory (`C3`), and SHA-256 digests of all executed binaries.
On macOS agent hosts (`Tier 1`, or `Tier 2` Witness 1 if the owner approves `N04` Option B), `velnor local up` installs `velnor-signer` as a `root`-owned `launchd` service backed by a non-exportable macOS Secure Enclave key, observing a locked-down Apple Containerization Linux microVM over a hypervisor vsock channel that the unprivileged agent UID cannot write.

### N10: How the PR verdict becomes mostly a lookup

Putting `N01` through `N09` and `N11` together eliminates the post-push execution phase for normal pull requests.
While the builder agent iterates, its final inner-loop `cargo clippy` and `cargo nextest` runs execute remotely on a warm cluster node (`N02`, `N08`) and populate Witness Slot 1 (`Tier 2`, `N03`, `N09`) in `velnor-ledger`.
Next, the mandatory independent `tailrocks-verifier` subagent runs `velnor verify`, which computes the virtual merge of the worktree with the live merge-queue tip (`N11`), reuses untouched roots from `main`'s `Tier 3` records, joins Witness Slot 1 from the builder (`N06`), and executes only Witness Slot 2 on a second cluster node with a different test-order seed and twin generation (`§6.2`).
Only after both witness slots pass does the agent run `git push`, open the PR with auto-merge enabled (`D2`), and add `velnor:verify`.
When `velnor-control` receives the `labeled` webhook (`1 to 2 s` [M]), it computes `merge-tree(queue_tip, pr_head)` (`~0.3 s` [E]), queries `velnor-ledger` for the obligation vector, finds 100% of non-`C5` records already satisfied by two valid `Tier 2` or `Tier 3` witnesses (`< 50 ms` [E]), and posts `Velnor / Verified: success`.
Assuming the 11 clock-reading test files (`§6.1`) use the key-bound deterministic clock (`G18`) so `C5 = 0`, the PR verdict drops from `26.7 min` P50 today [M] and `35 s` at the v3 Goal [E] to **`1 to 3 s`** [E], and 85 to 95% of merge groups also resolve by lookup in **`1 to 3 s`** [E], bringing push-to-merge to **`47 to 51 s`** [E] (`45 s` GitHub merge queue [M] + `2 to 6 s` Velnor).

### N11: Queue-tip virtual merge in the agent's local sandbox (`--against-queue`)

Today only `16%` of merge groups test the same tree that the PR tested (`7 of 45` [M, `§1.1`, `S4`]), because `main` or the queue moves between the PR's check and queue entry.
Section 8.3 raises that match rate to `60 to 75%` [E] by testing `merge-tree(queue_tip, pr_head)` at label time, and replay `N34` proved that when the window between verification and queue entry shrinks to `1 to 2 minutes`, the tree match rate reaches **`83 to 89%`** [M].
To capture that 1-minute window during local agent verification, `velnord` subscribes to a lightweight SSE stream from `velnor-control` that publishes the current merge-queue tip SHA and active speculative prefix trees (`N19`).
When `tailrocks-verifier` runs `velnor verify` seconds before `git push`, `velnord` computes `git merge-tree --write-tree <queue_tip> <worktree>` locally in `< 30 ms` [E] and mints Witness 1 and Witness 2 receipts for that exact merged tree hash.
When the agent pushes and labels immediately afterward, both the PR check (which merges against the same `queue_tip`) and the `merge_group` check hit 85 to 95% of the time [E], saving `6 to 38` runner-minutes per avoided group miss.

### N12: Structured failure receipts and cross-agent negative lookaside

Section 6.2 rightly forbids reusing a failed record to satisfy a gate, because a flake or transient fault must be re-runnable.
In local multi-agent work, however, a deterministic compile error or broken assertion on key `K` is frequently triggered multiple times in a row: an agent retries a command, a subagent checks the same broken worktree, or an `edited` or re-run event hits an unchanged head (`18.3%` of PR runs, `469` runs at `52.9` runner-min each [M, `§1.1`]).
When an obligation fails on key `K`, `velnor-ledger` writes a signed `FailedObservation` record containing the non-zero exit code, structured rustc and clippy JSON diagnostics, failing test IDs, and log blob digest.
If any agent invokes `velnor-shim` on the identical key `K` without changing a single input byte, `velnord` returns the cached structured JSON failure in `< 50 ms` [E] with a hint to pass `--rerun-failed` if testing for a flake.
Because a `FailedObservation` can only return a red exit code, its false-green risk is identically zero, while saving `1 to 4` redundant failed compiles per task (`30 to 120 s` of agent wait and `5 to 20` runner-minutes [E]).

## The first three steps

1. **Step 1: Build `velnord` and `velnor-shim` for remote-by-default inner-loop execution with `Tier 2` Witness 1 receipts (`N01`, `N02`, `N08`, `N09` cluster path; 32 agent-hours).**
   Implement the local `velnord` Unix-socket daemon and `cargo`, `nextest`, and `clippy` `PATH` shims, the delta-blob uploader against `velnor-node`'s bare Git mirror (`§7.4`), and the `interactive-witness-1` 30-second burst band in `velnor-dispatch` (`§9`).
   When an agent runs `cargo clippy` or `cargo nextest` locally on a Mac worktree, `velnord` syncs the `< 50 KiB` dirty-tree delta to a warm cluster sandbox, runs the canonical `velnor-ci` obligation over a reflinked `main` generation (`0.25 s` clone [M, `S12`]), streams compiler and test output back to the agent, and signs a `Tier 2` Witness 1 candidate receipt via the cluster node's out-of-sandbox `velnor-signer` (`§6.5`).
   **Immediate payoff:** removes local Mac CPU and RAM thrashing across concurrent worktrees, accelerates agent inner-loop builds from `61 s` [M] to `15 to 25 s` [E] (`0.56 s` on unchanged trees [M]), and completes 50% of CI witness verification during normal coding.
2. **Step 2: Wire `tailrocks-verifier` and `velnor verify` to execute Witness 2 against the live merge-queue tip (`N03`, `N06`, `N10`, `N11`; 20 agent-hours).**
   Add the queue-tip SSE broadcast from `velnor-control` and teach `velnor verify` (invoked by the mandatory pre-PR `tailrocks-verifier` subagent) to compute `git merge-tree --write-tree <queue_tip> <HEAD>`, reuse untouched roots from `main`'s `Tier 3` records, join Witness 1 from the builder agent's inner-loop receipts (`N06`), and schedule Witness 2 on a distinct cluster node with a distinct test-order seed (`§6.2`).
   Refactor the 5 `SystemTime`-reading test files in `velnor-ci` and `velnor-gen` (`§6.1`) to use the key-bound deterministic clock so `C5 = 0` for the helper and generator cohort.
   **Immediate payoff:** eliminates 100% of duplicate Witness 1 runs between builder and verifier subagents (`15 to 45` runner-minutes saved per task [E]), pre-fills both required `Tier 2` witness slots on the exact merge-group tree before `git push`, and turns both the `velnor:verify` PR verdict (`35 s` to `1 to 3 s` [E]) and 85 to 95% of merge-group verdicts (`25 s` to `1 to 3 s` [E]) into instant ledger lookups.
3. **Step 3: Ship instant ledger flake classification and structured failure lookaside in `velnord` (`N07`, `N12`; 16 agent-hours).**

   **Immediate payoff:** stops agents from burning 20 to 60 minutes debugging the repository's 8.1% background flakes [M, `S1`] and eliminates redundant failed compiles across subagents (`5 to 20` runner-minutes saved per task [E]) with zero relaxation of the zero-retry, zero-false-green merge gate.
