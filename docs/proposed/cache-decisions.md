# Cache redesign decisions

Status: adopted by the human owner for the CI cache redesign (seven decisions,
recorded 2026-10-20; decisions 8 and 9 adopted per the split brief, decision 10 per the 2026-10-22 security review, owner may revisit). Each decision below states what main implements now and
what the follow-up PRs deliver. This page is the decision record that
[`cache-contract.md`](cache-contract.md) section 2 and
[`hard-decisions.md`](../hard-decisions.md) decision 1 cite. A change to any
entry needs the owner's explicit approval.

Budget rule (applies to every entry): the repository cache quota is 10 GB.
Hot families plus the allowance for superseded entries stay at or below 85 %
of the configured quota, sizes come from
[`cache-measurements.md`](../implemented/cache-measurements.md), and a save that
would exceed its family ceiling is refused and reported, never attempted.
Successful and failed jobs are both covered: see decision 1 and the cases table.

## Decisions

| # | Decision | State on main | Remaining |
|---|---|---|---|
| 1 | **Save on build success even when tests fail.** A family saves when its producer step succeeded on a trusted run, regardless of test, lint or doc verdicts. It never saves on cancellation or a failed producer. | **Implemented** for every family. Sources (`sources-producer` job) and tools save on producer success; the compiled `mbx-bundle` family saves through `Record MBX producer success` (a marker written right after the compile step) and an `always() && !cancelled()` export and save that run only on trusted pushes, so a failing test, lint or doc step no longer starves the cache. Suite jobs that compile and test in one step mark after that step. | None. |
| 2 | **Dependency-seed family (D).** One Velnor-owned family archives the compiled dependency closure of the three fixed lane trees, minus `incremental/`, `examples/`, `tmp/`, `doc/` and every Cargo-reported executable. Written only by a non-crate seed job on a trusted main push; crate jobs restore read-only. | **Implemented on the MBX driver.** The family is the opaque `mbx-bundle` entry of unit `union` ([cache families](cache-families.md)): `Dependency seed` is one non-crate job per MBX Cargo workspace (`dependency-seed`, `dependency-seed-<root>`), runs on a protected default-branch push only, compiles the test, Clippy and documentation lanes for `--workspace`, and exports and saves the bundle after the producer succeeded. It uses job-level `continue-on-error: true` so cache failure cannot fail CI, runs no checks, uploads no report and is not in `Required`. Crate jobs restore the `union` entry read-only (no marker, export or save step). MBX decides the bundle content, so the exclusion list applies to a target-tree payload only, which no driver archives. **Seeds are off on main:** `[stacks.rust] dependency_seed = "off"` in `.velnor/config.toml` makes the generator emit no `Dependency seed` job, so nothing writes the family until P7 decides the compiled state. Authority: owner standing grant 2026-11-02, velnor-fast-ci GOAL.md, decisions.tsv row U-SEED. Undo: set `dependency_seed = "produce"` and regenerate. **Key v4 (schema 4, amended under owner standing grant 2026-11-02, velnor-fast-ci GOAL.md, decisions X53 and X57):** `velnor-v4-state-<trust>-<unit>-<root>-s256-<compat>-s256-<snapshot>-s256-<payload>`. The unit is `union` or `suite`; the root is a slug of the workspace root (`.` is `root`, `/` is `-`; a slug that collides with another root or contains the `s256` delimiter is a generation error). The compat digest binds the family, schema, path, unit, root, MBX version, toolchain, `uname -sm`, `ImageOS`, the resolved store path, the resolved checkout path and the literals `MBX_SHARE_OUT_DIR=1`, `MBX_BUILD_SCRIPT_EXECUTION=0`, `MBX_CC=0` and `SOURCE_DATE_EPOCH=0`; those four values are never read from the environment for the key and a publish gate refuses to export unless the job env holds them (`env_mismatch`). There is no ceiling line in compat. The snapshot digest covers only Rust inputs: the root `Cargo.lock`, the root's Rust inputs (tracked member directories, workspace manifest, `.cargo`, `rust-toolchain*` and the declared `[[stacks.rust.inputs]]` globs of its packages) and the producer task set, so a docs-only push keeps the snapshot. The payload digest is the sha256 of the stored file and is the last key segment, so a save never collides with an earlier writer of the same snapshot. Restore looks up the snapshot prefix first and the compat prefix as the fallback (newest entry of the same trust, unit, root and compat); an exact snapshot hit sets `producer_skip=true` and skips the save, while any other generation is saved even when its bytes shrink. Roots whose slugs collide are rejected at generation. | The Cargo driver has no seed (it archives no compiled state). |
| 3 | **Opaque `mbx cache export` bundles.** Velnor may archive the output of `mbx cache export --format directory`. It treats the bundle as opaque bytes; MBX owns the format and `mbx cache import` restores it. Velnor never parses or composes MBX objects. | **Implemented.** The `mbx-bundle` family ([cache families](cache-families.md)): key, restore, import, export and save steps in crate and suite jobs; the native action is install-only and `github-cache-mode: target` is removed with no compatibility path. The Plan job restores nothing (it installs MBX only). | None. |
| 4 | **Per-family pruning of superseded entries.** Deleting older exact keys of the same family on a trusted default-branch run, with `actions: write` scoped to that job, is not "global pruning". Other families and other trust scopes are never touched. | **Implemented.** The generated `.github/workflows/cache-prune.yml` has one job, `Prune superseded cache entries`, with `actions: write` as its only permission; it runs on `workflow_run` of the CI workflow (`types: [completed]`, `branches: [<default>]`, `workflows: [<ci workflow name>]`) and only when that run was a `push` to the default branch from this repository that was not cancelled (`event == 'push'`, `head_branch == <default>`, `head_repository.full_name == github.repository`, `conclusion != 'cancelled'`), never on a pull request, a fork, a manual or a scheduled run, and neither the Plan job nor `ci.yml` holds that scope. The trigger was `push` with `github.ref_protected == true`; it is amended under owner standing grant 2026-11-02, velnor-fast-ci GOAL.md, decisions X53 and X57, so that pruning runs after CI has finished saving its generation. The job has no checkout and runs no action. For each typed family except state it lists the `trusted` entries of that ref by key prefix, groups them by key without the final snapshot digest (one unit: root, workspace, version) and deletes all but the newest `retained_entries` of each unit. State entries (`velnor-v4-state-trusted-`) are grouped by `<trust>-<unit>-<root>` alone, so a compat change evicts the previous compat; in each group the newest complete entry and every entry newer than it are kept and every older entry is deleted. `complete(key)` means the key parses to the full v4 grammar (three `-s256-` segments of 64 lowercase hex digits after `<trust>-<unit>-<root>`) until the SEC-7 seal exists, then it means a verified seal. A key that does not parse, including a root slug that holds the `s256` delimiter, is never grouped and never deleted. Every retired state schema in the accumulating `RETIRED_STATE_PRUNE_PREFIXES` collection (`velnor-v1-state-trusted-`, `velnor-v2-state-trusted-` and `velnor-v3-state-trusted-`) is deleted entirely (retained count 0); each later state schema adds its retired prefix to that collection and never replaces it. The `pr` scope, other refs and anything outside a family are never listed. A failed list or delete is a `cache_unavailable` warning, never a failure. A non-hosted runner label falls back to `ubuntu-latest` (the job needs the GitHub CLI). | A save in flight when the job lists is pruned by the next CI completion. |
| 5 | **No PR-scope cache writes; one sources writer.** Pull requests, forks and merge groups never write the cache. The only writer of the sources family is the `sources-producer` job: push to the protected default branch only, after Plan reports that the exact sources key is missing, `continue-on-error`, outside `Required`. Every generated workflow runs under workflow-level `cache-mode: read`; only the named writers hold job-level `cache-mode: write`, and the generator rejects a writer role on a job that runs task code or a third-party `uses:` (outside the closed allowlist) or that is not gated to a trusted event. The `pr` trust scope and the per-PR cleanup handler are retired: #407 removed PR-scoped sources saves and `same-repository-scoped` is rejected as `obsolete_pr_write_policy`. | **Implemented** by CW-M (fci/cwm-cache-mode). Amended (earlier text: PR-scoped sources writes with cleanup on close) per owner standing grant 2026-11-02, velnor-fast-ci GOAL.md, decisions.tsv rows X57 and X59. The `qualification.yml` jobs that save (`cache-scale-set`, `empty-cache-hosted`, `empty-cache-scale-set`, `mbx-cache-write-hosted`) are writers only when dispatched from a non-default branch, so their entries never reach the default-branch scope; no release workflow dispatches `qualification.yml` (release gating uses `source-qualification.yml` and the generator-release composites), so the explicit-writer fallback of X59 is not used. The freshness procedure still names a manual "protected-main MBX cache roundtrip" as a precondition of SDK publication; that dispatch now runs from a non-default branch, which the pinned action supports through `save-on-workflow-dispatch`. `cache-mode` limits writes by scope, not by key name, so a forged key from a legitimate writer waits on SEC-7 attestation. | Family saves of jobs that run third-party code (Bun, Playwright, dbt, Python, Ansible stack families and MBX dependency seeds) are suppressed (`if: false`) until a producer role exists for them. PR-scoped compiled state is not written yet: the `pr` trust prefix of the v4 state key is reserved and trusted runs never restore it. Same-repository PR state writers, per-PR prune and the 8e9 B total admission follow in the PR-state unit (amended under owner standing grant 2026-11-02, velnor-fast-ci GOAL.md, decisions X53 and X57). |

| 10 | **Re-verify every restored Mise install.** A tools-cache entry can be written by any default-branch job that runs code, so no restored executable is trusted as restored: Rust is checked in `Verify restored Rust toolchain` against a pinned installed-tree digest (type, path, mode and SHA-256 of every entry, derived from the component tarballs of its pinned channel manifest; the stored `multirust-channel-manifest.toml` is an ordinary entry of the listing, bound by its SHA-256, and no parser reads it: rustup rewrites that file when it installs, so the installed phase and the file-by-file fallback overwrite it with the catalog-pinned `channel-rust-<version>.toml` bytes before they compare anything (the job-local verified copy if its SHA-256 equals the catalog row, else a download over HTTPS checked against that row; written to a temporary file in the same directory and renamed, mode 0644, never through a symlink or hard link and never into a directory), recreating it if it is missing, while the restored phase never repairs it, so a changed or missing manifest on the pinned path is `rust_tree_digest_mismatch`, and a restored match leaves the verified bytes in the job-local directory so the installed phase stays offline) before any network access. The pin is selected by the job's expected Rust version and target, never by the restored `components` file or toolchain directory name. Before any read of `toolchains/`, in both phases and on both paths, the step fails with `rust_toolchain_path_unexpected` unless `toolchains`, `lib` and `lib/rustlib` are real directories (an absent `toolchains/` is a fresh restore; a linked toolchain directory is `rust_toolchain_missing`), so no read or write goes through a link. The owned-home jobs, which restore the tools cache, render the target `x86_64-unknown-linux-gnu`. ARM targets have no pin row yet (owner standing grant 2026-11-02, velnor-fast-ci GOAL.md; decisions.tsv X44): when `toolchains/` holds exactly one entry, a `<version>-*-*-*` entry that is not `<version>-<target>`, the step treats it as unpinned and takes the file-by-file check; any other entry, or a second entry beside it, still fails the job. The check has three outcomes. A match passes with no network access. If a pin row exists for that version and target, only the pinned path runs: a components set no row pins, a `toolchains/` entry other than exactly `<version>-<target>`, a tree or listing difference, or a bookkeeping file over the size cap fails the job with `rust_tree_digest_mismatch` and never falls back. Only if no pin row exists for that version and target does the step print `pin_mismatch: no_pin` and fall back to the file-by-file check against the channel manifest. The default-home jobs, which restore no cache and install the default profile, always use that check. It fails the job on any file difference, but it does not see modes or the bytes of the bookkeeping regular files directly under `lib/rustlib`. The pin covers the bookkeeping files the derive reproduces byte for byte (`manifest-<component>`, `rust-installer-version`, and the channel manifest itself). Named residual risks: `multirust-config.toml`, which rustup writes in install order, is a size-capped regular-file entry with unbound content (denial of service only); the fallback, reachable for a version and target with no pin row and for a lone `<version>-*-*-*` toolchain entry that is not `<version>-<target>`, overwrites the channel manifest too (so `rustup component add` and `rustup target add`, which take download URLs and hashes from the installed manifest, read verified bytes) but leaves the `manifest-*` bytes, the `multirust-config.toml` content and all file modes unbound, which affects consumer repos that pin a Rust other than the pinned 1.99.1 in owned-home jobs; the pin binds only `toolchains/`, while the tools cache also restores the rest of `$RUNNER_TEMP/velnor/rustup` (`settings.toml`, `update-hashes`, `downloads`), which no check binds (info); the `components` file is hashed sorted, so a reordered file is accepted. No memo is stored in the cache payload. Every other install is checked against the release archive its `mise.lock` entry (or the Velnor catalog) pins for the runner platform. For those installs, a mismatch, an install with no pin, an escaping symlink or an executable in Mise bookkeeping is discarded and reinstalled by `Prepare pinned tools`; plugins and shims are never restored. Every check runs hermetically: an absolute shell, `PATH` reset to root-owned system directories before any helper runs, every helper (and `scripts/derive-rust-tree-digest`) run under `/usr/bin/env -i` with an allowlist (`PATH`, except that `scripts/derive-rust-tree-digest` sets its own fixed `PATH=/usr/bin:/bin:/usr/sbin:/sbin` before anything else and forwards no caller PATH; it scans `env -0` (never awk `ENVIRON`) and re-executes once under `env -i` with the documented allowlist and `VELNOR_DERIVE_REEXEC=1` whenever its environment holds anything else, and a second pass that still holds anything else exits 1 naming the variables, so no argument or marker can skip the clean environment and the script always terminates; `LC_ALL=C`, `HOME`, `RUNNER_TEMP`, `RUSTUP_HOME`, `MISE_RUSTUP_HOME`, `CARGO_HOME`, `VELNOR_TOOL_RUST`, the proxy variables and `SSL_CERT_FILE`, `SSL_CERT_DIR`, `CURL_CA_BUNDLE`), the pinned listing built by `find -printf` on Linux (the pins are `x86_64-unknown-linux-gnu`; other platforms take the file-by-file path, which needs no `-printf`), the Setup Mise `bin/` limited to its binary and version record, and every dot-named entry and alias target verified ([hermetic checks](tools-cache-v2.md#the-checks-run-hermetically)). | **Implemented** in the generated `velnor-tools-cache-restore` composite (`Re-verify restored Mise installs`, [tools cache V2](tools-cache-v2.md#re-verification-after-restore)). Amended; pinned tree digest implemented in this PR (fci/p3-tree-digest). ## Cases the design covers

| Case | Behavior |
|---|---|
| Main green | Seed job saves D on dependency change; sources saved by `sources-producer`. |
| Main red because tests fail | Producer steps (fetch, dependency compile) succeeded, so sources and D still save. A red main no longer starves the cache. |
| Dependency compile fails | No D save (producer failed); the previous entry stays valid. |
| Cancelled run | Nothing saves. |
| Same-repo PR | Restores trusted entries; writes nothing. |
| Fork PR, merge group | Read-only. |
| Over a ceiling | Save refused and reported as `over_ceiling` (state: `over_stored` or `over_extracted`, with the measured and ceiling bytes); older entries untouched. |
