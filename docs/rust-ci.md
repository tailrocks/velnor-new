# How Velnor keeps Rust CI fast

This page is for a project that runs `velnor-gen`. It says what the generated workflow does and which setting changes it. Every setting lives in `.velnor/rust-ci.toml`. The full reference is [`generator/CONFIG.md`](../generator/CONFIG.md), the exact cache keys are in [`rust-ci-cache-keys.md`](rust-ci-cache-keys.md), and the promises and targets are in [`goals.md`](goals.md). A project that moves from the velnor-actions engine starts with [`migrating-to-velnor-gen.md`](migrating-to-velnor-gen.md).

`velnor-gen generate` writes `.github/workflows/ci.yml`, named `CI`, and `.velnor/rust-metadata.json`. Rust jobs are in that workflow only when the repository has a Cargo workspace or package. `velnor-gen check` exits 1 when either file is out of date. A Cargo repository needs a pinned helper: `velnor-gen pin-helper <version>` writes `.velnor/rust-ci.lock` in the `--root` directory (the one that holds `.velnor/`), and stages it only when that directory is itself a git repository root. A `[[lint]]` entry needs velnor-ci 0.1.89 or later, and `pr_ci = "label"` needs 0.1.88 or later. Each generated mise install in a GitHub-hosted job (`hosted = true`) with a single known platform is checked against a SHA-256 digest that Velnor holds; a self-hosted, trusted-pool or matrix job gets no fixed digest, and on Linux (including a self-hosted runner with an `ubuntu-` label) and Windows it relies only on the action's signed-archive check, and an unrecognized platform fails the install ([mise binary pin](../generator/CONFIG.md#mise-binary-pin)). Every decision at run time is made by one program, `velnor-ci`, so each generated `run:` step is one command.

## How the generator picks jobs

### What a run selects

The first step of a run is `velnor-ci plan`. It lists the changed files, finds the packages that own them, and adds every package that depends on one of them. Each later step runs only for the packages and roots the plan selected. A run that selects no package skips the Rust steps. When more than half of a root's packages are selected, that root selects everything. The plan writes a job summary: one table per root with each selected package, its reason and its lanes (lint, test, doctests, docs), then a table of test groups and one of skipped lint jobs. `velnor-ci plan --explain` prints each selected package with its reason, each doctest or documentation step it left out and why, and what to add to the config for a file it cannot place.

- A pull request is judged by its diff. A push to the default branch and a merge queue run are judged by their diff when `on_main = "affected"` (the default), and select everything when `on_main = "everything"`.
- A scheduled run and a manual run select everything. `full_run` sets the schedule: `"nightly"` (default), `"hourly"`, `"weekly"`, `"off"` or a cron expression. For the built-in schedules `"hourly"`, `"nightly"` and `"weekly"`, the minute, hour and weekday come from a hash of the repository name, so projects do not start together. A cron expression runs as written.
- These changes select everything: a toolchain file, a Cargo config, a nextest config (`.config/nextest*.toml`), a root `Cargo.toml` (unless only workspace dependency versions changed together with the lock), `mise.toml`, `mise.lock`, `.velnor/rust-ci.toml`, the generated CI workflow `.github/workflows/ci.yml`, and any file the plan cannot place. Every other workflow that `velnor-gen` owns (its header carries a valid `velnor-gen-sha256` line, as `rust-cache-trim.yml`, `release.yml` and `qualification.yml` do; the header is read from the file's head version, or its base version when the file was deleted) selects nothing, since no Rust test reads it. A workflow that `velnor-gen` does not own selects everything as an unknown path. A changed `Cargo.lock` selects the packages that reach a changed entry, and everything when that cannot be told.
- `docs/`, `LICENSES/`, `NOTICE`, `CODEOWNERS`, `LICENSE*` and root-level `*.md` files select nothing (`default_ignores = true`), except a file inside a package directory or inside a Cargo root below the repository top, because the build can read it. `inputs` and `non_inputs` map other files to packages or to nothing.
- Documentation and doctest steps run only when the project has doc comments or doctests. On a full run they always run. They also always run when a procedural macro or build script generates code, or a dependency comes from outside the repository, because the generator cannot see every doc comment then.

### One job by default

The default shape is one job, `rust`, for each Cargo root. The generator never makes a job per crate. A crate gets a step (`Check <crate> alone`), not a job. The job count grows with Cargo roots, test groups and `[[lint]]` entries only. A second job costs start-up time, so the generator adds one only when it pays (`crates/velnor-rust/src/shape.rs`). The `shape` key chooses the layout; the table of the three shapes and the rule for `auto` is in [`generator/CONFIG.md`](../generator/CONFIG.md#run-selection).

`velnor-ci timings --repo owner/name` writes the timings file from the medians of at least three of the ten most recent first-attempt runs that pushed to the default branch or ran for a pull request into it. The generator writes the reason for the chosen shape into the workflow. A project with one root and one job has no `rust-plan` job; its plan is a step. Any other layout adds `rust-plan` first, and with several roots every job id gets a root suffix.

### Test groups

A group is a job for tests that need something the default job does not give: Docker, fewer threads, a longer limit or another machine.

```toml
[[test_groups]]
name = "database"
filter = "package(app) and test(/^db_/)"
needs = ["docker"]
```

The tests are built once and handed on as a nextest archive. `rust-test-default` runs everything that no group takes. With two or more groups in a root, `velnor-ci test-groups check` fails the build job when one test falls in two groups. `velnor-gen suggest-groups` reads the timings file and prints a group for every test binary that takes more than a third of its root's test time. Nothing creates groups on its own. The other keys of a group are `needs`, `test_threads`, `timeout_minutes`, `runner`, `hosted` (with a `runner`, needs `velnor-ci` 0.1.99), `root`, `paths`, `events`, `restore_cache`, `no_tests`, `partitions` and `artifacts`.

### Always present

`Required` (named by `required_check`) is the one check to require in a ruleset. It passes only when every selected job ran and passed. `Cache` reports cache waste; its MBX evidence is advisory and can be forged by code that runs in the job (see [rust-ci-cache-keys.md](rust-ci-cache-keys.md)). `Cache maintenance` (`rust-trim`) runs on the default branch only, and only when the pinned helper is velnor-ci 0.1.81 or later. A `policy` job runs `cargo-deny` when the project has a recognized cargo-deny configuration (`deny.toml`, `.deny.toml`, `.cargo/deny.toml` or `.config/deny.toml`, looked up from the Cargo root's folder up to the repository root) and `cargo-machete` when `mise.toml` pins it (a project with neither has no `policy` job and `Required` does not wait for one), and `[[lint]]` entries add non-Rust lint jobs.

## Caches

Three families hold the work between runs. Each key is built from one typed value in `crates/velnor-model/src/cache.rs`, never from a hand-written string.

| Family | Key holds | Restored from | Saved by |
|---|---|---|---|
| Tools | runner OS and arch, mise version, hash of `mise.lock` | exact key only | default branch, on a miss |
| Sources (cargo registry and git) | OS and arch, hash of every `Cargo.lock` | exact key, else the newest earlier entry | default branch, when sources are proven public, or private git sources in a repository proven private (see Private dependencies) |
| Target (build directory) | job, root, OS and arch, `compat`, lock hash, commit, run id | newest entry with the same lock hash, else the newest with the same `compat` | default branch, when the run compiled something |

**What makes a hit.**

- `compat` is a hash of the `rustc` version, build target, the CI build profile, the repository's `[profile]` tables, `RUSTFLAGS`, the runner image, the workspace path and the build driver (plain cargo or the mise wrapper that runs mbx). A different toolchain or profile starts a new line of entries.
- The lock hash leaves out the version of the workspace's own path packages (helper 0.1.88 or later). A release version bump does not move the key. A dependency bump does, and then the newest entry for the same `compat` is restored.
- A restore is useful only if cargo treats the files as fresh. `velnor-ci inputs save` records each tracked file's content and modification time with the build directory. `inputs restore` sets the time back on files whose bytes did not change. Cargo checks a build script that watches a folder with `cargo:rerun-if-changed` against the newest time of every file and directory in that folder. So `inputs save` also writes `.velnor/input-dirs.tsv`, which holds a digest of the entry list (names and kinds) of each directory that holds a saved file. The file is bound to the `inputs.tsv` it was saved with. After the file times, `inputs restore` sets a directory below the repository top to the newest restored time beneath it only when three things hold. Its entry list today equals the saved one, so no entry was added or deleted, tracked or not. Every entry is a file whose time was restored or a directory that qualifies the same way. The directory and its parents are real directories. Any other directory keeps its checkout time, and cargo reruns the build script. This includes a directory with an entry out of the restore scope, an untracked or ignored entry, or a symlink, because restore never sets symlink times. A base saved by a helper without this file, or with a file bound to other inputs, leaves every directory at its checkout time. `velnor-ci restored` gives files that share a time distinct times, so cargo picks the same file every run. From helper 0.1.111, `inputs audit` credits a `clippy.toml` repository's clippy units with their reads; a repository with a committed `.velnor/rust-inputs.lock` and a `clippy.toml` runs `velnor-ci inputs audit --write` once when it moves to 0.1.111 and commits the lock ([details](rust-ci-cache-keys.md#saving-the-build-directory)).
- The CI profile sets `CARGO_INCREMENTAL=0`, `SOURCE_DATE_EPOCH=0` and debug info to `line-tables-only` (`ci_debuginfo`). Every build step of a root uses the same `CARGO_TARGET_DIR`. A root at the repository root builds into `target`. Any other root builds into `target/velnor-roots/<root>` under the repository (locked helper 0.1.107 or later), outside every package directory, so Cargo's package fingerprint walk cannot meet a build that is writing there. A `build.target-dir` setting still wins. A lock that pins an older helper keeps `<dir>/target`, and moving the pin changes the target cache path of each nested root once, which costs one cold build.
- On the default branch, a restored Target older than seven days is dropped. The run builds cold and selects everything.

**What can write.** Only `push`, `schedule` and `workflow_dispatch` runs on the default branch save Tools, Sources and Target entries. A save waits for the build steps, not for the tests: once every build step has succeeded, the Target and Sources entries are saved even if a test fails, and a failed or skipped build saves neither. A build that the plan left out does not block the save, as long as one build finished. When the event asks for an audit (a schedule, a manual full run or an expired base), the audit must also pass. A pull request, a merge queue run and a fork pull request only restore them, except that a pull request from this repository saves its own delta (below). Each generated job carries a `cache-mode` key: `write` on a job that has a save step and `read` on every other job, and GitHub enforces that mode at the cache service. A job that calls a reusable workflow has no key, because GitHub documents none for it. A save needs at least one compiled, checked or documented crate, and incremental directories are removed first. When `Cargo.lock` holds a dependency that is not proven public, no Target or Sources entry is saved. The two newest entries of a group are kept. `Cache maintenance` prunes the repository towards `cache_budget_bytes` (default and maximum 8 GB of GitHub's 10 GB) on a best-effort basis. It deletes only entries it may delete (retired or superseded entries, idle pull request deltas, Target and Sources entries beyond the newest two of a group, tools anchor entries beyond the newest two of a host and a ref that no run read in the last day, and Tools entries idle for seven days other than the newest), so it can stay over budget when the entries it must keep are larger than the budget.

**Verified tools (helper 0.1.109 or later).** A restored `~/.local/share/mise` or `~/.rustup` holds executables that every later step runs. It is kept only when its BLAKE3 digest equals an anchor that a trusted default-branch run recorded with `velnor-ci tools-verify record`. Any mismatch deletes both directories and the tools install from scratch. A pull request never saves the tools. On a self-hosted runner the tools come from the node store. The steps, the limits of the check and the node store are in [rust-ci-cache-keys.md](rust-ci-cache-keys.md#verified-tools). An older pinned helper keeps the unverified restore, and `velnor-gen generate` and `check` print a note that names the gap. From helper 0.1.111 the digest hashes rustup's component list as a sorted set, so one `mise.lock` gives one digest (earlier helpers hash install order); a poisoned node-store entry heals on the next trusted save; the `mise` executable has its own SHA-256 pin ([details](rust-ci-cache-keys.md#verified-tools)).

**PR delta cache (helper 0.1.95 or later).** A pull request from this repository restores the Target entry, then a small per-pull-request delta layer (`velnor-dlt-` keys) on top of it. After the last compiling step the lane stages what the pull request changed in `target.velnor-delta` and saves it, so the next push to the same pull request starts from that work instead of the default branch's Target. `rust-cache-trim.yml` follows the workflow named `CI` and trims the deltas of a finished pull request. The lanes get these steps only when the lock pins `velnor-ci` 0.1.95 or later; the cleanup workflow needs 0.1.102 or later, because an earlier helper fails it once the pull request has merged. An older helper (0.1.81 to 0.1.94) is not refused: the generator silently leaves the delta steps out and the output is what it was without the layer.

**MBX compile cache.** MBX (Mr. Boxington) is a cargo wrapper that keeps a store of compiler results. Every generated job that compiles Rust runs cargo through it. The generated steps do not name mbx. The generator requires the repository's `mise.toml` to make `cargo` the mbx wrapper (one of two layouts, shown by the refusal) and refuses to generate without one. Each building job gets a `Private mbx store` step that points `MBX_CACHE_DIR` at `$RUNNER_TEMP/mbx`, so a job starts from an empty store and cannot read what another job or event wrote. With helper 0.1.111 or newer a second step, `Keep mbx build-script outputs in target`, sets `MBX_SHARE_OUT_DIR=0` (from 0.1.112 a shared-store job gets it from `velnor-ci mbx-store` and has no standalone step), so a restored base does not name build-script `OUT_DIR` files that are missing from the empty store and Cargo does not recompile every crate that `include!`s generated source (the reason and the price are in `generator/CONFIG.md`). `[cache] mbx = false` opts out (needs `velnor-ci` 0.1.109 or later in the lock). Details: [`generator/CONFIG.md`](../generator/CONFIG.md#mbx-by-default). From helper 0.1.111 the MBX requirement of the crates mirror covers only the checkout's own builds (helper 0.1.110 applies it to every `cargo` on `PATH`): a `cargo` that a test starts for a scratch project outside the workspace is not refused ([CONFIG.md](../generator/CONFIG.md#optional-crates-mirror)). Why every build goes through mbx, and the four exceptions: [repo-verification.md](implemented/ci-maintenance/repo-verification.md#everything-goes-through-mbx). Two settings replace the private store, so compiler results carry over between jobs:

- `mbx_shared_store = true`: a push, schedule or `workflow_dispatch` on the default branch uses the per-node directory in `VELNOR_MBX_SHARED_DIR`. A pull request, a fork or a merge queue run never writes to it; a pull request may copy missing files from the read-only `VELNOR_MBX_SEED_DIR` into a private store. See [`generator/CONFIG.md`](../generator/CONFIG.md#optional-shared-mbx-store).
- `[cache] mbx_remote = "github-actions"`: adds `jdx/mr-boxington-action`. It saves after a successful push to the default branch and after a successful pull request from the same repository, scoped to that pull request's merge ref. A fork pull request, a schedule, a merge queue run and a manual run only restore. It is refused with private dependencies. See [`generator/CONFIG.md`](../generator/CONFIG.md#optional-mbx-remote-cache).

**Debug a recompile.** `velnor-ci report` ends every cargo job and writes `ci-metrics.json`. The `Cache` check turns red when a crate was compiled although the restored cache held it, when a save failed, and on the other avoidable costs listed in [rust-ci-cache-keys.md](rust-ci-cache-keys.md). With velnor-ci 0.1.107 or later, a unit with no artifact evidence is not judged when cargo names its package as failed, since cargo's own error explains the missing evidence. The excuse is by package name: cargo's error line ``error: could not compile `<name>` `` carries no version, and cargo prints it in every message format, so every unit of that package name in the build is excused, whatever its version or target kind; units of other packages are still judged. An invocation that recorded no artifact at all counts every unit as compiled, with any helper version. Helper 0.1.106 and earlier give no excuse: in an invocation that recorded an artifact, every unit without artifact evidence is a verification error. It is advisory unless `cache_check_blocks = true`. Without `cache_debug` no `dirty` reason is recorded and no fingerprint log is uploaded. To see why cargo rebuilt a crate, set `cache_debug = true`, regenerate, and set the repository variable `VELNOR_CACHE_DEBUG` to `1`. The jobs then set `CARGO_LOG` to the fingerprint log and upload it as `velnor-cargo-log-<job>` for three days.

## Pull requests on request

`pr_ci = "label"` makes the full suite on a pull request something a maintainer asks for. It cannot be combined with `skip_draft_pull_requests`.

| Event | What runs | `Required` |
|---|---|---|
| Draft pull request | nothing | passes with the notice `draft: CI not requested` |
| Ready pull request | the quick set: plan, lint jobs (in a one-job workflow, every step except tests) and the policy job | passes when the quick set passes |
| Label `ci:run` | the full suite once for this commit; the job `ci-run-label` removes the label | the gate |
| Label `ci:auto` | the full suite on every push; the label stays | the gate |
| Merge queue, push to the default branch, schedule, manual run | the full suite | the gate |

A pull request from a fork gets the quick set whatever its labels. The full suite runs when it reaches the merge queue. `ci-run-label` is the only job with `pull-requests: write`. It has no checkout and runs no code of the pull request.

## Private dependencies

`[private_sources]` (`app_id`, `private_key`, `repositories`) names the private repositories the build may read. The full rules are in [`generator/CONFIG.md`](../generator/CONFIG.md#optional-private-dependencies). With `velnor-ci` 0.1.111 or later, the Sources and Target base caches also work for private git dependencies, but only while GitHub reports the repository private. From helper 0.1.112 those caches use `velnor-private-` keys, which no shared lane restores. Before such a repository goes public, disable its workflows and wait for the running jobs to finish, delete all its caches with `gh cache delete --all -R <owner/repo>`, and only then change its visibility: helper 0.1.111 stored private entries under `velnor-src-` and `velnor-tgt-` keys, a fork pull request of the public repository could restore them from the default branch, and `velnor-ci cache purge-private` covers only the `velnor-private-` keys and refuses to delete while workflow runs are in progress, so it does not replace that command.

- A GitHub App token that can read only the listed repositories is created, and `velnor-ci fetch` runs `cargo fetch --locked` with it. The token is revoked when the fetch ends, before any code of the project or its dependencies builds or runs. The fetch runs the real `cargo` and `git`, never a mise shim or a command wrapper, and fails closed when it finds only a shim. Every later cargo command runs with `--offline`. The token is written to no file. Each job that compiles creates its own token, because a cache or an artifact is readable by anyone who can read the repository. With `velnor-ci` 0.1.112 or later the App private key reaches no step that runs after checkout code: `velnor-ci app-token` signs the App JWT itself in one step before the tools install, with the key in that step's environment only, and has no post step; below 0.1.112 `actions/create-github-app-token` gives the key to a post step at the end of the job, which checkout code can rewrite (see **The App private key** in [`generator/CONFIG.md`](../generator/CONFIG.md#optional-private-dependencies)). With `velnor-ci` older than 0.1.111 the token is minted just before the first compiling step, so the repository-controlled steps before it, such as a Mise step, have already run; `velnor-gen generate` and `check` warn about it and render the same files and exit code. Repin `.velnor/rust-ci.lock` to 0.1.111 or later and run `velnor-gen generate` to mint it before those steps.
- The checkout stores no credentials and the jobs hold `contents: read`. No token is created for a fork pull request or for a pull request opened or pushed by a bot. In the merge queue a token is created only when the queued pull request comes from this repository (`velnor-ci private-token-allowed`). The `groups` shape builds and tests in one job and uploads no nextest archive, because workflow artifacts are readable by anyone who can read the repository. `[[test_groups]]` is refused together with `[private_sources]` for the same reason.
- `velnor-gen generate` prints a note that suggests this table when `Cargo.lock` locks a github.com git dependency over ssh or from the repository's own owner, and notes a locked repository of the token's owner that `repositories` does not list.

## Speed budget

The numbers in [`goals.md`](goals.md) section "Targets" are the budget: a run that selects nothing finishes Velnor's own jobs within 1 minute, a warm run of unchanged code compiles and downloads 0 crates, the first cargo command starts within 30 seconds, cache storage stays under 8 GB, and the job count does not grow with crates. These are targets, and the generator does not measure all of them. What holds them today:

- The shape rule above adds a second job only when it shortens the wait.
- `Cache` fails on compiled-but-cached crates and failed saves. `Cache maintenance` enforces `cache_budget_bytes`.
- `velnor-ci bench collect` turns a run into a metrics file, and `velnor-ci bench compare` prints a table for two of them. Use them to compare runs before and after a change.

Set the `budget` table (see Settings) to turn four of these into a check. The `rust-budget` job compares the run that executes it, and the median of that run and the last successful runs before it, with the wall-time, runner-time and setup-time limits you set, and fails on a breach or on a measurement it does not have. It runs on every push to the default branch and on the scheduled run (when `full_run` schedules one), never on a pull request, also when a job before it was skipped and only when the required check succeeded, and never fails the required check. A push that `skip_push_after_merge_group` skipped because the merge queue had already passed its commit is not a sample. A run that failed is not a sample, so a breach ends with the next run that is fast again. A push that selects nothing and a push that selects a core crate differ by a factor of ten, so the median of both is meaningless: `[budget.full]`, `[budget.affected]` and `[budget.none]` set limits per selection, and a run is compared only with earlier runs that made the same selection (see `generator/CONFIG.md`). With `velnor-ci` 0.1.116 or later the job keeps the plain name `Speed budget` and the step `Check the speed budget` records that selection in its name (`Check the speed budget (full)`, `(affected)`, `(none)` or `(unknown)`), which is how a later run is matched. GitHub does not evaluate the `name` of a skipped job, so a job whose name is an expression shows the raw expression when it is skipped; a step name is evaluated only when the step runs. With `velnor-ci` 0.1.104 to 0.1.115 the job title records the selection (`Speed budget (full)`) and a skipped budget job shows that expression. `velnor-ci` skips a skipped job when it reads the selection and the samples, and it reads the runs of a population from `status=success` only, so a cancelled run is never a sample.

## Settings

Every key of `.velnor/rust-ci.toml`, with its default. `generator/CONFIG.md` has the details.

| Key | Default | Meaning |
|---|---|---|
| `shape` | `"auto"` | `one-job`, `lint-test`, `groups` or `auto` |
| `test_groups` | none | `[[test_groups]]` entries, see above |
| `test_lane` | none | `[[test_lane]]` feature test lanes; a lane with `filter` also gets a `Test lane guard` step, `job = "parallel"` runs the lane as its own job (needs velnor-ci 0.1.107 or later), and any lane needs velnor-ci 0.1.93 or later, see `generator/CONFIG.md` |
| `on_main` | `"affected"` | what a push or merge queue run selects: `affected` or `everything` |
| `full_run` | `"nightly"` | `off`, `hourly`, `nightly`, `weekly` or a cron expression |
| `pr_ci` | `"always"` | `always` or `label` |
| `skip_draft_pull_requests` | `false` | draft pull requests run nothing |
| `ci` | none | table; `skip_push_after_merge_group = true` skips checks and archived test jobs the merge queue already ran (needs `velnor-ci` 0.1.103) |
| `docs` | `"always"` | `post_merge` runs `cargo doc` only on a `push`, `schedule` or `workflow_dispatch` run, not on a pull request or a merge queue run |
| `check_alone` | `"always"` | `post_merge` runs the per-crate `Check <crate> alone` steps only on a `push`, `schedule` or `workflow_dispatch` run, not on a pull request or a merge queue run |
| `sparse_checkout` | `false` | each Rust lane job checks out only the paths its lane reads |
| `inputs`, `non_inputs`, `exclude` | none | map files to packages, map files to nothing, or leave Cargo manifests out |
| `default_ignores` | `true` | documentation and licence files select nothing |
| `nextest_harnesses` | none | `package:target` entries for `harness = false` test targets that nextest can run; the others run in a direct step |
| `test_setup` | none | `[[test_setup]]` fixture steps that run before tests; `phase = "build"` runs one before the first compiling cargo step of each job, so clippy and `build.rs` see it |
| `policy` | none | table; `deny = true`, `false` or unset (on when a `deny.toml` exists) switches the cargo-deny lane, and `deny_checks` lists the checks it runs, one or more of `advisories`, `bans`, `licenses` and `sources`, each at most once (needs `velnor-ci` 0.1.111); `gate_on_plan = true` allocates the policy runner only when the plan selects `cargo-deny` or `cargo-machete` (needs `velnor-ci` 0.1.112, see [generator/CONFIG.md](../generator/CONFIG.md)) |
| `check_configurations` | none | `[[check_configurations]]` entries (`root`, optional `configurations` JSON file) that run `velnor-ci check-configurations` before the tests of a root; needs `velnor-ci` 0.1.110 or later, and from `velnor-ci` 0.1.112 the check runs once per root, also for a root without tests, see [generator/CONFIG.md](../generator/CONFIG.md) |
| `workspace_groups` | none | `[[workspace_groups]]` entries: Cargo workspaces that share one job set and one build folder, see `generator/CONFIG.md` |
| `external_workflows` | none | paths under `.github/workflows/` of hand-written workflows that `velnor-gen check` must not flag; needs velnor-ci 0.1.109 or later, see `generator/CONFIG.md` |
| `lint` | none | `[[lint]]` jobs for checks that are not cargo |
| `cache` | none | table; `mbx_remote = "github-actions"`, `mbx = false` (see MBX compile cache) |
| `mbx_shared_store` | `false` | use the node's MBX store, see above |
| `cache_budget_bytes` | `8000000000` | cache budget, at most 8 GB |
| `budget` | none | table; `pr_wall_seconds`, `main_wall_seconds`, `runner_seconds`, `setup_seconds` bound the speed, checked by `rust-budget` (needs `velnor-ci` 0.1.92). `[budget.full]`, `[budget.affected]` and `[budget.none]` take the same keys for runs whose plan selected everything, some packages or none, and each kind of run is measured against runs of its own selection (needs `velnor-ci` 0.1.104) |
