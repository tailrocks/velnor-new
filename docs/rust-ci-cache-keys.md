# Rust CI cache keys

`velnor-model` holds one type, `CacheKey`, for every cache entry of the generated Rust workflow. `velnor-render` has the only function that turns it into text (`render_key`). Every part that changes from commit to commit is an expression that GitHub fills in at run time, so a dependency bump changes no byte of the workflow file.

`host` is `${{ runner.os }}-${{ runner.arch }}`. `root` is the root's directory lower-cased, with every character other than an ASCII letter or digit turned into `_` (`root` for the repository root). `job` is the job id. `compat` is `steps.prepare.outputs.compat`.

| Family | Key | Restore fallbacks, in order | Path |
|---|---|---|---|
| Tools | `velnor-tools-<host>-mise<version>-${{ hashFiles('mise.lock') }}` | none | `~/.local/share/mise`, `~/.rustup` |
| Sources | `velnor-src-<host>-all.roots-${{ steps.sources_locks.outputs.hash }}` | `velnor-src-<host>-all.roots-` | `~/.cargo/registry/index`, `~/.cargo/registry/cache`, `~/.cargo/git/db` |
| Target | `velnor-tgt-<job>.<root>.<host>-<compat>-<lockhash>-${{ github.sha }}-${{ github.run_id }}` | `...-<compat>-<lockhash>-`, then `...-<compat>-` | `build.target-dir`, default `target` for the repository root and `target/velnor-roots/<root>` for every other root (locked helper 0.1.107 or later; earlier helpers use `<dir>/target`) |
| Delta | `velnor-dlt-pr<PR number>-<job>.<root>.<host>-<compat>-<base8>-${{ github.run_id }}` | `...-<compat>-<base8>-` | `<target-dir>.velnor-delta` |

`steps.sources_locks.outputs.hash` is the `hashFiles` of every Cargo root's `Cargo.lock` in path order, computed once per job by the `Hash the sources lockfiles` step. `<lockhash>` in a Target key is `${{ hashFiles('<dir>/Cargo.lock') }}` for a helper older than 0.1.88 and `${{ steps.prepare.outputs.lock_<root> }}` for 0.1.88 or later (see [Lock hash](#lock-hash)); the Sources key always uses the `hashFiles` value above. For a workspace group the Target key always hashes the lock files of every root of the group, `${{ hashFiles('<dir1>/Cargo.lock', '<dir2>/Cargo.lock') }}`, whatever the helper version. `<base8>` is `${{ steps.delta_base_<root>.outputs.base8 }}`, the first eight hex characters of the SHA-256 of the target restore's actual `cache-matched-key`. A fallback is always a strict prefix of its key, and the second fallback of a Target key is a strict prefix of the first. The second segment of every key is its family tag (`tools`, `src`, `tgt` or `dlt`), so a Delta key is never equal to, and never a prefix of, a Tools, Sources or Target key. Every Delta fallback retains the explicit PR number, lane, root, host, compat and base digest. A key never contains a branch name, a literal digest or `run_attempt`. `hashFiles` reads a root path literally. `*`, `?` and `[` are written as `[*]`, `[?]` and `[[]`, and a leading `!` or `#` gets a `./` prefix. `{` and `}` stay out of the quoted path. When the path contains either brace, the value is a `format` expression, and each brace is `fromJSON('"\u007b"')` or `fromJSON('"\u007d"')`. Generation fails when a key can pass 512 characters at run time (the `actions/cache` limit), counting every expression at its longest value. `build.target-dir` is read from the `.cargo/config.toml` or `.cargo/config` that applies to the root (the nearest wins, the file without `.toml` first); generation fails when it is absolute, outside the repository, holds the root, starts with `~`, or contains a `{` or `}` placeholder, and when `build.build-dir` is set, because the Target cache would not cover that directory. Every generated step that builds a root (clippy, doc, check, build, nextest, doctests and the audit build, not format, deny or machete) sets `CARGO_TARGET_DIR` to `${{ github.workspace }}/<target directory of that root>` (for a root in a workspace group, the shared `target-velnor/<name>` of the group), the same path the Target cache of that root restores and saves, so a wrapper such as MBX leaves the directory in place and the cache can save it. The value is on the step, not the job or the workflow, because one job can build several roots with different target directories. A step value wins over `$GITHUB_ENV`, and a cargo `[env]` entry is refused when its name starts with `CLIPPY`, `RUST` or `CARGO`, or when `force` is true, so a repository cannot set another target directory for a generated step. The run id at the end of a Target key lets a full run save a clean base when the commit has not changed since the last save. A rerun of the same run reuses that id on purpose: the save finds the key taken and writes nothing, so unchanged data is never saved twice, and a rerun after a failed save still saves because no entry exists yet.

## Lock hash

For a helper older than 0.1.88 the Target key hashes `<dir>/Cargo.lock` with `hashFiles`, so any change to the file, including a version bump of the workspace's own crates, moves the key.

With helper 0.1.88 or later `velnor-ci prepare` computes one value per root and writes it to the step output `lock_<root>`; the Target key reads it. `prepare` reads `.velnor/rust-metadata.json` for the roots and members and fails when that file is missing. From helper 0.1.104 the generated step names the roots its job reads, `velnor-ci prepare --lock-root <root>` for each, or `--no-locks` for a job that restores no Target cache, so a lane parses only its own lockfiles; without these flags `prepare` writes the value of every recorded root, and a `--lock-root` that names an unrecorded root is an error. It is a SHA-256 over the lockfile, with one change: the `version` of a package is left out when all three of these hold. The package is a workspace member of a root recorded in `.velnor/rust-metadata.json` (the members of every root count for every root); its name occurs exactly once in the lockfile; and it has no `source`, so it is a path package. The `[root]` table of a V1 or V2 lockfile counts as a package. Everything else stays in the hash: registry and git packages with their versions, sources and checksums, every dependency list, and the lockfile's own `version`. A bump of a dependency, a new or removed package, a changed source or a changed dependency edge therefore moves the key, while a version bump of a member (a release commit) does not.

A lockfile that cannot be read as UTF-8 or as a TOML table with a `package` array of named packages is hashed byte for byte under a different prefix than a normalised one, so the two forms never collide. A root without a `Cargo.lock` gets a fixed value of its own. The output is 64 hexadecimal characters, the same length as `hashFiles`, so the key length check is unchanged. The Sources key does not use this value: it stays on the raw `hashFiles` of every root's `Cargo.lock` (`steps.sources_locks.outputs.hash`), so a version bump of a member does move the Sources key. The restore then falls back to the newest `velnor-src-<host>-all.roots-` entry, and a miss saves a new Sources entry only when `cache decide` reports `sources=true`. Normalising the Sources key is not done; `a_helper_with_the_member_lock_key_reads_it_from_the_prepare_step_for_every_root` in `crates/velnor-gen/tests/it/cache_lock_identity.rs` pins the current behaviour.

## Tools cache

Every job that installs the tools restores the Tools entry in the step before `jdx/mise-action` (a shard job, which installs only cargo-nextest, restores it too; the plan job installs nothing and restores nothing). `~/.local/share/mise` holds the mise program itself (`bin/mise`, which the action finds and only verifies against the signed checksums, so it downloads nothing), the installed tools and the link to the Rust toolchain; `~/.rustup` holds the toolchain, because mise installs Rust through rustup. Rust components and targets are added in every job before the save, so every job saves the same content; with `profile = "complete"` the save follows `velnor-ci prepare`, which installs the components the profile implies.

Only a job that installs every tool saves it, only on the default branch and only when the restore was not an exact hit. When the node store served the tools (`steps.toolslocal.outputs.hit == 'true'`) the network restore is skipped, so the job runs an `actions/cache/restore` step with `lookup-only: true` for the same key on a trusted run (default-branch push, schedule or manual run). It downloads nothing; it only reports whether the entry exists, and the network save runs only when that lookup missed. Without this lookup an evicted network entry would never be refreshed by node-hit runs, and hosted lanes and fresh nodes would keep missing it. Pull request runs neither look up nor save, and a node miss restores and saves exactly as before. A tool-set change on a pull request installs fresh for that pull request and saves nothing. The key covers `mise.lock`, the mise program version the generator passes to `jdx/mise-action` as `version:`, the runner OS and the runner architecture: a changed tool version or a mise bump moves it (the entry is saved only on a miss, so without the mise version a bump would keep restoring a directory built by the old mise), a comment in `mise.toml` does not. It does not cover the runner image version or the targets in `rust-toolchain.toml`; a change in either only causes a re-download, never a wrong tool. Generation fails when `mise.lock` is missing, or when a pinned tool has no prebuilt binary for the runner's platform in it (a `cargo:` tool, for example); the error names the tool.

## Saving the build directory

With helper 0.1.81 or later, the ordinary lint and test lanes save Target entries on the default branch for `push`, `schedule` and `workflow_dispatch`. Saves require successful setup, a finished build and a passed input audit when one is asked for, but not the tests: a failing test still saves the Target entry, and the job then prints `target cache saved after test failure` (#1970). One builder writes these conditions for every shape of job (`crates/velnor-render/src/save_condition.rs`). A build is finished when its step `build_<n>` (the Nextest build that compiles the test binaries) has the outcome `success`, or, on helper 0.1.107 or later, when the test step has `outputs.built == 'true'` (see below). A skipped build is never a finished build, so a job whose earlier step failed saves nothing. A build of a group that the plan left out is the only build that may be missing, and at least one build must have finished (#2027). An audit that the event asks for (a schedule, a manual run or an expired base) must have the outcome `success`: a skipped or failed audit saves nothing (#2028). The audit itself runs after a failed test, once the build finished, so a failing test does not leave the target unaudited. Pull requests, merge groups and forks only restore, except that a same-repository pull request saves its own Delta entry (see [Pull-request deltas](#pull-request-deltas)).

On a saving Nextest run, helper 0.1.107 or later has no separate prebuild step. The test step builds the test binaries and runs them in one `cargo-nextest nextest run`, and `velnor-ci run` writes `built=true` to that step's outputs when nextest exits 0 or 100 (100 means tests failed after the build finished) and `built=false` when it exits 101 (the build failed). The saves wait for `steps.<test>.outputs.built == 'true'`, so a failed build saves nothing. An older helper keeps the prebuild, `cargo-nextest nextest run --workspace --locked --ignore-default-filter --no-run`, before the tests. Events that cannot save run the test command directly.

A single-job lane finishes its test commands and its full-run compile-input audit before publishing. A split lane runs the authoritative nextest run before it builds the doctests and the direct harnesses that nextest does not build, and publishes after both in step order, so a passing run leaves them in the published base and the next run compiles neither again; untrusted harness or doctest code never executes before the nextest run that the Required verdict reads. A failing test, doctest or direct-harness test does not block that publish: the save waits for the build step and the audit, as in the single-job lane. Split and multi-root lanes depend on the independent compile-input audit job, which runs for schedules, manual full runs and pushes with `on_main = "everything"`. Failed or cancelled audits block every writer. A skipped audit permits an ordinary affected run to reuse its existing base, but an expired base cannot be published by a split lane without a successful full audit. The Required gate checks the same audit event conditions.

The save sequence is:

1. `velnor-ci inputs save --target-dir <configured target directory>` writes `.velnor/inputs.tsv` inside the directory being cached.
2. `velnor-ci cache decide` reads `velnor-run.log` and rechecks dependency source safety. `save=true` requires at least one compiled, checked or documented crate. `sources=true` independently authorizes a missed Sources entry when all sources are proven public, or when every non-public source is a git dependency without credentials in its URL, `velnor-ci` 0.1.109 or later has asked `GET /repos/{repo}` with the job token and the repository is private (not public, not internal; any error refuses), and no credential file or token-bearing git config sits inside the saved Sources paths. A warm Target can therefore replenish Sources. Unreadable evidence produces no authorization.
3. Before a Target save, the helper removes Cargo incremental directories at the profile and target-triple/profile levels and removes the Nextest archive. Build-script output directories with the same name remain. Traversal, metadata and cleanup errors fail the decision. The helper records the cold-build date in `.velnor/born`, carries it forward on later saves and reports the directory size. `velnor-ci run` overrides Cargo's quiet configuration and refuses explicit quiet arguments so compilation remains visible.
4. `actions/cache/save` compresses the directory directly. The lane records each saved key as a job output without a token. The `rust-trim` Cache job, which runs no repository code, then runs `velnor-ci cache verify --key` with its own token against the read-only cache API to require an exact entry on the saving ref. This catches upload errors that the pinned action reports only as warnings. A failed verification fails the Cache check without changing Required.

**Private repositories (helper 0.1.109 or later).** A repository whose locks hold private git sources and that sets `[private_sources]` gets one more step, `velnor-ci cache private-repo` (step id `private_repo`), before the Sources restore. It writes `private=true` only when `GET /repos/{repo}` with the job token says the repository is private; a public or internal repository, any error and a missing token write `private=false`. Both restores (and, for a pull request, only when it comes from this repository), `inputs save`, `cache decide`, the offline sources fetch and both saves wait for that output, and the saves keep their default-branch event gate. The Sources and Target keys and paths are the ones in the table above. Delta keys are never used for such a repository.

Build lanes hold only `contents: read` and `actions: read`. The separate `rust-trim` job is named `Cache`, installs the checksum-verified released helper, checks upload results, prunes old entries and enforces the repository cache budget. It has `actions: write` and `pull-requests: read`, no checkout and no repository code. It needs every job that can save a cache and runs on every default-branch `push`, `schedule` and `workflow_dispatch` event, including a run in which no lane saved. Failed verification, listing or deletion makes Cache red. Required does not depend on Cache. A source-helper repository without a released helper of at least 0.1.81 saves no base because it cannot safely run privileged trimming.

The test lane owns Sources saves, or the lint lane when no tests exist. Every root's lane restores and may save the same Sources key of the repository, so one payload per host serves all roots instead of one per root. Because a cache entry is immutable per key, the lane that saves the key must hold the crates of every root. Before the save, on a Sources miss that `cache decide` authorised, the lane fetches the crates of every Cargo root (fetch only, no build). With a pinned `velnor-ci` of 0.1.88 or later that is one step, `velnor-ci sources fetch --roots . ./<dir>...` (more steps, each after the previous one succeeded, when the roots do not fit one run value), which runs `cargo fetch --locked` in each root's directory in the order listed through the same capture as `velnor-ci run`, and stops at the first failure. Older helpers (0.1.86 and 0.1.87 do not have the command) get one `velnor-ci run -- cargo fetch --locked` step per root, each after the previous one succeeded, so the workflow grows with the square of the root count and generation refuses a repository with more than 16 Cargo roots while Sources are saved. In every form the save requires the last fetch to have succeeded; a failed fetch saves nothing. Lanes that miss together race on one key and the loser's save writes nothing. The newest shared payload is still restored by the `all.roots-` prefix when a lockfile changed. The owner token `all.roots` holds a `.`, which a root slug never holds, so the shared key and its prefix neither equal nor prefix any key of another family or of a per-root `velnor-src-<host>-<root>-` key. An exact Sources hit is not uploaded again. Target and Sources families retain their newest two entries. Listing is paginated in batches of 100, with a bound of 20 pages and a warning if further pages remain.

Generation suppresses Target and Sources saves for non-crates.io dependencies or applicable Cargo source configuration. Runtime admission rechecks the explicitly supplied Cargo root manifests, their locks including unused patches, applicable ancestor Cargo configurations and `CARGO_HOME`. Missing, unreadable or unmodelled sources and source-related environment overrides disable both writes. Unrelated fixture lockfiles and descendant configurations do not affect admission.

A root outside the repository root builds below the repository's own `target` folder, not inside its package directory, so Cargo's fingerprint walk of that package never meets a build that another lane is writing. One function in `velnor-rust` (`target_dir`) decides the folder, and the Target cache path, the `CARGO_TARGET_DIR` of every Cargo step, `inputs restore` and `inputs save`, `cache decide`, the delta paths and the helper's cold cleanup and trim all read its result. A lock that pins a helper before 0.1.107 keeps `<dir>/target`, because an older helper computes the folder itself and would disagree. Moving the pin to 0.1.107 changes the Target and Delta paths once, so the first run on each nested root builds cold.

Target paths cannot overlap tracked checkout content or repository control directories. Runtime validation also rejects paths outside the checkout and paths through symlinks. The generator supplies configured targets in `VELNOR_CACHE_TARGETS`; `restored` uses those exact directories for expiry and cold cleanup after failed timestamp validation. Inputs restore receives the same configured target path. `velnor-ci inputs build` runs a Cargo command with `CARGO_TARGET_DIR` set to the target directory of the workspace the command selects, unless the job already names one, so a tool that manages target directories cannot replace the cached directory with a link.

A restored base more than seven days old, or with missing or unreadable `.velnor/born`, is removed on the default branch and reports `expired=true`. The following `replan` step selects everything, and subsequent commands read the full plan. A fresh base retains its partial selection. The limit is passed as `VELNOR_BASE_MAX_AGE_DAYS`.

## Pull-request deltas

A locked helper of 0.1.95 or later enables delta caching for roots using their default target directory (`<root>/target`, or `target/velnor-roots/<root>` from helper 0.1.107), including when lane jobs build their helper from source. Custom target directories receive no delta steps because the input manifest helper currently uses the default target path. A repository whose workflow with the delta layer would exceed the 500,000 bytes GitHub allows for one workflow file is generated without that layer, keeps every check it had, and the generator reports the omission with the size the workflow would have had. Generation rejects a tracked file or descendant at a supported lane's staging path. At runtime, every delta command checks the resolved target and staging paths against Git's tracked paths before it restores, stages or deletes cache data. It refuses overlapping tracked paths or an inability to verify the paths. After the Target restore, `velnor-ci delta prepare` fingerprints its matched key and captures the full tracked source digest. The delta cache action runs only when that Target restore matched a base. `velnor-ci delta apply` inventories the base before overlaying the delta with original modification times. A default-branch run records each file's digest in `target/.velnor/delta-inventory.json` before it saves the base; apply and `delta stage` read a file again only when its size, time or mode no longer match that record (apply) or its inode change time no longer matches the one apply recorded (stage), and both print `read N of M files`. A base without a usable inventory is read in full. The full base key saved inside the delta must equal the matched Target key; a missing base or different full key discards the delta. A failed overlay removes the restored target and builds cold. If the target directory is a symlink to an untracked directory, apply skips delta reuse without changing the linked build tree and staging saves nothing. Symlinks in delta contents are refused. Input restoration follows the overlay, so the delta's input manifest replaces the base manifest before source timestamps are restored. The existing `velnor-ci restored` then breaks timestamp ties.

`inputs save` writes `.velnor/inputs.tsv` with a digest of the full tracked source snapshot and records for tracked files. `delta stage` recaptures and verifies that source snapshot and the saved records before it compares the current tree against the original base inventory. The manifest envelope binds the source digest to its records, and restore rejects a missing or inconsistent binding. It includes new files, files whose bytes or modification times changed, and the input manifest. Size and time comparisons avoid hashing files already known to differ; streamed SHA-256 detects changes that retain both size and time. If the saved and current full source records differ, apply invalidates all Cargo fingerprints so the compiler rechecks sources while retaining cached artifact bytes. An identical source snapshot keeps fingerprint reuse. Deletion records prevent the next base restore from resurrecting removed outputs. The resulting payload is cumulative relative to the base, including when a later run changes nothing from an earlier delta or reverts a file to the base. Copies preserve modification times in both directions. Only Cargo's `<profile>/incremental` and `<triple>/<profile>/incremental` directories are excluded; regular files and deeper output directories named `incremental` remain cacheable. Delta bookkeeping is excluded.

Cached deletion paths must be relative paths of normal components. All deletion and copy destinations are validated before any change, and a symlink or malformed payload forces a cold recovery. Inventory and deletion metadata must be bounded regular files of at most 16 MiB. Applying a delta replaces inherited inventory bookkeeping before writing a new inventory; unavailable or invalid inventory prevents saving. A run with no workspace crate compilation saves nothing. A staged payload, including its base identity and deletion metadata, over 500,000,000 bytes reports its size in a notice and saves nothing; its size is checked before copying. A cold run without a matched base also saves nothing.

Only `pull_request` runs restore deltas. A same-repository PR may save only its own Delta key. Fork PRs restore only. Repositories with private dependency sources receive no delta prepare, restore, apply, staging or save steps and no delta cleanup workflow, whether or not the repository is private. Main and merge-group runs never restore or save deltas. Lane jobs have no `actions: write` permission.

A plan with delta saving generates `rust-cache-trim.yml`, which runs after Rust CI completes, using the default branch's workflow and locked released helper. Its sole `rust-trim` job checks out nothing, downloads no build artifacts, restores no cache and runs no project code. The helper validates the completed run's workflow, repository and same-repository PR identities before listing `refs/pull/N/merge` deltas. It reads every page before deleting, refuses changing totals, duplicate IDs or other refs, and keeps the newest entry per lane/root/host across compat and base generations. Cleanup runs for the same PR serialize without cancellation; different PRs use separate concurrency groups, with the completed run id as the fallback when the event omits its PR number. There can be multiple entries until trusted cleanup completes. Closed-PR cleanup and the aggregate 8 GB budget require the separate cache budget manager; this per-PR cleanup does not enforce them.

## Compat

`compat` is the first 16 hex characters of the SHA-256 of the following fields in order: `schema` (the decimal `COMPAT_SCHEMA`, bumped by hand when the cache layout changes), `rustc` (`rustc -vV`), `target` (`CARGO_BUILD_TARGET`, or empty), `profile-env` (the CI build profile environment lines below), `profile-config` (the dependency override config below, or empty), `repo-profile` (the effective repository Cargo profile tables), `image` (`ImageOS` and the `ID` and `VERSION_ID` fields from `/etc/os-release`, joined by `|`, with missing values empty), `rustflags` (`RUSTFLAGS`, or empty), `workspace` (the absolute workspace path), and `driver` (`cargo`, or `cargo-mise-wrapper` when the `cargo` that `PATH` resolves to is in a `command-wrappers/bin` directory, which is mise's command wrapper that runs mbx; `prepare` reads `PATH` as the job's cargo calls will). A repository that turns the wrapper on or off therefore changes `compat` and misses the Target cache once, instead of restoring a target built the other way. Each field is encoded as its name, a colon, the decimal byte length of its UTF-8 value, a colon, the value, and a newline. The digest covers the concatenated encoded fields. `velnor-ci prepare` gathers them and writes the result as a step output.

`repo-profile` concatenates, in repository path order, each effective Cargo config containing a `[profile]` table. Each contribution is the repository-relative path followed by a newline, the re-serialized TOML containing that table, and a newline. Configs without `[profile]` contribute nothing; a `.cargo/config.toml` shadowed by `.cargo/config` contributes nothing.

The helper function `cargo_config_paths` in `crates/velnor-rust/src/repo_profile.rs` finds configs only for Cargo roots recorded in `.velnor/rust-metadata.json`. `prepare` fails when that file is absent. For each root, the helper reads `.cargo/config` and `.cargo/config.toml` in the root's directory and each ancestor up to the checkout root. It does not search folders below the root's directory. `.cargo/config` shadows `.cargo/config.toml` in the same folder. Git is asked which of those files are tracked, and that answer is used to compare `build.target-dir` as read now with the same key read from the tracked files, and `build.build-dir` the same way. `build.target-dir` read now is also compared with the path recorded as `target_dir` for the root in `.velnor/rust-metadata.json` at generation (recorded when the helper pin is 0.1.85 or later, the first release that reads it; a file without it skips this comparison): `prepare` fails naming both paths when a committed change to `build.target-dir` was made without regenerating. When git cannot answer, none of them count as tracked. A path that is a symbolic link, or that goes through one, makes `prepare` fail with an error naming the file, because generation does not read through a symbolic link. A top-level `include` key in a config that applies (not one shadowed by `.cargo/config`) makes `prepare` fail with the same error generation reports. Not modelled: folders above the checkout (which cargo also searches) and `CARGO_HOME`; a `[profile]` set there does not change `compat`. Separately, before it writes profile or output files and before the workflow restores the Target cache, `prepare` resolves each root's current target directory and checks it against Git's current tracked paths. It fails if a tracked path is inside the target directory, contains the target directory, or if Git cannot prove that the target directory is untracked. Generation applies the same overlap rule to tracked paths in the checkout.

## CI build profile

`velnor-ci prepare` appends `RUSTUP_AUTO_INSTALL=0` to `$GITHUB_ENV` first, followed by these profile environment lines, the same in every lane. Only the profile environment lines form `profile-env` for `compat`, each encoded as `NAME=value` followed by a newline:

- `CARGO_INCREMENTAL=0`, `CARGO_TERM_COLOR=always`, `SOURCE_DATE_EPOCH=0`
- `CARGO_PROFILE_DEV_DEBUG` and `CARGO_PROFILE_TEST_DEBUG` set to `ci_debuginfo` (`full`, `line-tables-only` or `none`, default `line-tables-only`) for workspace crates

Cargo has no environment variable for the dependency override `[profile.<name>.package."*"]`. For `line-tables-only` and `none`, `prepare` writes it to `.cargo/config.toml` in the parent folder of the checkout, so it applies to every cargo command, including `cargo-nextest` and `cargo-clippy`. The file is Velnor's own: its first line is `# velnor-ci owns this file and rewrites it on every prepare`, `prepare` replaces it on every run and removes it when `ci_debuginfo` is `full`, and `prepare` fails when it needs the override and a file there does not carry that line. A `.cargo/config.toml` inside the repository takes precedence over it, which is why its `[profile]` tables are part of `compat`. Before Rust 1.71, which rejects string `debug` values, `prepare` writes `2`, `1` and `0` for `full`, `line-tables-only` and `none` and `debug = 0` for dependencies. Every action the generated workflow pins runs on node24, so a runner older than 2.327.1 stops at the first step, before any cache step. The override written for Rust 1.71 and later:

```toml
[profile.dev.package."*"]
debug = "none"

[profile.test.package."*"]
debug = "none"
```

## Cache telemetry and enforcement

With helper `0.1.81` or a supported source-built helper, each reporting-enabled
Cargo lane ends with `velnor-ci report` and uploads `ci-metrics.json`. These
steps also run after an earlier failure unless the run was cancelled. Report
and upload failures do not replace the lane's build result. The report retains
logs, provenance and step results, and emits local metrics without calling the
API or using `GITHUB_TOKEN`.
The workflow supplies each cache's family, root, and restore/save step IDs; the
helper derives observed facts from step results and filesystem evidence. When a
released bootstrap helper is older than `0.1.81`, the source-built artifact helper runs the
tokenless local checks and diagnostics without API access.

The separate `Cache` job checks the same-run metrics from every reporting
lane. With released helper `0.1.81` or later, it runs `report --check` to add
Actions API timings and cache archive sizes, then fails on cache waste, missing
metrics, or unverifiable required evidence. The job has `actions: read` for
this enrichment and receives an empty explicit API token on fork pull requests.
It has no checkout and runs no Cargo commands. It is advisory by default. To
include it in Required's dependencies and verdict specification, set this in
`.velnor/rust-ci.toml`:

```toml
cache_check_blocks = true
```

Besides compiled-despite-restored-inputs and download waste, the report names
five more avoidable costs, each only when the evidence shows it was avoidable:

- A sources cache miss although the Actions cache inventory already listed
  that exact key, on a ref the job may read, when the job started. The `Cache`
  job records this as `entry_before_job`; a cold lock stays clean.
- An MBX session with no hits although `MBX_CACHE_DIR` named a store that held
  entries older than the first Cargo invocation. A per-job or empty store, or a
  lane without MBX lines, stays clean here (the next item covers a
  declared MBX with no sessions).
- A lane that compiled without MBX: at least one compilation unit that Cargo
  did not report fresh, but no `mbx[cache]` session line in the lane's Cargo
  log, while the checkout declares MBX. The lane's `report` step records the
  declaration as `mbx.declared` in `ci-metrics.json` when a mise config at the
  checkout root (`mise.toml`, `.mise.toml`, `mise/config.toml`,
  `.mise/config.toml`, `.config/mise.toml` or `.config/mise/config.toml`) sets
  `mr_boxington = true` on a tool in `[tools]` or sets the command of
  `[wrappers.cargo]` to `mbx`. A pin of the `mr-boxington` tool alone declares nothing.
  A lane that compiled nothing, and a repository that does not declare MBX,
  stay clean. This is the proof that the declared routing really ran: without
  it a lane that bypassed MBX looked identical to one with no MBX at all. A
  consumer gets it by bumping its helper pin; the generator passes no new
  input.
- A toolchain component or target that `velnor-ci prepare` had to install
  (recorded in `$RUNNER_TEMP/velnor-toolchain-installs.txt`) although the tools
  cache had an exact hit. This includes a declared channel that rustup would
  install on its first `rustc` or `cargo` call: `prepare` checks for it before
  the first rustup call and records `toolchain <channel>`.
- A compilation unit (same root, package, target, profile, features, output
  files and execution environment) built by two Cargo invocations of one lane.

`rust-trim` continues to verify cache uploads and prune old entries without a
checkout or repository code. The `Cache` job needs no additional permission to
download artifacts from its own run. The schema-1 JSON separates cache
outcomes, captured Cargo invocations, display fields, verification errors, and
optional diagnostics.

## Worked example

A repository with the root `lab/Cargo.toml` and the job `rust-lint`, on `ubuntu-latest` (X64), at commit `c0ffee`, run `42`, compat `9f3a1c5e7b2d4a60`:

- Sources: `velnor-src-Linux-X64-lab-<hash of lab/Cargo.lock>`
- Target: `velnor-tgt-rust-lint.lab.Linux-X64-9f3a1c5e7b2d4a60-<hash of lab/Cargo.lock>-c0ffee-42`
- Restore tries the Target key, then `velnor-tgt-rust-lint.lab.Linux-X64-9f3a1c5e7b2d4a60-<hash of lab/Cargo.lock>-` (the latest save for this lockfile), then `velnor-tgt-rust-lint.lab.Linux-X64-9f3a1c5e7b2d4a60-` (the latest save for this toolchain and profile).
- After a dependency bump the lock hash changes: the first two tries miss and the third restores the previous build directory. A version bump of the workspace's own crates leaves the lock hash unchanged, so the second try restores the latest save of this lockfile. The workflow file is unchanged.

The new generator supports a runner-scoped [optional crates mirror](../generator/CONFIG.md).

## Pruning before a save

Before `cache decide` compares the build directory with the budget it removes what a later build rebuilds anyway or never reads, so the saved base holds only what dependency reuse needs. From the invocation records of the job (`velnor-invocations.jsonl`, written by `velnor-ci run` for every Cargo command it wraps, including the `build-script-executed` records), helper 0.1.107 and later learn the dependency units the job used: every `compiler-artifact` whose package is not a path package, and the output directory of every dependency build script. It then keeps, in each profile directory (`debug`, `release`, `<triple>/debug`):

- the `deps/` files of those units (rlib, rmeta, dylib, `.d`, object files), their `.fingerprint/` directories and their `build/` directories (the build script executable and its output);
- `.cargo-lock`, and in the target root every file and every directory the helper does not know.

It removes the `deps/` entries, fingerprints and build directories of every other unit, which covers the workspace's own crates and units left from earlier locks; test, bench and binary executables and their copies in the profile directory; `examples/`; incremental directories; and the `doc`, `nextest`, `tmp`, `package` and `criterion` directories. Workspace artifacts always rebuild when the code changes and are cheap, and a dependency unit that is fresh stays fresh because its fingerprint, outputs and build script records are all kept.

When the invocation records are missing or incomplete (a capture that was cut off or rejected), the helper does not know which units were used and keeps every unit, removing only executables, `examples/` and the scratch directories. Whenever `cache decide` prunes, its notice says which basis was used, lists the bytes before and after, and gives the bytes removed per category.

## Repository cache budget

`cache_budget_bytes` in `.velnor/rust-ci.toml` defaults to `8000000000` and accepts values from zero through that 8 GB maximum. A pinned released helper of 0.1.81 or later runs `velnor-ci cache budget --budget-bytes <bytes>` once as the final step of `rust-trim`, after all cache writers, the per-lane trims and the upload check. The job runs only on the default branch for push, schedule and manual events. Its budget step runs even when no lane saved, including a warm scheduled run. A repository with private dependencies still gets this budget step after its Tools writers, even when no Target or Sources trims exist. A source-built helper without a released helper of 0.1.81 or later gets no privileged cleanup job. It needs `actions: write` and `pull-requests: read`, installs the released helper without checking out repository code, and stays outside the required check.

Run `velnor-ci cache budget --dry-run --repo owner/name` to inspect the repository without deleting anything. `--budget-bytes` accepts a lower budget, including zero, up to the command’s 8 GB default. The command lists every cache and open pull request before deleting. An incomplete, inconsistent or failed listing aborts deletion. A PR absent from the open listing is checked individually before its delta is treated as closed. The table shows each family's count, bytes and newest and oldest creation timestamps. The report includes selected IDs, current bytes and projected remaining bytes.

Closed-PR deltas are always removed, even below budget. While over budget, deletion proceeds through deltas idle for at least three days, Target and Sources entries beyond the newest two per key group, Tools entries idle for at least seven days except the newest per host, then remaining deltas in access-time order. A delta is eligible only in a `refs/pull/<number>/merge` scope. Base groups are scoped to their Git ref, so PR entries cannot displace a default-branch base. Target groups retain job, root, host and compat; The Sources group retains the host alone. Tools versions share a host group. The newest base entries and unknown keys remain protected. If protected entries prevent reaching the budget, the report warns that retained bytes still exceed it. Saves never wait for a live usage query.

Three rules protect the newest base from the budget and from stale families. A Target entry whose compatibility family is not the one of the newest entry of the same job, root, host and ref is deleted whatever the budget, and the per-lane trim, which knows the compat the lane just saved, deletes every `velnor-tgt-<job>.<root>.<host>-` entry that is not in that family. A Sources entry that was restored (last accessed) within the last 24 hours is never trimmed or selected by the budget, however many newer locks exist, because a restore updates the access time of the entry it hit; the entry of the lockfile in the checkout is therefore kept while the repository keeps running. `cache decide` receives `cache_budget_bytes` as `VELNOR_CACHE_BUDGET_BYTES` and writes `save=false` with a notice when the build directory alone is larger than the budget, measured after it prunes the directory (see Pruning before a save); whether a save would push the repository total over the budget is not decided at save time, because that needs the usage query, so `cache budget` enforces the total afterwards. A helper that predates the budget input ignores it.
