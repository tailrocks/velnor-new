**Status:** Partially superseded. The active runner specification is
[macOS Scale Set runner](/docs/proposed/macos-scaleset-runner). Clauses marked
**Superseded** below are not normative. Workspace separation, no second task
graph, no generator-adapter dependency, one task and cache authority, exact
lock identities, durable recovery, truthful conclusions, and the ban on mounting
the host home or the outer Docker socket into a job remain in force.

## 1. Entry condition

Velnor Actions V1 is a proposed stack-generic workflow generator with a Rust adapter as its first stack. Separate crates own Rust analysis, Mise integration, generic workflow rendering, and orchestration. The runner is a later Velnor product. It may reuse generated workflows, task contracts, and cache conventions, but MUST NOT depend on the Rust or Mise adapter crates; those are generation integrations, not runner APIs. `rust-toolchain.toml`, `mise.toml`, and `mise.lock` remain optional repository-owned inputs that Velnor Actions only inspects and recommends changes for.

The self-hosted runner MUST consume those generated artifacts. It MUST NOT scan a repository to create a second workflow, invent a second task graph, or maintain a second cache policy. The V1 generator and task contract are the only source of workflow intent. Runner crates remain outside the `velnor-actions-*` adapter workspace; the future `velnor` product name stays reserved.

Runner implementation MUST NOT start until all applicable V1 gates are recorded as passing:

1. Deterministic human planning and workflow generation, with parity between
   `velnor-actions plan` and `generate --output-dir <fresh-temp-dir>`.
2. Correct Rust workspace discovery and affected-package selection.
3. Focused generated jobs with meaningful required results.
4. Mise, Rust, MBX, and cache identities locked and qualified.
5. Task-result reuse and invalidation tests passing.
6. Velnor's own generated CI running from the pinned bootstrap binary.

V2/V3 versions MUST follow the [Velnor version policy](/docs/proposed/version-policy).
Create and protect `.velnor/runner.lock` before runner implementation; the
runner lock and exact Turso crate pin MUST pass upstream freshness and platform
qualification checks before release.

An unverified or skipped V1 gate is a failed entry condition. No current V1 gate is implied by this roadmap.

### Deferred stages

| Stage | Scope | Required reuse |
|---|---|---|
| V2 | One macOS host running the official GitHub runner in an owned Linux container | V1 workflows, task IDs, tool versions, and cache conventions |
| V2-native | Replace the official runner for the restricted V1 profile with the real Rust protocol runtime | V1 runner profile plus V2 ownership, cleanup, and observability |
| V3 | Debian host support using the same supervisor and container contract | V2 lifecycle and V1 workflow contract; no Linux fork |

V2 and V3 are execution environments. They do not expand V1 into a general GitHub Actions interpreter. The native milestone is a separate runtime and MUST NOT be simulated by launching the official runner.

## 2. Product boundary

**Superseded:** mandatory one-slot-only scope. The active spec uses one host-wide capacity authority with configurable `max_jobs` (default 1) and requires qualification at `N>1`. One repository connection on the first host remains. The native interpreter is not a prerequisite for official Scale Set mode.

### Required topology

```text
GitHub workflow generated by V1
              |
              v
      GitHub assigns a job
              |
              v
     Velnor host supervisor
              |
        V2 official mode
        official runner
        in Linux Docker
              |
        Later native mode
        Rust protocol client
        + Linux job container
```

**Superseded:** implicit ARM64 execution. The active profile is `linux/amd64`. Host architecture, Docker VM architecture, container platform, and emulation are reported separately. ARM64 is not the x64 baseline. The following diagram is historical:

```text
control host:       macOS / arm64
execution platform: Linux / arm64
runtime:            official | native
```

V3 replaces the control host with Debian and Docker Engine. It MUST use the same container labels, state machine, task contract, cache namespaces, cancellation rules, and qualification suite. A native macOS job is outside this scope; Docker Desktop does not provide Xcode, Simulator, or Darwin execution.

### V1 and runner contract

Before any self-hosted runner implementation begins, the V1 generator MUST add a versioned compatibility output named `runner-rust-ci-v1`. It is a gated V1-to-runner integration change and is not part of the current proposed V1 output. Its exact path and schema are:

```text
<runner-state>/runner-rust-ci-v1.json
```

```json
{
  "schema": 1,
  "profile": "runner-rust-ci-v1",
  "plan_id": "plan-r123-a1",
  "source_sha": "<40 lowercase hex characters>",
  "generator_version": "<exact-semver>",
  "runner": {
    "mode": "self-hosted",
    "os": "Linux",
    "architecture": "ARM64",
    "labels": ["self-hosted", "Linux", "ARM64", "velnor-rust-ci-v1"]
  },
  "matrix": []
}
```

`matrix` MUST contain the exact V1 package/configuration entries and task IDs,
plus each task's fixed executable/argument vector, working directory, declared
environment names, input digest, and cache identity. It MUST NOT contain raw
shell fragments, secret values, or arbitrary action references. The profile is
written and validated by the same planner; it is included in the plan artifact
and covered by the generator's golden and compatibility tests.

This profile requires a deliberate V1 configuration-schema revision. Add:

```toml
[runner]
mode = "github-hosted" # or "self-hosted"
profile = "runner-rust-ci-v1"
platform = "linux-arm64" # linux-x64 or linux-arm64
```

`github-hosted` keeps the exact V1 Ubuntu image-family label from the
[version policy](/docs/proposed/version-policy) and emits no runner profile.
**Superseded:** classic self-hosted labels
`["self-hosted", "Linux", "ARM64", "velnor-rust-ci-v1"]` and the X64 variant.
The active selectors are `runs-on: ubuntu-26.04` (hosted) and
`runs-on: [velnor, ubuntu-26.04-scale-set]` (local). Do not emit those classic
labels. Schema-1 generation stays hosted until a repository deliberately
migrates to schema 2.

The runner consumes:

- the generated `runs-on` label;
- the assigned repository, commit SHA, job, and step identities;
- generated `run` commands that invoke V1 task IDs;
- the declared environment, tool, target, feature, and cache identities;
- the generated workflow's supported failure and cancellation semantics.

The runner MUST preserve task commands and IDs exactly. It MAY validate them against the V1 contract before execution. Any unsupported workflow input MUST be rejected before repository code runs.

V2 official mode executes the full generated workflow unchanged inside the
official runner container. The later native runtime does not invoke GitHub
marketplace JavaScript actions. For the profile above it MUST translate the
following exact pinned actions to built-in operations, using the action SHA in
`.velnor/generator.lock` as part of admission:

| V1 action | Native built-in operation |
|---|---|
| `actions/checkout` | Fetch and checkout the exact assigned SHA using a job-scoped credential; verify `HEAD` equals that SHA. |
| `actions/cache/restore` | Restore only the declared V1 source, MBX closure, or task-cache archive under its existing trust/key rules. |
| `actions/cache/save` | Save the same declared layer only after the owning task and report succeeded. |
| `actions/upload-artifact` | Upload run-scoped V1 plan, matrix, and report artifacts through the job's GitHub artifact runtime endpoint. |
| `actions/download-artifact` | Download only artifact IDs named in the validated V1 plan/report contract. |

These are native operations, not action JavaScript execution. An action name,
version, or behavior outside this table fails admission before repository code
runs. The action runtime credentials MUST never enter a task environment.

### Explicit exclusions

**Superseded:** the ban on Scale Sets, services, and nested Docker. The active
spec requires a repository-scoped Runner Scale Set, private DinD, and official
runner execution of marketplace actions inside the worker. Still normative:
Kubernetes, Firecracker, remote hosts, fleet provisioning, a dashboard, a TUI,
a general workflow engine, deployments, and a new remote cache service stay out
of scope. The job MUST NOT receive the host home directory or the outer Docker
socket.

## 3. Runner workspace and crate boundaries

Runner code MUST live in an independent Rust workspace under `crates/`. It MUST NOT be added to the V1 generator's dependency graph. A separate repository is preferred while the runner is experimental.

The runner consumes Velnor Actions' generated task/workflow contract. It MUST
NOT inspect or manage consumer `mise.toml`, `mise.lock`, or
`rust-toolchain.toml`; that read-only inspection belongs to the Velnor Actions
Mise and Rust adapters. Runner-specific tool pins belong in its separate
`.velnor/runner.lock`.

```text
velnor-runner/
├── Cargo.toml
├── Cargo.lock
├── mise.toml
├── rust-toolchain.toml
├── crates/
│   ├── velnor-runner-core/
│   ├── velnor-runner-github/
│   ├── velnor-runner-host/
│   └── velnor-runner-cli/
├── fixtures/
│   ├── protocol/
│   └── rust-smoke/
└── docs/
    ├── compatibility.md
    └── operations.md
```

### `velnor-runner-core`

This crate contains pure, typed logic only:

- `JobIdentity`, `AdmittedJob`, `ScriptStep`, `StepOutcome`, `JobConclusion`;
- `RuntimeKind`, `SlotIdentity`, `AttemptIdentity`, and `ResourceOwnership`;
- admission validation for `runner-rust-ci-v1`;
- environment-file parsing and masking rules;
- the lifecycle state machine and error classifications.

It MUST NOT depend on HTTP, Docker, SQLite, CLI parsing, or a process-spawning API. Its tests MUST be separate files and MUST cover rejected workflow features, state transitions, and file-command edge cases.

### `velnor-runner-github`

This crate owns GitHub-specific contracts:

- repository JIT configuration;
- runner authentication and refresh;
- broker session and job acquisition;
- run-service lease, logs, step results, and completion;
- API error classification and retry policy;
- wire fixtures and redacted protocol transcripts.

It converts GitHub messages into `velnor-runner-core` types. It MUST NOT own Docker resources or execute repository commands.

### `velnor-runner-host`

This crate owns effects:

- supervisor scheduling and fixed slots;
- Docker context resolution and the narrow Docker wrapper;
- named volumes, containers, exec processes, logs, and cancellation;
- the SQLite journal and restart reconciliation;
- explicit `OfficialRuntime` and `NativeRuntime` implementations.

Runtime selection MUST be an explicit `RuntimeKind` match. Do not introduce a universal provider framework or route official-runner jobs through the native step interpreter.

### `velnor-runner-cli`

This crate contains thin binaries only:

- `velnor-host`: start, stop, inspect, and run the supervisor;
- `velnor-doctor`: perform read-only Docker, tool, credential, and contract preflight.

CLI code MUST not contain protocol, scheduling, or workflow-generation logic.

## 4. Lifecycle and ownership

The durable lifecycle is:

```text
Empty → Registering → Idle → Running → Finishing → Cleaning → Empty
```

The supervisor MUST:

1. Reserve a slot and persist a unique attempt identity before creating external resources.
2. Register or acquire the selected runtime.
3. Create only resources labelled with installation, repository, slot, attempt, and runtime.
4. Execute one GitHub job and report terminal step and job results.
5. Persist pending result delivery independently from cleanup.
6. Remove only resources owned by the attempt and return the slot to `Empty`.

The journal MUST contain at least worker attempts, owned resources, and pending completion reports. It MUST NOT become a fleet database. Every restart MUST reconcile journal records against Docker and GitHub. Unknown execution state MUST NOT be replayed as a new step.

Implement the journal with Turso's `turso` Rust crate, using a local embedded
database file. The supervisor already requires Tokio, so journal operations use
Turso's async API on that runtime. V2 MUST NOT enable Turso Cloud sync, remote
database access, or a separate Turso service. Put SQL and migrations behind one
journal module; other crates depend on typed journal operations, not Turso
connections or SQL. Commit schema migrations and apply them before accepting
work. Lifecycle state changes that protect ownership or prevent duplicate
execution MUST commit before the corresponding external side effect proceeds.
Qualify crash recovery, transaction behavior, locking, and durability with the
pinned Turso version before V2 is released. The journal remains single-host and
single-daemon; Turso does not add distributed scheduling to this design.

The supervisor MUST resolve the active Docker context and freeze the socket endpoint and daemon identity for its lifetime. It MUST NOT hardcode `/var/run/docker.sock` or globally prune Docker resources.

## 5. V2 official runtime

V2 uses the repository-level JIT endpoint:

```text
POST /repos/{owner}/{repo}/actions/runners/generate-jitconfig
```

The request MUST set an owned runner name, resolved runner group, `runner-rust-ci-v1` labels, and a work folder. The host MUST persist the provisioning identity before making the request.

The official lifecycle is:

1. Run `velnor-doctor` and verify Docker, image, Mise, MBX, architecture, and credentials.
2. Request one JIT configuration for the reserved slot.
3. Start one pinned Linux image derived from the official runner image.
4. Provide the encoded configuration through the runner's JIT startup interface, `run.sh --jitconfig`.
5. Observe the official process and collect bounded, redacted diagnostics.
6. Treat GitHub's job conclusion as authoritative; process exit alone is not a passing job.
7. Remove the owned container and volumes, then replenish the slot.

The image MUST contain the locked Rust toolchain, Mise, MBX, and V1-required tools. An image digest does not prove which runner binary executed; runner update behavior MUST be qualified and the image refresh policy recorded. The container MUST be freshly provisioned for each JIT job. Official-runner mode MUST not assume that the official image provides a Docker daemon for nested container actions.

## 6. Later native runtime

Native mode MUST implement the real protocol lifecycle:

```text
JIT identity
→ authentication
→ broker session
→ job assignment
→ run-service acquisition
→ V1 profile admission
→ Docker execution
→ live logs and step results
→ job completion
→ session and registration cleanup
```

The protocol implementation MUST preserve authentication refresh, session expiry, acquisition ownership, lease renewal, cancellation, acknowledgement ordering, and distinct retryable, terminal, and ownership-conflict errors. `already acquired` and `unavailable` MUST NOT be handled by rerunning repository code.

The protocol client initially runs in the host process. User code runs only inside an owned Linux container. Each step uses explicit Bash, a controlled working directory, calculated environment, bounded output, and Docker exec. Repository scripts MUST never execute on the macOS or Debian host.

One real native job must complete in GitHub before adding more Actions features. A local mock or shell-only test is insufficient evidence.

## 7. `runner-rust-ci-v1` compatibility profile

**Superseded:** this restricted native interpreter is not a prerequisite for
official Scale Set mode. Do not implement it. The table below is historical.

| Capability | Required behavior |
|---|---|
| Job | One assigned job; generated sequential `run` steps |
| Shell | Explicit Bash |
| Source | Fresh checkout of the exact assigned SHA |
| Environment | Literal job/step values and supported runner variables |
| File commands | `GITHUB_ENV`, `GITHUB_PATH`, `GITHUB_OUTPUT` for later steps |
| Expressions | Only typed direct references emitted by V1 |
| Failure | Failed ordinary step fails the job and skips later ordinary steps |
| Cancellation | Stop the owned workload, report cancellation, and clean resources |
| Reporting | Live text logs, step states, and terminal job conclusion |
| Actions | No arbitrary `uses:` execution |
| Containers | Velnor's sandbox only; no services or nested actions |

The runtime MUST reject custom `if`, `continue-on-error`, reusable actions, unsupported expressions, services, and unknown execution semantics before repository code runs. GitHub remains responsible for workflow triggers, DAG scheduling, and job assignment.

Checkout MUST fetch and validate the assigned SHA. It MUST NOT substitute a branch tip. Private checkout credentials MUST be job-scoped and MUST NOT be the controller's administration token.

Environment-file parsing MUST apply changes only to subsequent steps, reject reserved `GITHUB_*`, `RUNNER_*`, and `NODE_OPTIONS` writes, handle multiline delimiters and incomplete writes, enforce byte limits, and never evaluate file contents as host shell code.

## 8. Security, recovery, and cancellation

Registration credentials MUST stay on the host. JIT data MUST not appear in persistent container environment metadata or logs. Diagnostics MUST be bounded and redacted. The initial allowlist MUST restrict repositories and events to trusted work.

Cancellation MUST stop the workload container and process tree, wait for bounded graceful termination, force terminate if required, verify that no owned process remains, and then report the cancellation. Cancelling a local Docker API request alone is insufficient.

API failure during result delivery MUST leave a durable pending report while allowing a safely cleaned sandbox to be removed. Cleanup retries MUST not duplicate execution. A runner refusing registration deletion because it is busy MUST be treated as an ownership/lifecycle state, not as permission to repeatedly delete it.

Mutable Cargo target and MBX state MUST be exclusive to a slot. Cache identity MUST include repository, trust domain, platform, toolchain, runtime, and slot. Cross-slot writable sharing is deferred until concurrency and trust tests pass.

## 9. Dependencies and engineering rules

The runner workspace MUST use Velnor's Rust baseline: Rust 2024, pinned patched stable toolchain, committed `Cargo.lock`, inherited workspace lints, stable rustfmt, separate test files, and enforced file-size limits. Runner production files SHOULD remain below 350 lines; `main.rs` and `lib.rs` SHOULD remain below 150 lines. These are policy gates, not suggestions to split behavior into meaningless wrappers.

The initial dependency set is deliberately narrow:

| Dependency | Use |
|---|---|
| `serde`, `serde_json`, `toml` | Typed wire and host configuration |
| `tokio` | Selected async runtime |
| `reqwest` | GitHub HTTP |
| `jsonwebtoken`, key-format support, `base64` | Established authentication handling |
| `bollard` | Local Docker operations |
| `turso` | Local embedded SQLite-compatible journal through the async Rust API; cloud sync and remote access are disabled |
| `thiserror`, `anyhow` | Classified component errors and CLI context |
| `tracing`, `tracing-subscriber` | Bounded diagnostics |
| `clap` | Thin binaries |
| `uuid` | Attempt and resource identities |
| `tokio-tungstenite`, `futures-util` | Only if the qualified protocol path requires them |
| `tempfile`, `wiremock` | Focused tests |

Use Mise for all tool installation and MBX for compiler caching. Do not invoke direct toolchain Cargo, hidden `cargo install`, or an additional cache owner in normal tasks. Keep protocol, Docker, authentication, and database access out of pure-core tests. Use Bollard only through the required local operations wrapper; exclude unused remote transports and BuildKit features.

## 10. Acceptance gates

| Gate | Evidence required | Status |
|---|---|---|
| V2 preflight | Reproducible macOS Docker/tool/credential checks | Not implemented |
| V2 official pass/fail | One real passing and one real failing generated GitHub job | Not implemented |
| V2 cleanup | No owned active containers, volumes, or processes after completion/cancellation | Not implemented |
| V2 recovery | Restart during registration, execution, reporting, and cleanup is safe | Not implemented |
| V3 parity | Debian uses the same contract and passes the V2 suite | Not implemented |
| Native protocol | One real native job acquires, executes, logs, completes, and cleans up in GitHub | Not implemented |
| Compatibility | Unsupported profile inputs fail before repository code; exact SHA is verified | Not implemented |
| Capacity | Fixed `N` never exceeds its worker population | Not implemented |
| Security | Controller credentials absent from workload environment and logs | Not implemented |
| Cache correctness | Warm reuse works; changed inputs invalidate; no shared mutable slot state | Not implemented |
Qualification MUST run the same commit and task set under official mode and native mode, comparing both with expected outcomes. A matching infrastructure failure in both modes is still a failure. Missing or skipped qualification is not success. Failure injection is required at every external side-effect boundary.

## 11. Delivery sequence
1. **Contract freeze:** record the qualified V1 profile schema, generated task IDs, labels, tool identities, and cache identities. Add compatibility fixtures.
2. **V2 official mode:** implement preflight, JIT registration, one container, diagnostics, authoritative result handling, cancellation, and owned cleanup.
3. **V2 recovery:** add the journal, reconciliation, pending result delivery, and fixed slots. Pass all V2 gates.
4. **V3 Debian:** port the host adapter and service packaging while retaining the same core, GitHub, contract, and qualification crates.
5. **Native protocol:** implement wire fixtures, acquisition, lease renewal, Docker step execution, logs, completion, and cleanup. Pass one real native job before broadening support.
6. **Controlled expansion:** add only a requested compatibility feature with a fixture, rejection behavior, and a regression gate. Revisit autoscaling and mixed runtime scheduling last.

Any implementation that adds a second workflow generator, silently broadens the compatibility profile, weakens ownership checks, or treats process exit as job success fails review.
