## Reproduced store-level lifecycle window

Three disposable tests are in the upstream v1.21.1 store source at commit a0a44c61ca6aaa8da41d59deeebdfc46fc9d3313. Their patch and passing log are attached under [native-mbx-active-run-gc](native-mbx-active-run-gc/README.md); the upstream MIT license notice accompanies them. The command is:

    rustup run 1.98.1 cargo test -p mbx-cache-store a_sweep_ --locked -- --nocapture

The first test records a completed action result and a live checkout with no persisted task manifest or group receipt, then runs GC. This models the store state while an agent-side prediction is pending, but the fixture does not instantiate CacheAgent or an in-memory prediction object. It verifies that the unrooted result is removed, then persists the receipt and confirms that export fails for synthetic digest 800f006f2aaae60a808991d88a45b5c6d3af11e6d2be2868e3301220599e6b02. A second test shows that collection after receipt persistence can preserve a small receipt-rooted closure while removing unrelated stale data. A third shows that a receipt-rooted closure can still be evicted when it exceeds the configured budget. All three tests passed in the attached run; these storage-level cases do not establish production capacity.

The checked-out source ordering explains how this window can exist:

1. The Rust shim publishes the compiler result and records the action prediction before calling the low-disk collector. See [rustc.rs, lines 695–725](https://github.com/jdx/mr-boxington/blob/a0a44c61ca6aaa8da41d59deeebdfc46fc9d3313/crates/mbx/src/rustc.rs#L695-L725). The prediction request is held in the CacheAgent's in-memory task state; [agent.rs, lines 2851–2889](https://github.com/jdx/mr-boxington/blob/a0a44c61ca6aaa8da41d59deeebdfc46fc9d3313/crates/mbx-cache-core/src/agent.rs#L2851-L2889) show the pending prediction map update.
2. Cargo invokes ActionRun::commit only after the Cargo command returns. That commit sends predictions to receipt persistence. See [cargo.rs, lines 496–506](https://github.com/jdx/mr-boxington/blob/a0a44c61ca6aaa8da41d59deeebdfc46fc9d3313/crates/mbx/src/cli/cargo.rs#L496-L506) and [session.rs, lines 1055–1078](https://github.com/jdx/mr-boxington/blob/a0a44c61ca6aaa8da41d59deeebdfc46fc9d3313/crates/mbx/src/session.rs#L1055-L1078).
3. GC considers the live checkout's persisted task-manifest actions and actions named by completed group receipts, subject to the configured storage budget. The fixture does not instantiate the agent: it models the store before receipt persistence, while the source shows the pending prediction only in CacheAgent memory. The over-budget case shows that a completed receipt is not a capacity guarantee. See [store/lib.rs, lines 1696–1706](https://github.com/jdx/mr-boxington/blob/a0a44c61ca6aaa8da41d59deeebdfc46fc9d3313/crates/mbx-cache-store/src/lib.rs#L1696-L1706) and [lines 2025–2033](https://github.com/jdx/mr-boxington/blob/a0a44c61ca6aaa8da41d59deeebdfc46fc9d3313/crates/mbx-cache-store/src/lib.rs#L2025-L2033).

This establishes a deterministic store-level reproduction of a missing result when collection precedes completed group-receipt persistence, with post-receipt cases showing both a small preserved closure and an over-budget failure. It does not instantiate CacheAgent, run the asynchronous low-disk scheduler, execute Cargo end to end, or test either production lane. It does not prove that CI digest 90517… was in the eviction set. The matching order and error make the lifecycle race a leading source-supported hypothesis, not a proven root cause for run 38024039383.

## Hosted and Scale Set scope

The independent review of the official action found that its GitHub object-GC default sets MBX_GC_AUTO=0 only for GitHub-hosted GitHub-object mode when the caller leaves the variable unset. Velnor explicitly sets MBX_GC_AUTO=1 for native MBX jobs in the renderer ([preflight constants](https://github.com/tailrocks/velnor-new/blob/d2271521f590f3610163d1905231b20a8711652f/crates/velnor-actions-workflow-renderer/src/cache_steps_mbx_preflight.rs#L48-L54), [job environment](https://github.com/tailrocks/velnor-new/blob/d2271521f590f3610163d1905231b20a8711652f/crates/velnor-actions-workflow-renderer/src/document.rs#L307-L311)); the linked d227 CI job has that value at line 737. The exact hosted log also reports MBX_GC_AUTO=1.

A hosted-only change to MBX_GC_AUTO would therefore leave the Scale Set native-MBX path with automatic collection enabled. Turning it off on both routes would avoid this automatic sweep path but would also remove its low-disk reclamation. The action post step exports and saves the GitHub cache; it does not perform a later MBX collection. No profile split or source setting is claimed here as a fix.

The cache directory is under the runner's `_temp` tree. In the pinned Actions runner v2.337.0, `runner.temp` resolves to `Work/_temp`; JobRunner initializes that directory before job steps, runs StepsRunner (including registered post steps), finalizes and uploads the job, then cleans temp. The runner catches and logs cleanup errors, so this cleanup is best-effort. It happens after the in-job GC/export ordering at issue and does not protect an active prediction from a sweep. See [HostContext.cs](https://github.com/actions/runner/blob/v2.337.0/src/Runner.Common/HostContext.cs#L2545-L2552), [JobRunner.cs](https://github.com/actions/runner/blob/v2.337.0/src/Runner.Worker/JobRunner.cs#L1591-L1805), and [TempDirectoryManager.cs](https://github.com/actions/runner/blob/v2.337.0/src/Runner.Worker/TempDirectoryManager.cs#L357-L419). GitHub documents the same beginning/end cleanup for [`RUNNER_TEMP`](https://docs.github.com/en/actions/reference/workflows-and-actions/variables) and [`runner.temp`](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts).

The Scale Set implementation mounts `/home/runner/_work` from a worker-specific `{private_volume}-work` volume. Its volume base is randomly generated per worker launch, and that work volume is shared by the runner/DinD pair rather than across workers. The runner's MBX directory is consequently worker-local; cross-run persistence comes from the GitHub Actions cache archive. Velnor removes named worker volumes with a claim fence and confirms their absence; a failed cleanup may leave a disk leak, and volume cleanup does not establish that stale processes have stopped. The separate `velnor-action-archive` mount is read-only and is not the MBX store. See [worker.rs](https://github.com/tailrocks/velnor-new/blob/d2271521f590f3610163d1905231b20a8711652f/crates/velnor-runner/crates/velnor-runner-host/src/worker.rs#L48-L58), [docker_spec.rs](https://github.com/tailrocks/velnor-new/blob/d2271521f590f3610163d1905231b20a8711652f/crates/velnor-runner/crates/velnor-runner-host/src/docker_spec.rs#L65-L114), [volumes.rs](https://github.com/tailrocks/velnor-new/blob/d2271521f590f3610163d1905231b20a8711652f/crates/velnor-runner/crates/velnor-runner-host/src/worker/volumes.rs#L49-L145), and [volume completion](https://github.com/tailrocks/velnor-new/blob/d2271521f590f3610163d1905231b20a8711652f/crates/velnor-runner/crates/velnor-runner-host/src/launch/completion/volume.rs#L12-L91).

The observed job imported 25.6 GiB of logical MBX objects and later reclaimed 20.8 GiB after a completed Cargo test before continuing to another test. No disk high-water measurement was captured. Therefore the evidence does not establish that suppressing in-job GC until a final step would fit available disk on either runner class. The store is worker-local on Scale Set, but its within-job reachability and capacity still require a safe design; cross-run cache persistence does not answer that question.

The upstream MBX v1.21.1 `mbx clean` path removes managed workspace target and incremental state; it does not collect the separate action-object store or its receipt closure. Target cleanup respects exclusive leases and may leave an active target in place, so a successful command alone does not prove that bytes were reclaimed. This does not establish a replacement for the observed object-cache reclamation. Any GC-off/final-clean experiment remains unqualified until it measures actual reclaimed bytes and disk high-water under representative hosted and Scale Set jobs. See [`clean.rs`](https://github.com/jdx/mr-boxington/blob/v1.21.1/crates/mbx/src/cli/clean.rs), [`target.rs`](https://github.com/jdx/mr-boxington/blob/v1.21.1/crates/mbx/src/target.rs), and [`config.rs`](https://github.com/jdx/mr-boxington/blob/v1.21.1/crates/mbx/src/config.rs).
