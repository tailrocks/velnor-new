Task daemons and native shims work better on Windows. <code>core:rust</code> now follows <code>mise.lock</code> and picks up new stable and beta toolchains. Lockfile, GitHub asset selection, Homebrew cask and plugin update problems are also fixed.</p>
<h2>Fixed</h2>
<h3>Tasks</h3>
<ul>
<li><strong><code>mise run --timeout</code> now stops the tasks it was running.</strong> Before, mise printed the timeout error and exited, but the task processes could keep running in the background. Now the whole-run timeout (<code>--timeout</code> or the <code>task.timeout</code> setting) stops tasks the same way a per-task <code>timeout</code> does. On Unix, mise sends SIGTERM and then SIGKILL after 5 seconds. On Windows, it runs <code>taskkill /F /T</code>. Tasks with <code>raw = true</code> are not stopped by the whole-run timeout. <a href="https://github.com/jdx/mise/pull/13876" data-hovercard-type="pull\_request" data-hovercard-url="/jdx/mise/pull/13876/hovercard">#13876</a> by <a class="user-mention notranslate" data-hovercard-type="user" data-hovercard-url="/users/Marukome0743/hovercard" data-octo-click="hovercard-link-click" data-octo-dimensions="link\_type:self" href="https://github.com/Marukome0743">@Marukome0743</a></li>
<li><strong>A single Ctrl-C lets tasks shut down cleanly.</strong> Before, one Ctrl-C could make mise exit right away while tasks were still cleaning up. This happened in three cases: a task that runs <code>mise run</code> itself got SIGINT twice; a tool like <code>docker compose up</code> treated the duplicate SIGINT as a force-quit; and a task that exits non-zero on SIGINT caused mise to send SIGTERM to its sibling tasks. Now mise waits for tasks to finish and then exits with status 130. A second Ctrl-C still force-quits. <a href="https://github.com/jdx/mise/pull/13904" data-hovercard-type="pull\_request" data-hovercard-url="/jdx/mise/pull/13904/hovercard">#13904</a></li>
<li><strong>Tab completion for the <code>:task</code> shorthand.</strong> In a monorepo, <code>mise run :&lt;TAB&gt;</code> now suggests tasks from the current config root, and task flags complete after the shorthand. <a href="https://github.com/jdx/mise/pull/13882" data-hovercard-type="pull\_request" data-hovercard-url="/jdx/mise/pull/13882/hovercard">#13882</a> by <a class="user-mention notranslate" data-hovercard-type="user" data-hovercard-url="/users/pikeas/hovercard" data-octo-click="hovercard-link-click" data-octo-dimensions="link\_type:self" href="https://github.com/pikeas">@pikeas</a></li>
</ul>
<h3>Daemons</h3>
<ul>
<li>
<p><strong>Task daemons start on Windows.</strong> A daemon declared with <code>task =</code> failed under <code>cmd /C</code> with <code>'exec' is not recognized</code>. mise now registers it as an argv command that pitchfork starts without a shell, so <code>args</code> reach the task exactly as written on every platform. <strong>This needs pitchfork 2.28.0 or later.</strong> With an older pitchfork, mise shows an error that tells you to upgrade, for example with <code>mise use pitchfork@latest</code>. Task daemons that use <code>init</code> still run through a shell, so they still don't work under <code>cmd /C</code>. <a href="https://github.com/jdx/mise/pull/13714" data-hovercard-type="pull\_request" data-hovercard-url="/jdx/mise/pull/13714/hovercard">#13714</a> by <a class="user-mention notranslate" data-hovercard-type="user" data-hovercard-url="/users/JamBalaya56562/hovercard" data-octo-click="hovercard-link-click" data-octo-dimensions="link\_type:self" href="https://github.com/JamBalaya56562">@JamBalaya56562</a></p>
</li>
<li>
<p><strong>Daemon <code>run</code> commands can use <code>\[env\]</code> and <code>\[vars\]</code>.</strong> Before, a template such as <code>{{ vars.test\_var }}</code> failed with <code>Variable 'vars' is not defined</code>. <code>mise x</code> now renders the command when the daemon starts, using the project's <code>\[env\]</code>, <code>\[vars\]</code> and mise template filters. Pitchfork's own variables, such as <code>{{ name }}</code>, still work. This applies only to <code>run</code> and requires a pitchfork release newer than 2.29.0. <a href="https://github.com/jdx/mise/pull/13894" data-hovercard-type="pull\_request" data-hovercard-url="/jdx/mise/pull/13894/hovercard">#13894</a></p>

<h3>Windows shims</h3>
<ul>
<li><strong>No more endless process chains from duplicate shim copies.</strong> If two copies of <code>mise-shim.exe</code> were on PATH (for example, one from winget's <code>Links</code> directory), they could keep calling each other through <code>mise x</code>. Running <code>mise-shim</code> by its own name now exits with an error. If <code>mise x</code> resolves a tool to another shim copy, mise stops after one step and names the PATH directory to remove. <a href="https://github.com/jdx/mise/pull/13681" data-hovercard-type="pull\_request" data-hovercard-url="/jdx/mise/pull/13681/hovercard">#13681</a> by <a class="user-mention notranslate" data-hovercard-type="user" data-hovercard-url="/users/JamBalaya56562/hovercard" data-octo-click="hovercard-link-click" data-octo-dimensions="link\_type:self" href="https://github.com/JamBalaya56562">@JamBalaya56562</a></li>
<li><strong>Node IPC works through the <code>node.exe</code> shim.</strong> A Node parent that spawned the shim with an <code>'ipc'</code> stdio entry used to wait forever. JSON IPC messages and disconnects now pass through the shim. Passing socket or server handles over the channel is still not supported. <a href="https://github.com/jdx/mise/pull/13903" data-hovercard-type="pull\_request" data-hovercard-url="/jdx/mise/pull/13903/hovercard">#13903</a></li>
</ul>
<h3>Rust</h3>
<ul>
<li><strong><code>mise upgrade rust</code> updates <code>stable</code> and <code>beta</code>.</strong> mise didn't recognize rustup 1.29's new <code>update available:</code> text. Even when it detected an update, the upgrade skipped the toolchain as already installed. mise now reads both spellings, counts only updates for the toolchain it manages, and updates the toolchain in place. If the update fails, the old toolchain stays usable. <a href="https://github.com/jdx/mise/pull/13898" data-hovercard-type="pull\_request" data-hovercard-url="/jdx/mise/pull/13898/hovercard">#13898</a></li>
<li><strong><code>core:rust</code> follows <code>mise.lock</code>.</strong> mise mistook rustup's symlinks for <code>mise link</code>ed versions, so it ignored the lockfile and installed the newest version even with <code>locked = true</code>. <a href="https://github.com/jdx/mise/pull/13915" data-hovercard-type="pull\_request" data-hovercard-url="/jdx/mise/pull/13915/hovercard">#13915</a></li>
</ul>
<h3>Backends, lockfiles and bootstrap</h3>
<ul>
<li><strong>GitHub auto-detection no longer installs metadata files.</strong> SBOMs, signatures, checksums and other sidecar files with platform names, such as <code>\*.tar.gz.sbom.json</code>, could be chosen as the tool and saved to <code>mise.lock</code>. Automatic selection now skips them. Explicit <code>url</code> and <code>asset\_pattern</code> options are unchanged. <a href="https://github.com/jdx/mise/pull/13908" data-hovercard-type="pull\_request" data-hovercard-url="/jdx/mise/pull/13908/hovercard">#13908</a></li>
<li><strong><code>mise lock</code> removes outdated duplicate entries.</strong> After you changed a tool option, for example by adding <code>uvx = false</code> to a <code>pipx:</code> tool, <code>mise lock --upgrade</code> could leave the old unbound entry next to the new bound one. Unfiltered <code>mise lock</code> runs now remove the old entry, unless it has platform data (checksum or URL) that the new entry doesn't have. <a href="https://github.com/jdx/mise/pull/13909" data-hovercard-type="pull\_request" data-hovercard-url="/jdx/mise/pull/13909/hovercard">#13909</a></li>
<li><strong>Aqua registry cache errors after upgrading.</strong> Compiled registry caches from earlier versions could load but then fail when a package was resolved. mise now ignores those caches and rebuilds them. <a href="https://github.com/jdx/mise/pull/13884" data-hovercard-type="pull\_request" data-hovercard-url="/jdx/mise/pull/13884/hovercard">#13884</a></li>
<li><strong>Packslip installs retry missing skills.</strong> If the binary installed but a declared skill couldn't be fetched, mise still marked the install as complete. Now the install fails with an error. The next <code>mise install</code> fetches only the missing skills and doesn't reinstall the tool. <a href="https://github.com/jdx/mise/pull/13885" data-hovercard-type="pull\_request" data-hovercard-url="/jdx/mise/pull/13885/hovercard">#13885</a></li>
<li><strong>Pkg-based <code>brew-cask</code> packages are no longer reinstalled on every run.</strong> Casks such as <code>google-drive</code> list package IDs for several architectures, and mise expected every one of them to be installed. Receipts now store only the patterns that match on your machine. Casks recorded by earlier versions are reinstalled once to write a corrected receipt. <a href="https://github.com/jdx/mise/pull/13893" data-hovercard-type="pull\_request" data-hovercard-url="/jdx/mise/pull/13893/hovercard">#13893</a></li>
<li><strong><code>mise plugins update</code> works when the remote isn't named <code>origin</code>.</strong> This happens, for example, when git's <code>clone.defaultRemoteName</code> is set to something else. mise uses <code>origin</code> if it exists and otherwise uses the first remote. <a href="https://github.com/jdx/mise/pull/13914" data-hovercard-type="pull\_request" data-hovercard-url="/jdx/mise/pull/13914/hovercard">#13914</a></li>
</ul>

Keyless cosign bundles must now match a pinned signer identity, and GitHub attestation workflow checks no longer accept partial matches. It also closes a <code>.tool-versions</code> trust gap that could leak <code>GITHUB\_TOKEN</code>, adds a per-cask <code>appdir</code> option for Homebrew casks, and fixes problems with locked SLSA installs, musl hosts and <code>mise backends switch</code>.</p>
<h2>Security</h2>
<ul>
<li><strong>Inline tool options in <code>.tool-versions</code> now require trust.</strong> This is the <code>.tool-versions</code> version of the <code>mise.toml</code> fix in 2026.9.18. An untrusted project could ship a <code>github:</code> entry with inline options, such as <code>\[api\_url=...\]</code>, pointing at another host. Commands such as <code>mise ls</code>, <code>env</code>, <code>current</code>, <code>outdated</code> and <code>latest</code> would then send your <code>GITHUB\_TOKEN</code> to that host without asking for trust. Any entry whose tool name contains <code>\[</code> now requires trust, the same as Tera templates. Plain lines like <code>node 20.0.0</code> still load without trust, and a <code>\[</code> inside a comment is ignored. Run <code>mise trust</code> for projects you rely on. <code>MISE\_SAFE=1</code> still skips trust checks. (<a title="GHSA-wcqh-j26q-g44x" href="https://github.com/jdx/mise/security/advisories/GHSA-wcqh-j26q-g44x">GHSA-wcqh-j26q-g44x</a>) <a href="https://github.com/jdx/mise/pull/13869" data-hovercard-type="pull\_request" data-hovercard-url="/jdx/mise/pull/13869/hovercard">#13869</a></li>\
<li><strong>Keyless cosign verification now checks who signed.</strong> Before, the aqua backend only checked that a bundle chained to Sigstore's Fulcio CA. Any GitHub Actions workflow in any repository can get such a certificate, so a bundle signed by the wrong workflow would still pass. mise now applies the registry's <code>--certificate-identity\[-regexp\]</code>, <code>--certificate-oidc-issuer\[-regexp\]</code> and <code>--certificate-github-workflow-{repository,ref,name,trigger,sha}</code> options to the signing certificate. It does this for both current and legacy bundles. Keyless verification now requires a pinned identity, and an unknown or empty <code>--certificate-\*</code> option is an error. Key-based verification (<code>--key</code>) is unchanged. Registry patterns that use RE2 <code>\\Q…\\E</code> quoted literals, such as the one for <code>vfox</code>, are supported. <a href="https://github.com/jdx/mise/pull/13875" data-hovercard-type="pull\_request" data-hovercard-url="/jdx/mise/pull/13875/hovercard">#13875</a>, <a href="https://github.com/jdx/mise/pull/13879" data-hovercard-type="pull\_request" data-hovercard-url="/jdx/mise/pull/13879/hovercard">#13879</a></li>\
<li><strong>GitHub attestation signer workflow matching is anchored.</strong> The expected <code>signer\_workflow</code> must now match the end of the certificate's workflow path as whole path segments. Before, it was a substring match against the whole identity, so a longer workflow file name such as <code>release.yml.evil.yml</code>, or a ref that contained the expected path, would pass. An empty <code>signer\_workflow</code> now fails verification. Both the bare form (<code>.github/workflows/release.yml</code>) and the repository-qualified form (<code>owner/repo/.github/workflows/release.yml</code>) still work. <a href="https://github.com/jdx/mise/pull/13877" data-hovercard-type="pull\_request" data-hovercard-url="/jdx/mise/pull/13877/hovercard">#13877</a></li>\
</ul>\

This overrides the global <code>MISE\_BREW\_CASK\_OPT\_APPDIR</code> setting, expands <code>~/</code>, and also applies to the cask's dependencies. <a href="https://github.com/jdx/mise/pull/13865" data-hovercard-type="pull\_request" data-hovercard-url="/jdx/mise/pull/13865/hovercard">#13865</a></p>\

<h2>Fixed</h2>\
<ul>\
<li><strong>Locked SLSA installs work again without a registry signer.</strong> Since 2026.9.17, a lockfile that recorded a checksum and SLSA provenance failed with "Aqua registry metadata has no signer\_identity and signer\_issuer" for tools such as <code>aqua:google/osv-scanner</code> and <code>aqua:fluxcd/flux2</code>. A lock entry with a checksum and recorded provenance is now trusted for SLSA too: the install only checks the artifact digest, as it already did for other provenance types. <code>locked\_verify\_provenance</code> or paranoid mode still re-verify and still require a signer. <a href="https://github.com/jdx/mise/pull/13856" data-hovercard-type="pull\_request" data-hovercard-url="/jdx/mise/pull/13856/hovercard">#13856</a></li>\
<li><strong>aqua on musl hosts.</strong> On Alpine and other musl hosts, an aqua tool whose registry entry only names a glibc build (such as <code>zizmor</code>) failed with "no asset found: ...-unknown-linux-musl...". mise now installs the asset the registry names. The binary still needs glibc or <code>gcompat</code> to run. <code>mise lock</code> for <code>linux-x64-musl</code> records the same asset. <a href="https://github.com/jdx/mise/pull/13857" data-hovercard-type="pull\_request" data-hovercard-url="/jdx/mise/pull/13857/hovercard">#13857</a></li>\
<li><strong><code>mise backends switch</code> handles stale lock entries.</strong> Sometimes <code>mise install</code> warned that a tool was locked to a replaced backend, for example <code>asdf:clojure</code> instead of <code>vfox:jdx/vfox-clojure</code>, but <code>mise backends switch</code> then reported there was nothing to switch. This happened when the config's version no longer matched the lock entry. The command now switches those entries too. Entries at a version the config no longer resolves to are relocked at the config's version and reported as <code>replacing stale &lt;tool&gt;@&lt;version&gt;</code>. <a href="https://github.com/jdx/mise/pull/13859" data-hovercard-type="pull\_request" data-hovercard-url="/jdx/mise/pull/13859/hovercard">#13859</a></li>\
<li><strong>Ctrl-C exits with status 130.</strong> Interrupting <code>mise install</code>, <code>upgrade</code>, <code>exec</code> and similar commands used to exit with 1, the same as an ordinary failure. They now exit with 130 (128 + SIGINT), matching <code>mise run</code>, so shells and scripts can tell when a user interrupted. A repeated Ctrl-C during <code>mise run</code> also exits with 130. This applies on Unix and Windows. <a href="https://github.com/jdx/mise/pull/13862" data-hovercard-type="pull\_request" data-hovercard-url="/jdx/mise/pull/13862/hovercard">#13862</a></li>\
<li><strong>Declining a trust prompt skips the config for that run.</strong> Before, declining still failed the current command with "not trusted". <a href="https://github.com/jdx/mise/pull/13868" data-hovercard-type="pull\_request" data-hovercard-url="/jdx/mise/pull/13868/hovercard">#13868</a></li>\
<li>The one-time startup migration for stale <code>latest</code> runtime directories has been removed. It was due to expire in this release and would have blocked normal installs. <code>mise install</code> still repairs a stale <code>latest</code> directory, but passive commands such as <code>mise ls</code> no longer touch it. <a href="https://github.com/jdx/mise/pull/13868" data-hovercard-type="pull\_request" data-hovercard-url="/jdx/mise/pull/13868/hovercard">#13868</a></li>\
<li><strong>Stale dotfile history watchers are diagnosed.</strong> A history watcher started on an older mise can fail every capture with an unknown-field error for newer settings such as <code>exclude</code>. <code>mise doctor</code> and <code>mise dot status</code> now report that the watcher is outdated and tell you to run <code>mise bootstrap services apply</code>, which restarts it. <a href="https://github.com/jdx/mise/pull/13864" data-hovercard-type="pull\_request" data-hovercard-url="/jdx/mise/pull/13864/hovercard">#13864</a></li>\
<li><strong>Java:</strong> the missing-metadata error now names the target platform, for example <code>no metadata found for version zulu-8 on windows-arm64</code>. <a href="https://github.com/jdx/mise/pull/13873" data-hovercard-type="pull\_request" data-hovercard-url="/jdx/mise/pull/13873/hovercard">#13873</a> (<a class="user-mention notranslate" data-hovercard-type="user" data-hovercard-url="/users/jsiu93/hovercard" data-octo-click="hovercard-link-click" data-octo-dimensions="link\_type:self" href="https://github.com/jsiu93">@jsiu93</a>)</li>\
</ul>\
