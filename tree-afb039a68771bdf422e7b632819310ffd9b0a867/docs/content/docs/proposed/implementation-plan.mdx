**Status:** Proposed. Each gate below is future work until implemented and verified.

The implementation MUST follow these gates in order. Do not begin self-hosted runner work until Gate 8 passes. Each gate produces reviewable code, fixtures, and evidence before the next gate starts. Parallel scheduling and safe omission rules are normative in the [parallelism and affected-work contract](/docs/proposed/parallelism-and-selection-contract).

## Work packages and merge gates

| Gate | Deliverable | Required proof to pass |
|---|---|---|
| 0. Repository contract | Velnor's own `.alint.yml`, the exact Alint action version, and a separate required repository-policy job | The generated Velnor repository workflow runs `asamarts/alint@v0.16.1`; `.alint.yml` is valid; negative fixtures reject each configured supported Alint rule; and no second repository-structure linter is needed. |
| 1. Repository root, config, inventory, and plan | `velnor-actions init`; shared analysis for `plan` and `generate` | Init locates the Git root from CWD, writes one non-overwriting sample config, and never writes elsewhere; the detector registry finds standalone, nested, and multiple Rust workspaces exactly once; unregistered stacks receive no validation claim; malformed Cargo manifests and missing tools return documented nonzero codes; `plan` deterministically lists every crate and intended workflow job/step, uses identical task IDs and matrix facts as generation, and writes no repository files. |
| 2. Deterministic generator | `velnor-actions generate [--output-dir PATH]`, shared plan/task graph, `.github/actionlint.yaml` and workflow tree | Staged tree passes pinned actionlint/ShellCheck and zizmor; all files carry the version marker; latest default full-SHA pins and the reviewed `asamarts/alint@v0.16.1` exception match the action catalog; no broad workflow-lint suppressions, `taiki-e/install-action`, or other installer actions; failed validation leaves old `.github` unchanged. |
| 3. Generated execution and visible jobs | Typed task graph, per-crate matrix, actionlint job, explicit final required gate | Cargo/MBX and Cargo-test/Nextest choices follow evidence; Clippy failure blocks dependent package tests; independent obligations finish and report; until actionlint parses native step concurrency, only validated job/matrix parallelism is emitted; missing results fail. |
| 4. Tool and compilation reuse | Exact Velnor-pinned Mise tools, Cargo-source transport, MBX object transport, reasoned cache reports | Cold, warm, unchanged, and source-change cases prove hits/misses; MBX hits never skip tests; untrusted PR caches cannot enter release path; project tool files remain byte-identical. |
| 5. Trusted baseline coverage | Protected default-branch baseline manifest, exact-base lookup and final-gate validation | Exact successful base proof covers only matching task/input identities; missing/untrusted/malformed baseline broadens execution; PRs cannot publish trusted evidence. |
| 6. Task-result reuse | Mise task caching for explicitly qualified tasks | Exact-input warm result is reused; each changed declared input invalidates; undeclared/non-deterministic tasks run normally; unavailable cache executes the task and reports why. |
| 7. Parallel test fan-out | Resource-bounded job/matrix fan-out, isolated Cargo lanes, conditional build-once Nextest archives and complete shard manifests | Same required task/test set as sequential plan; every shard joins; union equals selected tests and pairwise intersections are empty; missing/duplicate results fail. Enable native `parallel`/`background`/`wait` only after the exact actionlint pin supports it and qualification passes. |
| 8. Velnor dogfooding | Production workflow generated by Velnor and committed to Velnor | The locked bootstrap binary generates the workflow; Velnor's `candidate` validation mode builds one candidate with MBX and reuses that artifact for generation and fixture qualification; merge-queue and pull-request paths return required results; no separate hand-maintained production CI exists. |

Gate 0's only product package names are `velnor-actions-contract`,
`velnor-actions-rust`, `velnor-actions-mise`, `velnor-actions-actionlint`,
`velnor-actions-workflow-renderer`, `velnor-actions-orchestrator`, and
`velnor-actions-cli`. The last package declares the `velnor-actions` binary.

The actionlint qualification fixtures MUST include malformed workflow YAML,
invalid expressions, missing/invalid action inputs, shellcheck findings,
untrusted expression interpolation, stale full-SHA action metadata, an
unsupported runner label, a valid versioned runner label bridged through the
actionlint config, and currently unsupported `parallel`/`background`/`wait`
syntax. The last case MUST remain rejected until the pinned actionlint release
supports it. Generation runs the exact same lint executable and config against
the staged `.github` tree before replacing any repository files.

The configuration gate MUST define one automatic detector registry. V1 registers
only the Rust adapter and stores its settings under `[stacks.rust]`; the shared
`[stacks].ignore` list is applied after detection; `[discovery].exclude`
paths are applied before every detector. The public CLI exposes only `init`,
`plan`, and `generate [--output-dir PATH]`; `plan` has no options and reports
the shared plan as concise text. The CLI has no root, stack-selection, ignore,
format, comparison, or check flag. Future TypeScript and Bun adapters register
new detectors and add only their own `[stacks.typescript]` or `[stacks.bun]`
settings. An unregistered stack has no validation claim; it does not cause Rust
heuristics to inspect the project.

The composition gate proves that Rust discovery/task proposals, Mise tool-file
inspection and command construction, workflow YAML rendering, and CLI parsing reside only in
their named crates. The orchestrator alone composes those crates. A policy
fixture MUST fail if the Rust and Mise packages depend on each other, a stack
adapter contains Mise parsing/commands, the Mise crate contains Rust graph
logic, the renderer emits Mise syntax, or the CLI invokes external tools.
It MUST also fail if process execution escapes the Mise adapter or if the
orchestrator constructs shell commands instead of issuing typed tool requests.
Policy fixtures are committed policy tests per [rust-quality
§5](/docs/proposed/rust-quality-contract) (cargo-metadata edge test, exact member-set
test, literal-substring ownership tests, Alint-generic plus Clippy sizes,
human-reviewed snapshots); custom linters are forbidden and Alint stays
generic-only.

An implementation gate passes only when all listed proofs pass on the named CI runner and the result is recorded with the code. A skipped, cancelled, missing, or infrastructure-failed proof does not pass a gate.

Two gate vocabularies are normative: `policy-on-source` (a check that
validates repository source, e.g. Alint, deny, actionlint, zizmor) and
`qualification-of-generator` (a check that validates a candidate
generator binary against fixtures and golden files, never by asking the
old bootstrap to reproduce new output). Gates MUST label each proof
with the vocabulary it satisfies.

## Gate 0: bootstrap repository contract

Create the virtual Cargo workspace and files defined in [architecture](/docs/proposed/architecture), including `.velnor/version-policy.toml` and `.alint.yml`. Velnor's own `workflow.policy = "velnor-repository-v1"` enables a separate required Alint job using exactly `asamarts/alint@v0.16.1`; `consumer-v1` does not require `.alint.yml`.

Alint MUST enforce only configured capabilities supported by its selected
version: file and path rules, required-file rules, structured configuration
checks, and file line-count rules used by Velnor. Negative fixtures MUST prove
each enabled Alint rule rejects a violation; successful examples alone are
insufficient. Do not import a violation ratchet from an old project. No
additional repository-structure linter is part of Gate 0. Cargo-deny,
actionlint, and zizmor remain separate later workflow/dependency checks and
must not be presented as Alint capabilities.

## Gate 1–2: deterministic inputs and outputs

Keep all domain planning pure. Use Cargo's metadata JSON as the inventory format; use the exact command and schemas in [architecture](/docs/proposed/architecture). First run metadata without dependency resolution for inventory. Resolve the locked graph only after preparation, with network disabled. Treat failure to resolve as an explicit preparation error; do not fall back to parsing Rust source or silently produce an incomplete graph.

Define stable package/task IDs before rendering workflows. `plan` and `generate` MUST share one analysis and workflow-IR implementation. Plan output lists detected workspaces/crates and intended workflow files/jobs/steps in deterministic human-readable text, writes no repository files, and emits no YAML or JSON. Its facts MUST match the generated workflow for identical inputs. Generated output MUST be ordered deterministically, use safe YAML scalar quoting, include a generator/schema version, and include a first-line ownership header with no generation date. `generate` renders to a temporary destination first, validates every output, and then atomically replaces the root `.github` tree. `generate --output-dir PATH` writes the same tree to the explicit preview destination and never edits the repository. There is no `--check` command or option.

## Gate 3: executable task contract

Every internal task has a stable ID, declared package/configuration, tool identity, inputs, outputs, and execution command. The generated workflow invokes only validated commands emitted by the workflow/Mise adapters; no public `task run`, `task explain`, `report validate`, or `report merge` command exists. The orchestrator validates task identities before generated workflow output is written, and the workflow preserves child exit codes and writes run-scoped reports for its final gate.

The generated workflow has one planning/format job, an affected-crate matrix, and a required result job. The default matrix entry performs Clippy, test build, tests, then doctests as distinct steps. Matrix entries run concurrently. A crate's test work begins only after its Clippy succeeds. This is crate-scoped fail-fast; a global lint-before-any-test barrier is not the default.

The planner emits one schema-1 `plan.json` and one compact
`{"include": [...]}` matrix output. Each entry has a stable `id` and derived
`matrix_key`; the run adds exact `report_id` and `artifact_id` values. The
matrix job writes one task report per expected task plus one aggregate matrix
report. The final job aggregates only those declared IDs and fails on missing,
duplicate, malformed, or unexpected reports. The exact fields, paths, and
derivation rules are normative in [the cache contract](/docs/proposed/cache-contract).

## Gate 4: tools and compilation cache qualification

Implement caches in this order: tool installation; Cargo source archives; MBX compilation objects; qualified Mise task-result caching. Each layer has one owner. Record hit, miss, bypass, invalidation, and unavailable reasons. Never convert a cache miss into a skipped check. Never assume a compiler artifact proves test success.

Do not treat compilation reuse as task-result reuse. Task-result caching stays disabled until Gate 6.

## Gate 5: trusted baseline coverage

Publish an evidence-only baseline artifact after a protected default-branch push passes the final gate. Resolve only the exact base commit for PR, merge-group, or subsequent default-branch push. The planner classifies all task obligations before constructing the execute-only matrix. If lookup, trust, identity, or completeness checks fail, execute otherwise-unproven tasks. Qualify forward dependency propagation, baseline carry-forward, artifact expiry, malformed artifacts, and final coverage aggregation.

## Gate 6: task-result caching

Enable Mise caching only for tasks with complete declared inputs, environment, outputs, trust rules, and independent invalidation fixtures. Mise task caching is experimental; if its pinned version fails qualification or is unavailable, execute the task without result reuse and report `cache_unavailable`. MBX compilation hits never satisfy this gate.

## Gate 7: parallel test fan-out

For detected Nextest workspaces, compile each test configuration once into an archive. Keep small suites in one test-runner job; shard only when measured execution time exceeds archive transfer and additional runner setup. Cargo-test workspaces use their detected Cargo/MBX command with no Nextest archive. Use separate Cargo target directories for concurrent compiler tasks, explicit resource limits, and a non-fast-failing crate matrix. Verify exact test identity coverage and non-overlap before final success.

## Gate 8: non-circular bootstrap and self-hosting

Implement the [bootstrap and release contract](/docs/proposed/bootstrap-and-release-contract).
Velnor's own protected `.velnor/generator.lock` selects its bootstrap; consumer
workflows embed the exact released generator URL and SHA-256. The bootstrap
MUST determine the current graph and MUST NOT wait for a binary built from the
current source.

The initial seed and every later candidate use this sequence:

1. Build the seed or candidate with a fixed Cargo/MBX argument vector through
   Mise, using exact pins from the compiled-in catalog (verified against
   Velnor's `.velnor/version-policy.toml` mirror); it does not call the
   candidate or load project tool files.
2. Record the source commit, target triple, compiler/tool identities, version,
   and SHA-256 in a candidate manifest. Upload the executable and manifest as
   one run-scoped artifact.
3. Download that exact artifact once in candidate qualification. Verify its
   manifest and digest before running it. Do not rebuild it in a downstream
   job.
4. Run candidate generation checks, policy checks, and fixture qualification
   with the candidate. The candidate may validate output that the old locked
   generator cannot reproduce. The candidate MUST NOT emit a matrix; golden
   files are the oracle for changed output, and committed digests MUST be
   real measured values, never placeholders.
5. Promote only after all candidate checks and the required final aggregation
   pass. Publish immutable per-target release assets, verify their digests, and
   update the protected generator lock in a separate reviewed change.

The candidate is never used to produce the plan or matrix that builds it. Until
promotion and lock update finish, ordinary CI continues to use the previous
locked binary. The first release therefore has no circular dependency on a
previous Velnor release: its fixed Mise/MBX build invocation and manually
reviewed seed artifact are the only bootstrap inputs.

The internal plan/matrix/report wiring MUST follow the
[workflow](/docs/proposed/workflow-contract) and [cache/report](/docs/proposed/cache-contract)
contracts. These are implementation artifacts, not public CLI commands:

- The generated workflow creates the internal plan, emits the exact
  `matrix.include` JSON through `GITHUB_OUTPUT`, and uploads
  `velnor-plan-<run-key>`.
- Matrix entries have deterministic `matrix_key`, `report_id`, and
  `artifact_id` values. Each matrix job uploads exactly one artifact containing
  one aggregate matrix report and one task report for every expected task,
  including `not_selected` tasks after an upstream failure.
- `required` downloads exact derived artifact IDs, validates the plan and
  report sets, validates candidate evidence when self-hosting is enabled, and
  writes `final-<run-key>` before returning the required status.
- A missing, duplicate, malformed, or unexpected report is a failure. A cache
  miss is not a failure by itself; the task executes and records the miss.

Committed fixture workflows are qualification harnesses only. Velnor's own
production workflow is generated by Velnor and checked into the repository.
Generated workflow execution MUST handle pull requests, default-branch updates,
and `merge_group` on every repository from V1. A repository with no merge queue
does not produce merge-group runs, but the workflow keeps that trigger ready.
The final gate
must not be skipped when there is no Rust work.

## Performance qualification

Record baseline and regression data for these exact cases on named hardware:

1. Empty-cache cold run.
2. New checkout with populated compatible MBX cache.
3. Unchanged repeated task.
4. One-file change in a leaf crate.
5. Public API change in a shared crate.
6. Two and four concurrent validation lanes.
7. Dependency/toolchain update.

Capture elapsed and queue time separately; tool restore/install; cache transfer; origin downloads; compiler execution; MBX hit/miss/bypass; test execution; task-result reuse; and selected/omitted tasks. Initial objectives are under two seconds for provisioned structural preflight, seconds for warm leaf validation, and a two-minute warm path for the small fixture and normal dogfood on named GitHub runner hardware. These are budgets to measure, not existing results. A regression requires investigation; it never authorizes dropping required checks.

## Recording implementation status

The [implemented index](/docs/implemented) records only landed code.
Every implementation pull request MUST add or update its record in that same
pull request, including its spec link, delivered scope, merged PR link, and
passing acceptance evidence. Missing records block merge. Never record a draft,
prototype, skipped check, or failed gate as implemented.
