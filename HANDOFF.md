## 2. How releases are cut

The release path is one script, then one pin.

1. Run `~/.local/share/velnor-agent/release-tools.sh NEW_VERSION`. It does this:
   - creates a worktree from `origin/main` on branch `fast/tools-NEW_VERSION`;
   - bumps the `velnor-gen` and `velnor-ci` versions in `Cargo.toml`, the exact `velnor-gen` pin in `velnor-ci`, and both lockfiles;
   - runs `velnor-gen generate` and `velnor-gen check`;
   - opens a PR with a signed-off commit, marks it ready, and squash admin-merges it at its head;
   - tags the merge commit `tools-vNEW_VERSION` and pushes the tag.
2. The tag starts `release.yml` (`family_trigger = "tag_push"`).
3. Repin the consumers. Run `velnor-gen pin-helper <version>`. It writes `.velnor/rust-ci.lock`. Then run `velnor-gen generate`.
4. `rust-metadata.json` can drift after a version change. `regen-main.sh` fixes it within 5 minutes.

Right now: 0.1.104 is released, but main still pins 0.1.103. The repin PR is not open yet.

## 3. The helper-gate rule

`scripts/check-helper-gates.sh` enforces it. It runs on PRs.

- A gate is a version check in `crates/velnor-gen`, `crates/velnor-render` or `crates/velnor-rust`. For example, "needs velnor-ci 0.1.N or later".
- The script reads the velnor-ci version on the base branch. It fails when an added or changed gate is not strictly greater than that version. A gate must name the next release, the base version plus one patch.
- A correction is a gate that must sit below the next release because the feature is already shipped. It carries a marker on the gate line, or on the line above:
  `// helper-gate: first in tools-v0.1.N via <commit-ish>`
- A marker passes only when the gate is `0.1.N`, the commit is in `tools-v0.1.N`, and the commit is not in `tools-v0.1.(N-1)`. Fetch tags first (`git fetch --tags`).

## 4. Merge tooling

All scripts live in `~/.local/share/velnor-agent/`. Merges log to `~/.cache/velnor-fast-merge.log`.

- **`mergenow.sh PR`.** Marks the PR ready, runs `protected-check.sh`, and squash admin-merges at the current head. It prints the final state. Use it for one PR you have reviewed.
- **`fast-merge-sweep.sh`.** A loop, one pass every 120 s. For each open, non-draft PR based on main, it admin-merges when all of these hold:
  - the PR is not conflicting;
  - it has 0 unresolved review threads;
  - its DCO check passes;
  - it is not in `hold.list`;
  - `protected-check.sh` passes.
  It dequeues the PR from the merge queue first. It does not wait for CI. The loop skips every pass while `~/.local/share/velnor-agent/main-freeze` exists.
- **`hold.list`.** PR numbers or branch names the sweep must skip. Now: 1916 and 1920. Remove a line only after the PR is fixed.
- **`protected-check.sh PR`.** Exits 1 when the PR touches `docs/goals.md` or `docs/hard-decisions.md`. Both need recorded owner approval. Edits to them stay out of fast delivery.

## 7. How to run an issue

1. Claim it. `gh issue edit N --add-label in-progress`. Move the project card to "In Progress". The ids are in `docs/roadmap.md`.
2. Brief the executor. Include:
   - the issue number;
   - "read AGENTS.md, docs/goals.md, and the #574 rules: 400-line file cap, I/O only in `io`, one test executable, no explanatory comments, a test plan before tests, red/green evidence";
   - a branch `fast/<n>-<slug>` from `origin/main`;
   - signed-off commits (`git commit -s`), and main brought in only with `git merge --signoff origin/main`. Never rebase or force-push;
   - a ready PR, not a draft (`gh pr ready` if needed);
   - a body with `Closes #N`, a test plan, and every "Done when" command with its output;
   - no edits to the PR body after a push, because that restarts CI. Use PR comments instead;
   - answer every review thread: fix real bugs with red/green, or reply with evidence, then resolve the thread. After two rounds, fix only real correctness or security bugs;
   - clean up, and report what was removed.
3. Review with a separate agent, briefed with the diff and the issue, never with the executor's conclusion. It runs mutations and checks the test plan. After a later push, send only the delta to the same reviewer.
4. Merge with `mergenow.sh PR` (or let the sweep do it). Check first:
   - the PR is not behind main in a way that matters;
   - 0 unresolved threads;
   - DCO passes;
   - `Required` is green, unless the owner has accepted fast delivery for that PR.
5. After the merge, check the issue closed. Remove `in-progress`. Tick the "Done when" boxes with proof links. Print the ready query and one line per issue: number, PR, merged, and the proof for each box.
6. Merging one PR makes the others "behind". Have each executor run `git merge --signoff origin/main` after each merge.

## 9. Model and parallelism rules

These are the owner's rules. They still apply.

- **Models.** Use only Haiku 5.5, Sonnet 5.5 and Opus 5.5. **Never use Fable.**
- **Who gets the work.**
  - Haiku: small mechanical issues, ticking boxes, reviews of small diffs.
  - Sonnet: most executors and reviewers.
  - Opus 5.5: security-critical or deep design work only. That means the release gate and publish, runner recovery, the bouncer and local authority, and trust-boundary research. Use Opus at high effort only when the issue says so.
- **Concurrency.** Run up to about 8 issues at once, provided no two touch the same files. Group by folder: `generator/`, `ci-helper/`, `local/`, `crates/velnor-runner/`, `crates/velnor-actions-*`, `.github/`, and velnor-lab. Issues in one folder that touch the same module run one after another.
- **Budget.** Work in parallel, and keep agents busy. Do not poll. Watchers notify you when checks finish.
