# #1290 homebrew-adoption.yml in velnor-gen: Step 1 design (stopped before code)

## Decision

Do not implement in this pass. The feature is larger than the 90 minute limit, and the first slice needs an owner decision. Proposed shape:

- A new opt-in file `.velnor/homebrew-adoption.toml` (same pattern as `.velnor/release.toml`). Absent file: no new output, so default output stays byte-identical.
- Keys: `repository` (owner/name that publishes the SDK release), `signer_workflow`, `runner`, `timeout_minutes`, `matrix_max_parallel`, `artifact_retention_days`. There is no tap and no secret in the file: see below.
- A new `velnor-render::homebrew_adoption` module renders a `workflow_call` workflow with four jobs: `plan`, `native-checks` (matrix from the plan output), `required`, `required-gate`.
- The 40-line bootstrap `run:` (download manifest, sha256 check, `gh attestation verify`, jq checks, asset download, install) breaks design rule 9. It must become one helper command, for example `velnor-ci stage-sdk`, taking `repository`, `signer-workflow`, version, source sha and manifest sha from env. That helper lives in `ci-helper/` and needs a helper release before the generator can pin it.
- `Setup Mise` and `Install pinned GitHub CLI` come from the existing mise pin logic, so the gh version comes from `mise.toml` pins rather than a literal.

## What the current workflow contains

- Trigger: `workflow_call` only, with four required string inputs: `transition_id`, `sdk_version`, `sdk_source_sha`, `sdk_manifest_sha256`. Not triggered by push or schedule.
- Permissions (workflow and each job except the gate): `contents: read`, `actions: read`, `attestations: read`. `required-gate` sets none. Also a non-standard top-level `cache-mode: read` that actionlint does not know.
- Secrets: none. Only `github.token`, exposed as `GH_TOKEN`. The gate job blanks every token variable and runs `env -u ... false`.
- Target tap: none in this file. The tap lives in `.velnor/qualification/homebrew/jackin/transition.json` and is passed in through `transition_id`. The only hard-coded repository is `tailrocks/velnor-new`, the SDK release source, which becomes `repository` config.
- Jobs: `plan` (stage SDK, checkout, `write-request-v1`, `plan-v1`, upload plan artifact), `native-checks` (matrix, `fail-fast: false`, `max-parallel: 2`, download plan, `execute-native-homebrew-check-v1`, upload report), `required` (`fetch-reports-v1`, `write-request-v1`, `merge-v1`, upload final report), `required-gate` (fail unless the verdict passed).
- Every non-bootstrap step runs the staged old-engine binary `velnor-actions-$VERSION` selected by `VELNOR_INTERNAL_OP`. That is the old engine, not `velnor-ci`.

## Why this is over the size limit and risky

1. Byte-identical proof is impossible by design. The current file embeds the shell bootstrap and the old `velnor-actions` ops, and the header says `Generated by Velnor Actions 0.1.80`. Moving the bootstrap to a helper changes the file by definition, so the proof would be a reviewed semantic diff, not an empty diff.
2. The generator has no `workflow_call` trigger, no job `outputs`/matrix-from-JSON fan-out, no `cache-mode` key, and no per-step `continue-on-error`. Each needs a model type, renderer, rule check and linter allowance.
3. The helper command needs its own tests and a published helper release, which the generator then pins. That is two releases in sequence.
4. Open owner question (goals.md rule 14 and the hard decisions): `velnor-gen` is meant to drive the helper `velnor-ci`, while this workflow drives the old engine binary. Generating it means the new generator knows the old engine's op names. That coupling should be approved before code.

## Suggested split

1. `ci-helper`: `stage-sdk` command (red-first tests against recorded release data), released.
2. `velnor-model`/`velnor-render`: `workflow_call` trigger, matrix-from-output and `cache-mode` support, behind the new config only.
3. `homebrew-adoption.toml` config, sample `homebrew-adoption`, CONFIG.md entry, golden test red before the renderer exists.
4. Proof: generate velnor-new's workflow and diff it against `.github/workflows/homebrew-adoption.yml`; the expected diff is the header, the bootstrap step and `cache-mode`.
